The dashboard is a local web page for seeing what CC Safety Net blocked on this machine, why, and what you can change. Run `cc-safety-net gui` to open it. From it you can review decisions, edit your policy without writing JSON, draft a project policy, and install the hook for each coding agent.

The underlying formats live elsewhere. The `policy.json` fields are on [Policy](/configuration/policy), rulebook authoring is on [Custom rules](/configuration/custom-rules), and the record format is on [Audit log](/reference/audit-log).

## Launch the dashboard

```bash
cc-safety-net gui
```

The command prints the dashboard URL and opens it in your default browser:

```text
CC Safety Net policy GUI: http://127.0.0.1:52341/?token=...
```

Pass `--no-open` to get the URL without opening a browser, for example over SSH or in a container:

```bash
cc-safety-net gui --no-open
```

The server runs in the foreground until you stop it with `Ctrl-C`. See [`gui`](/reference/cli/gui) for the flags, argument errors, and what happens when the browser cannot open.

### Local loopback scope

The dashboard is not a hosted service. The server listens only on `127.0.0.1`, so nothing on your network can reach it. Each launch creates a new token in the URL, and the server rejects requests without it. A URL bookmarked from an earlier launch stops working, so run `cc-safety-net gui` again to get a fresh one.

`gui` prints the token on stdout, so whoever launched the command can read it. An agent that ran `cc-safety-net gui` itself therefore holds the token and can use the dashboard, including the project-policy apply. CC Safety Net still denies an agent that edits `policy.json` directly or runs `cc-safety-net policy apply`.

Everything the page shows comes from your local policy file and audit logs. Overview makes two outbound requests when it opens. One checks the npm registry for updates, and the other reads the repository's public star count from GitHub. Neither sends a credential. `Star on GitHub` uses your `gh` login only when you click it.

## The six views

The sidebar has six views. Each view has its own address, so you can bookmark one within a session. The address also keeps the filters on Activity and Protections, so a reload or Back restores them.

| View | What it answers |
| --- | --- |
| **Overview** | What has CC Safety Net been doing on this machine recently? |
| **Activity** | Which commands did your agents run, and what happened to each? |
| **Protections** | What should CC Safety Net block? |
| **Custom rules** | Which custom rulebook rules are enforced right now? |
| **Agents** | Which coding agents on this machine have the hook installed? |
| **Settings** | How long are logs kept, where do files live, and how do I reset? |

A banner above every view appears when a protection is off or when a configuration error makes the runtime enforce a fallback. It shows one line per condition:

- `Command protection is off: built-in destructive command rules are not enforced. Catastrophic and custom rules still apply.`
- `Secret protection is off: sensitive files and deny paths are not blocked.`
- `A fallback configuration is being enforced: <reason>`

The banner reflects the saved policy, not unsaved edits. See [Recovery](/configuration/recovery#configuration-states) for what a fallback configuration means and how to get out of it.

## Overview

Overview summarizes the last 7 days, or your whole retention window when retention is shorter.

**Status card.** The card at the top shows one headline:

| Headline | When it appears |
| --- | --- |
| `Your policy file needs repair` | The saved policy file has errors |
| `Checking your agents…` | Agent detection has not finished |
| `Not protecting any agent yet` | No detected agent has an active hook |
| `Partly protected` | Command protection or secret protection is off |
| `Protected` | None of the above |

Below the headline, the card names your preset, adds `, customized` when you changed it, and lists the agents with an active hook. It links to Agents when no agent has a hook, and to Protections otherwise. It reflects the saved policy only.

**Needs attention.** This list appears only when something needs action, and each item links to where you act on it:

- `<Agent> is detected but its hook is disabled.` opens Agents.
- `N blocks in the last N days look like a false positive.` opens Activity filtered to likely false positives.
- `N guard errors in the last N days: commands blocked because evaluation failed, not by policy.` opens Activity filtered to errors. CC Safety Net could not finish checking these commands, so it blocked them. See [Troubleshooting](/guides/troubleshooting) if they recur.
- `Version <version> is available.` opens the release notes on GitHub.

**Tiles, Recent blocks, and Most-triggered rules.** `Blocked` and `Commands checked` show a count and a per-day chart. Recent blocks lists the eight latest blocked commands, and Most-triggered rules lists the five rule IDs with the most blocks. Select a row to open the rule on Custom rules, or to open Activity searched for that rule ID.

## Activity

Activity lists the commands your agents ran, newest first, under day headings. Secret redaction recognizes only known credential shapes, so entries can still contain paths, hostnames, and names. Read [Secret redaction](/reference/audit-log#secret-redaction) before you share anything from this view.

The window selector offers windows up to your audit retention, and Activity opens on the last 7 days. See [Retention](/reference/audit-log#retention) to keep more history.

### Filters

- **Decision.** `Blocked` (the default, which includes guard errors), `Allowed`, and `All`, each with its count. `Errors` appears when the window has guard errors. `Likely false positive` appears when CC Safety Net finds a block that records a failure stage, or the same command blocked twice or more in one session.
- **Search.** `Search commands or rule IDs` matches rule IDs and command text, ignoring case.
- **Agent.** `All agents` plus one option per agent. It appears when the window has two or more agents.
- **Window.** How many days back to look.

With the default filters and nothing blocked, the list reads `Nothing was blocked in the last N days.` and offers `Show all activity`. The refresh icon beside the title reloads both Activity and Overview.

The footer reads `Showing X of Y entries from the last N days.` The list loads at most the newest 500 entries of each decision, but the counts and tiles always cover the whole window. Narrow the window to see older entries. When Activity cannot read some log files, the footer says so, and both the list and the counts are incomplete.

### Per-entry actions

Each row shows the time, a decision badge (`Blocked`, `Allowed`, or `Error`), the agent, the command, and the rule ID. Select a row to see the full command, reason, rule, and folder. A rule ID links to that rule on Protections or Custom rules.

- Blocked entries offer **Report false positive**. See the next section.
- Allowed entries offer **Block this in future**. It opens Custom rules with the command filled into the `What should be blocked?` box. It does not create a rule by itself.
- Every entry offers **Copy log entry**, which copies the raw audit record as JSON. See [Record schema](/reference/audit-log#record-schema) for its fields.

### Report a false positive

**Report false positive** opens a dialog that prepares a public GitHub issue from the project's false-positive form. You can edit every field: an optional reason, the title, the blocked command, and the audit entry as JSON.

The dialog replaces your project path with `<project>` and your home directory with `~`. Other paths and names stay, so edit out anything you would rather not publish. `Open GitHub form` opens the filled-in form in a new tab. Nothing reaches GitHub until you submit the form there. When the report is too long for the link, the dialog copies a field to your clipboard and names where to paste it.

## Protections

Protections is where you choose what CC Safety Net blocks. Everything here is a built-in protection: the safety preset, the destructive-command rules, and the secret-protection rules. Your own rulebooks are on Custom rules. `My policy` and `Project policy` at the top choose which policy you edit.

### Saved versus unsaved

Edits collect in a draft until you save. A save bar shows `N unsaved changes` with **Discard** and **Save**, and the sidebar marks Protections `Unsaved`. The draft survives a reload in the same browser session, and the page asks before you leave it. **Discard** asks for confirmation. **Save** writes your user policy file and reports its path.

While the saved policy has errors, the dashboard opens Protections, shows built-in defaults in the form, and disables **Save** so those defaults cannot overwrite your file. Use [Repair](#repair) first.

### Draft a project policy

`Project policy` switches Protections into a draft of the project's `policy.json`, which everyone working in that folder gets on top of their own policy. The draft targets the folder you launched the dashboard from, and `Change folder…` picks another. If you have unsaved changes to your own policy, the dashboard asks to discard them first. `My policy` takes you back.

Every control gets a tag:

- `Inherited` means the project file leaves this setting out, and each person keeps their own value.
- `Project` means the project file sets it. Click the tag to stop setting that field.

Editing a control marks it `Project`. A marked path list starts empty, so the draft does not write your personal paths into the repository.

**Save** becomes **Review and apply**, which opens `Apply this project policy?`. The dialog shows the target path, a `Setting` / `Now` / `After` table of the effective policy, and a warning for each setting the draft makes weaker than your own policy. [Reported weakenings](/configuration/policy#reported-weakenings) lists the warnings. The dashboard writes nothing until you select `Apply project policy`. In a draft, **Discard** returns to what the project file already has, after a confirmation.

The draft refuses to start with `Repair your policy first` while your own policy file has errors. It also cannot write to the folder that holds your user `.cc-safety-net/`. Use `Change folder…` to pick a project, and see [The user config directory is not a project](/configuration/policy#the-user-config-directory-is-not-a-project).

See [Project policy](/configuration/policy#project-policy) for how the two policies merge. The draft makes the same checks as `cc-safety-net policy apply`.

### Test a command

`Test a command` opens a dialog. Enter a shell command and select `Test` to see whether it would be blocked. Nothing runs. The test uses your unsaved edits and your custom rulebooks, so you can check a change before you save it. In a project draft, it tests your policy with the draft applied on top.

The result reads `Blocked` with the rule ID, reason, and the blocked part of a compound command. Otherwise it reads `Allowed. No rule blocks this command.` with a `Create a rule to block it` link to Custom rules. Use [`explain`](/reference/cli/explain) for the same check in the terminal.

### Safety preset

Three cards choose the preset: **Standard**, **Strict**, and **Paranoid**. Each includes everything in the one before it. `<Preset>, customized` appears when your overrides differ from the preset. [Modes](/configuration/modes) describes what each preset changes.

When an environment variable raises protection, the view lists it after `An environment variable raises protection beyond these settings:`. CC Safety Net can then block more than the preset shown.

The collapsed **Advanced settings** card turns single capabilities on or off without changing the preset: `Fail closed`, `Paranoid rm -rf checks`, and `Paranoid interpreters`. Each offers `From preset`, `Always on`, or `Always off`. The same card holds `Allow discarding local changes in linked git worktrees`.

### Search protections

The search box (`Type / to search by name, path or rule ID`) matches rule names, IDs, descriptions, and the paths a secret rule protects. Press `/` to focus it. `Changed from default` lists only the rules you or an environment variable changed.

### Command protection

The **Command protection** panel holds the built-in destructive-command rules. Its header has a master switch, a `Reset all` button, and a summary such as `N on · N off · N always on`.

The `Always on` group comes first. It holds the catastrophic rules, which show a lock instead of a switch because you cannot turn them off. One group per category follows, such as `Git` and `Filesystem`. Each rule row shows a switch, the rule name and ID, and a description. A `Strict` or `Paranoid` badge marks a rule that needs that preset, and an info button shows an example command the rule blocks.

A note explains a value that does not come from the preset:

| Note | Meaning |
| --- | --- |
| `Changed by you` | You set this rule. `Reset` beside it returns it to the preset value |
| `<Capability> forced on in Advanced` or `<Capability> forced off in Advanced` | An Advanced setting decides the rule |
| `Set by environment: <variable>` | An environment variable turned the rule on |
| `Needs the Strict preset` or `Needs the Paranoid preset` | The rule is off because the current preset does not include it |

`Reset all` returns every rule in the panel to its preset value after a confirmation. To allow one blocked command, turn off its rule here rather than the whole panel. See [Allow a blocked command](/reference/blocked-commands#allow-a-blocked-command).

Turning the master switch off asks for confirmation. Afterward the summary reads `Off. Built-in rules are not enforced; catastrophic and custom rules still apply. Your rule settings are kept.`

### Secret protection

The **Secret protection** panel works the same way: a master switch, `Reset all`, and a summary such as `N on · N off`. It groups its rules by category, such as `Sensitive file names`, `Sensitive file extensions`, and `Coding agent credentials`. A rule that protects specific file paths has an info button listing those paths.

The `Coding agent settings` rules ship off and show `Off by default`. Turn them on one at a time. See [Coding CLI config tier](/reference/secret-protection#coding-cli-config-tier-off-by-default) for why. To allow one blocked file, see [Allow a blocked file](/reference/secret-protection#allow-a-blocked-file).

Turning the master switch off asks for confirmation. Afterward the summary reads `Off. Sensitive files and deny paths are not blocked. Your rule settings and paths are kept.`

<Warning>
  Turning off command protection or secret protection disables every configurable rule in that layer until you turn it back on. Only the `Always on` command rules keep blocking. Prefer a single rule override or a lower preset over the master switch.
</Warning>

### Exceptions and extra paths

The **Exceptions and extra paths** panel holds three path lists. Entries can be absolute or start with `~/`. The panel rejects your home directory and the folders above it. Paste several lines to add many entries at once.

| List | Policy field | Effect |
| --- | --- | --- |
| `Allow recursive deletes in` | `destructive_command_protection.allow_paths` | CC Safety Net does not block recursive deletes inside these paths. Use it for a scratch folder under `/tmp`. Disabled while command protection is off |
| `Always block access to` | `secret_protection.deny_paths` | CC Safety Net blocks these paths and everything inside them while secret protection is on |
| `Paths exempt from secret patterns` | `secret_protection.allow_paths` | Files, folders, or a file name under a folder, such as `~/code/**/.env.local`, are exempt from the built-in file rules. Deny paths and coding agent credentials still apply |

A rejected entry shows `Not added: <paths>. <reason>`, and a duplicate shows `Already listed: <paths>`. See [Allow paths](/configuration/policy#allow-paths), [Deny paths](/configuration/policy#deny-paths), and [Secret allow paths](/configuration/policy#secret-allow-paths) for what each list relaxes and which entries it accepts.

### Policy JSON

The collapsed **Policy JSON** card at the bottom is a read-only copy of the policy with a `Copy` button. It shows the policy the form would save, the file as it is on disk while it has errors, or, in a project draft, the exact file the apply would write.

### Repair

When the policy file has errors, Protections shows `Your policy file needs repair` with the errors and a `Repair` button. Repair asks for confirmation, then keeps every valid setting and drops the invalid ones. If the file is not readable JSON, it restores the defaults.

<Warning>
  Repair drops invalid settings, and restores defaults when the file is not readable JSON. If the file holds hand-written configuration you care about, copy it somewhere safe first.
</Warning>

To reset the policy completely, use **Reset policy** in [Settings](#settings).

## Custom rules

Custom rules shows the rulebooks you wrote, as they are enforced now. These rules are separate from the built-in protections. See [Custom rules](/configuration/custom-rules) for the rulebook format.

<Warning>
  The Custom rules view is not a rulebook editor. CC Safety Net never writes a rulebook from the dashboard. This view shows rules read-only as they are enforced, and composes prompt text for you to copy into a coding agent that does the authoring.
</Warning>

### Rulebooks (read-only)

Each rulebook shows its name, version, scope (`All projects` or `This project`), and rule count. Each rule shows the command it matches, its `custom.<name>` ID, its reason, and the arguments that trigger it. The view does not list a rule that an override turns off. The refresh icon reads the files again.

With no rulebooks, the view reads `No custom rules yet.` and points you to `Create a rule` or `npx -y cc-safety-net rule init`.

### Problems

The **Problems** section appears only when there is something to report. An error there means CC Safety Net skipped a rulebook and enforces none of its rules. Look here when a rule you wrote is not firing.

### Create a rule (copy only)

**Create a rule** builds a prompt for your coding agent to write the rule. Its only action is **Copy prompt**.

- **Applies to.** `This project` or `All projects`.
- **Project folder.** Shown for `This project`, starting at the folder you launched the dashboard from.
- **What should be blocked?** Describe the rules you want. Rules match a command, its subcommands, and exact arguments. They do not match file paths. To block a file or folder, add it to `Always block access to` in [Exceptions and extra paths](#exceptions-and-extra-paths).
- **Try.** Starter prompts `Suggest rules`, `Block a command`, and `Verify rules`.

The prompt tells your agent to use the `cc-safety-net` skill, or `npx -y cc-safety-net rule doc` when the skill is missing. It includes your existing rulebook names so the agent picks an unused one. After copying, the page reports `Prompt copied`.

## Agents

Agents installs or removes the CC Safety Net hook for each coding agent on this machine. See [Installation](/installation) for each agent's setup outside the dashboard.

Each row shows the agent, its version or `Not detected`, a status, and an action:

| Status | Meaning | Action offered |
| --- | --- | --- |
| `Hook installed` | The hook is configured and active | `Uninstall` |
| `Hook disabled` | The agent is installed, but its hook is disabled | `Enable` |
| `Status unknown: its settings file could not be read` | CC Safety Net found the agent but could not read its settings file | `Install` |
| No status | The agent is installed with no hook | `Install` |
| `Not detected` in the version column | CC Safety Net did not find the agent on this machine | None |

The command output appears under the row after an action. A failure reports `Install failed` or `Uninstall failed`. Select the refresh icon (`Refresh agents`) after you install an agent or edit its config by hand.

## Settings

**Appearance.** `Theme` offers `Auto`, `Light`, and `Dark`. The dashboard saves it together with your [language](#dashboard-language), not in your policy.

**Audit log.** `Keep logs for` sets how many days of audit records to keep, from 1 to 365. Unlike Protections, it saves as soon as you change it. It refuses with `Retention unchanged` while the policy needs repair, a project draft is open, or Protections has unsaved changes. `Log folder` shows the audit log directory with a `Copy` button. See [Retention](/reference/audit-log#retention).

<Warning>
  Shortening retention cannot be undone. The next cleanup deletes entries older than the new window. The dashboard asks you to confirm and names the folder it will prune. Copy any entries you need first with `Copy log entry` on Activity.
</Warning>

**Files.** Read-only rows show the user policy path, with `(not created yet)` when the file does not exist, and the project policy path when one is in force. When the project policy weakens your settings, a notice lists each change under `The project policy changes these settings:`. To refuse those changes, see [Ignore project weakenings](/configuration/policy#ignore-project-weakenings).

**Danger zone.** **Reset policy** replaces your policy file with the defaults after a confirmation. It is unavailable while a project draft is open.

<Warning>
  Reset discards your saved configuration. Every preset choice, rule override, allow path, and deny path returns to defaults, with no undo. Reset affects only the policy file. It does not touch custom rulebooks.
</Warning>

## Dashboard language

The language menu at the bottom of the sidebar, or of the page on a narrow screen, switches the dashboard between English, Japanese (日本語), and Simplified Chinese (简体中文). Until you pick one, the dashboard follows your browser's language and falls back to English. Block reasons, rule ids, and server errors stay in English.

The dashboard saves your language and theme to `gui.json` in `~/.cc-safety-net/`, or in `$CC_SAFETY_NET_HOME` when that variable is set. Both choices survive a relaunch, even though each launch uses a new port. They are not part of your policy.
