Use this page when you configure or debug an integration. It describes how each agent calls CC Safety Net and receives a decision. See [How it works](/guides/how-it-works) for the user-facing lifecycle.

CC Safety Net supports sixteen coding agents, and it does not plug into all of them the same way. There are four integration models. Knowing which one your agent uses helps you debug a hook that is not firing and know where its configuration lives.

See [Installation](/installation) for the commands that install or remove each integration. Every model on this page feeds the same guard, specified once in [Architecture](/guides/architecture).

## Integration models by agent

| Model | Agents | How it works |
| --- | --- | --- |
| **Stdin hook subprocess** | Antigravity CLI, Claude Code, Codex, Cursor, Devin CLI, Factory Droid, Gemini CLI, GitHub Copilot CLI, Grok Build, Hermes Agent, Kimi Code | The agent runs `cc-safety-net hook <flag>` as a short-lived process for each tool call, writing the call as JSON to its stdin. CC Safety Net analyzes it and prints an agent-specific deny object on stdout, exiting 0. |
| **Agent-loaded plugin** | DeepSeek Harness, OpenClaw, OpenCode | The agent loads CC Safety Net as a plugin of its own package format. There is no `hook` flag for these agents. |
| **In-process extension** | Pi | Pi loads CC Safety Net's extension directly into the Pi process and calls it in memory. It uses no subprocess, stdin, or stdout. |
| **Event plugin** | Amp Code | Amp loads a managed personal plugin from the account's Personal Plugins repository and delivers each `tool.call` event to it, in process. |

## Stdin hook subprocess agents

For these eleven agents, the protection is the runtime `hook <flag>` command, which reads JSON from stdin. Each agent names its pre-execution event and its command tool differently, and each expects a different deny shape on stdout:

| Agent | Runtime flag | Hook event | Command tool | Deny output shape |
| --- | --- | --- | --- | --- |
| Antigravity CLI | `-ac` / `--agy-cli` | `PreToolUse` | `run_command` | `{ "decision": "deny", "reason": … }` |
| Claude Code | `-cc` / `--coding-cli` | `PreToolUse` | `Bash`, `PowerShell`, `Monitor` | `hookSpecificOutput.permissionDecision: "deny"`, or `"ask"` when [standard mode could not verify the command](#when-claude-code-asks-instead-of-denying) |
| Codex | `-cx` / `--codex` | `PreToolUse` | `Bash` | `hookSpecificOutput.permissionDecision: "deny"` |
| Cursor | `-cu` / `--cursor` | `preToolUse` | `Shell` | `{ "permission": "deny", "user_message": …, "agent_message": … }` |
| Devin CLI | `-dv` / `--devin` | `PreToolUse` | `exec`, `write_to_process` | `{ "decision": "block", "reason": … }` |
| Factory Droid | `-fd` / `--droid` | `PreToolUse` | `Execute` | `hookSpecificOutput.permissionDecision: "deny"` |
| Gemini CLI | `-gc` / `--gemini-cli` | `BeforeTool` | `run_shell_command` | `{ "decision": "deny", "reason": …, "systemMessage": … }` |
| GitHub Copilot CLI | `-cp` / `--copilot-cli` | `PreToolUse` | `bash`, `Bash`, `powershell`, `PowerShell` | `{ "permissionDecision": "deny", "permissionDecisionReason": … }` |
| Grok Build | `-gb` / `--grok-build` | `PreToolUse` | `run_terminal_command`, `monitor` | `{ "decision": "deny", "reason": … }` |
| Hermes Agent | `-ha` / `--hermes-agent` | `pre_tool_call` | `terminal` | `{ "action": "block", "message": … }` |
| Kimi Code | `-kc` / `--kimi-code` | `PreToolUse` | `Bash` | `hookSpecificOutput.permissionDecision: "deny"` |

Claude Code's `Monitor` and Grok Build's `monitor` also run a shell command, so both are command tools. `Monitor` goes to the POSIX analyzer and `monitor` uses automatic dialect detection. A `Monitor` call with no `command` field keeps the non-command route. That is the WebSocket variant, which sends `ws: { url, protocols? }` instead. As a command tool its missing command would fail closed and deny every WebSocket watch.

Devin CLI's `write_to_process` is a command tool only for the text it types into a running process. A non-empty string `text_input` goes to the analyzer as a shell command with automatic dialect detection, and nothing else in the call is read. Every other `write_to_process` call takes the unknown-tool input route, so CC Safety Net checks a `bytes_input` keypress for protected paths instead of parsing it as a command.

Factory Droid's `Glob` tool takes `{ patterns, folder }`. CC Safety Net reads both keys as paths on the glob route, so `patterns: "**/.env"` reaches the secret checks and blocks under `secret.basename.env`.

<Note>
  Because these agents use different events and deny formats, CC Safety Net emits the correct shape per agent. Gemini CLI, for example, expects a `decision`/`systemMessage` object with exit 0 rather than Claude Code's `hookSpecificOutput`. You do not need to configure the output format because the flag selects it.
</Note>

### When Claude Code asks instead of denying

The Claude Code hook is the only one that can answer `ask`. In place of `permissionDecision: "deny"` it emits `permissionDecision: "ask"`, and Claude Code puts the call in front of you as a permission prompt.

Two denials become an ask, and only while the fail-closed capability is off, which is the standard level:

- The rule `raw-text.dangerous-command`, which fires when a command CC Safety Net could not parse still reads as destructive.
- The reason `shell execution source cannot be verified safely. Use a literal command string or ask the user to run it manually.` Two cases here keep the deny. One is a command whose raw text also holds a destructive pattern. The other is an unverifiable source fed to a bare shell reading stdin, such as `sh -`.

Every other denial stays a deny, as does every denial at [strict and paranoid](/configuration/modes#strict-mode-cc_safety_net_strict=1), because both turn fail-closed on.

An ask is only useful when a person sees it, so the hook emits it in the `default`, `acceptEdits`, and `plan` permission modes. Any other value, and a missing one, gets the deny instead. In the remaining modes Claude Code can settle a prompt with nobody watching, which would turn the ask into a quiet allow.

No other host asks. Codex and Kimi Code run through the same `PreToolUse` adapter but do not enable the ask output, and Cursor's hook shape carries only `allow` and `deny`. A host that does not prompt on `ask` runs the command instead of stopping it. Codex rejects the value and runs the tool.

The prompt carries different wording from a block message, and the audit log still records the call as a denial. [What a block looks like](/guides/how-it-works#what-a-block-looks-like) shows both messages, and [When standard cannot verify a command](/configuration/modes#when-standard-cannot-verify-a-command) covers the same two denials from the policy side.

### Use the shared Coding CLI hook

`hook --coding-cli` (short flag `-cc`) is the canonical name of the Claude-shaped hook. It is called "Coding CLI" rather than "Claude Code" because the entry point accepts that payload shape from any agent that sends it.

`hook --claude-code` is accepted as a legacy alias and is not advertised in `hook --help`. Do not use it in new configuration.

Separately, three agents keep legacy **top-level** forms that skip the `hook` word: `cc-safety-net -cc` / `--claude-code`, `-gc` / `--gemini-cli`, and `-cp` / `--copilot-cli`. The canonical `--coding-cli` is not a top-level flag. A bare `cc-safety-net --coding-cli` errors with `Unknown option: --coding-cli`.

<Note>
  The `statusline` command is unrelated to the hook and still requires `--claude-code` or `-cc`. See [Status line](/configuration/status-line).
</Note>

### Hook configuration locations

CC Safety Net writes files directly for seven of the eleven agents. Six use hook configuration entries, and Hermes Agent uses a managed plugin. The other four use their own plugin or extension distribution channel, which then invokes the stdin hook:

| Agent | Config location and load mechanism |
| --- | --- |
| Antigravity CLI | Written directly: a managed `PreToolUse` entry in `~/.gemini/config/hooks.json` running `npx -y cc-safety-net hook --agy-cli` |
| Claude Code | Plugin `cc-safety-net@cc-marketplace`; plugin state in `~/.claude/settings.json` under `enabledPlugins` |
| Codex | Plugin `cc-safety-net@cc-marketplace`; the plugin's own `hooks/codex.json` registers the `PreToolUse` entry that runs `node "${PLUGIN_ROOT}/dist/bin/cc-safety-net.js" hook --codex` |
| Cursor | Written directly: a managed `preToolUse` entry in `~/.cursor/hooks.json` running `npx -y cc-safety-net hook --cursor` with `timeout: 30` and `failClosed: true`. The config is global, so it covers Cursor IDE and Cursor CLI across all projects. When Cursor imports Claude Code plugins, it also runs the hook from the enabled Claude Code plugin. That plugin's `.cursor-plugin/plugin.json` points at `hooks/cursor.json`, which runs `node "${CURSOR_PLUGIN_ROOT}/dist/bin/cc-safety-net.js" hook --cursor` with no matcher. See [Cursor installation](/installation#cursor-installation) |
| Devin CLI | Written directly: a managed `PreToolUse` entry under `hooks` in `$XDG_CONFIG_HOME/devin/config.json` (`~/.config/devin/config.json` by default, `%APPDATA%\devin\config.json` on Windows) running `npx -y cc-safety-net hook --devin` with `timeout: 30`. The entry carries no matcher, so file tools reach the hook alongside `exec`. Devin allows comments in that file, so CC Safety Net strips `//` and `/* */` comments before parsing, and a rewrite is plain JSON that no longer holds them. Install stops without writing and names the file when it does not parse, when its root is not a JSON object, when `hooks` is not an object, or when `hooks.PreToolUse` is not an array. Uninstall removes the managed handler and writes the file back; it never deletes `config.json` |
| Factory Droid | Written directly: a managed `PreToolUse` entry in the top-level `PreToolUse` array of `~/.factory/hooks.json` running `npx -y cc-safety-net hook --droid` with `timeout: 30` and no matcher, so file tools reach the hook alongside `Execute`. Droid reads hooks from the `hooks` key of `~/.factory/settings.json` while `hooks.json` is absent, so install seeds a new `hooks.json` with that event map before appending the managed entry, and never writes `settings.json`. Uninstall deletes `hooks.json` only when the stripped `PreToolUse` is its one remaining key and no `settings.json` exists; otherwise it writes the stripped file, because deleting it would re-activate the fallback. A `commandRegex` on the managed entry narrows which `Execute` calls reach the hook, and `doctor` reports it as drift that a reinstall repairs |
| Gemini CLI | Extension `gemini-safety-net`, loaded from the `gemini-safety-net` repository, not a `cc-marketplace` plugin |
| GitHub Copilot CLI | Plugin `cc-safety-net@cc-marketplace`, or hook files under `~/.copilot/hooks` / inline hooks in Copilot config. Hook support is version-gated, so which of those sources works depends on your Copilot CLI version. See [Installation](/installation#github-copilot-cli-installation). `disableAllHooks: true` disables all hooks |
| Grok Build | Written directly: a managed `PreToolUse` entry in `~/.grok/hooks/cc-safety-net.json` (or `$GROK_HOME/hooks/cc-safety-net.json`) running `npx -y cc-safety-net hook --grok-build` with `timeout: 30`. The entry carries no matcher, so file and patch tools reach the hook alongside `run_terminal_command`. Install and uninstall only ever touch the managed handler, so foreign entries in the file and foreign handlers inside a shared entry are left alone |
| Hermes Agent | Written directly: a managed Python plugin at `<Hermes home>/plugins/cc-safety-net/` (`__init__.py` plus `plugin.yaml`), then enabled with `hermes plugins enable cc-safety-net --no-allow-tool-override`. Enablement is recorded in Hermes' own `config.yaml` under `plugins.enabled` |
| Kimi Code | Written directly: a `[[hooks]]` block in `~/.kimi-code/config.toml` (or `$KIMI_CODE_HOME/config.toml`) running `npx -y cc-safety-net hook --kimi-code`. Alternatively, a native Kimi Code plugin installed inside Kimi Code with `/plugins install https://github.com/kenryu42/cc-safety-net`; its manifest runs the same hook entry (`node ./dist/bin/cc-safety-net.js hook --kimi-code`, `PreToolUse` event, 30-second timeout) with no matcher, so file tools also reach the hook |

For a Kimi Code `Bash` call, `tool_input.cwd` becomes the execution directory when it is present. It must be a non-empty string that resolves inside the session `cwd`; an invalid or escaping value fails closed.

For a Gemini CLI `run_shell_command` call, a string `dir_path` becomes the execution directory, because Gemini runs the command in `path.resolve(targetDir, dir_path)`. CC Safety Net resolves the value against the payload `cwd` and takes an absolute value unchanged. The session cwd stays the configuration directory, so the project's own rule configuration still applies.

The resolved path must be a directory that already exists. CC Safety Net denies the call when it is not, and the denial names the requested working directory as the cause. A whitespace-only or non-string `dir_path` fails closed. `""` means no `dir_path` at all, which matches Gemini's own check, so the command is analyzed in the session cwd.

Unlike Kimi Code's `cwd`, the resolved directory does not have to stay inside the session cwd. Gemini already validates `dir_path` against the workspace, the `--include-directories` roots, and the project temp directory before the `BeforeTool` hook fires. Amp's `dir` resolves the same way.

For a GitHub Copilot CLI call, `toolArgs` arrives as an object or as a string. CC Safety Net uses an object unchanged. It parses a string as JSON, and denies a string that is not JSON with the reason `Failed to parse toolArgs JSON.` One string is the exception. On a patch route, a string whose trimmed start is `*** Begin Patch` passes through as raw patch text. Copilot routes `powershell` and `PowerShell` calls to the PowerShell analyzer, and `bash` and `Bash` calls to automatic dialect detection.

On the plugin path Copilot sends its Windows `powershell` tool under the name `Bash`. The Claude-shaped adapter would otherwise route that call as a POSIX command. The adapter reads the environment variable `COPILOT_CLI` and routes `Bash` with the `auto` dialect when the value is `1`, so the PowerShell removal rules still apply. See [PowerShell `Remove-Item`](/guides/analysis-engine#powershell-remove-item).

For a Grok Build call, the trusted root is `workspaceRoot`, or `cwd` when `workspaceRoot` is absent. `cwd` must canonicalize to a directory inside that root, and an absent or empty `cwd` is treated as `.`. A root that cannot be canonicalized, or a `cwd` outside it, fails closed. A `toolInputTruncated: true` envelope also fails closed, because Grok Build truncates tool input at 128 KB and the truncated command cannot be analyzed.

For a Factory Droid call, the payload `cwd` is both the configuration and the execution directory. Unlike Kimi Code's `Bash`, the adapter reads no working directory out of the tool input, so an `Execute` call is analyzed in that same directory. A `cwd` that is present but not a non-empty string fails closed, and a `cwd` that does not resolve to a usable directory is denied, naming the session directory as the cause.

A Devin CLI payload carries no `cwd`, and the adapter does not read one. Both directories come from the hook process's own working directory, which is the session directory Devin starts the hook in.

### How Codex reaches the hook

Codex loads CC Safety Net as the `cc-safety-net@cc-marketplace` plugin from the `cc-marketplace` marketplace. The plugin is packaged in Codex's own format, and its manifest points at `hooks/codex.json`, which registers the `PreToolUse` hook. The same plugin carries the `cc-safety-net` skill.

Codex will not run an untrusted hook, so the hook stays inert until it is marked trusted inside Codex. See [Installation](/installation#codex-installation) for that step.

### How Hermes Agent reaches the hook

Hermes does not run the hook command from a hook config. CC Safety Net installs a managed Python plugin that Hermes loads in process, and the plugin registers a `pre_tool_call` handler. For each supported tool call, the handler runs `npx -y cc-safety-net hook --hermes-agent` and writes the call as JSON to its stdin. Empty stdout means the call is allowed. A `{ "action": "block", "message": … }` object blocks it, and Hermes shows the message to the model as the tool result.

The plugin forwards four tools: `terminal` for command analysis, `write_file` and `patch` for protected writes, and `read_file` for protected reads. Calls to any other Hermes tool are not forwarded and get no decision.

The plugin turns every failure into an explicit block that names its cause: `npx` missing from PATH, a spawn failure, a timeout (30 seconds, killing the analyzer's whole process group), a non-zero exit, or unreadable or unexpected output. A Hermes directory lookup the plugin cannot read also blocks. Analyzing the wrong directory would clear every path-scoped protection.

The plugin analyzes each tool in the directory Hermes itself would use. For `terminal` calls the plugin first reads Hermes' per-session cwd record, which holds the session's `cd` state. On the first command, before that record exists, it uses `TERMINAL_CWD`, then the Hermes process directory. A `terminal` call with an unusable `workdir` fails closed.

For `read_file`, `write_file`, and `patch` the plugin calls `_resolve_base_dir(task_id or "default")`. Hermes uses that same lookup to resolve those tools' relative paths. It walks the session's cwd record, the task's cwd override, `TERMINAL_CWD`, then the process directory. The import comes from `tools.file_tools`, which defines `_resolve_base_dir` up to Hermes v2026.8.31 and re-exports it from `tools.file_tools_paths` since v2026.9.7. If the import fails, the plugin blocks the call and names the lookup:

```text
CC Safety Net failed closed: the Hermes file tool directory could not be read (<error>). Update cc-safety-net and reinstall the plugin with: npx -y cc-safety-net install --hermes-agent.
```

The `terminal` lookup blocks with the same message, with `session` in place of `file tool`.

The analyzer subprocess starts from the home directory rather than Hermes' working directory, so `npx` cannot resolve a repository-local `cc-safety-net` in place of the real one.

The Hermes home decides where the managed plugin goes, and the Hermes CLI re-homes to a profile directory. A `HERMES_HOME` whose parent directory is named `profiles` is already a profile directory, so CC Safety Net uses it unchanged. Otherwise the root is `HERMES_HOME`, or `~/.hermes` when that is unset. CC Safety Net reads the `active_profile` file in that root, trims it, and lowercases it. The result selects `<root>/profiles/<name>`. An empty name, the name `default`, and a missing or unreadable file all keep the root. A name that fails Hermes' profile-id pattern stops the command:

```text
Invalid Hermes profile name "<profile>" in <root>/active_profile; run `hermes profile use <name>` with a valid profile.
```

Every managed file starts with a header line marking it as CC Safety Net's; the installer refuses to overwrite a file without it. Uninstall runs `hermes plugins disable cc-safety-net` before removing the files, because Hermes only resolves a plugin that is still on disk. In both directions the plugin change is inert until Hermes restarts. See [Installation](/installation#hermes-agent-installation) for the setup and removal commands.

Unlike Pi, `doctor` detects Hermes Agent entirely from disk: the managed plugin directory plus the `plugins.enabled` list in Hermes' `config.yaml`. No runtime probe is involved.

## Agent-loaded plugins

### DeepSeek Harness

DeepSeek Harness loads CC Safety Net **in process** as a profile plugin bundle. The package's `dsh.bundle.patch` field points at `dist/deepseek-harness/cordis.patch.yml`, which inserts one `cc-safety-net` row naming the bundle entry `./index.js`. The entry asks for the host's `tools` service and registers a single guard through `ctx.tools.guard`. There is no `hook` flag and no JSON-over-stdio.

The guard can only deny. Returning nothing allows the call, and returning a string blocks it with that text as the reason. DeepSeek Harness runs it after every `tools/pre-execute` listener, so approvals and Auto review have already run before CC Safety Net sees the call.

The guard analyzes two tools as shell commands, both reading the command from the execution's `arguments.command`:

| Tool | Analyzer dialect |
| --- | --- |
| `bash` | POSIX |
| `pwsh` | PowerShell |

Every other tool name goes through the non-command input routes, so file, patch, and search tools still reach path and secret protection.

The session's working directory is both the configuration and the execution directory. It comes from `agent.session.header.cwd`, and falls back to the directory the plugin was loaded in when the execution carries no session header. The session id comes from `agent.session.header.id`. A `workdir` argument on a `bash` or `pwsh` call is resolved against that working directory and becomes the execution directory; it must already exist as a directory, and the denial names the requested directory when it does not. Unlike OpenClaw's `workdir`, it is not required to stay inside the session directory.

The guard fails closed on a malformed execution object, a tool name that is not a non-empty string, a missing or empty `command`, an `arguments` value that is not an object, a `workdir` that is present but not a non-empty string, and a session directory it cannot resolve.

Installation drives DeepSeek Harness's own `dsh plugin ... add` command, once for the `web` profile through `npx -y @deepseek-ai/dsh` and once for the `desktop` profile through Desktop's bundled `dsh`. See [Installation](/installation#deepseek-harness-installation) for the setup and removal commands.

Like Hermes Agent and unlike Pi, `doctor` detects DeepSeek Harness entirely from disk. It reads each `<profiles>/<name>/package.json` under `~/.dsh/profiles` (or `$DSH_HOME/profiles`) and checks two things: whether `dependencies` lists `cc-safety-net`, and whether `dsh.profile.bundles` includes it. A profile with the dependency but without the bundle is installed and not enabled, and the row carries the error:

```text
cc-safety-net is installed in the <name> profile but its bundle is disabled
```

With at least one enabled profile the host reads `Configured` with the method `dsh bundle`, and any disabled profile still prints its error. With only disabled profiles the host reads as disabled. A profile manifest that cannot be read leaves the host `Not inspected`, and no profile with the dependency at all reads `n/a`.

### OpenClaw

OpenClaw loads CC Safety Net **in process** as a native OpenClaw plugin. The plugin ships as a packaged directory with three files. The runtime entry `index.js` is a self-contained bundle with every dependency inlined because a local directory install gets no `node_modules`. The `openclaw.plugin.json` manifest is validated before OpenClaw loads any code. A `package.json` points `openclaw.extensions` at the entry. There is no `hook` flag and no JSON-over-stdio.

The plugin registers a `before_tool_call` handler matched to the `exec` tool. Only the untagged shell `exec` is analyzed. An `exec` event with a `toolKind` discriminator, such as Code Mode's JavaScript `exec`, gets no decision because its `command` field is not a proven shell-command mapping. No other OpenClaw tool is forwarded to the guard. The handler returns either no decision (allow) or `{ block: true, blockReason }`; it never rewrites tool parameters.

It resolves the agent's workspace directory through OpenClaw's runtime API and uses it as both the policy and execution directory; a `workdir` in the call is resolved contained within that workspace. CC Safety Net fails closed on a malformed event, a missing or empty command, a workspace it cannot resolve, a `workdir` outside the workspace, or a call already cancelled. An `exec` call whose `host` is anything other than `auto` or `gateway` is also blocked. `gateway` is proven local. A call with `host: "auto"` (or no `host` at all) is analyzed with local Gateway semantics, but the plugin does not check where OpenClaw routes it. The sandbox case is listed in [Known limitations](/guides/known-limitations).

OpenClaw owns its plugin state, so installation drives OpenClaw's own CLI. It runs one command, `openclaw plugins install <packaged dir> --force --accept-capabilities`. Since OpenClaw 2026.8.1 that install enables the plugin itself unless you pass `--no-enable`, so there is no separate `openclaw plugins enable` step. If you disabled the plugin by hand in `openclaw.json`, it stays disabled and the runtime check below reports the non-loaded status rather than silently re-enabling it. `--accept-capabilities` does not exist before 2026.8.1, so an older OpenClaw rejects the install with an unknown-option error. There is no version check and no fallback.

`openclaw plugins uninstall` leaves an `enabled: false` marker behind, and `plugins install` does not enable an entry that is explicitly disabled. An install, uninstall, install sequence therefore used to land on status `disabled`. CC Safety Net now covers that one case. When the managed plugin's entry file was absent before the install and the runtime check reports `disabled`, it runs `openclaw plugins enable cc-safety-net` once and checks again. A plugin that was already installed and that you disabled stays disabled on install and on update, so an ordinary install or update never calls enable.

With a Gateway running, that enable can fail with `config reload superseded by a newer runtime config source`. OpenClaw saves `plugins.entries.cc-safety-net.enabled=true` before the runtime apply that gets superseded, and it never rolls that write back. CC Safety Net therefore does not retry the enable and does not fail the install on it. The second runtime check decides the result. Any other enable failure still fails the install. The Gateway applies the saved config in its own follow-up reload, or at its next start.

Before any `--force` command, CC Safety Net verifies that the target extension directory holds only its own managed files. It cannot overwrite or delete a plugin that is not provably its own. After installation, it runs `openclaw plugins inspect cc-safety-net --runtime --json` and treats only a `loaded` status as success. Otherwise, a broken enabled plugin could install cleanly and then protect nothing. A `disabled` status names the command to run:

```text
OpenClaw reports the cc-safety-net plugin with status "disabled"; run `openclaw plugins enable cc-safety-net`. Run `openclaw plugins inspect cc-safety-net --runtime` for details.
```

The installed copy lives at `<state dir>/extensions/cc-safety-net/`. The effective home is `OPENCLAW_HOME` when it is set to a non-empty value, and the OS home otherwise. A leading `~` in `OPENCLAW_HOME` expands against the OS home. The state dir is `OPENCLAW_STATE_DIR`, else the directory holding `OPENCLAW_CONFIG_PATH`, else `<effective home>/.openclaw`. A leading `~` in either of those two variables expands against the effective home. Enablement lives in OpenClaw's own config (`openclaw.json` in the state dir, or `OPENCLAW_CONFIG_PATH`): the global `plugins.enabled` switch, the `plugins.allow` and `plugins.deny` lists, and the per-plugin `plugins.entries.cc-safety-net.enabled` entry all take part. If `plugins.allow` is set, it must also list `cc-safety-net`.

Restart the OpenClaw Gateway after installing or uninstalling. The manifest activates the plugin at startup (`activation: { onStartup: true }`), so a running Gateway does not pick up the change. See [Installation](/installation#openclaw-installation) for the setup and removal commands.

### OpenCode

OpenCode loads CC Safety Net **in process** as a plugin object, declared in the `plugin` or `plugins` array of `opencode.json` (or `.jsonc`) in OpenCode's config directory. One npm package covers OpenCode 1.18.29+ and 2.0.6+, and the two generations implement different plugin contracts. V1's `bash` tool and v2's `shell` tool run through the same policy, analyzer, and audit code.

On OpenCode 1.x the plugin implements the `@opencode-ai/plugin` contract and does two things:

1. Implements `tool.execute.before`, which OpenCode calls ahead of every tool execution. CC Safety Net analyzes the call and throws a denial when the command is destructive; there is no JSON-over-stdio.
2. Implements the `config` hook to inject CC Safety Net's builtin commands into the OpenCode command set, without overwriting commands you have already defined.

For the `bash` tool, the plugin selects the analyzer dialect from OpenCode's `shell` setting. If the setting is not a string, it defaults to PowerShell on Windows and uses `SHELL` elsewhere. It then reads the last path segment of that value, lowercased and without a `.exe` suffix. `powershell` and `pwsh` select PowerShell, `cmd` uses automatic dialect detection, and every other executable selects POSIX. An empty or whitespace-only value uses automatic detection, as does a missing `SHELL` off Windows. A supplied `workdir` becomes the execution directory only when it resolves to a readable, searchable directory. On Windows, documented `/C:`, `/C`, `/cygdrive/C`, and `/mnt/C` forms are normalized, while other slash-rooted paths pass through for OpenCode to resolve.

On OpenCode 2.x the plugin registers under the id `cc-safety-net` and hooks `tool.execute.before`, returning typed `Tool.Error` denials. It checks the `shell` tool as a command, and read, edit, write, patch, grep, glob, and unknown tools through the same input routes as v1. Code Mode's child tool calls cross this hook too; CC Safety Net does not interpret the outer Code Mode JavaScript. The plugin also registers `/cc-safety-net` through the command API, and leaves an existing command of that name alone.

V2's `shell` tool resolves its workdir with the host's `FileAccess.resolvePath`, which maps `~` to the home directory and `~/x` to `<home>/x`. On v2 the plugin does the same, after the Windows drive normalization above. Exactly `~` is the home directory, `~/` is joined under it, and `~\` is too on win32. Every other form, such as `~other` or `~x`, stays project-relative. V1 does no tilde expansion, because OpenCode v1 resolves the workdir with `path.resolve`.

#### The v2 shell dialect

V2's tool event does not name the shell executable, so the analyzer dialect comes from the plugin's `shell` option rather than OpenCode's `shell` setting. It defaults to `powershell` on Windows and `posix` everywhere else. Set it in the config entry if you run PowerShell on Unix, or Git Bash on Windows:

```json
{
  "plugins": [
    {
      "package": "cc-safety-net@latest",
      "options": { "shell": "powershell" }
    }
  ]
}
```

Use `"posix"` for any shell that runs POSIX `sh` syntax, such as ash, bash, dash, ksh, sh, or zsh, and `"powershell"` for powershell or pwsh. The option does not select OpenCode's executable; it has to match the one OpenCode uses. Any other value fails the plugin with `CC Safety Net: plugin option shell must be posix or powershell.`

A `shell.create.before` hook checks the real executable before the spawn. With `"powershell"`, the executable's name has to be `powershell` or `pwsh`. With `"posix"`, the hook refuses `powershell`, `pwsh`, and `cmd` by name, with or without a `.exe` suffix, because OpenCode invokes those differently, and every other executable has to pass a probe. A failed check stops the spawn:

```text
CC Safety Net: actual shell "<actual>" does not match plugin option shell "<configured>". Configure the plugin's shell option to match OpenCode; supported dialects are posix and powershell.
```

The probe runs `x=ccsn; case $x in ccsn) echo $x-posix;; esac` through `<shell> -c`, in the plugin's `location` directory and with the environment OpenCode passes to the shell. The executable passes when that command exits without an error and its output contains `ccsn-posix`. The probe builds the marker from `$x`, so a shell that echoes the probe text back in an error message cannot pass. A shell that does not run POSIX `sh` syntax, such as fish, nushell, or tcsh, fails the probe and is refused rather than analyzed with the wrong parser.

The probe runs once per executable path. Shell creations that arrive while a check is pending share that one check. The plugin remembers a passing executable, so later creations of the same path skip the probe, and it forgets a failed or timed-out check, so the next creation probes again. A 10-second timer settles the check as failed and kills the probe with `SIGKILL`, so the result never waits for a shell that hangs.

That stop is not an ordinary tool denial. OpenCode's shell hook has no typed denial channel and no session ID, so a mismatch may fail the current operation, and it leaves no session-attributed audit entry. The check covers every shell created in the plugin's `location`, the OpenCode directory context the plugin was loaded for, including shell operations outside agent tool calls. It is not an operating-system sandbox.

OpenCode 1.x can serve a stale cached copy of the plugin, so a wiring change may not take effect until the cache is cleared. See [Installation](/installation#opencode-installation).

## The Pi extension

Pi loads CC Safety Net as an in-process extension, declared through the package's `pi.extensions` field and recorded as the package source `npm:cc-safety-net` in `settings.json` under Pi's agent directory. That directory is `PI_CODING_AGENT_DIR` when it is set, with a leading `~` expanded, otherwise `~/.pi/agent`. The extension does two things:

1. **Registers a `tool_call` event handler** (`pi.on('tool_call')`). The handler inspects Pi tool calls before they run and returns a block result when a command or path violates the policy. Nothing crosses a process boundary.
2. **Registers a `/cc-safety-net` builtin command** for managing rulebooks interactively inside Pi.

### Tools Pi protects

Pi has two command-tool adapters, the built-in `bash` and `powershell` tools. Both read a `command` field, and that command runs against the session cwd. `bash` goes to the POSIX analyzer, and `powershell` to the PowerShell analyzer. The obsolete custom `Shell` adapter is not supported. Pi's non-command tools still reach path and secret protection. In particular, `find` is classified as a read-only glob tool, so its `pattern` and path values are inspected without treating the search itself as a write. If a command call or its session cwd is malformed, CC Safety Net fails closed.

| Tool | Command field | Working directory |
| --- | --- | --- |
| `bash` | `command` | session cwd |
| `powershell` | `command` | session cwd |

### Detecting Pi

Because there is no hook config file to inspect, the `doctor` command detects Pi with a runtime probe (it spawns `pi` and asks whether the extension is loaded and enabled). This is why a Pi status in `doctor` may read `n/a` even when Pi is installed, if the probe cannot run.

## The Amp Code event plugin

Amp Code loads CC Safety Net as a **personal plugin**: a `cc-safety-net` directory in your Amp account's hosted Personal Plugins repository, holding the self-contained entry file `index.ts`. The plugin subscribes to Amp's `tool.call` event through the `@ampcode/plugin` API and returns either `allow` or `reject-and-continue` with a message. Like DeepSeek Harness, Pi, OpenClaw, and OpenCode, it runs in process. Because a personal plugin follows the account rather than one machine, it also covers threads that run on a remote executor such as an Amp Orb.

The Amp workspace root (`amp.system.workspaceRoot`) is the configuration directory. When a shell tool call carries a string `dir`, that value becomes the execution directory: a relative path resolves against the workspace root, the result goes through `realpath`, and it must exist and be a directory. Windows namespace paths are rejected. A `dir` that cannot be resolved fails closed, and the call is not analyzed for destructive commands. The denial no longer reports an unexpected analyzer failure. It names the working directory as the cause and tells the agent to use a directory that already exists and is accessible, or to create the missing one first. Unlike OpenClaw's `workdir`, the resolved directory is not required to stay inside the workspace. Amp legitimately points it at its own skills cache or a sibling repository, and the same work written as `cd <dir> && …` already runs there. The workspace root stays the configuration directory, so the project's own rule configuration still applies. The git-metadata guard anchors to both the execution directory and the configuration directory, so the workspace's own `.git` keeps its protection while the command runs elsewhere. See [Git metadata](/reference/blocked-commands#git-metadata).

`install --amp` publishes the artifact to that repository. It checks that the account has a writable Personal Plugins repository (`amp plugins repositories --json`), clones it into a throwaway checkout (`amp clone user-plugins`), writes `cc-safety-net/index.ts`, then commits and pushes. Staging uses an explicit pathspec (`git add -- cc-safety-net/index.ts`) rather than the directory, so a gitignored plugin path stops the install instead of staging nothing. Install and uninstall only ever write or `git rm` that one entry, so files you keep beside it in the directory are never touched.

A managed header identifies the entry as CC Safety Net's and marks it as safe to replace. Install and uninstall both refuse a `cc-safety-net` entry that is a symlink or not a directory, and an `index.ts` that is a symlink, not a regular file, or unmanaged. Releases before the directory layout published `cc-safety-net.ts` at the repository root; install removes a managed one in the same commit, and an unmanaged one fails the install.

A local plugin masks the personal one, so install also cleans up under `~/.config/amp/plugins/`. It removes a managed legacy `cc-safety-net.ts`, and a hand-copied `cc-safety-net/` directory that holds nothing but a managed `index.ts`. Any other local entry at those two paths fails the install. See [Installation](/installation#amp-code-installation) for the setup and removal commands.

### The embedded policy snapshot

The published artifact carries a snapshot of your user policy: one `globalThis.__CC_SAFETY_NET_EMBEDDED_POLICY__ = …` assignment appended to the file, with the policy normalized before it is written. At runtime, the snapshot applies only on a machine with no policy file of its own, such as an Orb with an empty home directory. A machine that has a policy file, even an invalid one, keeps its own behavior. Audit retention, user rulebooks, and project-scope policy are not embedded. A policy edit ships only on the next `install` or `update`.

Amp reads plugins at startup, so a newly published or removed plugin has no effect on the running session until Amp reloads.

### Detecting Amp Code

`doctor` detects the plugin by parsing `amp plugins list` output, where a personal-scope plugin renders as `✓ cc-safety-net (User Plugins) <status>`. That output carries no version, so `doctor` never reports version drift for Amp. `cc-safety-net update` republishes the current artifact regardless.

### Amp Code coverage limits

- Amp does not define the execution order of multiple plugins subscribed to the same `tool.call` event. CC Safety Net evaluates the input it receives and cannot re-evaluate an input that another plugin rewrites after CC Safety Net has already allowed it.
