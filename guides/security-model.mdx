CC Safety Net is a best-effort, static pre-execution hook for supported coding-agent tool calls. It stops recognized destructive commands and secret reads before they run. It is not an operating-system sandbox, a privilege boundary, or protection for commands that bypass an installed integration.

## What CC Safety Net protects

CC Safety Net treats every command an agent generates as untrusted. Prompt injection, confused context, or adversarial instructions can make an agent emit a destructive command, so the hook checks each supported tool call before the host runs it and denies the call when it finds a block reason.

How much of a call gets checked depends on the tool:

- An integration's own shell tools get full command analysis at your safety level.
- A tool you declare in [`command_tools`](/configuration/custom-rules#community-shell-tools) is analyzed like a built-in shell tool when the call carries a non-empty string `command`.
- Every other tool gets policy-file, Git-metadata, and sensitive-path checks only. CC Safety Net never treats its text as a shell command.
- A command that does not go through an installed integration is never checked.

The safety level sets how much analysis catches. [Which safety level should I use?](/configuration/modes#which-safety-level-should-i-use) compares the levels.

<Warning>
  Standard mode is **not adversarial-grade**. Standard allows dynamic `rm -rf` targets such as `rm -rf "$target"`; strict and paranoid block them. Use strict or paranoid when commands may come from prompt injection or another adversarial context.
</Warning>

No level or policy setting turns off the [catastrophic rules](/reference/blocked-commands#catastrophic-rules), which cover recursive deletion of `/` or your home directory, and the protections for [Git metadata](/reference/blocked-commands#git-metadata) and [`policy.json`](/reference/blocked-commands#protected-policy-json-files). While secret protection is on, no level relaxes reading a recognized secret file's contents or a path you listed in `deny_paths`.

## What CC Safety Net trusts

Three inputs from outside the hook can change what it enforces. CC Safety Net validates each one before it takes effect.

| Input | Who controls it | How CC Safety Net checks it |
| --- | --- | --- |
| User configuration | You, through your user [`policy.json` and `rule.json`](/configuration/environment#where-configuration-lives) | Schema-validates every file and never enforces a rejected one |
| Project policy | Anyone who can commit `.cc-safety-net/policy.json` to the repository | Schema-validates it and merges it over the user policy. `status` and `doctor` report every field it relaxes, and you can refuse them all. See [Project policy](/configuration/policy#project-policy) |
| Rulebook sources | Whoever publishes a rulebook you vendor, or you for a local one | Validates fetched content and runs its fixtures before writing the vendored copy, then validates the file again on every load |

An invalid configuration never denies ordinary work on its own. CC Safety Net drops the rejected source and reports the runtime as `degraded`. Dropping a rulebook removes its denials, so a command it blocked can run again until you fix it. [Configuration recovery](/configuration/recovery) lists every failure and its fallback.

## What happens when analysis fails

When analysis of one tool call cannot finish, CC Safety Net denies that call instead of letting it run:

- An unexpected analyzer error produces a deny with a "failed closed" reason.
- CC Safety Net denies malformed hook input, and any command too large or too deeply nested to analyze, at every safety level, standard included. A command that hits an analysis budget gets a reason that tells the agent to simplify or split it.
- Strict and paranoid also deny a command the parser cannot read. Standard lets safe-looking unparseable text through and still scans it for destructive patterns.

This depends on the host honoring the deny. Grok Build, Factory Droid, and Devin CLI fail open by design, so a hook that crashes, times out, or prints nothing lets the call run. [Known limitations](/guides/known-limitations) lists each host's behavior.

## What redaction hides and what it keeps

Before CC Safety Net writes command text to the audit log or returns it in a denial message, it replaces recognized credentials with `<redacted>`. The list covers private keys, URL credentials, secret-bearing environment assignments and HTTP headers, presigned-URL signatures, JWTs, AWS access key IDs, and known token prefixes. The [audit log reference](/reference/audit-log#secret-redaction) gives the full list.

Redaction matches known credential shapes only. It keeps absolute paths, project and directory names, hostnames, IP addresses, usernames, and any credential in an unlisted format. Avoid passing real credentials through commands an agent runs. `explain` and `doctor` output carries the same raw text, so read it before you share it. See [Before you share a trace](/reference/explain-trace#before-you-share-a-trace).

## How an attacker could try to get past it

| Attack | What the attacker tries | What stops it |
| --- | --- | --- |
| Parser tricks | Hide a destructive payload behind unusual quoting, nested substitution, or operator ambiguity | The parser leaves variables unexpanded, so dynamic targets stay visible. Strict and paranoid deny commands they cannot parse, and a parser error denies the call |
| Wrappers and interpreters | Hide a destructive command behind `sudo`, `env`, `bash -c`, `cmd /c`, `pwsh -c`, or an interpreter one-liner | CC Safety Net strips wrappers and re-analyzes the inner command or script. It blocks a recursive delete it cannot read inside `cmd` or PowerShell. Declare any other proxy as a [transparent wrapper](/configuration/custom-rules#transparent-wrappers) |
| Sensitive-file access | Read `.env`, `~/.ssh/id_*`, or `~/.aws/credentials` through a command, file tool, search, or patch | [Secret protection](/reference/secret-protection) covers those shapes for a fixed set of credential files plus your deny paths. It is not a general read boundary |
| Malicious rulebook | Serve a harmful rulebook from a GitHub source | `rule add` and `rule update` pin the source to a commit, refuse redirects, and validate the content. The vendored file lands in your repository for review. A rulebook can add blocking rules but cannot remove built-in ones |
| Project policy | Commit a project `policy.json` that lowers the level or allows a sensitive path for everyone who clones the repository | A project file cannot drop a user deny path or change audit settings. Every relaxation shows in `status`, `doctor`, and the status line, and [`CC_SAFETY_NET_PROJECT_TIGHTEN_ONLY=1`](/configuration/policy#ignore-project-weakenings) refuses them all. An agent can neither write `policy.json` nor run `cc-safety-net policy apply` |

Network attacks, attacks on the agent platform itself, and a symlink swapped between the check and the run are outside what a pre-execution hook can stop. See [Out-of-scope protections](/guides/known-limitations#out-of-scope-protections).
