CC Safety Net is a pre-execution hook. It receives each shell command and file operation your coding agent is about to run, checks it on your machine, and returns allow or block before the operation reaches the operating system. A blocked call never runs, and the agent gets a message telling it why and what to do instead.

## Does CC Safety Net use an LLM?

No. A local, rule-based parser makes every decision. It parses the command into its executable, subcommand, flags, and arguments, then applies fixed rules to that structure. The same command, working directory, and configuration always get the same decision. Nothing is sent to a model or over the network, and no wording in a prompt can turn a block into an allow.

## The lifecycle of one tool call

<Steps>
  <Step title="Your agent prepares a tool call">
    The agent prepares a shell command such as `git reset --hard`, or a file write, edit, search, or patch, and hands it to its tool layer.
  </Step>
  <Step title="The integration intercepts it">
    CC Safety Net's integration for that agent receives the call before the tool executes. How it receives the call depends on the agent. See [Integration models](#integration-models).
  </Step>
  <Step title="CC Safety Net checks the operation">
    CC Safety Net parses the input once and runs the checks in [What gets checked, in order](#what-gets-checked-in-order). The order is the same for every agent.
  </Step>
  <Step title="An allow or a block comes back">
    An allowed call executes normally. A blocked call never runs, and the agent receives the [block message](#what-a-block-looks-like) as the tool result.
  </Step>
  <Step title="The decision is logged">
    The decision goes to the local [audit log](#the-audit-record).
  </Step>
</Steps>

## Integration models

CC Safety Net supports sixteen agents through four integration models. Every model runs the same checks and reaches the same decision for the same call.

| Model | Agents | How the agent calls CC Safety Net |
| --- | --- | --- |
| Stdin hook subprocess | [Antigravity CLI](/installation/antigravity-cli), [Claude Code](/installation/claude-code), [Codex](/installation/codex), [Cursor](/installation/cursor), [Devin CLI](/installation/devin-cli), [Factory Droid](/installation/factory-droid), [Gemini CLI](/installation/gemini-cli), [GitHub Copilot CLI](/installation/github-copilot-cli), [Grok Build](/installation/grok-build), [Hermes Agent](/installation/hermes-agent), [Kimi Code](/installation/kimi-code) | The agent runs [`cc-safety-net hook`](/reference/cli/hook) as a short-lived process for each tool call and passes the call as JSON on stdin. |
| Agent-loaded plugin | [DeepSeek Harness](/installation/deepseek-harness), [OpenClaw](/installation/openclaw), [OpenCode](/installation/opencode) | The agent loads CC Safety Net as a plugin in its own package format. There is no `hook` flag for these agents. |
| In-process extension | [Pi](/installation/pi) | Pi loads CC Safety Net's extension into the Pi process and calls it in memory. |
| Event plugin | [Amp Code](/installation/amp-code) | Amp loads a personal plugin from your account's Personal Plugins repository and sends it each `tool.call` event. |

Each agent's page under Installation lists the tools it protects and where its configuration lives. To call the same check from your own Node.js program, see the [Library API](/reference/library-api).

## What gets checked, in order

Every tool call runs through the same stages, in this order:

1. **Bounded input extraction.** CC Safety Net reads the command out of the tool input under limits on depth, field count, and size. It blocks input past a limit.
2. **A single parse.** CC Safety Net parses the command once, and every later stage reuses the result. It blocks input that exhausts a parser budget at every safety level.
3. **Policy-file protection.** CC Safety Net blocks anything that would modify or delete its own `policy.json`, its directory, or an ancestor.
4. **Git-metadata protection.** CC Safety Net blocks anything that would delete, move, overwrite, or patch your repository's `.git` metadata or hooks directory, including from inside the working directory.
5. **Configuration load.** CC Safety Net resolves your policy, rulebooks, and safety level.
6. **Sensitive-path protection.** CC Safety Net checks commands, paths, searches, and patches against built-in sensitive locations (`.env`, `~/.ssh`, cloud and coding-CLI credential files) and any deny paths you configured.
7. **Destructive-command analysis.** CC Safety Net splits the command into segments and unwraps wrappers and interpreters. The matching analyzer then classifies each segment. Analyzers cover `git`, `rm`, `Remove-Item`, `find`, `xargs`, `parallel`, device commands, and custom rules.

Steps 3 and 4 run before step 5, so no configuration can weaken them. Step 6 follows your policy, so you can turn it off or extend it with your own deny paths.

## What the analyzer sees through

Hiding a command inside another one does not get it past step 7:

- **Wrappers and interpreters.** The analyzer unwraps `sh -c`, `bash -c`, `sudo`, `env`, and `python -c` or `node -e` one-liners and analyzes the inner command, up to 10 levels deep. Deeper nesting is blocked. See [Shell wrappers and interpreter one-liners](/reference/blocked-commands#shell-wrappers-and-interpreter-one-liners).
- **`cd` within one command.** The analyzer judges `cd dir && rm -rf x` in `dir`. A `cd` the analyzer cannot resolve makes later targets unverifiable. See [Filesystem commands](/reference/blocked-commands#filesystem-commands).
- **Shell functions.** The analyzer checks a function body where the function is called, so `cleanup() { rm -rf ../outside; }; cleanup` blocks. A definition that is never called is allowed. See [Filesystem commands](/reference/blocked-commands#filesystem-commands).
- **Heredocs.** `cat > note.md <<'EOF'` writes data and is allowed whatever the body says. A heredoc a shell runs as its program, as in `bash <<'EOF'`, is analyzed command by command. See [Heredocs in strict and paranoid](/reference/blocked-commands#heredocs).
- **Shell scripts.** The analyzer reads the script behind `sh x.sh`, `source x.sh`, and `./x.sh`, whether a heredoc in the same command wrote it or it was already on disk, and names the file and line in the block reason. Interpreter files such as `python3 tool.py` are not read. See [Scripts run from a file](/reference/blocked-commands#scripts-run-from-a-file).
- **Compound commands.** The analyzer checks commands inside `if`, `while`, `until`, and `{ …; }` bodies like top-level commands, so `if true; then rm -rf ~; fi` blocks.
- **Dynamic targets.** A target built from a variable or substitution, such as `rm -rf "$target"`, cannot be verified before it runs. Standard allows it, and [strict](/configuration/modes#strict-mode-cc_safety_net_strict=1) and paranoid block it. See [Filesystem commands](/reference/blocked-commands#filesystem-commands).

## Why intent, not string matching

CC Safety Net decides on what a command does. Two commands with the same first words can get different outcomes:

| Command | What it does | Outcome |
| --- | --- | --- |
| `git checkout -b feature` | Creates a new branch | Allowed |
| `git checkout -- file` | Discards uncommitted changes in a file | Blocked |

Both begin with `git checkout`, so a prefix rule cannot tell them apart without repeating Git's option logic. Parsing the command also catches reordered flags (`rm -r -f /`), shell wrappers (`sh -c "rm -rf /"`), and interpreter one-liners (`python -c 'import os; os.system("rm -rf /")'`).

This page does not list rules. [Blocked and allowed commands](/reference/blocked-commands) lists what is stopped and what is not.

## What a block looks like

The agent receives the block message as the tool result:

```text
BLOCKED by CC Safety Net

Reason: git checkout -- discards uncommitted changes permanently. Use 'git stash' first.

Rule: git.checkout-double-dash

Command: git checkout -- src/main.py

Do not retry the blocked form. Continue the task using the safer alternative described above.
```

The `Rule:` line gives the id of the rule or [fixed denial](/reference/blocked-commands#fixed-denial-ids) that blocked the call. Only a hook call whose input is missing or is not valid JSON is blocked without one. When they apply, the message also carries the `Tool:` name, the `Segment:` that triggered the block, and a `Config warning:` when a fallback configuration is in force. It adds a `Working directory:` line when CC Safety Net refused the call over the directory it would have run in. CC Safety Net shortens command and segment text and redacts secrets from the whole message.

A block does not end the agent session. The rule's intent selects the closing instruction, which sends the agent back to its task instead of retrying variants:

| Intent | What the agent is told to do |
| --- | --- |
| `hard_stop` | Do not retry or work around it by any means; report the block and continue with the rest of the task |
| `use_alternative` | Do not retry the blocked form; continue using the safer alternative named in the reason |
| `scope_down` | Retry with a narrower, explicit target; escalate to the user if the broad operation is required |
| `manual_only` | Ask the user for explicit permission and have them run it manually |
| `stop_and_explain` | Do not brute-force variants; simplify or restructure the command, or report the block |

The instruction tells the agent what to do next. The block itself does not depend on the agent following it, because the command never runs.

### When the message asks instead of blocking

In Claude Code, a command that standard mode could not verify reaches you as a permission prompt instead of a block. The message keeps the same fields and changes the first and last lines:

```text
CC Safety Net could not verify this command

Reason: shell execution source cannot be verified safely. Use a literal command string or ask the user to run it manually.

Command: eval "$CMD"

Segment: eval $CMD

Approve only if you expected this command.
```

The closing line replaces the intent instruction, because you decide this one rather than the agent. Approving runs the command and declining does not. The audit log records the call as a denial either way. [When Claude Code asks you instead of blocking](/installation/claude-code#when-claude-code-asks-you-instead-of-blocking) lists which denials can ask and in which permission modes.

## The audit record

CC Safety Net records every denial, and allowed command decisions by default, in a local audit log. Read it with `npx cc-safety-net logs`. The [audit log reference](/reference/audit-log) covers its location, fields, retention, and redaction.

## When a decision surprises you

<Steps>
  <Step title="Ask why">
    `npx cc-safety-net explain "<command>"` replays the analysis and shows which rule matched and why. Add `--json` for the structured trace.
  </Step>
  <Step title="Check that protection is in force">
    `npx cc-safety-net status` prints `ready` or `degraded`. `degraded` means a configuration source was rejected and a fallback is in force. See [`status`](/reference/cli/status) for the output and [Configuration recovery](/configuration/recovery) to repair the source.
  </Step>
  <Step title="Adjust or report">
    If the block is correct but too strict for your workflow, change your [safety mode](/configuration/modes) or add a per-rule override. If a safe command is blocked or a destructive one was not, see [Troubleshooting](/guides/troubleshooting) and the [security policy](/security) for where to report it.
  </Step>
</Steps>

## What CC Safety Net does not cover

CC Safety Net checks the tool call your agent attempts. It cannot see what an arbitrary binary does once it runs, commands sent through an opaque proxy, or network activity. It is not an OS sandbox or a privilege boundary, and it does not protect commands that bypass an installed integration. See [Known limitations](/guides/known-limitations) for the full list and mitigations.
