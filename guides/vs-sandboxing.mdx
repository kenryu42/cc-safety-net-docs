## Do I still need CC Safety Net if I run my agent in a sandbox or container?

If you care about uncommitted work, probably yes. A sandbox like Claude Code's or Codex's limits writes to the project directory and restricts network access. But `git reset --hard` and `rm -rf .` write inside that directory, and `git push --force` goes to a remote you allowed, so the sandbox permits all three. CC Safety Net blocks them. It does not contain processes or control the network. If your main worry is prompt injection, malicious dependencies, untrusted code, or data leaving over the network, a sandbox is the better choice. Use both.

## Do I need CC Safety Net if my agent has permission deny rules?

It depends. As of October 2026, Claude Code's deny rules are deterministic and still apply in `bypassPermissions` mode, so if you only need to block a few exact commands in one CLI, they may be enough. Deny rules match the command string against a wildcard pattern, so reordered flags (`rm -r -f`), a shell wrapper (`sh -c "..."`), or an interpreter can slip past. CC Safety Net parses what the command does, so it catches those variants. It also applies one policy and one audit log across 16 CLIs. Many setups use both.

## What each layer covers and misses

Each layer decides on different evidence, so each one misses cases the others catch.

| Layer | How it decides | What it covers | What it misses |
|---|---|---|---|
| OS-level sandboxing | The operating system enforces a boundary on the whole process tree | Writes outside the working and temporary directories, and network access, which is restricted or off | Anything inside the boundary: `git reset --hard`, `rm -rf .`, and reads of credential files, since reads are broad by default |
| Permission deny rules | A wildcard pattern matches the command string | The exact commands you name, in every permission mode | Variants of those commands with reordered flags, a wrapper, or an interpreter, and every command you did not name |
| Permission prompts and approval classifiers | You or a classifier model judge each action before it runs | Destructive git commands and other actions a reviewer recognizes | A 17% false-negative rate published as of October 2026, and a bypass mode that asks about nothing |
| Containers, VMs, and checkpoints | The session runs on a machine you can throw away, and edits can be rewound | Damage to your own machine, and file edits captured before each prompt | The mounted workspace holds real work, pushes reach the real remote, and rewind does not cover bash commands |
| CC Safety Net | Static analysis of what each supported tool call does, before it runs | Destructive git and filesystem operations wherever they point, Git metadata, and reads of recognized credential files | Network egress, credentials in files it does not recognize, behavior inside a binary, and commands outside an installed integration. A denial is not filesystem enforcement |

[Known limitations](/guides/known-limitations#out-of-scope-protections) lists what CC Safety Net cannot protect, and which layer covers each case.

## Why a sandbox allows destructive git commands

A sandbox restricts *where* a process can write, not what it does inside that area. As of October 2026, Claude Code's [sandboxing docs](https://code.claude.com/docs/en/sandboxing) scope writes to the working directory by default. So `git reset --hard` and `rm -rf .` on your project are permitted writes. `git push --force` rewrites your remote and writes nothing locally, so a local write scope does not cover it. The sandbox has no concept of Git history, uncommitted changes, stash entries, or which files hold credentials.

| Command | OS-level sandboxing | CC Safety Net |
|---|---|---|
| `git reset --hard` | Allowed (within cwd) | Blocked |
| `git checkout -- .` | Allowed (within cwd) | Blocked |
| `git stash clear` | Allowed (within cwd) | Blocked |
| `git push --force` | Allowed (if remote domain allowed) | Blocked |
| `rm -rf .` | Allowed (within cwd) | Blocked |
| `cat .env` | Allowed (reads are broad) | Blocked |

<Note>
  Whether these commands run automatically or require confirmation depends on your agent's sandbox mode and approval policy. `git push --force` also depends on your allowed-domain configuration.
</Note>

Sandbox reads are broad by default. As of October 2026, Claude Code's sandboxing docs say of the default read behavior that "There is no built-in credential deny list", and name `~/.aws/credentials` and `~/.ssh/` as files it still allows reading. CC Safety Net blocks content access to those paths with no configuration.

## When sandboxing is the better choice

Use a sandbox when your main concern is one of these:

- **Prompt injection.** Restrict outbound network domains to reduce exfiltration.
- **Malicious dependencies.** Limit the filesystem writes and network access of untrusted packages.
- **Untrusted code.** OS-level containment is stronger than command-text analysis.
- **Network control.** CC Safety Net has no network layer.

## Permission prompts and approval classifiers

This layer asks you, or a classifier model, before an action runs. As of October 2026, Claude Code's [permission modes](https://code.claude.com/docs/en/permission-modes) stop and ask before most edits and shell commands in Manual mode. In auto mode, "a second model, the classifier, reviews actions instead of you", and it blocks destructive git commands such as `git reset --hard` and `git stash clear` by default.

That review is a judgment, and you can turn it off. Anthropic publishes a 17% false-negative rate for the [auto-mode](https://www.anthropic.com/engineering/claude-code-auto-mode) classifier on real overeager actions and calls it "not a drop-in replacement for careful human review". Under `bypassPermissions`, everything runs without asking.

A CC Safety Net denial applies in every permission mode, including `bypassPermissions`. See [Claude Code permission modes and bypass mode](/installation/claude-code#claude-code-permission-modes-and-bypass-mode) for the version it was verified against.

## Containers, VMs, and checkpoints

A machine you can throw away is real containment, and Claude Code recommends `bypassPermissions` for "Isolated containers and VMs only". It does not protect the work inside the machine. A cloud session clones your repository, commits, and pushes back to your real remote, so `git reset --hard` costs the same uncommitted work there, and `git push --force` lands on a branch your teammates pull. A local container that mounts your working tree is the same, because the mount is writable. [Cloud environments](/guides/cloud-environments) covers the credential side.

Checkpoints cover part of that gap. As of October 2026, Claude Code's [checkpointing docs](https://code.claude.com/docs/en/checkpointing) state that "Checkpointing does not track files modified by bash commands." A destructive git command runs as a bash command, so a rewind does not restore the work it discards.

## Use sandboxing with CC Safety Net

A sandbox limits what any command can reach, and CC Safety Net stops the destructive commands and credential reads that a sandbox allows inside that boundary. A classifier and a disposable machine with checkpoints catch or undo part of what remains.

Sandboxes and allowlists also break. In 2026, CVE-2026-25725 escaped Claude Code's bubblewrap sandbox through `settings.json`, and CVE-2026-22708 bypassed Cursor's command allowlist. Run every layer you have.
