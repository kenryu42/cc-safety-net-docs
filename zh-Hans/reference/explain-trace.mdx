`explain --json` 命令返回命令分析的结构化跟踪。本页定义供脚本和其他工具使用的 JSON 结构，并说明一条跟踪在你分享之前可能暴露哪些内容。

有关标志和退出行为，请参阅 [CLI 命令](/zh-Hans/reference/cli-commands#explain)。命令被意外阻止时的排查方法，请参阅 [故障排除](/zh-Hans/guides/troubleshooting)。

```bash
npx cc-safety-net explain --json "git checkout -- file.txt"
```

<Warning>
  跟踪并不自动适合分享。请先阅读 [分享跟踪之前](#before-you-share-a-trace)。
</Warning>

## ExplainResult

`explain --json` 返回的顶级对象。

| 字段 | 类型 | 存在性 | 描述 |
| --- | --- | --- | --- |
| `result` | `"blocked" \| "allowed"` | 始终 | 命令的最终结果 |
| `reason` | `string` | 仅在 blocked 时 | 阻止原因 |
| `segment` | `string` | 仅在 blocked 时 | 触发决策的具体片段 |
| `ruleId` | `string` | 仅在 blocked 并匹配规则时 | 产生该阻止的规则 ID |
| `trace` | `ExplainTrace` | 始终 | 跟踪容器，含顶级步骤和各片段的步骤 |
| `customRule` | `object` | 匹配到自定义规则或 rulebook 规则时 | `id`，以及可选的 `rulebook`（`name`、`version`）、`source` 和 `override`（`{ type: "reason", reason }`） |
| `configSource` | `string \| null` | 始终 | 有效配置所来自的配置文件 |
| `configValid` | `boolean` | 始终 | 加载的配置是否顺利通过校验 |
| `effectiveLevel` | `"standard" \| "strict" \| "paranoid" \| "custom"` | 始终 | 环境标志和覆盖生效之后实际采用的级别 |
| `selectedPreset` | `"standard" \| "strict" \| "paranoid"` | 始终 | 策略中命名的预设，默认为 `standard` |
| `effectiveCapabilities` | `object` | 始终 | 各项能力的状态 — 见下文 |
| `destructiveCommandRuleOverrides` | `Record<string, "on" \| "off">` | 始终，可能为空 `{}` | 策略中存储的按规则覆盖 |
| `ruleActivation` | `object` | 视情况 — 见下文 | 相关规则的开启/关闭状态是怎么来的 |

这四个配置字段——`effectiveLevel`、`selectedPreset`、`effectiveCapabilities` 和 `destructiveCommandRuleOverrides`——只构建一次，并出现在每条返回路径中，因此即使解释的是空命令，它们也存在。

### `effectiveCapabilities`

`effectiveCapabilities` 是一个以 `fail_closed`、`paranoid_rm` 和 `paranoid_interpreters` 为键的记录。每个值包含：

| 字段 | 类型 | 描述 |
| --- | --- | --- |
| `enabled` | `boolean` | 该能力是否已开启 |
| `source` | `"preset" \| "capability_override" \| "environment"` | 决定最终状态的因素 |
| `sources` | `array` | 所有起了作用的输入，按优先级顺序排列 |

各项能力分别改变什么，请参阅 [模式](/zh-Hans/configuration/modes)。

### `ruleActivation`

`ruleActivation` 只在相关规则声明了激活能力时才存在。相关规则要么是匹配到的规则，要么是受模式门控的候选规则；后者指的是只要所需的级别或能力处于启用状态就会匹配的规则。

| 字段 | 类型 | 描述 |
| --- | --- | --- |
| `id` | `string` | 规则 ID |
| `enabled` | `boolean` | 该规则当前是否启用 |
| `inheritedEnabled` | `boolean` | 该规则是否仅凭继承就会启用 |
| `changesInherited` | `boolean` | 生效状态是否与继承来的状态不同 |
| `source` | `string` | 由什么决定：`catastrophic`、`master_disabled`、`rule_override`、`preset`、`capability_override`、`environment` 或 `built_in_default` |
| `activationCapability` | `string` | 可选。门控该规则的能力 |
| `override` | `"on" \| "off"` | 可选。若存在，即为存储的该规则覆盖值 |

在人类可读输出中，它渲染成一行：`Rule activation: <id> — on|off via <source>`。

## `ExplainTrace`

| 字段 | 类型 | 描述 |
| --- | --- | --- |
| `steps` | `TraceStep[]` | 顶级步骤。大多数跟踪以全局的 `parse` 步骤开始，保护短路时可能没有这一步。 |
| `segments` | `object[]` | 各片段的条目，每个条目都有一个 `index` 和自己的 `steps` 数组 |

跟踪是被动的：记录跟踪不会改变任何决策，普通的防护评估也从不构建跟踪。它只为 `explain` 而存在。

**上限。** 记录器会限制自己保留的内容：最多 512 个事件、每个文本值最多 2,048 个字符、每个列表最多 128 项、每个对象最多 128 个属性、最多 16 层嵌套。超出上限的事件只计数而不存储，并且每个记录下来的值都会被深度冻结。被丢弃的事件数量不会在 `ExplainTrace` 中暴露——它只有 `steps` 和 `segments`。

## `TraceStep` 变体

先用 `type` 选出变体，再读取它的其他字段。

| `type` | 关键字段 | 何时出现 |
| --- | --- | --- |
| `parse` | `input`, `segments` | 最初的 shell 拆分，得到 token 片段 |
| `env-strip` | `input`, `envVars`, `output` | 从片段开头剥离的环境赋值（值已脱敏） |
| `leading-tokens-stripped` | `input`, `removed`, `output` | 分析前删除的前导 token（例如 `env`、`command`） |
| `shell-wrapper` | `wrapper`, `innerCommand` | 解开了 `bash -c` 之类的 shell 包装器 |
| `interpreter` | `interpreter`, `codeArg`, `paranoidBlocked` | 检查了解释器单行命令；`paranoidBlocked` 标记 paranoid 模式下的直接拒绝 |
| `busybox` | `subcommand` | busybox 风格的分派解析为子命令 |
| `transparent-wrapper` | `wrapper`, `output` | 看穿了一个已注册的透明包装器 — 见下文 |
| `recurse` | `reason`, `innerCommand`, `depth` | 触发了递归重新分析 |
| `rule-check` | `ruleModule`, `ruleFunction`, `matched`, `reason?` | 评估了内置规则模块 |
| `worktree-relaxation` | `originalReason`, `gitCwd` | 因为目标是链接的工作树，git 丢弃类命令被放宽 |
| `tmpdir-check` | `tmpdirValue`, `isOverriddenToNonTemp`, `allowTmpdirVar` | `$TMPDIR` 解析和覆盖检测 |
| `fallback-scan` | `tokensScanned`, `embeddedCommandFound?` | 对剩余 token 的危险文本 fallback 扫描 |
| `custom-rules-check` | `rulesChecked`, `matched`, `reason?` | 评估了用户定义的规则 |
| `cwd-change` | `segment`, `effectiveCwdNowUnknown` | `cd`/`pushd` 改变了有效 cwd；后续分类使用新的或未知的 cwd |
| `dangerous-text` | `token`, `matched`, `reason?` | 按危险文本模式扫描了某个 token |
| `strict-unparseable` | `rawCommand`, `reason` | strict 模式在无法解析的命令上 fail closed |
| `segment-skipped` | `index`, `reason` | 因为前一个片段已经阻止，所以跳过了该片段 |
| `error` | `message`, `partial?` | 捕获了分析错误；`partial` 标记了部分输出 |

### `recurse` 原因

`recurse.reason` 取以下八个值之一：`shell-wrapper`、`interpreter`、`busybox`、`shell-eval`、`shell-trap`、`shell-stdin`、`shell-heredoc` 或 `heredoc-file`。

当命令运行的是分析已经知道其内容的脚本文件时——即同一命令中此前经由 `cat >` 或 `tee` 写入该路径的带引号 heredoc body——就会记录 `heredoc-file`，并把存储的 body 当作该脚本重新分析；请参阅 [Heredoc 分析](/zh-Hans/guides/analysis-engine#heredoc-分析)。

### `transparent-wrapper` 步骤

`transparent-wrapper` 是片段范围的步骤，当你用 `rule wrapper add` 注册的命令被看穿时记录。每个候选子命令——主子命令加上每个备选项——都会发出一个步骤，每个步骤携带：

| 字段 | 类型 | 描述 |
| --- | --- | --- |
| `wrapper` | `string` | 包装器命令名称 |
| `output` | `string[]` | 分析将递归进入的候选 token 列表 |

该步骤在递归进入这些 token 之前立刻记录，因此总是排在被包装命令的分析之前。人类可读输出把它渲染为带编号的 `Transparent wrapper` 步骤，显示 `Wrapper:` 和 `Tokens:`。

使用 `rule wrapper add`、`rule wrapper remove` 和 `rule wrapper list` 命令管理包装器。请参阅 [`rule wrapper`](/zh-Hans/reference/cli-commands#rule-wrapper)。

## 跟踪顺序

典型的跟踪流程为 `parse` → 每个片段的 `env-strip` / `leading-tokens-stripped` → 检测（`shell-wrapper` / `interpreter` / `busybox` / `transparent-wrapper`）→ `rule-check` 或 `custom-rules-check` → 决策。递归表现为 `depth` 递增的 `recurse` 步骤——`busybox` 分派除外，它会记录 `recurse` 步骤但不消耗递归深度，因此一连串 busybox 包装器会重复同一个 `depth` 值。只需要判定结果时，直接读顶级的 `result`（以及 `reason`、`segment` 和 `ruleId`），不必遍历整条跟踪。

有三种保护会在评估器运行之前短路：策略文件保护、Git 元数据保护和机密保护。其中之一阻止命令时，跟踪只含**一个合成的 `rule-check` 步骤，且没有 `parse` 步骤**，`ruleId` 设为 `policy-protection`、`git-metadata-protection` 或匹配到的机密规则的 ID。假定每条跟踪都以 `parse` 步骤开头的工具需要处理这种情况。

## 分享跟踪之前

<Warning>
  **explain 跟踪本身并不天然可以安全分享。** `parse` 步骤会记录你提供的原始命令字符串，以及从中解析出的每一个 token。许多其他步骤同样携带原始文本——`fallback-scan.tokensScanned`、`dangerous-text.token`、`shell-wrapper.innerCommand`、`interpreter.codeArg`、`recurse.innerCommand`、`strict-unparseable.rawCommand`、`transparent-wrapper.output`、`worktree-relaxation.gitCwd` 和 `cwd-change.segment`。`configSource` 是绝对路径，通常位于你的主目录内。

  脱敏只移除已识别的凭证**形式**——用的正是 [审计日志](/zh-Hans/reference/audit-log#机密脱敏) 那份有界的模式列表。它对文件路径、主机名、IP 地址、用户名、项目或客户名称，以及任何格式不在列表中的机密都不作任何保证，也无法脱敏它认不出来的内容。

  分享跟踪之前：用**占位凭证和占位路径**复现该场景，然后**从头到尾读一遍输出**，删掉任何你不愿公开的内容。
</Warning>

例如，解释包含 `--token=…` 赋值的命令时，token 会被脱敏，但同一命令中 `/srv/acme-prod/customer-dump.sql` 这样的路径会完整返回，命令文本里的任何主机名、IP 地址或账户名也一样。

可以在漏洞报告中附上 `explain` 输出。脱敏是尽力而为的控制手段，而不是保证；脱敏绕过属于可上报的漏洞。粘贴之前请通读完整输出。
