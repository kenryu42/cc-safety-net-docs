配置或调试集成时请查阅本页。这里说明各智能体如何调用 CC Safety Net 并接收判定。用户看到的完整流程见<a href="/zh-Hans/guides/how-it-works">工作原理</a>。

CC Safety Net 支持十六种编码智能体，它们通过四种模型接入。先确认智能体采用哪种模型，再排查未触发的 hook 或查找配置位置。

各集成的安装和删除命令见<a href="/zh-Hans/installation">安装</a>。四种模型都接入同一个防护，完整定义见<a href="/zh-Hans/guides/architecture">架构</a>。

## 按智能体划分的集成模型

| 模型 | 智能体 | 工作方式 |
| --- | --- | --- |
| **Stdin hook 子进程** | Antigravity CLI、Claude Code、Codex、Cursor、Devin CLI、Factory Droid、Gemini CLI、GitHub Copilot CLI、Grok Build、Hermes Agent、Kimi Code | 每次工具调用时，智能体都会以短生命周期进程运行 `cc-safety-net hook <flag>`，并把该调用作为 JSON 写入其 stdin。CC Safety Net 分析调用，在 stdout 打印智能体专用 deny 对象，并以 0 退出。 |
| **智能体加载的插件** | DeepSeek Harness、OpenClaw、OpenCode | 智能体按自己的软件包格式加载 CC Safety Net 插件。这些智能体没有 `hook` 标志。 |
| **进程内扩展** | Pi | Pi 直接在 Pi 进程中加载 CC Safety Net 扩展并在内存中调用，无子进程、stdin 或 stdout。 |
| **事件插件** | Amp Code | Amp 从账户的 Personal Plugins 仓库加载托管的个人插件，并在进程内向其发送每个 `tool.call` 事件。 |

## Stdin hook 子进程智能体

对这十一种智能体来说，保护由运行时 `hook <flag>` 命令提供，该命令从 stdin 读取 JSON。各智能体对执行前事件和命令工具的命名各不相同，要求的 stdout deny 形式也不同：

| 智能体 | 运行时标志 | Hook 事件 | 命令工具 | Deny 输出形式 |
| --- | --- | --- | --- | --- |
| Antigravity CLI | `-ac` / `--agy-cli` | `PreToolUse` | `run_command` | `{ "decision": "deny", "reason": … }` |
| Claude Code | `-cc` / `--coding-cli` | `PreToolUse` | `Bash`, `PowerShell`, `Monitor` | `hookSpecificOutput.permissionDecision: "deny"`；<a href="#when-claude-code-asks-instead-of-denying">standard 模式无法验证命令时</a>则为 `"ask"` |
| Codex | `-cx` / `--codex` | `PreToolUse` | `Bash` | `hookSpecificOutput.permissionDecision: "deny"` |
| Cursor | `-cu` / `--cursor` | `preToolUse` | `Shell` | `{ "permission": "deny", "user_message": …, "agent_message": … }` |
| Devin CLI | `-dv` / `--devin` | `PreToolUse` | `exec`, `write_to_process` | `{ "decision": "block", "reason": … }` |
| Factory Droid | `-fd` / `--droid` | `PreToolUse` | `Execute` | `hookSpecificOutput.permissionDecision: "deny"` |
| Gemini CLI | `-gc` / `--gemini-cli` | `BeforeTool` | `run_shell_command` | `{ "decision": "deny", "reason": …, "systemMessage": … }` |
| GitHub Copilot CLI | `-cp` / `--copilot-cli` | `PreToolUse` | `bash`, `Bash`, `powershell`, `PowerShell` | `{ "permissionDecision": "deny", "permissionDecisionReason": … }` |
| Grok Build | `-gb` / `--grok-build` | `PreToolUse` | `run_terminal_command`, `monitor` | `{ "decision": "deny", "reason": … }` |
| Hermes Agent | `-ha` / `--hermes-agent` | `pre_tool_call` | `terminal` | `{ "action": "block", "message": … }` |
| Kimi Code | `-kc` / `--kimi-code` | `PreToolUse` | `Bash` | `hookSpecificOutput.permissionDecision: "deny"` |

Claude Code 的 `Monitor` 和 Grok Build 的 `monitor` 同样会执行 shell 命令，因此两者都按命令工具处理：`Monitor` 走 POSIX 分析器，`monitor` 使用自动方言检测。只有不带 `command` 字段的 `Monitor` 调用例外，它仍按非命令工具处理。这类调用是 WebSocket 变体，发送的是 `ws: { url, protocols? }`。若按命令工具处理，它会因找不到命令而 fail closed，从而拒绝所有 WebSocket 监视。

Devin CLI 的 `write_to_process` 只有在向运行中的进程输入文本时才算命令工具。`text_input` 是非空字符串时，这段文本按 shell 命令分析，并使用自动方言检测，调用中的其他内容都不读取。其余的 `write_to_process` 调用走未知工具的输入路径，因此 `bytes_input` 按键不会解析为命令，只检查其中有没有受保护路径。

Factory Droid 的 `Glob` 工具接受 `{ patterns, folder }`。在 glob 路由上，这两个键都按路径读取，因此 `patterns: "**/.env"` 也会进入机密保护检查，并按 `secret.basename.env` 阻止。

<Note>由于这些智能体使用不同的事件和 deny 格式，CC Safety Net 会按智能体发出正确的形式。例如，Gemini CLI 要求以 0 退出并返回 `decision`/`systemMessage` 对象，而不是 Claude Code 的 `hookSpecificOutput`。无需配置输出格式，传入的标志会决定使用哪种格式。</Note>

<span id="when-claude-code-asks-instead-of-denying"></span>

### Claude Code 何时改为询问而不是拒绝

只有 Claude Code 的 hook 能返回 `ask`。它不输出 `permissionDecision: "deny"`，而是输出 `permissionDecision: "ask"`，由 Claude Code 把这次调用作为权限提示交给你确认。

只有两类拒绝会变成 `ask`，且仅在 fail-closed 能力关闭时，也就是 standard 级别：

- 规则 `raw-text.dangerous-command`，在 CC Safety Net 无法解析的命令文本读起来仍具有破坏性时触发。
- 原因为 `shell execution source cannot be verified safely. Use a literal command string or ask the user to run it manually.` 的那一类。其中两种情况仍然保持拒绝：命令原文本身也含有破坏性模式，或者把无法验证的来源交给了 `sh -` 这类只从 stdin 读取程序的 shell。

其余拒绝一律不变。<a href="/zh-Hans/configuration/modes#strict-mode">strict 和 paranoid</a> 都会开启 fail-closed，因此这两个级别的拒绝同样不变。

`ask` 只有在有人看到时才有意义，所以 hook 仅在 `default`、`acceptEdits` 和 `plan` 三种权限模式下输出它。其他取值，以及缺少该字段的情况，都按拒绝处理。在其余模式下，Claude Code 可能在无人查看的情况下处理掉提示，`ask` 就等同于悄悄放行。

其他宿主都不会询问。Codex 和 Kimi Code 使用同一个 `PreToolUse` 适配器，但未启用 ask 输出；Cursor 的 hook 形式只有 `allow` 和 `deny`。不会在 `ask` 上弹出提示的宿主会直接运行命令，而不是拦截它。Codex 就会拒绝这个取值并执行该工具。

提示文案与阻止消息不同，审计日志仍按拒绝记录这次调用。两种消息都可以在<a href="/zh-Hans/guides/how-it-works#what-a-block-looks-like">阻止消息的形式</a>中查看；这两类拒绝在策略层面的说明见<a href="/zh-Hans/configuration/modes#when-standard-cannot-verify-a-command">`standard` 无法验证命令时</a>。

### 使用共享 Coding CLI hook

`hook --coding-cli`（短标志 `-cc`）是 Claude 形式 hook 的规范名称。名称使用 `Coding CLI`，不使用 `Claude Code`，因为该入口点接受任何智能体发来的这种形式的 payload。

`hook --claude-code` 作为旧别名仍被接受，但不会在 `hook --help` 中列出。不要在新配置中使用。

另有三个智能体保留了省略 `hook` 一词的旧**顶层**形式：`cc-safety-net -cc` / `--claude-code`、`-gc` / `--gemini-cli` 和 `-cp` / `--copilot-cli`。规范 `--coding-cli` 有意不是顶层标志，单独运行 `cc-safety-net --coding-cli` 会报 `Unknown option: --coding-cli`。

<Note>`statusline` 命令与 hook 无关，仍要求 `--claude-code` 或 `-cc`。见<a href="/zh-Hans/configuration/status-line">状态行</a>。</Note>

### Hook 配置位置

十一种智能体中有七种由 CC Safety Net 直接写入文件：其中六种写为 hook 配置条目，Hermes Agent 写为托管插件。另外四种通过各自的插件或扩展分发渠道接入，再由其调用 stdin hook：

| 智能体 | 配置位置和加载机制 |
| --- | --- |
| Antigravity CLI | 直接写入：`~/.gemini/config/hooks.json` 中运行 `npx -y cc-safety-net hook --agy-cli` 的托管 `PreToolUse` 条目 |
| Claude Code | 插件 `cc-safety-net@cc-marketplace`；插件状态位于 `~/.claude/settings.json` 的 `enabledPlugins` |
| Codex | 插件 `cc-safety-net@cc-marketplace`；`PreToolUse` 条目由插件自带的 `hooks/codex.json` 注册，运行 `node "${PLUGIN_ROOT}/dist/bin/cc-safety-net.js" hook --codex` |
| Cursor | 直接写入：`~/.cursor/hooks.json` 中运行 `npx -y cc-safety-net hook --cursor` 的托管 `preToolUse` 条目，含 `timeout: 30` 和 `failClosed: true`。配置全局有效，覆盖所有项目中的 Cursor IDE 和 Cursor CLI。Cursor 导入 Claude Code 插件时，也会从已启用的 Claude Code 插件运行该 hook：插件的 `.cursor-plugin/plugin.json` 指向 `hooks/cursor.json`，后者不带 matcher，运行 `node "${CURSOR_PLUGIN_ROOT}/dist/bin/cc-safety-net.js" hook --cursor`。见 [Cursor 安装](/zh-Hans/installation#cursor-installation) |
| Devin CLI | 直接写入：`$XDG_CONFIG_HOME/devin/config.json`（默认为 `~/.config/devin/config.json`，Windows 上为 `%APPDATA%\devin\config.json`）的 `hooks` 下运行 `npx -y cc-safety-net hook --devin` 的托管 `PreToolUse` 条目，含 `timeout: 30`。该条目不设 matcher，因此除 `exec` 外，文件工具也会到达 hook。Devin 允许在该文件中写注释，因此解析前会先去掉 `//` 和 `/* */` 注释；写回的内容是普通 JSON，注释不再保留。该文件无法解析、根不是 JSON 对象、`hooks` 不是对象，或 `hooks.PreToolUse` 不是数组时，安装会指出该文件并停止，不做任何写入。卸载移除托管 handler 并把文件写回，从不删除 `config.json` |
| Factory Droid | 直接写入：`~/.factory/hooks.json` 顶层 `PreToolUse` 数组中运行 `npx -y cc-safety-net hook --droid` 的托管条目，含 `timeout: 30`，且不设 matcher，因此除 `Execute` 外，文件工具也会到达 hook。`hooks.json` 不存在期间，Droid 从 `~/.factory/settings.json` 的 `hooks` 键读取 hook，因此新建 `hooks.json` 时，安装会先把那些 hook 事件带入文件，再追加托管条目，而 `settings.json` 本身始终不写入。只有当移除 handler 后留下一个空的 `PreToolUse`，且它是文件中唯一的键，并且 `settings.json` 不存在时，卸载才删除 `hooks.json`；存在 `settings.json` 时改为写入移除后的文件，因为删掉它会重新启用 `settings.json` 中的后备 hook。托管条目带有 `commandRegex` 时，能到达 hook 的 `Execute` 调用会变少，`doctor` 会把它报告为重新安装即可修复的 drift |
| Gemini CLI | 从 `gemini-safety-net` 仓库加载的扩展 `gemini-safety-net`，不是 `cc-marketplace` 插件 |
| GitHub Copilot CLI | 插件 `cc-safety-net@cc-marketplace`，或 `~/.copilot/hooks` 下的 hook 文件/ Copilot 配置中的内联 hook。Hook 支持受版本限制，因此哪一种来源可用取决于 Copilot CLI 版本，详见<a href="/zh-Hans/installation#github-copilot-cli-installation">安装</a>。`disableAllHooks: true` 会禁用所有 hook |
| Grok Build | 直接写入：`~/.grok/hooks/cc-safety-net.json`（或 `$GROK_HOME/hooks/cc-safety-net.json`）中运行 `npx -y cc-safety-net hook --grok-build` 的托管 `PreToolUse` 条目，含 `timeout: 30`。该条目不设 matcher，因此除 `run_terminal_command` 外，文件工具和 patch 工具也会到达 hook。安装和卸载只改动托管 handler，文件中的其他条目以及同一条目内的其他 handler 都会保留 |
| Hermes Agent | 直接写入：`<Hermes home>/plugins/cc-safety-net/` 下的托管 Python 插件（`__init__.py` 加 `plugin.yaml`），再运行 `hermes plugins enable cc-safety-net --no-allow-tool-override` 启用。启用状态记录在 Hermes 自身 `config.yaml` 的 `plugins.enabled` 中 |
| Kimi Code | 直接写入：`~/.kimi-code/config.toml`（或 `$KIMI_CODE_HOME/config.toml`）中的 `[[hooks]]` 块，运行 `npx -y cc-safety-net hook --kimi-code`。另一种方式是在 Kimi Code 内运行 `/plugins install https://github.com/kenryu42/cc-safety-net` 安装原生 Kimi Code 插件；manifest 运行相同的 hook 入口（`node ./dist/bin/cc-safety-net.js hook --kimi-code`、`PreToolUse` 事件、30 秒超时），不设 matcher，因此文件工具也会到达 hook |

对于 Kimi Code `Bash` 调用，如果存在 `tool_input.cwd`，它会成为执行目录。该值必须是非空字符串，且解析结果必须位于会话 `cwd` 内；无效或越出该目录的值会 fail closed。

对于 Gemini CLI 的 `run_shell_command` 调用，字符串 `dir_path` 会成为执行目录，因为 Gemini 本身就在 `path.resolve(targetDir, dir_path)` 中运行该命令。CC Safety Net 以 payload 的 `cwd` 为基准解析该值，绝对路径则原样采用。配置目录仍是会话 cwd，因此项目自身的规则配置照常生效。

解析结果必须是已存在的目录；目录不存在时拒绝该调用，并指明起因是请求的工作目录。只含空白字符的值或非字符串值会 fail closed。`""` 表示完全没有指定 `dir_path`，与 Gemini 自己的判断一致，此时在会话 cwd 中分析该命令。

与 Kimi Code 的 `cwd` 不同，解析结果不要求留在会话 cwd 内：在 `BeforeTool` hook 触发之前，Gemini 已经对照 workspace、`--include-directories` 根目录和项目临时目录校验过 `dir_path`。Amp 的 `dir` 也按同样方式解析。

对于 GitHub Copilot CLI 调用，`toolArgs` 可能是对象，也可能是字符串。对象原样采用。字符串按 JSON 解析，不是 JSON 的字符串以 `Failed to parse toolArgs JSON.` 为原因拒绝。只有一种字符串例外：在 patch 路由上，去掉开头空白后以 `*** Begin Patch` 开头的字符串会作为 patch 原文直接传入。Copilot 把 `powershell` 和 `PowerShell` 调用路由到 PowerShell 分析器，把 `bash` 和 `Bash` 调用交给自动方言检测。

在插件路径上，Copilot 把自己在 Windows 上的 `powershell` 工具改名为 `Bash` 发送，否则 Claude 形式的适配器会把它当作 POSIX 命令。为此适配器会读取环境变量 `COPILOT_CLI`，取值为 `1` 时按 `auto` 方言路由 `Bash`，PowerShell 的删除规则因此照常生效。见<a href="/zh-Hans/guides/analysis-engine#powershell-remove-item">PowerShell `Remove-Item`</a>。

对于 Grok Build 调用，受信任的根目录是 `workspaceRoot`；没有 `workspaceRoot` 时用 `cwd` 作为根目录。`cwd` 必须规范化为该根目录内的某个目录，`cwd` 缺失或为空时按 `.` 处理。根目录无法规范化，或 `cwd` 位于根目录之外，都会 fail closed。`toolInputTruncated: true` 同样 fail closed：Grok Build 在 128 KB 处截断工具输入，被截断的命令无法分析。

对于 Factory Droid 调用，payload 中的 `cwd` 同时作为配置目录和执行目录。与 Kimi Code 的 `Bash` 不同，适配器不从工具输入中读取工作目录，因此 `Execute` 调用也在同一个目录下分析。`cwd` 存在但不是非空字符串时会 fail closed；无法解析为可用目录时则拒绝该调用，并指明起因是会话目录。

Devin CLI 的 payload 不带 `cwd`，适配器也不去读取它。两个目录都取自 hook 进程自身的工作目录，也就是 Devin 启动该 hook 的会话目录。

### Codex 如何到达 hook

Codex 从 `cc-marketplace` marketplace 加载 `cc-safety-net@cc-marketplace` 插件。该插件按 Codex 自己的格式打包，其 manifest 指向 `hooks/codex.json`，由后者注册 `PreToolUse` hook。同一个插件还附带 `cc-safety-net` 技能。

Codex 不会运行未受信任的 hook，因此在 Codex 内把它标记为受信任之前，hook 一直不生效。该步骤见<a href="/zh-Hans/installation#codex-installation">安装</a>。

### Hermes Agent 如何到达 hook

Hermes 不通过 hook 配置运行 hook 命令。CC Safety Net 会安装一个由 Hermes 在进程内加载的托管 Python 插件，该插件注册 `pre_tool_call` handler。每次受支持的工具调用，handler 都会运行 `npx -y cc-safety-net hook --hermes-agent`，并把调用作为 JSON 写入其 stdin。空 stdout 表示允许；`{ "action": "block", "message": … }` 表示阻止，Hermes 会把消息作为工具结果显示给模型。

插件转发四个工具：用于命令分析的 `terminal`、用于受保护写入的 `write_file` 和 `patch`，以及用于受保护读取的 `read_file`。其他 Hermes 工具不转发，也不获得判定。

插件把每种失败都转为指明起因的显式阻止：PATH 中缺少 `npx`、spawn 失败、超时（30 秒，并终止分析器的整个 process group）、非零退出，或输出无法读取或不符合预期。插件读不到某次 Hermes 目录查找的结果时同样会阻止，因为分析错误的目录会使所有路径范围的保护失效。

插件按 Hermes 自身会使用的目录来分析每个工具。对 `terminal` 调用，插件先读取 Hermes 的每会话 cwd 记录，其中保存会话的 `cd` 状态。第一个命令执行时，如果该记录尚不存在，则依次使用 `TERMINAL_CWD` 和 Hermes 进程目录。`terminal` 调用带有不可用的 `workdir` 时会 fail closed。

对 `read_file`、`write_file` 和 `patch` 调用，插件调用 `_resolve_base_dir(task_id or "default")`。Hermes 也用同一套查找来解析这三个工具的相对路径，顺序是会话 cwd 记录、任务的 cwd 覆盖值、`TERMINAL_CWD`，最后是进程目录。该函数一律从 `tools.file_tools` 导入：Hermes v2026.8.31 之前由该模块自己定义，v2026.9.7 起由它从 `tools.file_tools_paths` 重新导出。导入失败时，插件阻止该调用并指明是哪一次查找失败：

```text
CC Safety Net failed closed: the Hermes file tool directory could not be read (<error>). Update cc-safety-net and reinstall the plugin with: npx -y cc-safety-net install --hermes-agent.
```

`terminal` 的查找失败时消息相同，只是 `file tool` 换成 `session`。

分析器子进程从主目录启动，而不是 Hermes 的工作目录，因此 `npx` 无法解析到仓库本地的 `cc-safety-net` 来顶替真正的那个。

托管插件放在哪里由 Hermes 主目录决定，而 Hermes CLI 会把主目录切换到 profile 目录。父目录名为 `profiles` 的 `HERMES_HOME` 本身就是 profile 目录，CC Safety Net 原样采用。否则根目录取 `HERMES_HOME`，未设置时取 `~/.hermes`。CC Safety Net 读取该根目录下的 `active_profile` 文件，去掉首尾空白并转为小写，用得到的名称选出 `<root>/profiles/<name>`。名称为空、名称是 `default`，以及文件缺失或无法读取，都保持根目录不变。名称不符合 Hermes 的 profile id 模式时，命令会中止：

```text
Invalid Hermes profile name "<profile>" in <root>/active_profile; run `hermes profile use <name>` with a valid profile.
```

每个托管文件首行都有标明其属于 CC Safety Net 的 header，安装程序拒绝覆盖没有该标记的文件。卸载会先运行 `hermes plugins disable cc-safety-net` 再删除文件，因为 Hermes 只能解析仍在磁盘上的插件。安装和卸载都要重启 Hermes 后才生效。设置和删除命令见<a href="/zh-Hans/installation#hermes-agent-installation">安装</a>。

与 Pi 不同，`doctor` 完全从磁盘检测 Hermes Agent：检查托管插件目录和 Hermes `config.yaml` 中的 `plugins.enabled` 列表，不做 runtime probe。

## 智能体加载的插件

### DeepSeek Harness

DeepSeek Harness 把 CC Safety Net 作为 profile 的插件 bundle **进程内**加载。软件包的 `dsh.bundle.patch` 字段指向 `dist/deepseek-harness/cordis.patch.yml`，该文件插入一个 `cc-safety-net` 行，其中写明 bundle 入口 `./index.js`。入口请求宿主的 `tools` 服务，并通过 `ctx.tools.guard` 注册一个 guard。没有 `hook` 标志，也没有 JSON-over-stdio。

这个 guard 只能拒绝。不返回任何值表示允许调用，返回字符串则以该文本为理由阻止调用。DeepSeek Harness 在所有 `tools/pre-execute` 监听器之后运行它，因此 CC Safety Net 看到调用时，审批和 Auto review 都已经运行过。

guard 按 shell 命令分析两个工具，两者的命令都读自执行对象的 `arguments.command`：

| 工具 | 分析器方言 |
| --- | --- |
| `bash` | POSIX |
| `pwsh` | PowerShell |

其他工具名走非命令输入路径，因此文件类、patch 类和搜索类工具仍受路径与机密保护。

会话的工作目录同时作为配置目录和执行目录，取自 `agent.session.header.cwd`；执行对象没有会话标头时，退回到加载插件时所在的目录。会话 ID 取自 `agent.session.header.id`。`bash` 和 `pwsh` 调用带 `workdir` 参数时，该参数相对这个工作目录解析，并成为执行目录；它必须是已存在的目录，否则拒绝消息会指出请求的目录。与 OpenClaw 的 `workdir` 不同，它不必留在会话目录内。

以下情况下 guard 会 fail closed：执行对象格式不正确、工具名不是非空字符串、`command` 缺失或为空、`arguments` 不是对象、`workdir` 存在但不是非空字符串、会话目录无法解析。

安装过程驱动 DeepSeek Harness 自己的 `dsh plugin ... add` 命令：`web` profile 通过 `npx -y @deepseek-ai/dsh` 执行一次，`desktop` profile 通过桌面应用自带的 `dsh` 执行一次。安装和删除命令见<a href="/zh-Hans/installation#deepseek-harness-installation">安装</a>。

和 Hermes Agent 一样，但与 Pi 不同，`doctor` 完全从磁盘检测 DeepSeek Harness。它读取 `~/.dsh/profiles`（或 `$DSH_HOME/profiles`）下每个 `<profiles>/<name>/package.json`，检查两件事：`dependencies` 是否列出 `cc-safety-net`，以及 `dsh.profile.bundles` 是否包含它。有依赖但没有 bundle 的 profile 属于已安装但未启用，该行会带上这条错误：

```text
cc-safety-net is installed in the <name> profile but its bundle is disabled
```

只要有一个已启用的 profile，宿主就显示 `Configured`，方式为 `dsh bundle`，同时仍会打印任何未启用 profile 的错误。只有未启用的 profile 时，宿主显示为已禁用。某个 profile 的 manifest 无法读取时，宿主为 `Not inspected`；没有任何 profile 带该依赖时为 `n/a`。

### OpenClaw

OpenClaw 把 CC Safety Net 作为原生插件**进程内**加载。插件以包含三个文件的打包目录形式分发：运行时入口 `index.js`（所有依赖内联的自包含 bundle，因为本地目录安装没有 `node_modules`）、OpenClaw 在加载任何代码前验证的 `openclaw.plugin.json` manifest，以及 `openclaw.extensions` 指向该入口的 `package.json`。没有 `hook` 标志，也没有 JSON-over-stdio。

插件为 `exec` 工具注册 `before_tool_call` handler。只分析没有标签的 shell `exec`。带 `toolKind` 区分标记的 `exec` 事件（如 Code Mode 的 JavaScript `exec`）不会得到判定，因为其 `command` 字段并非已证实的 shell 命令映射。其他 OpenClaw 工具都不会转发给防护。Handler 要么不返回判定（允许），要么返回 `{ block: true, blockReason }`，绝不改写工具参数。

插件通过 OpenClaw runtime API 解析智能体的 workspace 目录，并把它同时用作策略目录和执行目录；调用中的 `workdir` 会在解析后限定在该 workspace 内。遇到格式错误的事件、缺失或为空的命令、无法解析的 workspace、workspace 之外的 `workdir`，或已取消的调用时，CC Safety Net 都会 fail closed。`host` 不是 `auto` 或 `gateway` 的 `exec` 调用同样会被阻止。`gateway` 已证明为本地。`host: "auto"` 或完全没有 `host` 的调用按本地 Gateway 语义分析，但插件不会检查 OpenClaw 实际把它路由到哪里。沙箱情况见<a href="/zh-Hans/guides/known-limitations">已知限制</a>。

插件状态由 OpenClaw 自己掌管，因此安装过程通过 OpenClaw 自身的 CLI 完成，只运行一条命令：`openclaw plugins install <packaged dir> --force --accept-capabilities`。自 OpenClaw 2026.8.1 起，只要不传 `--no-enable`，install 本身就会启用插件，因此不再单独执行 `openclaw plugins enable`。若你在 `openclaw.json` 中手动禁用了插件，它会保持禁用，下面的运行时检查会如实报告未加载状态，CC Safety Net 不会悄悄把它重新启用。`--accept-capabilities` 在 2026.8.1 之前并不存在，更早的 OpenClaw 会以 unknown-option 错误拒绝安装。这里没有版本判断，也没有回退。

`openclaw plugins uninstall` 会留下 `enabled: false` 标记，而 `plugins install` 不会启用一个被显式禁用的条目，因此按安装、卸载、安装的顺序操作，过去会停在 `disabled` 状态。CC Safety Net 只补上这一种情况：安装前托管插件的入口文件不存在，且运行时检查报告 `disabled` 时，它运行一次 `openclaw plugins enable cc-safety-net` 并再检查一遍。已经安装且被你禁用的插件，在安装和更新时都保持禁用，所以常规的安装和更新从不调用 enable。

Gateway 正在运行时，这次 enable 可能以 `config reload superseded by a newer runtime config source` 失败。OpenClaw 会在那次被取代的运行时应用之前先保存 `plugins.entries.cc-safety-net.enabled=true`，并且不会回滚这次写入。因此 CC Safety Net 不重试这次 enable，也不会因此让安装失败，结果由第二次运行时检查决定。enable 因其他原因失败时，安装照旧失败。保存下来的配置会在 Gateway 自己的后续 reload 中生效，或在它下次启动时生效。

执行任何 `--force` 命令前，CC Safety Net 都会验证目标扩展目录只含自有的托管文件，因此绝不会覆盖或删除无法证明属于自己的插件。安装后它会运行 `openclaw plugins inspect cc-safety-net --runtime --json`，并且只把 `loaded` 状态视为成功：bundle 损坏的插件即使已启用，安装过程也不会报错，之后却静默地不提供任何保护。状态为 `disabled` 时，消息会给出应运行的命令：

```text
OpenClaw reports the cc-safety-net plugin with status "disabled"; run `openclaw plugins enable cc-safety-net`. Run `openclaw plugins inspect cc-safety-net --runtime` for details.
```

安装副本位于 `<state dir>/extensions/cc-safety-net/`。生效的主目录为 `OPENCLAW_HOME`（取值非空时），否则为操作系统主目录；`OPENCLAW_HOME` 开头的 `~` 按操作系统主目录展开。state dir 为 `OPENCLAW_STATE_DIR`；否则为 `OPENCLAW_CONFIG_PATH` 所指文件的所在目录；两者都未设置时为 `<effective home>/.openclaw`。这两个环境变量开头的 `~` 都按生效的主目录展开。启用状态位于 OpenClaw 自身的配置中（state dir 中的 `openclaw.json`，或 `OPENCLAW_CONFIG_PATH` 指向的文件）：全局 `plugins.enabled` 开关、`plugins.allow` 和 `plugins.deny` 列表，以及针对单个插件的 `plugins.entries.cc-safety-net.enabled` 条目都会起作用。设置了 `plugins.allow` 时，其中必须也列出 `cc-safety-net`。

安装或卸载后要重启 OpenClaw Gateway。Manifest 在启动时激活插件（`activation: { onStartup: true }`），因此正在运行的 Gateway 不会应用该更改。设置和删除命令见<a href="/zh-Hans/installation#openclaw-installation">安装</a>。

### OpenCode

OpenCode 把 CC Safety Net 作为插件对象**进程内**加载，插件在 OpenCode 配置目录下 `opencode.json`（或 `.jsonc`）的 `plugin` 或 `plugins` 数组中声明。同一个 npm 包覆盖 OpenCode 1.18.29+ 和 2.0.6+，两代实现的插件约定并不相同。v1 的 `bash` 工具和 v2 的 `shell` 工具走同一套策略、分析器和审计代码。

在 OpenCode 1.x 上，插件实现 `@opencode-ai/plugin` 约定，并执行两项工作：

1. 实现 `tool.execute.before`，OpenCode 在每次工具执行前都会调用它。CC Safety Net 分析该调用，并在命令具有破坏性时抛出拒绝。没有 JSON-over-stdio。
2. 实现 `config` hook，把 CC Safety Net 的内置命令注入 OpenCode 命令集，同时不覆盖你已定义的命令。

对于 `bash` 工具，插件根据 OpenCode 的 `shell` 设置选择分析方言。如果该设置不是字符串，Windows 上默认使用 PowerShell，其他系统使用 `SHELL`。随后插件取该值路径的最后一段，转为小写并去掉结尾的 `.exe`：`powershell` 和 `pwsh` 选择 PowerShell，`cmd` 使用自动方言检测，其他可执行文件一律选择 POSIX。值为空或只含空白字符时使用自动检测，非 Windows 上没有设置 `SHELL` 时也一样。只有在给定的 `workdir` 解析为可读、可搜索的目录时，它才会成为执行目录。在 Windows 上，会归一化文档化的 `/C:`、`/C`、`/cygdrive/C` 和 `/mnt/C` 形式，其他以斜线开头的路径保持不变，交由 OpenCode 解析。

在 OpenCode 2.x 上，插件以 `cc-safety-net` 为 ID 注册，hook `tool.execute.before`，返回带类型的 `Tool.Error` 拒绝。它把 `shell` 工具当作命令检查，read、edit、write、patch、grep、glob 以及未知工具则走与 v1 相同的输入路径。Code Mode 的子工具调用同样经过这个 hook；CC Safety Net 不解释外层 Code Mode 的 JavaScript。插件还通过 command API 注册 `/cc-safety-net`，并保留已经存在的同名命令。

v2 的 `shell` 工具用宿主的 `FileAccess.resolvePath` 解析 workdir，它把 `~` 映射到主目录，把 `~/x` 映射到 `<home>/x`。v2 上插件在前述 Windows 盘符归一化之后做同样的处理：只写 `~` 时取主目录，以 `~/` 开头时拼接到主目录下，win32 上 `~\` 同理。`~other`、`~x` 等其他形式仍按项目相对路径处理。v1 不做波浪号展开，因为 OpenCode v1 用 `path.resolve` 解析 workdir。

#### v2 的 shell 方言

v2 的工具事件不给出 shell 可执行文件，因此分析方言来自插件的 `shell` 选项，而不是 OpenCode 的 `shell` 设置。默认值在 Windows 上是 `powershell`，其他系统上是 `posix`。如果你在 Unix 上用 PowerShell，或在 Windows 上用 Git Bash，请在配置条目中指定：

```json
{
  "plugins": [
    {
      "package": "cc-safety-net@latest",
      "options": { "shell": "powershell" }
    }
  ]
}
```

任何运行 POSIX `sh` 语法的 shell 都用 `"posix"`，例如 ash、bash、dash、ksh、sh、zsh；powershell 和 pwsh 用 `"powershell"`。该选项不决定 OpenCode 使用哪个可执行文件，它必须与 OpenCode 实际使用的保持一致。填其他值会让插件以 `CC Safety Net: plugin option shell must be posix or powershell.` 失败。

`shell.create.before` hook 会在启动 shell 之前检查真实的可执行文件。配置为 `"powershell"` 时，可执行文件名必须是 `powershell` 或 `pwsh`。配置为 `"posix"` 时，`powershell`、`pwsh` 和 `cmd` 按名称直接拒绝，带不带 `.exe` 后缀都一样，因为 OpenCode 调用它们的方式不同；其他可执行文件都必须通过一次探测。检查不通过就阻止启动：

```text
CC Safety Net: actual shell "<actual>" does not match plugin option shell "<configured>". Configure the plugin's shell option to match OpenCode; supported dialects are posix and powershell.
```

探测通过 `<shell> -c` 运行 `x=ccsn; case $x in ccsn) echo $x-posix;; esac`，工作目录是插件的 `location`，环境变量用 OpenCode 传给 shell 的那一份。该命令无错误退出且输出中含有 `ccsn-posix` 时，这个可执行文件即算通过。标记由 `$x` 拼出，因此把探测原文当作报错回显的 shell 不可能通过。不运行 POSIX `sh` 语法的 shell，例如 fish、nushell 和 tcsh，会在探测中失败并被拒绝，而不是用错误的 parser 去分析。

每个可执行文件路径只探测一次。检查进行期间发起的其他 shell 创建共用这一次检查结果。探测通过的可执行文件会记录下来，同一路径后续创建时不再探测；失败或超时的检查不保留，下一次创建会重新探测。10 秒的定时器会把检查判定为失败，并用 `SIGKILL` 结束探测进程，因此结果不必等待迟迟不退出的 shell。

这种停止不同于普通的工具拒绝。OpenCode 的 shell hook 既没有带类型的拒绝通道，也没有会话 ID，因此一旦不一致，当前操作可能直接失败，而且不会留下归属到会话的审计记录。该检查覆盖插件所在 `location`（即插件被加载时对应的 OpenCode 目录上下文）中创建的每一个 shell，包括智能体工具调用之外的 shell 操作。它不是操作系统级沙箱。

OpenCode 1.x 可能沿用缓存中过期的插件副本，因此更改接入方式后，可能要清除缓存才会生效，见<a href="/zh-Hans/installation#opencode-installation">安装</a>。

## Pi 扩展

Pi 把 CC Safety Net 作为进程内扩展加载。扩展由软件包 `pi.extensions` 字段声明，并在 Pi 智能体目录下的 `settings.json` 中记录为软件包来源 `npm:cc-safety-net`。该目录为 `PI_CODING_AGENT_DIR`（若已设置，开头的 `~` 会展开），否则为 `~/.pi/agent`。它执行两项工作：

1. **注册 `tool_call` 事件 handler**（`pi.on('tool_call')`），在 Pi 工具运行前检查调用。命令或路径违反策略时返回阻止结果，不跨进程边界。
2. **注册 `/cc-safety-net` 内置命令**，用于在 Pi 内交互管理 rulebook。

### Pi 保护的工具

Pi 有两个命令工具适配器：内置的 `bash` 和 `powershell` 工具。两者都读取 `command` 字段，该命令在会话 cwd 下执行。`bash` 走 POSIX 分析器，`powershell` 走 PowerShell 分析器。已不支持旧的自定义 `Shell` 适配器。Pi 的非命令工具仍会进入路径保护和机密保护。其中，`find` 被分类为只读 glob 工具，因此会检查其 `pattern` 和路径值，但不会把搜索本身当作写入。命令调用或会话 cwd 格式错误时，CC Safety Net 会 fail closed。

| 工具 | 命令字段 | 工作目录 |
| --- | --- | --- |
| `bash` | `command` | 会话 cwd |
| `powershell` | `command` | 会话 cwd |

### 检测 Pi

没有可检查的 hook 配置文件，因此 `doctor` 通过 runtime probe 检测 Pi：启动 `pi` 并询问扩展是否已加载和启用。这就是 Pi 已安装但 probe 无法运行时，`doctor` 中 Pi 状态可能为 `n/a` 的原因。

## Amp Code 事件插件

Amp Code 把 CC Safety Net 作为**个人插件**加载：Amp 账户托管的 Personal Plugins 仓库中一个名为 `cc-safety-net` 的目录，里面是自包含的入口文件 `index.ts`。插件通过 `@ampcode/plugin` API 订阅 Amp 的 `tool.call` 事件，返回 `allow` 或带消息的 `reject-and-continue`。它和 DeepSeek Harness、Pi、OpenClaw、OpenCode 一样在进程内运行。个人插件跟随账户而不是单台机器，因此也覆盖在 Amp Orb 等远程执行器上运行的线程。

Amp 的 workspace 根目录（`amp.system.workspaceRoot`）就是配置目录。shell 工具调用带有字符串 `dir` 时，该值成为执行目录：相对路径基于 workspace 根目录解析，结果再经过 `realpath`，并且必须是已存在的目录。Windows 命名空间路径会被拒绝。无法解析的 `dir` 会 fail closed，也不会再对该调用做破坏性命令分析。拒绝原因不再报告分析器的意外失败，而是指明起因是工作目录，并让智能体改用已存在且可访问的目录，或先创建缺失的目录。与 OpenClaw 的 `workdir` 不同，解析结果不要求留在 workspace 内：Amp 把它指向自己的技能缓存或同级仓库都是正当用法，而同样的操作写成 `cd <dir> && …` 本来就在那里执行。配置目录仍是 workspace 根目录，因此项目自身的规则配置照常生效。Git 元数据防护同时以执行目录和配置目录为锚点，所以命令在别处执行时，workspace 自身的 `.git` 仍受保护。见<a href="/zh-Hans/reference/blocked-commands#git-metadata">Git 元数据</a>。

`install --amp` 把 artifact 发布到该仓库：确认账户有可写的 Personal Plugins 仓库（`amp plugins repositories --json`），把仓库克隆到一次性 checkout（`amp clone user-plugins`），写入 `cc-safety-net/index.ts`，然后提交并推送。暂存使用明确的 pathspec（`git add -- cc-safety-net/index.ts`）而不是整个目录，这样插件路径被 gitignore 时会中止安装，而不是什么都不暂存。安装和卸载写入或 `git rm` 的始终只有这一个入口文件，因此你放在同一目录里的其他文件不会被改动。

该入口带有托管 header，标明它属于 CC Safety Net，可以安全替换。安装和卸载都会拒绝符号链接或非目录的 `cc-safety-net` 条目，也会拒绝符号链接、非普通文件或不带托管 header 的 `index.ts`。在改用目录结构之前，插件以 `cc-safety-net.ts` 的形式发布在仓库根目录：托管的旧文件会在同一次提交中删除，非托管的旧文件会使安装失败。

本地插件会遮蔽个人插件，因此安装还会清理 `~/.config/amp/plugins/` 下的残留：托管的旧文件 `cc-safety-net.ts`，以及手动复制过来、其中只有一个托管 `index.ts` 的 `cc-safety-net/` 目录。这两个路径上的其他任何本地条目都会使安装失败。设置和删除命令见<a href="/zh-Hans/installation#amp-code-installation">安装</a>。

### 嵌入的策略快照

发布的 artifact 携带用户策略的快照：文件末尾追加一条 `globalThis.__CC_SAFETY_NET_EMBEDDED_POLICY__ = …` 赋值，策略在写入前先归一化。运行时只有在自身没有策略文件的机器上（Orb 的空 home 目录）快照才生效；有策略文件的机器即使文件无效，也保持自身行为。审计保留期、用户 rulebook 和项目范围策略不会嵌入，策略修改要在下一次 `install` 或 `update` 时才发布。

Amp 启动时读取插件，因此新发布或删除的插件要重新加载 Amp 才会影响当前会话。

### 检测 Amp Code

`doctor` 通过解析 `amp plugins list` 输出检测插件；个人范围插件显示为 `✓ cc-safety-net (User Plugins) <status>`。该输出不含版本号，因此 `doctor` 不会报告 Amp 的版本偏差。`cc-safety-net update` 始终重新发布当前 artifact。

### Amp Code 覆盖限制

- Amp 不定义订阅同一 `tool.call` 事件的多个插件之间的执行顺序。CC Safety Net 只评估它收到的输入；如果另一个插件在 CC Safety Net 允许该调用之后改写了输入，CC Safety Net 无法重新评估。

## 验证集成

`npx cc-safety-net doctor` 会报告每个智能体检测到的集成和配置路径，并在保护处于活动状态的地方运行自检。选项和退出行为见 <a href="/zh-Hans/reference/cli-commands">CLI 命令</a>。

某个智能体的 hook 未触发时，见<a href="/zh-Hans/guides/troubleshooting">故障排除</a>中按智能体划分的步骤。
