用自定义阻止规则来落实团队约定或项目专用的安全策略。规则采用**基于 rulebook 的布局**，并合并用户范围和项目范围的配置。这样既能保留个人默认值，又能用项目覆盖来调整。

<Warning>
**重大更改**：运行时不再加载旧版内联配置文件（`.safety-net.json` 和 `~/.cc-safety-net/config.json`）。如果它们包含规则，**这些规则在迁移前不会生效**。运行时会静默忽略旧文件。`rule verify` 会就此发出警告。普通命令照常运行。运行 `npx -y cc-safety-net rule migrate` 可将旧规则转换为 rulebook 布局。请参阅[迁移旧配置](#迁移旧配置)。
</Warning>

<Tip>
编写自定义规则最快的方式，是在智能体中使用 **`/cc-safety-net` 技能**，用自然语言交互式地创建规则。示例：

  ```text
  /cc-safety-net read my package.json and suggest blocking rules
  /cc-safety-net set up rules to block all terraform destroy commands
  /cc-safety-net verify my rules and fix any errors
  ```

如果智能体不支持技能，可以这样提示它：

  ```text
  run npx -y cc-safety-net rule doc and help me set up custom rules
  ```
</Tip>

## 规则配置文件位置

CC Safety Net 从两个范围加载 rulebook 并将它们合并：

1. **用户范围**：`~/.cc-safety-net/rules/rule.json`（用 `rule init --global` 创建）。用它保存适用于所有项目的个人默认值。
2. **项目范围**：项目根目录中的 `.cc-safety-net/rules/rule.json`。用它保存可提交到版本控制的团队或项目专属规则。

本地 rulebook 源通过 `project-rules` 这样的裸名称引用。GitHub rulebook 源使用 `owner/repo#ref/<rulebook-name>`，指向该仓库中的 `.cc-safety-net/rules/<rulebook-name>/rulebook.json`。

### 范围合并行为

- 两个范围的 rulebook 会合并，用户范围在前。
- **活动 rulebook 名称重复时，以先声明者为准。** 用户范围先加载，因此它占用的名称会遮蔽同名的项目 rulebook；后一个 rulebook 完全不贡献规则，而不是只部分遮蔽前一个。名称冲突会以警告形式报告，并使运行时进入 `degraded` 状态——重命名其中一个，再运行 `rule sync`。由于冲突只是被消解而非致命错误，即使某个名称已被另一个范围占用，本范围的 `rule sync` 仍会成功。
- **每个范围的 `overrides` 只作用于该范围自己的规则。** 指向用户范围规则的项目覆盖会被忽略并给出警告，该规则保持其用户配置的状态——项目配置无法禁用或改写用户规则。
- 不匹配任何已知规则的覆盖键会被忽略并给出警告；其他覆盖和规则保持各自配置的状态。
- 两个范围的 `transparent_wrappers` 取并集。

如果两个位置都没有配置，则只有内置规则生效。

## 管理 rulebook 源

rulebook 源由 `rule.json` 的 `rules` 数组中的条目引用。共有两类：

- **本地源**：形如 `project-rules` 的裸名称。rulebook 位于 `.cc-safety-net/rules/project-rules/rulebook.json`（项目）或 `~/.cc-safety-net/rules/project-rules/rulebook.json`（用户）。本地源必须留在各自的配置目录内。
- **GitHub 源**：`owner/repo#ref/<rulebook-name>`，指向该仓库该 ref 下的 `.cc-safety-net/rules/<rulebook-name>/rulebook.json`。

用 `rule` 命令来添加、更新和删除源，不要手动编辑 `rule.json` 和 lockfile：

```bash
# Add a local rulebook source and sync
npx -y cc-safety-net rule add project-rules

# Add a GitHub rulebook source (creates a lock entry pinned by SHA-256 digest)
npx -y cc-safety-net rule add kenryu42/cc-safety-net#main/example-rules

# Refresh the lock and cache after editing sources
npx -y cc-safety-net rule sync

# Update a single source, or all sources when no source is given
npx -y cc-safety-net rule update example-rules

# List active rulebooks and their resolved sources
npx -y cc-safety-net rule list

# Remove a source (--delete-source also deletes a local source directory)
npx -y cc-safety-net rule remove example-rules --delete-source
```

加上 `--global`（`-g`）即可操作用户范围而非项目范围。每个 `rule` 子命令、它的选项及退出行为见 [CLI 命令](/zh-Hans/reference/cli-commands)。

### 资源限制

每个范围的 `rules` 数组最多容纳 **64** 个源。条目更多的 `rule.json` 会验证失败，只报出单条错误 `Rule config exceeds CC Safety Net's safe source limit.`——超限的数组不会逐条列出，整个范围的配置会像其他任何无效 `rule.json` 一样被丢弃。

`rule sync` 在固定预算下运行：最多并发处理 **4** 个源，单次运行最多发出 **131** 个 GitHub 请求，所有源合计最多读取 **64 MiB** 响应字节。超出任一预算都会中止本次运行，并报 `Rule synchronization exceeds CC Safety Net's safe resource limits.`

### 锁定和缓存

每个已配置的源都通过 SHA-256 摘要固定在 `rule.lock` 文件中，其 rulebook 缓存在 `.cc-safety-net/cache/rulebooks/` 下。运行时，CC Safety Net 会按摘要校验缓存的 rulebook，且在校验期间绝不写入、获取或缓存任何内容。

校验失败后的表现取决于哪一侧出了问题：

- **缺少 lockfile、缺少 lock 条目、缺少缓存条目、摘要不匹配，或缓存的 rulebook 无法解析**，都会丢弃该源。在你运行 `rule sync` 之前，它不会贡献任何规则。其他所有已校验的源和全部内置保护继续生效，普通命令也照常运行。被丢弃的源只是让运行时进入 `degraded`，并不会阻塞工作。
- **本地源偏离其固定摘要**——包括在磁盘上丢失、无法解析或不符合 schema——并不算故障状态。运行时只读取经过摘要校验的**缓存** rulebook，绝不会重新读取本地副本。在你运行 `rule sync` 之前，本地未同步的改动不会生效。完整的 `rule sync` 和 `rule verify` 仍会拒绝无效的或符号链接的本地源。

完整的状态模型、确切的诊断字符串和修复步骤见[配置恢复](/zh-Hans/configuration/recovery)。

## 透明包装器

如果团队通过 `rtk` 之类的包装器运行命令，分析默认只看到包装器，看不到底层命令。把包装器列入 `transparent_wrappers`，CC Safety Net 就能看穿它、直达其中可见的受保护子命令，于是内置分析和你的自定义规则会像处理裸命令一样处理 `rtk git reset --hard` 和 `rtk docker system prune`。

用 `rule wrapper` 子命令来配置包装器，不要手动编辑 `rule.json`：

```bash
# List configured wrappers for the project scope
npx -y cc-safety-net rule wrapper list

# Trust a wrapper, or stop trusting it
npx -y cc-safety-net rule wrapper add rtk
npx -y cc-safety-net rule wrapper remove rtk

# Operate on the user scope instead
npx -y cc-safety-net rule wrapper add rtk --global
```

这个字段的规则：

- **没有内置默认值。** 只配置你有意信任的包装器。
- 包装器名称必须匹配 `^[a-zA-Z][a-zA-Z0-9_-]*$`，并且在文件内必须唯一。
- **保留命令不能作为包装器**：`git`、`busybox`、内置分析的命令 `rm`、`find`、`xargs` 和 `parallel`、所有 shell 包装器、所有解释器以及 awk 解释器。
- 解包时，会取包装器标志和 `VAR=value` 赋值之后的第一个*可保护*子命令，或者显式 `--` 之后紧跟的那个 token。本身不可保护的子命令不会被解包。
- 这里**未**列出的包装器，以及重写或隐藏子命令而不是 exec 一个可见子命令的包装器，仍然不会被解包。这类命令只有顶层危险文本 fallback 扫描才可能捕获。

<Warning>
`transparent_wrappers` 位于 `rule.json` 中，而 `rule.json` 不带 lock 或摘要。如果某个范围的 `rule.json` 变得不可读，该范围的包装器就不再生效——这是配置被丢弃会削弱内置覆盖范围的唯一一处。被丢弃的 **rulebook**（缺少缓存条目、缺少 lock 条目、摘要不匹配）不影响 `rule.json` 的可读性，因此包装器不受影响。
</Warning>

## 创建你的第一个自定义规则

创建一份入门用的项目规则配置：

```bash
npx -y cc-safety-net rule init
```

这会创建一个**未生效的** `.cc-safety-net/rules/rule.json`，其中尚未配置 rulebook 源：

```json
{
  "version": 1,
  "rules": [],
  "overrides": {},
  "transparent_wrappers": []
}
```

加上 `--example` 还会在 `.cc-safety-net/rules/example-rules/rulebook.json` 写入一个未激活的示例 rulebook。只有该文件尚不存在时才会写入；而且 `rule init` 并不会引用它，因此必须把它添加为源，它才会生效：

```bash
npx -y cc-safety-net rule init --example
npx -y cc-safety-net rule add example-rules
```

要编写自己的 rulebook，请创建 `.cc-safety-net/rules/project-rules/rulebook.json`，再用 `npx -y cc-safety-net rule add project-rules` 注册它。此时 `rule.json` 如下：

```json
{
  "version": 1,
  "rules": ["project-rules"],
  "overrides": {},
  "transparent_wrappers": []
}
```

规则定义就写在该 rulebook 文件里：

```json
{
  "rulebook_version": 1,
  "name": "project-rules",
  "version": "1.0.0",
  "description": "Project-specific CC Safety Net rules.",
  "author": "project",
  "allowed_commands": ["git"],
  "rules": [
    {
      "name": "block-git-add-all",
      "command": "git",
      "subcommand": "add",
      "block_args": ["-A", "--all", "."],
      "reason": "Use 'git add <specific-files>' instead of blanket add."
    }
  ],
  "tests": [
    {
      "command": "git add -A",
      "expect": "blocked",
      "rule": "block-git-add-all"
    },
    {
      "command": "git add README.md",
      "expect": "allowed"
    }
  ]
}
```

编辑 rulebook 后，运行：

```bash
npx -y cc-safety-net rule sync
npx -y cc-safety-net rule verify
```

`rule sync` 让编辑后的 rulebook 生效，随后 `rule verify` 检查生效的配置。

现在 `git add -A`、`git add --all` 和 `git add .` 都会被阻止，并显示你的自定义消息。

## `rule.json` schema

顶层 `rule.json` 决定哪些 rulebook 生效、应用覆盖并声明透明包装器。它与 `policy.json` 相互独立：`policy.json` 配置安全级别、内置保护、允许和拒绝路径以及审计保留期——那个文件见[策略](/zh-Hans/configuration/policy)。

<ParamField body="version" type="integer" required>
schema 版本。必须为 `1`。
</ParamField>

<ParamField body="rules" type="array">
rulebook 源字符串列表。默认为空数组。文件内的源名称必须唯一，且最多允许 64 个源——见[资源限制](#资源限制)。
</ParamField>

<ParamField body="overrides" type="object">
以 `<rulebook-name>/<rule-name>` 为键的规则覆盖。值可以是 `"off"`（禁用该规则），也可以是一个对象（替换该规则的阻止消息）。对象形式必须包含 `reason`，可以带上可选的 `intent`；省略 `intent` 时，规则自身的意图保持不变。
</ParamField>

<ParamField body="transparent_wrappers" type="array">
会透明执行可见受保护子命令的命令名称，让分析能够看穿它们。默认为空数组。条目必须唯一，且不能是保留命令。见[透明包装器](#透明包装器)。
</ParamField>

同时替换消息和面向智能体的意图的覆盖如下所示：

```json
{
  "version": 1,
  "rules": ["project-rules", "owner/repo#main/team-rules"],
  "overrides": {
    "project-rules/block-docker-system-prune": {
      "reason": "Use targeted Docker cleanup commands.",
      "intent": "use_alternative"
    },
    "team-rules/block-npm-global": "off"
  },
  "transparent_wrappers": ["rtk"]
}
```

### `rule.json` 编辑器支持

CC Safety Net 为 `rule.json` 发布了一份 JSON Schema，它由运行时校验所用的同一份 schema 生成。把编辑器指向它，即可获得补全和校验：

```json
{
  "$schema": "https://raw.githubusercontent.com/kenryu42/cc-safety-net/main/assets/cc-safety-net.schema.json",
  "version": 1,
  "rules": [],
  "overrides": {},
  "transparent_wrappers": []
}
```

它涵盖的正是上面列出的 `rule.json` 字段——`version`、`rules`、`overrides` 和 `transparent_wrappers`。运行 `rule verify` 会为缺少 `$schema` 的有效规则配置补上这一引用。`policy.json` 没有公开发布的 schema。

## Rulebook schema

每个 rulebook 都放在各自的 `rulebook.json` 文件中。

<ParamField body="rulebook_version" type="integer" required>
rulebook schema 版本。必须为 `1`。
</ParamField>

<ParamField body="name" type="string" required>
rulebook 名称。必须与本地目录名或 GitHub 源名称一致。
</ParamField>

<ParamField body="version" type="string" required>
rulebook 版本字符串。
</ParamField>

<ParamField body="description" type="string">
rulebook 的人类可读描述。
</ParamField>

<ParamField body="author" type="string">
rulebook 作者。
</ParamField>

<ParamField body="allowed_commands" type="array" required>
此 rulebook 允许为其定义规则的命令。
</ParamField>

<ParamField body="rules" type="array" required>
自定义阻止规则。见[规则 schema](#规则-schema)。
</ParamField>

<ParamField body="tests" type="array">

## 规则 schema

<ParamField body="name" type="string" required>
在 rulebook 内必须唯一。必须以字母开头，后跟字母、数字、连字符或下划线。最多 64 个字符。
</ParamField>

<ParamField body="command" type="string" required>
要匹配的基础命令。必须列在 `allowed_commands` 中。
</ParamField>

<ParamField body="subcommand" type="string">
要匹配的子命令，例如 `add` 或 `install`。如果省略，则匹配任何子命令。
</ParamField>

<ParamField body="block_args" type="array" required>
触发阻止的参数（至少需要一个）。
</ParamField>

<ParamField body="reason" type="string" required>
阻止时显示的消息。最多 256 个字符。
</ParamField>

<ParamField body="intent" type="string">
追加到阻止消息页脚的智能体行为意图。取 `hard_stop`、`use_alternative`、`scope_down`、`manual_only` 或 `stop_and_explain` 之一。默认为 `manual_only`。
</ParamField>

## Fixture schema

fixture 是对预期行为的可选说明。它们只做结构校验，CC Safety Net 不会执行。

<ParamField body="command" type="string" required>
Shell 命令 fixture。
</ParamField>

<ParamField body="expect" type="string" required>
只能是 `blocked` 或 `allowed`。
</ParamField>

<ParamField body="rule" type="string">
预期会阻止该命令的规则。`blocked` fixture 必填。
</ParamField>

## 匹配行为

CC Safety Net 使用以下匹配规则：

- **命令规范化**：匹配前，命令先取其 basename。`/usr/local/bin/npm` 能匹配 `"command": "npm"` 的规则。
- **子命令检测**：子命令是紧跟在命令之后的第一个非选项参数。在 `git --no-pager add -A` 中，子命令是 `add`。
- **参数匹配**：`block_args` 中的参数按字面匹配，不支持正则表达式或 glob。
- **短选项展开**：合并书写的短标志会在匹配前拆开。`-Ap` 视为 `-A` 和 `-p`。
- **长选项匹配**：长选项按字符串精确匹配。`--all-files` **不**匹配 `--all`。
- **任意参数匹配**：只要命令中出现 `block_args` 里的任意一个参数，就会被阻止。
- **只增不减**：自定义规则只能新增限制，无法绕过内置保护。

<Note>
**已知限制**：`-Cfoo` 被视为 `-C -f -o -o`，而不是 `-C foo`。阻止 `-f` 时，可能对紧贴在选项后的取值产生误报。
</Note>

## 阻止消息格式

完整的阻止消息布局见[阻止消息的形式](/zh-Hans/guides/how-it-works#阻止消息的形式)。自定义规则额外加的是一个包含 rulebook 名称和规则名称的前缀，让你能看出是哪个 rulebook 触发了这次阻止：

```text
BLOCKED by CC Safety Net

Reason: [project-rules/block-git-add-all] Use 'git add <specific-files>' instead of blanket add.

Command: git add -A
```

前缀是 `<rulebook-name>/<rule-name>`。它也是你在 `rule.json` 的 `overrides` 中用来禁用规则（`"off"`）或替换其 reason 的键。

## 验证你的 rulebook

创建或编辑 rulebook 后，用以下命令验证：

```bash
npx -y cc-safety-net rule sync
npx -y cc-safety-net rule verify
```

- `rule sync` 为已配置的 rulebook 源重建 lock 和缓存。
- `rule verify` 检查配置、lock 和缓存状态、本地 rulebook，以及可共享的 GitHub 源 rulebook 目录。它不获取远程内容。

## 迁移旧配置

旧版内联配置文件（`.safety-net.json` 和 `~/.cc-safety-net/config.json`）**不再在运行时加载**。

| 旧文件状态 | 新行为 |
| --- | --- |
| 空的旧文件 | 静默忽略：只有内置规则生效 |
| 含规则的旧文件 | 在用 `rule migrate` 迁移之前，其中的规则**不会生效**；运行时静默忽略该文件 |
| 无效的旧文件 | 同上：在修复并迁移或删除之前一直不生效 |

旧规则永远不会在原位置生效，也永远不会阻碍工作。运行时根本不读取旧文件，因此防护阶段不会有任何提示——对残留的旧文件发出警告的是 `npx -y cc-safety-net rule verify`。升级后请运行一次。

```bash
# Convert legacy inline rules into the rulebook layout
npx -y cc-safety-net rule migrate

# Optionally delete verified legacy files after migration
npx -y cc-safety-net rule migrate --cleanup

# Validate the migrated rules
npx -y cc-safety-net rule verify
```

**之前**，规则内嵌在单个内联配置文件中：

```text
.safety-net.json                # project rules (inline)
~/.cc-safety-net/config.json    # user rules (inline)
```

**之后**，`rule migrate` 自动创建基于 rulebook 的布局：

```text
.cc-safety-net/rules/rule.json                    # project rulebook sources + overrides
.cc-safety-net/rules/project-rules/rulebook.json  # migrated project rules
~/.cc-safety-net/rules/rule.json                  # user rulebook sources + overrides
~/.cc-safety-net/rules/user-rules/rulebook.json   # migrated user rules
```

## 无效的自定义规则配置

无法通过校验的自定义规则配置会被**丢弃、不再生效，也永远不会变成一次拒绝**。普通命令照常运行，其他所有已校验的源继续生效，全部内置保护依然适用。运行时会把自己报告为 `degraded`，让这种情况显现出来。

因为被丢弃的源是**移除**拒绝而不是新增拒绝，所以这类故障本身不会造成操作阻碍。`npx cc-safety-net status` 是低成本的日常检查。完整的故障回退矩阵、诊断字符串、报告界面和修复顺序见[配置恢复](/zh-Hans/configuration/recovery)。

<Warning>
自定义规则配置**不具备防篡改能力**。`rule.json`、rulebook、lockfile 和缓存都只是尽力而为；只有规范位置的用户 `policy.json` 属于受保护路径。如果手动添加或修改自定义规则，请务必用 `npx -y cc-safety-net rule verify` 验证。
</Warning>
