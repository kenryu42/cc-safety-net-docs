自定义规则用你写的原因，阻止内置规则放行的命令，例如 `git push` 或 `npm install -g`。规则写在 rulebook 文件中，每个范围的 `rule.json` 列出要加载的 rulebook。自定义规则只会新增阻止，绝不放宽内置规则。

<Warning>
  旧版内联配置文件（`.safety-net.json` 和 `~/.cc-safety-net/config.json`）已不再加载。在[迁移](#migrate-legacy-configuration)之前，其中的规则不起任何作用。
</Warning>

<Tip>
  [`/cc-safety-net` 技能](/zh-Hans/guides/skill)可以替你编写规则。说明你想要什么即可，例如 `/cc-safety-net block terraform destroy in this project`。
</Tip>

## 规则配置文件位置

CC Safety Net 从两个范围加载 rulebook 并合并：

1. **用户范围**：`~/.cc-safety-net/rules/rule.json`（用 `rule init --global` 创建）。用于适用于所有项目的个人默认规则。
2. **项目范围**：项目根目录下的 `.cc-safety-net/rules/rule.json`。用于可提交到版本控制的团队或项目专属规则。

两个文件都不存在时，只有内置规则生效。在存放用户 `.cc-safety-net/` 的目录（默认是主目录）中，项目路径就是用户配置，因此写入项目范围的 `rule` 子命令在那里会拒绝运行。参见[在用户配置目录中运行 rule](/zh-Hans/reference/cli/rule#rule-in-the-user-config-directory)。

<span id="scope-merge-behavior"></span>

### 范围合并行为

- CC Safety Net 先加载用户范围，再合并两个范围的 rulebook。
- 两个范围列出同名 rulebook 时，以用户范围的为准，项目范围的那个不贡献任何规则。CC Safety Net 会报告警告，运行时显示 `degraded`。重命名其中一个即可解决。
- 每个范围的 `overrides` 只作用于本范围的规则。指向用户规则的项目覆盖会被忽略并报告警告，因此项目配置无法关闭或改写用户规则。
- 不匹配任何规则的覆盖键同样会被忽略并报告警告。
- 两个范围的 `transparent_wrappers` 和 `command_tools` 会合并。

## 管理 rulebook 来源

`rule.json` 的 `rules` 数组中的每个条目都是一个 rulebook 来源：

- **本地来源**：`project-rules` 这样的裸名称。rulebook 位于 `.cc-safety-net/rules/project-rules/rulebook.json`（项目）或 `~/.cc-safety-net/rules/project-rules/rulebook.json`（用户）。
- **GitHub 来源**：`owner/repo#ref/<rulebook-name>`，指向该仓库中的 `.cc-safety-net/rules/<rulebook-name>/rulebook.json`。`rule add` 和 `rule update` 会把这个文件复制到你自己范围内的相同路径，因此它的加载方式与本地 rulebook 相同。

请用 `rule` 命令管理来源，不要手动编辑 `rule.json`：

```bash
# Add a local rulebook source
npx -y cc-safety-net rule add project-rules

# Add one rulebook from a GitHub repository and ref
npx -y cc-safety-net rule add kenryu42/cc-safety-net#main/example-rules

# Add every rulebook a repository publishes, from its default branch
npx -y cc-safety-net rule add acme/safety-rules

# Add selected rulebooks from a branch, tag, or commit
npx -y cc-safety-net rule add acme/safety-rules --ref v2 --only aws gcloud

# Re-fetch a single source, or every source when no source is given
npx -y cc-safety-net rule update example-rules

# List active rulebooks, rules, overrides, and wrappers
npx -y cc-safety-net rule list

# Remove a source (--delete-source also deletes a local source directory)
npx -y cc-safety-net rule remove example-rules --delete-source
```

加上 `--global`（`-g`）即可修改用户范围而不是项目范围。`--only` 和 `--ref` 的说明见[官方 rulebook](/zh-Hans/configuration/rulebooks#install)，每个子命令及其输出和错误见 [`rule`](/zh-Hans/reference/cli/rule)。

<span id="rulebooks-are-live-files"></span>

### rulebook 是实时文件

运行时在每次工具调用时从磁盘读取每个 `rulebook.json`。保存的修改从下一条命令起生效，无需发布或重建。缺失、不可读或无效的 rulebook 不贡献任何规则，其他所有 rulebook 和内置规则继续生效，运行时报告 `degraded`。对于从未获取过的 GitHub 来源，请运行 `npx -y cc-safety-net rule update`。修复步骤见[配置恢复](/zh-Hans/configuration/recovery)。

<span id="transparent-wrappers"></span>

## 透明包装器

透明包装器是运行另一条命令的命令，例如 `timeout 5 git push`。CC Safety Net 会穿过透明包装器，看到它实际运行的命令，因此内置规则和自定义规则对 `timeout 5 docker system prune` 的作用与对 `docker system prune` 相同。

有八个包装器是内置的，无需配置：`caffeinate`、`exec`、`nice`、`nohup`、`setsid`、`stdbuf`、`time` 和 `timeout`。

如果团队通过 `rtk` 等其他包装器运行命令，请添加它：

```bash
# List configured wrappers for the project scope
npx -y cc-safety-net rule wrapper list

# Trust a wrapper, or stop trusting it
npx -y cc-safety-net rule wrapper add rtk
npx -y cc-safety-net rule wrapper remove rtk

# Operate on the user scope instead
npx -y cc-safety-net rule wrapper add rtk --global
```

- 包装器名称必须匹配 `^[a-zA-Z][a-zA-Z0-9_-]*$`，且在文件内唯一。
- 保留命令不能作为包装器：`git`、`busybox`、内置分析的命令 `rm`、`find`、`xargs` 和 `parallel`、所有 shell 包装器、所有解释器以及 awk 解释器。
- 只添加按原样运行子命令的包装器。会改写或隐藏子命令的包装器，即使列出了，CC Safety Net 也不会穿过它。

你添加的包装器保存在 `rule.json` 中，因此 `rule.json` 不可读时它们会失效。参见 [`rule.json` 中声明的覆盖范围](/zh-Hans/configuration/recovery#coverage-declared-in-rule-json)。

<span id="community-shell-tools"></span>

## 社区 shell 工具

插件可以为智能体添加自带的 shell 工具，例如 `dsh-ops` 插件会加入 `ops_bash` 和 `ops_run_background`。CC Safety Net 不认识这些名称，因此只检查它们的路径参数，从不把它们的 `command` 当作 shell 命令解析。在你声明之前，`ops_bash` 执行 `git reset --hard` 不会被阻止。

声明该工具后，CC Safety Net 就会分析它的命令：

```bash
# Declare one or more tools in the user config
npx -y cc-safety-net rule tool add ops_bash ops_run_background

# Name the argument that carries the working directory
npx -y cc-safety-net rule tool add ops_run_background --cwd-arg dir

# Write the project config instead
npx -y cc-safety-net rule tool add team_shell --project

# List every declared tool in both scopes, or stop analyzing one
npx -y cc-safety-net rule tool list
npx -y cc-safety-net rule tool remove ops_bash
```

这会写入 `command_tools` 数组：

```json
{
  "version": 1,
  "rules": [],
  "overrides": {},
  "transparent_wrappers": [],
  "command_tools": ["ops_bash", { "name": "ops_run_background", "cwd": "dir" }]
}
```

从下一次工具调用起，已声明工具的调用会和内置 shell 工具一样，适用相同的内置规则、自定义规则和安全级别。此时 `ops_bash` 执行 `git reset --hard` 会被 `git.reset-hard` 阻止。

- `rule tool` 默认写入用户配置，加 `--project` 则写入项目配置。
- 名称必须与智能体发送的工具名完全一致，包括大小写。
- 声明无法改变 CC Safety Net 处理内置工具的方式，`rule tool add` 也会拒绝内置工具名。其他命名规则见 [`rule tool add` 名称错误](/zh-Hans/reference/cli/rule#rule-tool-add-name-errors)。
- CC Safety Net 只分析带有非空字符串 `command` 的调用。
- `cwd` 指出由哪个参数承载工作目录。未指定时，CC Safety Net 读取 `workdir`、`cwd` 或 `working_directory`。没有工作目录的调用在会话工作区中运行。值为空白或目录不存在时，该调用 fail closed。

声明保存在 `rule.json` 中，因此 `rule.json` 不可读时，该范围声明的工具会失效。手动编辑该文件后，请运行 `npx -y cc-safety-net rule verify`。

## 创建你的第一条自定义规则

<Steps>
  <Step title="创建 rule.json">
    ```bash
    npx -y cc-safety-net rule init
    ```

    这会创建一个空的 `.cc-safety-net/rules/rule.json`，其中没有任何 rulebook 来源：

    ```json
    {
      "version": 1,
      "rules": [],
      "overrides": {},
      "transparent_wrappers": []
    }
    ```

    `rule init --example` 还会在 `.cc-safety-net/rules/example-rules/rulebook.json` 写入一个示例 rulebook。在运行 `npx -y cc-safety-net rule add example-rules` 之前，它不会生效。
  </Step>
  <Step title="编写 rulebook">
    创建 `.cc-safety-net/rules/project-rules/rulebook.json`：

    ```json
    {
      "rulebook_version": 1,
      "name": "project-rules",
      "version": "1.0.0",
      "description": "Project-specific CC Safety Net rules.",
      "author": "project",
      "allowed_commands": ["git"],
      "rules": [
        {
          "name": "block-git-add-all",
          "command": "git",
          "subcommand": "add",
          "block_args": ["-A", "--all", "."],
          "reason": "Use 'git add <specific-files>' instead of blanket add."
        }
      ],
      "tests": [
        {
          "command": "git add -A",
          "expect": "blocked",
          "rule": "block-git-add-all"
        },
        {
          "command": "git add README.md",
          "expect": "allowed"
        }
      ]
    }
    ```
  </Step>
  <Step title="注册 rulebook">
    ```bash
    npx -y cc-safety-net rule add project-rules
    ```

    现在 `rule.json` 中列有 `"rules": ["project-rules"]`。从下一条命令起，CC Safety Net 会以你写的原因阻止 `git add -A`、`git add --all` 和 `git add .`。
  </Step>
  <Step title="验证 rulebook">
    ```bash
    npx -y cc-safety-net rule verify
    ```

    `rule verify` 会检查两个范围的 `rule.json`，按运行时的方式加载每个来源，并运行版本 2 的 fixture。它从不获取远程内容。
  </Step>
</Steps>

## `rule.json` schema

`rule.json` 选择生效的 rulebook、应用覆盖，并声明透明包装器和社区 shell 工具。安全级别、内置保护、允许路径和拒绝路径以及审计保留期在另一个文件中配置，参见[策略](/zh-Hans/configuration/policy)。

<ParamField body="version" type="integer" required>
  Schema 版本，必须为 `1`。
</ParamField>

<ParamField body="rules" type="array">
  rulebook 来源字符串列表，默认为空数组。来源名称在文件内必须唯一，文件最多列出 64 个来源。
</ParamField>

<ParamField body="overrides" type="object">
  以 `<rulebook-name>/<rule-name>` 为键的规则覆盖。值可以是 `"off"`（关闭该规则），也可以是一个对象（替换该规则的阻止消息）。对象形式必须包含 `reason`，可以带上可选的 `intent`；省略 `intent` 时，规则自身的意图保持不变。
</ParamField>

<ParamField body="transparent_wrappers" type="array">
  在八个内置包装器之外，额外需要穿过的命令，默认为空数组。条目必须唯一，且不能是保留命令。参见[透明包装器](#transparent-wrappers)。
</ParamField>

<ParamField body="command_tools" type="array">
  插件为智能体添加、而 CC Safety Net 并不认识的 shell 工具。在这里声明后，CC Safety Net 会像分析内置 shell 工具一样分析它的 `command`。每个条目可以是工具名，也可以是 `{ "name": "ops_bash", "cwd": "dir" }` 这样的对象，指出由哪个参数承载工作目录。默认为空数组。名称在文件内必须唯一，且不能是内置工具名。参见[社区 shell 工具](#community-shell-tools)。
</ParamField>

同时替换消息和面向智能体的意图的覆盖如下：

```json
{
  "version": 1,
  "rules": ["project-rules", "owner/repo#main/team-rules"],
  "overrides": {
    "project-rules/block-docker-system-prune": {
      "reason": "Use targeted Docker cleanup commands.",
      "intent": "use_alternative"
    },
    "team-rules/block-npm-global": "off"
  },
  "transparent_wrappers": ["rtk"]
}
```

### `rule.json` 编辑器支持

CC Safety Net 为 `rule.json` 发布了一份 JSON Schema。把编辑器指向它，即可获得补全和校验：

```json
{
  "$schema": "https://raw.githubusercontent.com/kenryu42/cc-safety-net/main/assets/cc-safety-net.schema.json",
  "version": 1,
  "rules": [],
  "overrides": {},
  "transparent_wrappers": []
}
```

对于缺少这一行的有效 `rule.json`，`rule verify` 会补上 `$schema`。`policy.json` 没有发布 schema。

## Rulebook schema

每个 rulebook 都放在各自的 `rulebook.json` 文件中。

<ParamField body="rulebook_version" type="integer" required>
  rulebook schema 版本，必须为 `1` 或 `2`。其他值会以 `rulebook_version must be 1 or 2` 校验失败。参见[版本 2 规则](#version-2-rules)。
</ParamField>

<ParamField body="name" type="string" required>
  rulebook 名称，必须与本地目录名或 GitHub 来源名称一致。
</ParamField>

<ParamField body="version" type="string" required>
  rulebook 版本字符串。
</ParamField>

<ParamField body="description" type="string">
  rulebook 的可读描述。
</ParamField>

<ParamField body="author" type="string">
  rulebook 作者。
</ParamField>

<ParamField body="allowed_commands" type="array" required>
  此 rulebook 可以为其定义规则的命令。
</ParamField>

<ParamField body="rules" type="array" required>
  自定义阻止规则。参见[规则 schema](#rule-schema)。
</ParamField>

<ParamField body="tests" type="array">
  可选的 rulebook fixture。参见 [Fixture schema](#fixture-schema)。版本 1 的 fixture 只校验结构；版本 2 的 fixture 还会针对该 rulebook 自身的规则求值。
</ParamField>

<span id="rule-schema"></span>

## 规则 schema

以下字段定义 `rulebook_version` 1 的规则。版本 2 用 `match` 对象取代了 `subcommand` 和 `block_args`，参见[版本 2 规则](#version-2-rules)。

<ParamField body="name" type="string" required>
  在 rulebook 内唯一的名称，最多 64 个字符。必须以字母开头，后跟字母、数字、连字符或下划线。
</ParamField>

<ParamField body="command" type="string" required>
  要匹配的基础命令，必须列在 `allowed_commands` 中。
</ParamField>

<ParamField body="subcommand" type="string">
  要匹配的子命令，例如 `add` 或 `install`。省略时匹配任何子命令。
</ParamField>

<ParamField body="block_args" type="array" required>
  触发阻止的参数。至少需要一个，因此版本 1 规则无法阻止某个子命令的所有用法。这种需求请用[版本 2 规则](#block-every-git-push)。
</ParamField>

<ParamField body="reason" type="string" required>
  规则阻止命令时 CC Safety Net 显示的消息，最多 256 个字符。
</ParamField>

<ParamField body="intent" type="string">
  给智能体的意图，追加在阻止消息的页脚。取 `hard_stop`、`use_alternative`、`scope_down`、`manual_only` 或 `stop_and_explain` 之一，默认为 `manual_only`。
</ParamField>

<span id="version-2-rules"></span>

## 版本 2 规则

设置 `"rulebook_version": 2`，即可按精确的命令路径匹配，而不是子命令加一组参数。在 `gcloud compute` 下阻止 `delete` 的版本 1 规则，会在命令中任意位置查找该 token，因此也会阻止 `gcloud compute instances create delete`；命令路径为 `["compute", "instances", "delete"]` 的版本 2 规则则不会。

版本 1 的 rulebook 保持原有的字段、匹配方式和只校验结构的 fixture。CC Safety Net 按每个 rulebook 自己声明的版本校验它。

版本 2 规则沿用版本 1 的 `name`、`command`、`reason` 和 `intent`，并用 `match` 对象取代 `subcommand` 和 `block_args`。

<ParamField body="match.command_path" type="array" required>
  必须按顺序跟在命令后面的命令词，是由非空字符串组成的非空数组。由于路径不能为空，没有规则能匹配某个命令的所有调用，例如所有 `aws` 调用。
</ParamField>

<ParamField body="match.any_args" type="array">
  参数中必须至少字面出现其中一个 token。由非空字符串组成、无重复的非空数组。省略时，命令路径匹配后不论参数如何都会命中。
</ParamField>

<ParamField body="match.exclude_args" type="array">
  参数中只要字面出现其中任意一个 token，规则就不匹配。由非空字符串组成、无重复的非空数组。
</ParamField>

版本 2 不会忽略版本 1 的字段，而是直接拒绝。仍带有 `subcommand` 或 `block_args` 的规则会以 `rules[0].subcommand: not supported in rulebook_version 2` 和 `rules[0].block_args: not supported in rulebook_version 2` 校验失败。

```json
{
  "rulebook_version": 2,
  "name": "terraform-rules",
  "version": "1.0.0",
  "allowed_commands": ["terraform"],
  "rules": [
    {
      "name": "block-terraform-apply-destroy",
      "command": "terraform",
      "match": {
        "command_path": ["apply"],
        "any_args": ["-destroy", "--destroy"]
      },
      "reason": "Review a destroy plan first with 'terraform plan -destroy'.",
      "intent": "use_alternative"
    }
  ],
  "tests": [
    {
      "command": "terraform apply -destroy",
      "expect": "blocked",
      "rule": "block-terraform-apply-destroy"
    },
    {
      "command": "terraform -chdir=infra apply",
      "expect": "allowed"
    }
  ]
}
```

<span id="version-2-matching"></span>

### 版本 2 匹配

- **命令**：与版本 1 一样，CC Safety Net 把命令规范化为小写 basename。
- **命令路径**：CC Safety Net 跳过已识别的全局选项及其取值。之后的命令词必须与 `command_path` 完全一致，顺序也要一致。路径之后的参数不影响路径匹配。
- **全局选项**：CC Safety Net 只认识 `aws`、`gcloud` 和 `az` 的带值全局选项。对其他命令，取值分开书写的选项（如 `git -C repo push`）会导致规则匹配不上。Terraform 的 `-chdir=DIR` 是单个 token，会被跳过。
- **不展开短选项**：`-Ap` 就是 `-Ap`。请列出想匹配的每种写法，例如 `"-destroy"` 和 `"--destroy"`。
- **字面匹配，区分大小写**：不支持正则表达式、glob 或子串匹配。
- **先命中者生效**：CC Safety Net 按顺序求值规则，第一条命中的规则产生阻止。
- **发布通道需要单独的规则**：`gcloud beta compute instances delete` 不匹配 `command_path` 为 `["compute", "instances", "delete"]` 的规则。请另写一条 `["beta", "compute", "instances", "delete"]` 的规则。

## Fixture schema

Fixture 用于记录预期行为。CC Safety Net 解析其中的命令，交给该 rulebook 的规则求值，但从不执行它们。

<ParamField body="command" type="string" required>
  Shell 命令 fixture。
</ParamField>

<ParamField body="expect" type="string" required>
  `blocked` 或 `allowed`。
</ParamField>

<ParamField body="rule" type="string">
  预期会阻止该命令的规则。`blocked` fixture 必填。
</ParamField>

版本 1 的 fixture 只校验结构。`rule add`、`rule update` 和 `rule verify` 会对版本 2 的 fixture 求值。`blocked` fixture 只有在它指定的规则第一个命中时才算通过，`allowed` fixture 只有在没有任何规则命中时才算通过。fixture 失败的来源会在写入之前被 `rule add` 和 `rule update` 拒绝。每条失败都以该 fixture 在 `tests` 中的下标标明：

```text
tests[<index>]: expected "<rule>" to block "<command>" but no rule matched
tests[<index>]: expected "<rule>" to block "<command>" but "<other-rule>" matched first
tests[<index>]: expected "<command>" to be allowed but "<rule>" matched
tests[<index>]: could not parse fixture command: <command>
```

`rule verify` 会在每条前面加上 rulebook 文件名，形如 `example-rules/rulebook.json: tests[0]: ...`。

## 匹配行为

下面关于子命令、参数和选项的说明适用于 `rulebook_version` 1 的规则，版本 2 规则的匹配方式见[版本 2 匹配](#version-2-matching)。命令规范化、透明包装器和嵌套对两个版本都适用。

- **命令规范化**：匹配前，CC Safety Net 把命令规范化为 basename。`/usr/local/bin/npm` 能匹配 `"command": "npm"` 的规则。
- **子命令检测**：子命令是命令之后的第一个非选项参数。在 `git --no-pager add -A` 中，子命令是 `add`。
- **参数匹配**：`block_args` 中的参数按字面匹配，不支持正则表达式或 glob。
- **短选项展开**：匹配前，CC Safety Net 会拆开合并书写的短选项。`-Ap` 视为 `-A` 和 `-p`。
- **长选项匹配**：长选项按字符串精确匹配。`--all-files` 不匹配 `--all`。
- **任意参数匹配**：只要出现 `block_args` 中的任意一个参数，规则就阻止该命令。
- **只增不减**：自定义规则只能新增限制，无法绕过内置保护。
- **任意嵌套深度**：规则作用于嵌套命令的方式与顶层命令相同。为 `rm` 写了规则后，`bash -c 'rm -r ./tmpdir'` 和 `eval 'rm -r ./tmpdir'` 都会被阻止，`sh -c` 和被调用的函数正文也一样。内置分析器同样覆盖的命令也不例外：`rm`、`rmdir`、`git`、`find`、`xargs` 和 `parallel`。

<Note>
  **已知限制**：CC Safety Net 把 `-Cfoo` 视为 `-C -f -o -o`，而不是 `-C foo`。因此阻止 `-f` 的规则可能误匹配紧贴在选项后的取值。
</Note>

### 规则匹配的是命令，不是文件路径

自定义规则匹配的是 shell 命令及其参数。它看不到智能体用自带的读取和编辑工具打开的文件，因此规则无法保护 `~/.zshrc` 这样的文件。要阻止对某个文件或目录的一切访问，请把它加入 `policy.json` 的 [`secret_protection.deny_paths`](/zh-Hans/configuration/policy#deny-paths)。拒绝路径也会阻止读取。

## 示例

<span id="block-every-git-push"></span>

### 阻止所有 git push

`command_path: ["push"]` 且不带 `any_args` 的版本 2 规则，会阻止带任何参数的 `git push`。版本 1 规则做不到这一点，因为 `block_args` 至少需要一个参数。

```json
{
  "rulebook_version": 2,
  "name": "project-rules",
  "version": "1.0.0",
  "allowed_commands": ["git"],
  "rules": [
    {
      "name": "block-git-push",
      "command": "git",
      "match": {
        "command_path": ["push"]
      },
      "reason": "A person pushes this repository. Commit locally and stop."
    }
  ],
  "tests": [
    {
      "command": "git push",
      "expect": "blocked",
      "rule": "block-git-push"
    },
    {
      "command": "git push --force origin main",
      "expect": "blocked",
      "rule": "block-git-push"
    },
    {
      "command": "git status",
      "expect": "allowed"
    }
  ]
}
```

由于 `timeout` 是[透明包装器](#transparent-wrappers)，这条规则也会阻止 `timeout 5 git push`。它不会命中 `git -C repo push`，因为 `push` 前面有一个取值分开书写的 git 全局选项。参见[版本 2 匹配](#version-2-matching)。

<span id="turn-off-one-rule"></span>

### 关闭单条规则

要关闭某条自定义规则，在列出该 rulebook 的那个范围的 `rule.json` 中，把它的 `<rulebook-name>/<rule-name>` 键加入 `overrides`，值设为 `"off"`。阻止消息中会打印这个键。

```json
{
  "version": 1,
  "rules": ["project-rules"],
  "overrides": {
    "project-rules/block-git-push": "off"
  },
  "transparent_wrappers": []
}
```

rulebook 文件本身保持不变，因此 `rule update` 不会撤销这条覆盖。要关闭 `git.push-force` 这样的内置规则，请改用 `policy.json`，参见[允许被阻止的命令](/zh-Hans/reference/blocked-commands#allow-a-blocked-command)。

### 阻止全局 npm 安装

```json
{
  "rulebook_version": 1,
  "name": "project-rules",
  "version": "1.0.0",
  "allowed_commands": ["npm"],
  "rules": [
    {
      "name": "block-npm-global",
      "command": "npm",
      "subcommand": "install",
      "block_args": ["-g", "--global"],
      "reason": "Global npm installs can cause version conflicts. Use npx or local install."
    }
  ],
  "tests": [
    {
      "command": "npm install -g typescript",
      "expect": "blocked",
      "rule": "block-npm-global"
    },
    {
      "command": "npm install typescript",
      "expect": "allowed"
    }
  ]
}
```

### 阻止 docker system prune

```json
{
  "rulebook_version": 1,

  "allowed_commands": ["docker"],
  "rules": [

      "name": "block-docker-system-prune",

    }

    {
      "command": "docker system prune",

    },

```

## 阻止消息格式

阻止消息的完整布局见[阻止消息的形式](/zh-Hans/guides/how-it-works#what-a-block-looks-like)。自定义规则会在原因前加上 rulebook 名称和规则名称，便于看出是哪个 rulebook 触发了阻止：

```text
BLOCKED by CC Safety Net

Reason: [project-rules/block-git-add-all] Use 'git add <specific-files>' instead of blanket add.

Command: git add -A
```

前缀 `<rulebook-name>/<rule-name>` 也是你在 `rule.json` 的 `overrides` 中用来[关闭该规则](#turn-off-one-rule)或替换其原因的键。

<span id="migrate-legacy-configuration"></span>

## 迁移旧配置

CC Safety Net 不再加载旧版内联配置文件（`.safety-net.json` 和 `~/.cc-safety-net/config.json`）。其中的规则不起作用，运行时也不会给出警告。`npx -y cc-safety-net doctor` 和 `rule verify` 会把残留的文件报告为 `Legacy inline rule configs are ignored`。

```bash
# Convert legacy inline rules into the rulebook layout
npx -y cc-safety-net rule migrate

# Optionally delete verified legacy files after migration
npx -y cc-safety-net rule migrate --cleanup

# Validate the migrated rules
npx -y cc-safety-net rule verify
```

`rule migrate` 没有 `--global`，会同时迁移两个范围。在主目录中运行时，它会跳过项目范围。参见[在用户配置目录中运行 `rule migrate`](/zh-Hans/reference/cli/rule#rule-migrate-in-the-user-config-directory)。

它会把内联文件转换为以下布局：

```text
.cc-safety-net/rules/rule.json                    # project rulebook sources + overrides
.cc-safety-net/rules/project-rules/rulebook.json  # migrated project rules
~/.cc-safety-net/rules/rule.json                  # user rulebook sources + overrides
~/.cc-safety-net/rules/user-rules/rulebook.json   # migrated user rules
```

## 无效的自定义规则配置

加载失败的自定义规则配置会被 CC Safety Net 丢弃，绝不会因此拒绝命令。其他有效来源和所有内置规则继续生效，运行时报告 `degraded`。被丢弃的来源意味着少了一些阻止，而且不会有任何拒绝来提醒你。编辑规则或升级后，请运行 `npx -y cc-safety-net status`。参见[配置恢复](/zh-Hans/configuration/recovery)。

<Warning>
  自定义规则配置不具备防篡改能力。智能体可以编辑 `rule.json` 和 rulebook 文件，只有 `policy.json` 是受保护路径。手动添加或修改自定义规则后，请用 `npx -y cc-safety-net rule verify` 验证。
</Warning>
