CC Safety Net 在每次工具调用时加载策略快照，读取本地策略文件、`rule.json`、规则 lockfile 和经过 digest 验证的 rulebook 缓存。该加载过程从不写入、从不访问网络，也从不缓存结果，因此快照始终反映磁盘上当前的配置。

快照只有两种状态：**`ready`** 和 **`degraded`**。本页是两者的完整契约，包括某个来源被拒绝时哪些内容不再执行，以及如何回到 `ready`。

## 配置状态

| 状态 | 何时发生 | 含义 |
| --- | --- | --- |
| `ready` | 每个生效的来源都完整加载并通过验证 | 完全按照你编写的配置进行常规评估 |
| `degraded` | 任何规则错误、任何规则警告或任何 `policy.json` 错误 | 常规评估继续进行，但依据的是回退配置，并且每个报告位置都会带上一条警告，指出被拒绝的来源 |

一条警告就足以让运行时进入 `degraded`。错误与警告的区别在于来源，而不是状态的严重程度：

- **错误**指出某个来源已被**丢弃**。该来源不再提供任何规则。
- **警告**指出某个来源**仍然生效**，只是被拒绝的那部分被忽略。

两者都产生 `degraded`。

<Note>
`ready` 和 `degraded` 是 `cc-safety-net status` 打印的仅有两种判定，判定直接读自快照状态。禁用 Claude Code 插件不会改变判定；`status` 会把它报告为 `Not active` 下的第一项："plugin cc-safety-net@cc-marketplace is disabled in Claude Code; nothing is enforced in Claude Code until it is re-enabled. Other integrations are not affected."
</Note>

## 无效配置的行为

无效配置绝不会仅仅因为无效就拒绝正常工作。无效的候选配置不会被执行，但也不会把智能体挡在门外。

- 无法验证的规则来源会被**丢弃**，其规则不再执行。
- 其他每个通过验证的范围都会继续执行自己的规则。
- 每项内置保护在任何情况下都继续生效——破坏性命令规则、机密保护、策略文件保护和 Git 元数据保护根本不读取任何规则配置。
- 无法读取的 `policy.json` 会回退到**保护性**默认值，因此破坏性命令保护和机密保护都保持开启。

处于 `degraded` 时没有特殊的恢复模式，也没有允许列表，因为没有任何操作会仅仅因为配置不可用而被拒绝。读取 `rule.json`、就地编辑它以及运行 `cc-safety-net rule sync` 都是普通的工具调用，各自独立地通过或失败，因此智能体可以自行修复配置。

<Warning>
丢弃某个来源并非安全中立。它**移除**了该来源带来的拒绝，因此你在被丢弃的 rulebook 中刻意阻止的命令又能运行了，直到你修复并重新同步它。永远不要以为错误中提到的 rulebook 仍在保护你。
</Warning>

在所有状态下始终受保护的只有一样东西：规范的用户 `policy.json`。策略文件保护和 Git 元数据保护在加载配置快照**之前**运行，因此不会受到损坏配置的影响。具体阻止哪些操作见[策略](/zh-Hans/configuration/policy)。

## 配置回退矩阵

### 错误 —— 来源被丢弃

| 失败 | 哪些内容不再执行 | 仍然适用的内容 |
| --- | --- | --- |
| 已配置规则来源但缺少 lockfile | 该范围内的每个 rulebook | 另一范围中已验证的规则和所有内置保护 |
| 已配置的来源缺少 lock 条目 | 该 rulebook | 其他所有 rulebook 和所有内置保护 |
| 来源缺少缓存条目 | 该 rulebook | 其他所有 rulebook 和所有内置保护 |
| 缓存 digest 不匹配 | 该 rulebook | 其他所有 rulebook 和所有内置保护 |
| 缓存的 rulebook 无法解析或未通过 schema 校验 | 该 rulebook | 其他所有 rulebook 和所有内置保护 |
| lockfile 条目与其配置的来源标识不匹配——`kind` 有误，或 `path`/`name` 与来源声明不一致 | 该范围内的每个 rulebook——整个 lockfile 因格式错误而被拒绝 | 另一范围中已验证的规则和所有内置保护 |
| `rule.json` 格式错误、为空或使用了不受支持的 `version` | 整个范围，**包括其 `transparent_wrappers`** | 另一范围中已验证的规则和所有内置保护 |
| 无法安全读取策略所在的文件系统 | 该范围 | 另一范围中已验证的规则和所有内置保护 |

上述每一条消息都会指明它拒绝的文件或来源，并在存在修复办法时提示你运行 `cc-safety-net rule sync`。

### 警告 —— 来源仍然生效

| 失败 | 被忽略的内容 | 仍然执行的内容 |
| --- | --- | --- |
| 两个生效的 rulebook 声明了相同的名称 | 后声明的 rulebook，其规则不生效 | 先声明的一方；解析时用户范围优先 |
| `rule.json` 中存在未知的覆盖键 | 仅该条覆盖 | 其他所有覆盖和每条规则都保持已配置的状态 |
| 项目覆盖指向用户范围的规则 | 仅该条覆盖 | 该规则保持用户配置的状态 |

<Warning>
两张表中都刻意没有列出本地 rulebook 来源。运行时加载只读取经过 digest 验证的缓存，因此编辑本地 rulebook、把它改坏，或删除其源目录，都**不会产生任何警告**——真正执行的是缓存中的 rulebook，即上次成功同步时的那一份，而不是你刚刚编辑的文件。只有 `cc-safety-net rule sync` 成功后，你的编辑才会生效。
</Warning>

重复的 rulebook 名称按确定的规则解析：先声明者胜出，而用户范围先加载，因此用户范围声明的名称会遮蔽项目范围的同名 rulebook。后声明的 rulebook 不提供任何规则，而不是部分遮蔽规则。由于这种冲突会被解决而不是视为致命错误，当另一个范围已经使用该名称时，某一个范围的 `rule sync` 仍会成功。

### `policy.json` —— 逐字段保留或替换为保护性默认值

| 情况 | 结果 | 状态 |
| --- | --- | --- |
| 文件不存在 | 内置默认值 | `ready`，没有诊断 |
| 文件为空或只有空白字符 | 内置保护性默认值 | `degraded` |
| 文件不是有效的 JSON | 内置保护性默认值 | `degraded` |
| 文件解析结果不是对象 | 内置保护性默认值 | `degraded` |
| 文件解析为对象但验证失败 | **逐字段保留**：每个已识别的有效部分继续生效，其余部分使用保护性默认值 | `degraded` |
| 文件有效 | 完全按你编写的策略执行 | `ready` |

逐字段保留意味着一个无效字段不会连带丢掉文件其余部分配置的保护。保护性默认值刻意偏向更多拒绝：强制开启破坏性命令保护和机密保护，丢弃两个允许路径列表中的无效条目，并丢弃用于关闭规则的覆盖。有效的机密允许路径仍会保留在策略中。每个字段的保留行为见[策略](/zh-Hans/configuration/policy)。

运行时永远不会重写 `policy.json`。手动修复，或使用仪表板中的修复操作。

在文件仍有错误期间，仪表板表单显示的是完整默认值，而不是保留下来的值。修复文件之前无法保存。修复操作会保留每个已识别的有效设置；只有在无法解析 JSON 时，它才会用默认值替换整个文件。

## 透明包装器的覆盖缺口

`transparent_wrappers` 声明在 `rule.json` 中，而不是在 rulebook 中，而 `rule.json` 本身没有 lock 也没有 digest。这有两个后果：

- **被丢弃的 rulebook** 仍保留其范围的包装器，因为 `rule.json` 本身仍然可读。
- **无法读取的 `rule.json`** 会丢失该范围的包装器，因为没有经过验证的副本可以回退。分析不再穿透这些包装命令去识别其下受保护的命令。

这是唯一一处被拒绝的配置会削弱内置覆盖，而不只是移除你自己的规则。当某个范围因此被丢弃时，请先修复 `rule.json`。

## Fail-closed 情形

“Fail closed”用来描述运行时和分析失败是准确的，它拒绝的是**那一次工具调用**——它从来都不是对无效配置行为的描述。

| 情形 | 行为 |
| --- | --- |
| 分析器或某个依赖在任一防护阶段意外抛出异常 | 在所有模式中，该工具调用都以“failed closed”为原因被拒绝 |
| hook 或工具负载格式错误或过大 | 在所有模式中都被拒绝 |
| 命令路由上的空命令或仅含空白字符的命令 | 在所有模式中都被拒绝 |
| 命令超出递归深度限制 | 在所有模式中都被拒绝 |
| 命令结构超出安全验证限制 | 在所有模式中都被拒绝 |
| `fail_closed` 能力开启时命令无法拆分成 token | 被拒绝——见 [strict 模式](/zh-Hans/configuration/modes#strict-mode) |
| worktree 放宽无法明确确认当前位于 linked worktree | 不应用放宽，保留更严格的默认值 |

无效配置正相反：规则来源被丢弃，`policy.json` 逐字段保留或替换为保护性默认值，而工作继续进行。

## `degraded` 状态的报告方式

| 呈现位置 | 你会看到什么 |
| --- | --- |
| 下一次用户可见的拒绝 | 追加在阻止消息后的 `Config warning:` 行，其中带有完整原因 |
| 审计记录 | `configFallback` 标志，在允许和拒绝的决策上同样会设置 |
| `cc-safety-net status` | 判定 `ready` 或 `degraded`，并在 `Not active` 下逐行列出诊断 |
| `cc-safety-net doctor` | 一条标题为 "Runtime is enforcing a fallback configuration" 的 `config.runtime-degraded` 警告项，详情是完整原因 |
| `cc-safety-net rule list` | `Issues` 与 `Warnings` 两个部分，仅涉及规则配置 |
| 状态行 | 快照处于 `degraded` 期间显示 `⚠️` 标记 |
| 仪表板 | 保护横幅中显示的状态 |

`doctor` 是唯一同时报告规则配置和 `policy.json` 的命令。有关每个命令的选项和退出行为，请参阅 [CLI 命令](/zh-Hans/reference/cli-commands)。

有两个结构性限制值得了解：

- `Config warning:` 行和审计 `configFallback` 标志只出现在快照加载**之后**做出的决策上。策略文件和 Git 元数据的拒绝发生在此之前，因此两者都不会带上它们。
- 诊断只**指明**被拒绝的文件和触发条件，绝不会复制其中的字节。恰好位于格式错误配置文件中的机密不会出现在消息里。

## 可见的失败与静默的失败

- **被丢弃的规则来源是静默的。** 它移除的是拒绝，而不是增加拒绝，因此一次正常的会话既不会遇到摩擦，也不会收到任何信号。每次改动规则配置之后、每次升级之后，都要专门检查这一点。把 `cc-safety-net status` 变成习惯；需要完整报告时运行 `doctor`。
- **本地 rulebook 的编辑和未迁移的旧配置更加静默。** 两者都不会产生运行时诊断：经过 digest 验证的缓存仍在执行编辑前的 rulebook，而旧配置文件根本不会被加载。`rule sync` 会让编辑生效，`rule verify` 会标记出旧文件。
- **无效的 `policy.json` 大多会自己暴露出来**，因为被拒绝的部分会回退到保护性默认值：两项保护被强制开启，允许路径被丢弃，用于关闭规则的覆盖被丢弃。你会因为出现*比配置更多*的拒绝而发现它。
- **无效 `policy.json` 静默的那一半**：无效的 `safety.level` 会静默回退到 `standard`，因此把 `paranoid` 拼错反而会**降低**你的预设。无效的 `secret_protection.deny_paths` 条目，以及会把规则提到高于默认值的按规则覆盖，都会被丢弃而不是被修复。
- 只有状态行标记是被动呈现的。`Config warning:` 行需要依附一次无关的拒绝才会出现，其他所有呈现位置都要等你运行命令或打开仪表板。

## 恢复配置

下面的每个命令都是普通的工具调用，因此即使运行时处于 `degraded`，智能体也可以自行跑完整个流程。[CLI 命令](/zh-Hans/reference/cli-commands)给出了每个命令的完整选项和退出行为。

<Steps>
<Step title="检查判定结果">
    ```bash
    npx cc-safety-net status
    ```

打印 `ready` 或 `degraded`，并在 `Not active` 下为每项诊断打印一行。禁用的 Claude Code 插件显示为第一个 `Not active` 项，而不是单独的判定。它纯粹提供信息，因此把它当作低成本的日常检查，而不是一道关卡。
</Step>
<Step title="获取完整报告">
    ```bash
    npx cc-safety-net doctor
    ```

唯一一条同时涵盖规则配置和 `policy.json` 的命令。运行时处于 `degraded` 时会显示为 `config.runtime-degraded` 警告，该检查项的详情就是指明每个被拒绝来源的完整原因。
</Step>
<Step title="查看实际生效的内容">
    ```bash
    npx cc-safety-net rule list
    ```

列出实际生效的内容，之后是 `Issues` 和 `Warnings`。用它确认被丢弃的来源带走了哪些规则。只有在策略存在错误时它才以非零值退出；只有警告时会打印在 `Warnings` 下并以 `0` 退出。
</Step>
<Step title="验证你的规则配置">
    ```bash
    npx cc-safety-net rule verify
    ```

根据 schema 校验用户和项目的 `rule.json`，并重放运行时的加载过程，因此能发现防护在运行时会遇到的同样问题。它还会标记出仍需迁移的旧文件。有一处写入需要留意：当有效的 `rule.json` 缺少 `$schema` 键时，`rule verify` 会补上一个并打印 `Added $schema to <scope> config.`——除此之外它不会改动任何内容。
</Step>
<Step title="修复并重新同步">
    ```bash
    npx cc-safety-net rule sync
    ```

重写所同步范围的 lockfile 和缓存，然后完全按照防护的加载方式重新加载该范围。如果仍有诊断，它会报告该诊断并以非零值退出，而不是声称成功——所以 `Rule config synced.` 对该范围来说确实表示一切正常。

验证仅涵盖正在同步的范围。
</Step>
<Step title="手动修复 policy.json">
运行时永远不会重写 `policy.json`。自行更正诊断中指出的字段，或使用仪表板中的修复操作，然后重新运行 `status`。完整 schema 和默认值见[策略](/zh-Hans/configuration/policy)。
</Step>
</Steps>

每次修复后都重新运行一次 `status`。运行时会在下一次工具调用时重新加载，因此不需要重启任何东西。

## 迁移旧的内联规则

旧的内联配置文件——`~/.cc-safety-net/config.json` 和 `.safety-net.json`——不再在运行时加载，运行时也不会发出与之相关的诊断：**它们的规则根本不会执行**，而其他一切照常工作，快照仍保持 `ready`。这是升级后典型的静默保护缺失：什么都没坏，那些规则却什么也没保护，会话期间也没有任何提示。`cc-safety-net rule verify` 才是标记出仍待迁移旧文件的地方。

在要转换旧配置的那个项目中运行迁移：

```bash
npx -y cc-safety-net rule migrate
```

`rule migrate` 会传递同步结果，因此如果迁移后的范围仍有诊断，它会报告该诊断而不是报告成功。迁移后的文件已经写入，旧文件也会保留，所以你可以修复报告出的问题后再运行一次。它迁移成的 rulebook 布局见[自定义规则](/zh-Hans/configuration/custom-rules)。
