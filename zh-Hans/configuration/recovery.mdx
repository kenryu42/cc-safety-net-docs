---

**Degraded** 表示 CC Safety Net 拒绝了你的部分配置，例如有 JSON 错误的 rulebook，或值不正确的 `policy.json` 字段。它会用能加载的内容继续工作。这组缩减后的配置就是**回退配置**：文件中所有有效的部分、代替被拒绝 `policy.json` 字段的内置默认值，以及全部内置保护。

`doctor` 把这种状态报告为“Runtime is enforcing a fallback configuration”，仪表板横幅显示“A fallback configuration is being enforced”。`doctor` 的诊断项会指出每个被拒绝的文件和字段。按[下面的步骤](#recover-configuration)修复即可。

被拒绝的 rulebook 在修复之前不再阻止任何命令。被拒绝的 `policy.json` 字段会回退到默认值，而默认值通常比你配置的阻止得更多。

<span id="configuration-states"></span>

## 配置状态

| 状态 | 何时发生 | 含义 |
| --- | --- | --- |
| `ready` | 每个生效的来源都完整加载并通过验证 | 完全按照你编写的配置进行常规评估 |
| `degraded` | 任何规则错误、任何规则警告，或任一范围的 `policy.json` 错误 | 常规评估基于回退配置继续进行，每个报告位置都带有一条警告，指出被拒绝的来源 |

一条警告就足以让运行时进入 `degraded`：

- **错误**指出 CC Safety Net 已丢弃的来源。该来源不再提供任何规则。
- **警告**指出仍然生效的来源。CC Safety Net 只忽略被拒绝的那部分。

## 无效配置的行为

无效配置本身绝不会阻止正常工作，CC Safety Net 也绝不会执行被拒绝的那部分。

- 无法验证的规则来源会被 CC Safety Net 丢弃，其规则不再生效。
- 其他每个通过验证的范围继续执行自己的规则。
- 所有内置保护继续生效。破坏性命令规则、机密保护、`policy.json` 保护和 Git 元数据保护都不读取规则配置。
- 无效的 `policy.json` 保留有效字段，其余字段使用内置默认值。参见[逐字段保留的 `policy.json` 或保护性默认值](#policy-json-salvaged-or-replaced-with-protective-defaults)。

Degraded 状态不会额外放行任何东西，也没有恢复模式。读取或编辑 `rule.json`、运行 `cc-safety-net rule update` 都是普通工具调用，因此智能体可以自行修复规则配置。

<Warning>
  丢弃来源并非对安全没有影响。该来源提供的拒绝会随之消失，因此你在被丢弃的 rulebook 中特意阻止的命令，在修复之前又能运行了。不要假定错误中提到的 rulebook 仍在保护你。
</Warning>

原因为“failed closed”的被阻止命令是另一回事：它表示 CC Safety Net 没能完成对那一条命令的分析。参见 [Fail-closed 执行](/zh-Hans/guides/security-model#what-happens-when-analysis-fails)。

## 配置回退矩阵

<span id="errors-the-source-is-dropped"></span>

### 丢弃来源的错误

| 失败 | 不再执行的内容 | 仍然适用的内容 |
| --- | --- | --- |
| 远程来源尚未落盘，因此缺少 `rules/<name>/rulebook.json` | 该 rulebook | 其他所有 rulebook 和全部内置保护 |
| 本地来源的 `rules/<name>/rulebook.json` 缺失或已被删除 | 该 rulebook | 其他所有 rulebook 和全部内置保护 |
| rulebook 文件不是有效的 JSON，或未通过 rulebook schema 校验 | 该 rulebook | 其他所有 rulebook 和全部内置保护 |
| rulebook 的 `name` 与列出它的来源不一致 | 该 rulebook | 其他所有 rulebook 和全部内置保护 |
| `rule.json` 格式错误、为空或 `version` 不受支持 | 整个范围，包括其 `transparent_wrappers` 和 `command_tools` | 另一范围中已验证的规则和全部内置保护 |
| 无法安全读取策略所在的文件系统 | 该范围 | 另一范围中已验证的规则和全部内置保护 |

上述每条消息都会指明它拒绝的文件或来源，以及对应的修复办法。远程来源缺少 rulebook 时，消息以 ``run `cc-safety-net rule update` to vendor <source>`` 结尾；本地来源缺少 rulebook 时，以 `create that file or remove that source from the rules config` 结尾；rulebook 无效和名称不一致都以 `fix that file` 结尾。

<span id="warnings-the-source-stays-active"></span>

### 保留来源的警告

| 失败 | 被忽略的内容 | 仍然执行的内容 |
| --- | --- | --- |
| 两个生效的 rulebook 声明了相同的名称 | 后声明的 rulebook，其规则不生效 | 先声明的一方，解析时用户范围优先 |
| `rule.json` 中有未知的覆盖键 | 仅该条覆盖 | 其他所有覆盖和每条规则都保持已配置的状态 |
| 项目覆盖指向用户范围的规则 | 仅该条覆盖 | 该规则保持用户配置的状态 |

重复名称如何解析，见[范围合并行为](/zh-Hans/configuration/custom-rules#scope-merge-behavior)。

<span id="policy-json-salvaged-or-replaced-with-protective-defaults"></span>

### 逐字段保留的 `policy.json` 或保护性默认值

对于能解析为 JSON 对象的文件，CC Safety Net 会逐字段保留：每个有效字段保持不变，每个无效字段按第二张表回退。其他损坏的用户文件会被替换为保护性默认值，即两项保护都开启、没有覆盖、没有允许路径或拒绝路径的内置默认值。

| 情况 | 结果 | 状态 |
| --- | --- | --- |
| 用户文件不存在 | 内置默认值 | `ready`，没有诊断 |
| 用户文件为空、只含空白字符、不是有效的 JSON，或不是 JSON 对象 | 保护性默认值 | `degraded` |
| 用户文件是对象，但部分字段未通过验证 | 逐字段保留 | `degraded` |
| 项目文件不存在 | 仅用户策略 | `ready`，没有诊断 |
| 项目文件为空、不是有效的 JSON，或不是 JSON 对象 | 仅用户策略 | `degraded` |
| 项目文件是对象，但部分字段未通过验证 | 其有效字段叠加在用户策略之上 | `degraded` |
| 项目文件带有 `audit` 部分 | 使用用户策略的 audit 设置，项目文件的其他字段照常叠加 | `degraded` |
| 用户文件损坏，而项目文件设置了有效字段 | 保护性默认值，其上叠加项目字段 | `degraded` |

| 字段 | 无效时 |
| --- | --- |
| `version` | 视为 `1` |
| `safety.level` | 回退到 `standard` |
| `safety.overrides.*` | 丢弃无效的键，该能力从预设继承 |
| `workflow.worktree_mode` | 回退到 `false` |
| `destructive_command_protection.enabled`、`secret_protection.enabled` | 回退到 `true`，保护开启 |
| `destructive_command_protection.overrides`、`secret_protection.overrides` | 丢弃无效条目，保留有效的 `"on"` 和 `"off"` 条目。非对象变为 `{}` |
| `destructive_command_protection.allow_paths`、`secret_protection.allow_paths` | 丢弃无效条目，保留有效条目。非数组变为 `[]` |
| `secret_protection.deny_paths` | 丢弃无效条目。非数组变为 `[]` |
| `audit.retention_days` | 取 `1` 和 `365` 中较近的一个；不是整数时取 `30` |

运行时从不重写 `policy.json`。请手动修复，或使用[仪表板](/zh-Hans/guides/dashboard)中的修复操作。

<span id="coverage-declared-in-rule-json"></span>

## `rule.json` 中声明的覆盖范围

`transparent_wrappers` 和 `command_tools` 会扩大内置分析的覆盖范围，两者都写在 `rule.json` 中，而不是 rulebook 中。

- Rulebook 被丢弃时，这两个字段仍然保留，因为 `rule.json` 本身仍可读取。
- `rule.json` 无法读取时，该范围会同时失去这两个字段。分析不再穿过该范围声明的包装命令，CC Safety Net 也不再分析它声明的[社区 shell 工具](/zh-Hans/configuration/custom-rules#community-shell-tools)。八个内置包装器（`caffeinate`、`exec`、`nice`、`nohup`、`setsid`、`stdbuf`、`time`、`timeout`）不依赖任何文件，仍然有效，另一范围的声明也照常生效。

只有这种情况下，被拒绝的配置会削弱内置覆盖，而不只是移除你自己的规则。`rule.json` 无法读取导致某个范围被丢弃时，请先修复这个文件。

## degraded 状态的报告方式

| 呈现位置 | 你会看到什么 |
| --- | --- |
| 下一次用户可见的拒绝 | 阻止消息末尾追加的 `Config warning:` 行，带有完整原因 |
| 审计记录 | `configFallback` 字段，允许和拒绝的决策都会设置 |
| `cc-safety-net status` | 判定 `ready` 或 `degraded`，并在 `Not active` 下逐行列出诊断 |
| `cc-safety-net doctor` | 标题为“Runtime is enforcing a fallback configuration”的 `config.runtime-degraded` 警告级诊断项，详情为完整原因 |
| `cc-safety-net rule list` | `Issues` 和 `Warnings` 两个部分，仅涉及规则配置 |
| 状态行 | 快照处于 degraded 期间显示 `⚠️` 标记 |
| 仪表板 | 保护横幅中显示的状态 |

`doctor` 是唯一同时报告规则配置和 `policy.json` 的命令。诊断会指出被拒绝的文件和问题，但从不复制文件内容，因此不会把损坏文件中的机密再次显示出来。

## 可见的失败与静默的失败

- **规则来源被丢弃时没有任何动静。** 它减少的是拒绝，因此会话中不会有任何阻止或警告。每次修改规则配置以及每次升级后，请运行 `cc-safety-net status`。
- **未迁移的旧规则文件更加静默。** CC Safety Net 不加载它，状态保持 `ready`，而其中的规则什么也不保护。`doctor` 会报告 `config.legacy-ignored`。参见[迁移旧配置](/zh-Hans/configuration/custom-rules#migrate-legacy-configuration)。
- **无效的 `policy.json` 字段通常会暴露出来。** 保护会回退到开启状态，因此你会看到比配置的更多的拒绝。
- **有两种 `policy.json` 错误会静默降低保护。** 无效的 `safety.level` 回退到 `standard`，因此把 `paranoid` 拼错会降低你的预设。无效的 `deny_paths` 条目会被丢弃，对应位置不再受保护。
- 只有状态行标记无需你做任何操作就会出现。`Config warning:` 行要依附一次无关的拒绝才会出现，其他呈现位置都要等你运行命令或打开仪表板。

<span id="recover-configuration"></span>

## 恢复配置

即使运行时处于 degraded，智能体也能运行下面的每条命令。选项和退出码见 [CLI 参考](/zh-Hans/reference/cli/overview)。

<Steps>
  <Step title="查看判定">
    ```bash
    npx cc-safety-net status
    ```

    它打印 `ready` 或 `degraded`，并在 `Not active` 下逐行列出诊断。参见 [`status`](/zh-Hans/reference/cli/status)。
  </Step>
  <Step title="获取完整报告">
    ```bash
    npx cc-safety-net doctor
    ```

    它同时涵盖规则配置和 `policy.json`。`config.runtime-degraded` 诊断项会指出每个被拒绝的来源。参见 [`doctor`](/zh-Hans/reference/cli/doctor)。
  </Step>
  <Step title="检查规则配置">
    ```bash
    npx cc-safety-net rule list
    npx cc-safety-net rule verify
    ```

    `rule list` 显示哪些规则正在生效，可以看出被丢弃的来源带走了什么。`rule verify` 按运行时的加载方式检查两个 `rule.json` 文件，有问题时以 `Config validation failed.` 结束。参见 [`rule verify`](/zh-Hans/reference/cli/rule#rule-verify)。
  </Step>
  <Step title="修复来源">
    对于本地 rulebook，编辑诊断中指出的文件。运行时会在下一次工具调用时读取它。

    对于缺失或过期的远程来源，重新落盘：

    ```bash
    npx cc-safety-net rule update
    ```

    加上来源名称可以只更新那一个，加上 `--global` 则操作用户范围。仍有诊断时它会如实报告，而不会声称成功。参见 [`rule update`](/zh-Hans/reference/cli/rule#rule-update)。
  </Step>
  <Step title="自己修复 policy.json">
    智能体无法编辑 `policy.json`。请修正诊断中指出的字段，或使用仪表板中的修复操作。参见[编辑策略文件](/zh-Hans/configuration/policy#edit-the-policy-file)。
  </Step>
</Steps>

每次修复后再运行一次 `status`。运行时会在下一次工具调用时重新加载，无需重启任何东西。
