CC Safety Net 会在每次工具调用时加载策略快照。它读取用户策略文件、叠加在其上的项目策略文件，以及两个范围的 `rule.json`。`rule.json` 列出的每个 rulebook 都是实时文件，在同一次调用中从 `<scope>/rules/<name>/rulebook.json` 读取。加载过程不写入文件、不访问网络，也不缓存结果，因此快照反映磁盘上的当前配置。

快照只有两种状态：**`ready`** 和 **`degraded`**。本页说明两种状态的完整约定，包括配置来源被拒绝后的执行范围，以及恢复到 `ready` 的方法。

## 配置状态

| 状态 | 何时发生 | 含义 |
| --- | --- | --- |
| `ready` | 每个生效的来源都完整加载并通过验证 | 完全按照你编写的配置进行常规评估 |
| `degraded` | 任何规则错误、任何规则警告，或任一范围的 `policy.json` 错误 | 常规评估继续进行，但依据的是回退配置，并且每个报告位置都会带上一条警告，指出被拒绝的来源 |

一条警告就足以让运行时进入 `degraded`。错误与警告的区别在于来源，而不是状态的严重程度：

- **错误**指出某个来源已被**丢弃**。该来源不再提供任何规则。
- **警告**指出某个来源**仍然生效**，只是被拒绝的那部分被忽略。

两者都产生 `degraded`。

<Note>
`ready` 和 `degraded` 是 `cc-safety-net status` 打印的仅有两种判定，判定直接读自快照状态。禁用 Claude Code 插件不会改变判定；`status` 会把它报告为 `Not active` 下的第一项："plugin cc-safety-net@cc-marketplace is disabled in Claude Code; nothing is enforced in Claude Code until it is re-enabled. Other integrations are not affected."
</Note>

## 无效配置的行为

无效配置本身不会阻止普通命令。系统不会执行无效的候选配置，但智能体仍可继续工作。

- 无法验证的规则来源会被**丢弃**，其规则不再执行。
- 其他每个通过验证的范围都会继续执行自己的规则。
- 所有内置保护都会继续生效。破坏性命令规则、机密保护、策略文件保护和 Git 元数据保护不读取自定义规则配置。
- 无法读取的用户 `policy.json` 会回退到**保护性**默认值，因此破坏性命令保护和机密保护都保持开启。无法读取的项目 `policy.json` 不提供任何内容，用户策略照常生效。

`degraded` 状态没有特殊恢复模式或允许列表。配置不可用不会单独导致某项操作被拒绝。读取或编辑 `rule.json`，以及运行 `cc-safety-net rule update`，都是普通工具调用，各自独立判定。因此，智能体可以自行修复配置。

<Warning>
丢弃配置来源会降低保护。该来源的拒绝规则会被**移除**，因此原本被 rulebook 阻止的命令可能再次运行。修复之前，不要假定错误中提到的 rulebook 仍在生效。
</Warning>

在所有状态下始终受保护的是两个范围的 `policy.json`。策略文件保护和 Git 元数据保护在加载配置快照**之前**运行，因此不会受到损坏配置的影响。具体阻止哪些操作见[策略](/zh-Hans/configuration/policy)。

## 配置回退矩阵

### 错误：来源被丢弃

| 失败 | 哪些内容不再执行 | 仍然适用的内容 |
| --- | --- | --- |
| 远程来源尚未落盘，缺少 `rules/<name>/rulebook.json` | 该 rulebook | 其他所有 rulebook 和所有内置保护 |
| 本地来源的 `rules/<name>/rulebook.json` 缺失或已被删除 | 该 rulebook | 其他所有 rulebook 和所有内置保护 |
| rulebook 文件不是有效的 JSON，或未通过 rulebook schema 校验 | 该 rulebook | 其他所有 rulebook 和所有内置保护 |
| rulebook 的 `name` 与列出它的来源不一致 | 该 rulebook | 其他所有 rulebook 和所有内置保护 |
| `rule.json` 格式错误、为空或使用了不受支持的 `version` | 整个范围，**包括其 `transparent_wrappers`** | 另一范围中已验证的规则和所有内置保护 |
| 无法安全读取策略所在的文件系统 | 该范围 | 另一范围中已验证的规则和所有内置保护 |

上述每一条消息都会指明它拒绝的文件或来源，以及对应的修复办法。远程来源缺少 rulebook 时，消息以 ``run `cc-safety-net rule update` to vendor <source>`` 结尾；本地来源缺少 rulebook 时以 `create that file or remove that source from the rules config` 结尾；rulebook 无效和名称不一致这两种情况都以 `fix that file` 结尾。

### 警告：来源仍然生效

| 失败 | 被忽略的内容 | 仍然执行的内容 |
| --- | --- | --- |
| 两个生效的 rulebook 声明了相同的名称 | 后声明的 rulebook，其规则不生效 | 先声明的一方；解析时用户范围优先 |
| `rule.json` 中存在未知的覆盖键 | 仅该条覆盖 | 其他所有覆盖和每条规则都保持已配置的状态 |
| 项目覆盖指向用户范围的规则 | 仅该条覆盖 | 该规则保持用户配置的状态 |

<Note>
每个 rulebook 都是实时文件，保存后的编辑在下一次工具调用即生效，无需任何发布步骤。改坏了也不会毫无提示：无法解析或未通过 schema 校验的文件会被丢弃，并报出上面那条 invalid rulebook 错误；被删除的文件同样被丢弃，报的是 missing rulebook file 错误。两种情况都会让快照进入 `degraded`。
</Note>

重复的 rulebook 名称按固定顺序处理。先声明者生效，而用户范围先加载，因此用户 rulebook 会遮蔽同名的项目 rulebook。后声明的 rulebook 不提供任何规则。名称冲突本身不是致命错误，因此在一个范围内的改动不会因为另一个范围已占用该名称而失败。

### `policy.json`：逐字段保留或替换为保护性默认值

| 情况 | 结果 | 状态 |
| --- | --- | --- |
| 用户文件不存在 | 内置默认值 | `ready`，没有诊断 |
| 用户文件为空或只有空白字符 | 内置保护性默认值 | `degraded` |
| 用户文件不是有效的 JSON | 内置保护性默认值 | `degraded` |
| 用户文件解析结果不是对象 | 内置保护性默认值 | `degraded` |
| 用户文件解析为对象但验证失败 | **逐字段保留**：每个已识别的有效部分继续生效，其余部分使用保护性默认值 | `degraded` |
| 用户文件有效 | 完全按你编写的策略执行 | `ready` |
| 项目文件不存在 | 仅用户策略 | `ready`，没有诊断 |
| 项目文件为空、不是有效的 JSON，或解析结果不是对象 | 仅用户策略。项目文件不提供任何内容 | `degraded` |
| 项目文件解析为对象，但部分字段验证失败 | 逐字段保留：已识别的有效字段仍叠加在用户策略之上，其余部分被丢弃 | `degraded` |
| 项目文件带有 `audit` 部分 | 用户策略的 audit 设置。项目文件的其他字段照常叠加 | `degraded` |
| 用户文件无法读取，而项目文件设置了字段 | 内置保护性默认值，其上叠加项目文件中有效的字段 | `degraded` |

逐字段保留意味着一个无效字段不会连带丢掉文件其余部分配置的保护。保护性默认值刻意偏向更多拒绝：强制开启破坏性命令保护和机密保护，丢弃两个允许路径列表中的无效条目，并丢弃用于关闭规则的覆盖。有效的机密允许路径仍会保留在策略中。`.cc-safety-net/policy.json` 这个项目文件也按同样方式逐字段保留，只有一处不同：`audit` 仅属于用户范围，因此项目文件中的 `audit` 部分会被忽略，并给出诊断 `project policy audit settings are ignored; audit is user scope only`。每个字段的保留行为见[策略](/zh-Hans/configuration/policy)。

运行时永远不会重写 `policy.json`。手动修复，或使用仪表板中的修复操作。

在文件仍有错误期间，仪表板表单显示的是完整默认值，而不是保留下来的值。修复文件之前无法保存。修复操作会保留每个已识别的有效设置；只有在无法解析 JSON 时，它才会用默认值替换整个文件。

## 透明包装器的覆盖缺口

`transparent_wrappers` 声明在 `rule.json` 中，而不是在 rulebook 中，并且 `rule.json` 本身没有 digest。这有两个后果：

- **被丢弃的 rulebook** 仍保留其范围的包装器，因为 `rule.json` 本身仍然可读。
- **无法读取的 `rule.json`** 会丢失该范围的包装器，因为没有经过验证的副本可以回退。分析不再穿透这些包装命令去识别其下受保护的命令。

这是唯一一处被拒绝的配置会削弱内置覆盖，而不只是移除你自己的规则。当某个范围因此被丢弃时，请先修复 `rule.json`。

## Fail-closed 情形

"Fail closed" 描述的是运行时或分析失败。它会拒绝**当次工具调用**，不用于描述无效配置的处理方式。

| 情形 | 行为 |
| --- | --- |
| 分析器或某个依赖在任一防护阶段意外抛出异常 | 在所有模式中，该工具调用都以 "failed closed" 为原因被拒绝 |
| hook 或工具负载格式错误或过大 | 在所有模式中都被拒绝 |
| 命令路由上的空命令或仅含空白字符的命令 | 在所有模式中都被拒绝 |
| 命令超出递归深度限制 | 在所有模式中都被拒绝 |
| 命令结构超出安全验证限制 | 在所有模式中都被拒绝 |
| `fail_closed` 能力开启时命令无法拆分成 token | 被拒绝。见 [strict 模式](/zh-Hans/configuration/modes#strict-mode) |
| worktree 放宽无法明确确认当前位于 linked worktree | 不应用放宽，保留更严格的默认值 |

无效配置正相反：规则来源被丢弃，`policy.json` 逐字段保留或替换为保护性默认值，而工作继续进行。

## `degraded` 状态的报告方式

| 呈现位置 | 你会看到什么 |
| --- | --- |
| 下一次用户可见的拒绝 | 追加在阻止消息后的 `Config warning:` 行，其中带有完整原因 |
| 审计记录 | `configFallback` 标志，在允许和拒绝的决策上同样会设置 |
| `cc-safety-net status` | 判定 `ready` 或 `degraded`，并在 `Not active` 下逐行列出诊断 |
| `cc-safety-net doctor` | 一条标题为 "Runtime is enforcing a fallback configuration" 的 `config.runtime-degraded` 警告项，详情是完整原因 |
| `cc-safety-net rule list` | `Issues` 与 `Warnings` 两个部分，仅涉及规则配置 |
| 状态行 | 快照处于 `degraded` 期间显示 `⚠️` 标记 |
| 仪表板 | 保护横幅中显示的状态 |

`doctor` 是唯一同时报告规则配置和 `policy.json` 的命令。有关每个命令的选项和退出行为，请参阅 [CLI 命令](/zh-Hans/reference/cli-commands)。

有两个结构性限制值得了解：

- `Config warning:` 行和审计 `configFallback` 标志只出现在快照加载**之后**做出的决策上。策略文件和 Git 元数据的拒绝发生在此之前，因此两者都不会带上它们。
- 诊断只**指明**被拒绝的文件和触发条件，绝不会复制其中的字节。恰好位于格式错误配置文件中的机密不会出现在消息里。

## 可见的失败与静默的失败

- **规则来源被丢弃时，会话中可能没有提示。** 它减少的是拒绝，因此普通会话可能没有任何异常。每次修改规则配置或升级后，都应运行 `cc-safety-net status` 检查。需要完整报告时运行 `doctor`。
- **未迁移的旧配置更加静默。** 运行时既不加载该文件，也不报告它，因此即使其中的规则毫无保护作用，快照仍保持 `ready`。用 `rule verify` 才能标记出来。
- **无效的 `policy.json` 大多会自己暴露出来**，因为被拒绝的部分会回退到保护性默认值：两项保护被强制开启，允许路径被丢弃，用于关闭规则的覆盖被丢弃。你会因为出现*比配置更多*的拒绝而发现它。
- **无效 `policy.json` 静默的那一半**：无效的 `safety.level` 会静默回退到 `standard`，因此把 `paranoid` 拼错反而会**降低**你的预设。无效的 `secret_protection.deny_paths` 条目，以及会把规则提到高于默认值的按规则覆盖，都会被丢弃而不是被修复。
- 只有状态行标记是被动呈现的。`Config warning:` 行需要依附一次无关的拒绝才会出现，其他所有呈现位置都要等你运行命令或打开仪表板。

## 恢复配置

以下命令都是普通工具调用。即使运行时处于 `degraded`，智能体也可以执行完整的恢复流程。各命令的选项和退出行为见 [CLI 命令](/zh-Hans/reference/cli-commands)。

<Steps>
<Step title="检查判定结果">
    ```bash
    npx cc-safety-net status
    ```

命令会打印 `ready` 或 `degraded`，并在 `Not active` 下逐行列出诊断。禁用的 Claude Code 插件显示为第一个 `Not active` 项，不会形成单独判定。`status` 只提供信息，适合作为日常检查。
</Step>
<Step title="获取完整报告">
    ```bash
    npx cc-safety-net doctor
    ```

唯一一条同时涵盖规则配置和 `policy.json` 的命令。运行时处于 `degraded` 时会显示为 `config.runtime-degraded` 警告，该检查项的详情就是指明每个被拒绝来源的完整原因。
</Step>
<Step title="查看实际生效的内容">
    ```bash
    npx cc-safety-net rule list
    ```

列出实际生效的内容，之后是 `Issues` 和 `Warnings`。用它确认被丢弃的来源带走了哪些规则。只有在策略存在错误时它才以非零值退出；只有警告时会打印在 `Warnings` 下并以 `0` 退出。
</Step>
<Step title="验证你的规则配置">
    ```bash
    npx cc-safety-net rule verify
    ```

根据 schema 校验用户和项目的 `rule.json`，并重放运行时的加载过程，因此能发现防护在运行时会遇到的同样问题。它还会标记出仍需迁移的旧文件。没有问题时以 `All configs valid.` 或 `Configs valid with warnings.` 结束，有问题时打印 `Config validation failed.` 并以 `1` 退出。有一处写入需要留意。当有效的 `rule.json` 缺少 `$schema` 键时，`rule verify` 会补上一个并打印 `Added $schema to <scope> config.`。除此之外，它不会改动任何内容。
</Step>
<Step title="修复来源">
本地 rulebook 不需要运行任何命令。编辑诊断指出的那个文件，防护会在下一次工具调用时读取它。

远程来源缺失或过期时，重新落盘一次：

    ```bash
    npx cc-safety-net rule update
    ```

重新解析每个已配置的远程来源，把各自的内容写入 `rules/<name>/rulebook.json`，然后完全按照防护的加载方式重新加载该范围。指定某个来源即可只更新它，用户范围加 `--global`。如果仍有诊断，它会报告该诊断并以非零值退出，不会声称成功。`Rule config synced.` 后面跟着 `Active rulebooks (<n>):` 列表，表示该范围没有诊断。

每个来源各自独立更新。失败的来源会打印 `Failed to update <spec>: <message>` 并保留原有副本，其他来源照常更新。验证仅涵盖正在更新的范围。
</Step>
<Step title="手动修复 policy.json">
运行时永远不会重写 `policy.json`。自行更正诊断中指出的字段，或使用仪表板中的修复操作，然后重新运行 `status`。完整 schema 和默认值见[策略](/zh-Hans/configuration/policy)。
</Step>
</Steps>

每次修复后都重新运行一次 `status`。运行时会在下一次工具调用时重新加载，因此不需要重启任何东西。

## 迁移遗留的 lock 与缓存

由早期版本配置过的范围可能仍带有 `rule.lock` 和 `cache` 目录。两者都不再被读取，因此快照保持 `ready`，也不会从中执行任何内容。`cc-safety-net doctor` 会把它们报告为 `info` 级检查项 `config.v2-leftovers`，标题为 `Rulebook lock and cache leftovers detected`，详情是 `Files an earlier version left behind are no longer read: <paths>.`，修复提示为 ``Run `cc-safety-net rule sync` (add `--global` for user scope) to migrate them, then rerun doctor.``

如今 `rule sync` 只做这一件事。它离线运行，开头先打印弃用提示：

```
`cc-safety-net rule sync` is deprecated: rulebooks are live files that need no synchronization. This run only migrates the lock and cache an earlier version left behind.
```

它会把仍与记录 digest 相符的缓存 rulebook 落盘，对无法迁移的来源打印 ``Could not migrate <source> from the v2 cache. Run `cc-safety-net rule update <source>` to vendor it.``，然后删除 lock 和缓存目录。没有可迁移内容时打印 `No v2 lock or cache leftovers found in <dir>; nothing to migrate.` 并以 `0` 退出。如果残留仍在而该范围的 `rule.json` 缺失或无法读取，它会拒绝执行，因为此时只有 lock 还记录着已配置的来源。

## 迁移旧的内联规则

运行时不再加载旧的内联配置文件 `~/.cc-safety-net/config.json` 和 `.safety-net.json`，也不会为它们生成诊断。**其中的规则不会执行**，但其他功能照常工作，快照仍可能保持 `ready`。这会造成升级后的静默保护缺失。`cc-safety-net rule verify` 会标记仍需迁移的旧文件。

在要转换旧配置的那个项目中运行迁移：

```bash
npx -y cc-safety-net rule migrate
```

`rule migrate` 会传递同步结果，因此如果迁移后的范围仍有诊断，它会报告该诊断而不是报告成功。迁移后的文件已经写入，旧文件也会保留，所以你可以修复报告出的问题后再运行一次。它迁移成的 rulebook 布局见[自定义规则](/zh-Hans/configuration/custom-rules)。
