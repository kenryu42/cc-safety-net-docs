欢迎通过 [GitHub issue](https://github.com/kenryu42/cc-safety-net/issues) 提交 bug 报告、功能需求和技术分析。创建拉取请求仅限受邀协作者。本页说明贡献策略、issue 报告规则、开发环境设置以及项目采用的约定。完整指南见源代码仓库中的 [CONTRIBUTING.md](https://github.com/kenryu42/cc-safety-net/blob/main/CONTRIBUTING.md)。

## 提交 issue，而不是拉取请求

只有受邀协作者才能创建拉取请求。希望修复或改进某处时，请在投入时间实现之前，先在 issue 中说明问题。检测规则、配置更改、文档修正和小 bug 修复都从 issue 开始；提案被接受也不等于获得提交拉取请求的许可。

AI 生成的提交内容增加了审查外部贡献所需的工作量。即使补丁看上去合理，仍然需要有人核实问题、理解改动、确认它对项目其余部分的影响，并来回修改。维护者本人也用编码智能体实现修复，因此一份详细的 issue 报告往往比审查并重写一份未经邀请的拉取请求更快解决问题。其中最有用的是复现步骤和技术分析。

CC Safety Net 的范围明确：防止编码智能体意外犯错并造成数据丢失，例如 `rm -rf ~/` 或 `git reset --hard`。它不是通用的安全加固或攻击防护工具。

## 报告 bug

多数 issue 由编码智能体撰写。源代码仓库中的 `AGENTS.md` 要求智能体在提交 issue 前先阅读 `CONTRIBUTING.md`。无论你是智能体还是人，都请遵循以下规则：

- 先搜索现有 issue（`gh issue list --search "<keywords>" --state all`）。如果问题已有人报告，请把新证据补充到那个 issue 里，不要再开一个。
- 一个 issue 只报告一个问题。
- 在最新版本上复现问题。只描述你实际运行过的复现过程；没能运行就直接说明。
- 开头先写问题和证据：你做了什么、预期是什么、实际发生了什么。报告要简短。
- 写上你的 CC Safety Net 版本、操作系统、编码智能体或 CLI 及其版本，以及 CC Safety Net 的安装方式。`npx cc-safety-net doctor --json` 覆盖其中大部分信息，也会显示是否有自定义规则参与。
- 欢迎提供根因分析。请放在证据之后，并在没有测试或跟踪佐证时标注为假设。
- 不要附上补丁或 diff。用文字描述你建议的修复方式。
- 提交前，请让委托你工作的人先审阅这个 issue。

如果是命令判定有误，即破坏性命令被放行或安全命令被阻止，还请提供：

- 完整命令，包括整条命令链，而不只是匹配到的那一段。
- 工作目录和安全级别。
- `npx cc-safety-net explain --cwd <dir> "<command>"` 的输出。
- 对于已经发生的阻止，提供 `npx cc-safety-net logs` 中的条目（`npx cc-safety-net logs --id <id> --json`）。
- 判定本应是什么，以及为什么。

漏掉破坏性命令属于公开 bug，不是漏洞。必须私密报告的少数问题见[安全策略](/zh-Hans/security)。

提交前请删除凭证和 token。日志会脱敏机密，但不会脱敏文件路径。请把私有目录名替换为 `<project>` 和 `~`，同时保留路径结构，使命令仍可复现。

## 提交功能需求

说明你要解决的问题、期望的行为，以及一个能体现用处的具体例子。上述规则同样适用：先搜索、一个 issue 只提一个需求、不要附补丁。

## 设置开发环境

本页余下内容面向受邀协作者，以及任何需要在本地构建的人。

- **Bun 1.4.2**：必需的构建和测试运行时，也是唯一受支持的包管理器（[安装指南](https://bun.sh/docs/installation)）。它已在 `package.json` 的 `packageManager` 字段中固定版本。
- **Node.js 18 或更高版本**：构建产物受支持的运行时。运行已发布的 CLI 或插件不需要 Bun。
- **Claude Code** 或 **OpenCode**：仅当你要在本地加载并测试插件时需要。构建项目或运行测试套件不需要它们。

```bash
git clone https://github.com/kenryu42/cc-safety-net.git
cd cc-safety-net
bun install
bun run build
bun run check
```

`bun run check` 是唯一的质量门。它依次运行 Oxlint、代码注释检查、Oxfmt 格式检查、TypeScript 类型检查、`knip` 死代码检测、`jscpd` 重复检测、带覆盖率统计的测试套件，以及覆盖率阈值检查。完成更改后运行一次即可。`AGENTS.md` 要求把它作为最终检查，并禁止把其中的单项检查当作额外的最终检查来运行。

迭代过程中也可以单独运行这些命令：

```bash
bun run lint          # Lint (Oxlint, type-aware)
bun run lint:comments # Code-comment check
bun run format        # Format (Oxfmt)
bun run typecheck     # TypeScript
bun run knip          # Dead-code detection
bun test              # Full test suite
bun test tests/gate                          # One directory or file
bun test --test-name-pattern "checkout"      # Tests matching a pattern
bun run build         # Build for distribution
```

## 测试本地插件

先构建，再加载本地插件来测试真实的阻止行为：

- **Claude Code**：禁用任何已安装的 safety-net 插件，退出 Claude Code，然后在仓库根目录运行 `claude --plugin-dir .`。
- **OpenCode**：将 `~/.config/opencode/opencode.json` 中的 `plugin[]` 数组指向已构建的 `file://.../cc-safety-net/dist/index.js`，删除 npm `cc-safety-net` 条目以避免冲突，然后重启 OpenCode。运行 `/status`，并确认插件名称显示为 `dist`。

使用只含排除项的无害 pathspec 确认已知阻止行为：`git checkout -- ':(exclude,top)**'` 必须被阻止。如果保护未生效，该 pathspec 也不会选中任何文件。

## 遵循代码约定

| 约定 | 规则 |
| --- | --- |
| 构建/测试运行时 | Bun 1.4.2 |
| 已发布版本的运行时 | Node.js 18+ |
| 包管理器 | 仅使用 bun（`bun install`、`bun run`） |
| 格式化工具/linter | Oxfmt，以及以 type-aware 模式运行的 Oxlint |
| 类型 | 依赖类型推断；仅在导出需要或有助于清晰时才添加显式注解。优先使用 `type \| null`，不要使用 `type \| undefined` |
| 文件命名 | `kebab-case`；`docs/` 中的文件也使用小写 kebab-case |
| 函数/类型命名 | 函数使用 `camelCase`，类型使用 `PascalCase` |
| 常量 | `SCREAMING_SNAKE_CASE`（例如原因常量） |
| 导入 | 包内使用相对导入 |
| 测试 | 放在 `tests/` 中，目录结构镜像 `src/`；绝不与源码并置在 `src/` 中 |
| 构建输出 | 忽略 `dist/`。lefthook 的 pre-commit hook 会重新构建它 |

### 样式指南

- 除非代码确实可组合或可复用，否则将代码保留在一个函数中。
- 避免使用 `try`/`catch`、`any` 类型和 `else` 分支。优先使用提前返回。
- 优先使用函数式数组方法（`flatMap`、`filter`、`map`），不要使用 `for` 循环；对 `filter` 使用类型守卫，以便下游保留类型推断。
- 优先使用 `const`，不要使用 `let`；使用三元表达式或提前返回，不要重新赋值。
- 直接内联只使用一次的值，不要为其命名，并避免不必要的解构。

### 范围纪律

过度工程是本项目最常见的失败模式。只做满足需求的最小更改。任何额外内容都必须对应一种具体故障。每项检查都必须能在实际使用中证伪。在出现第一个真实条目前，不要预先构建 schema、验证器、注册表或测试框架。流程要求应写进文档，不要用代码强制执行。

### Knip

绝不在 `knip.ts` 的 `ignoreIssues` 中添加条目。当 knip 标记未使用的导出时，请修复根本原因：删除或取消导出确实无用的代码；使用 `/** @internal */` JSDoc 注释标记仅用于测试的导出（knip 以 `--production` 模式运行，因此排除测试文件）；从 barrel 文件中删除未使用的名称。

## 受邀协作者提交拉取请求

实现更改前，先在相关 issue 中与维护者就范围达成一致。

1. 从 `main` 创建分支。
2. 遵循 `AGENTS.md` 和上述约定。
3. 涉及行为更改时，先写一个有意义的失败测试，再确认修复让它通过。新规则需要测试，覆盖率至少为 90%。
4. 开发过程中运行范围较小的测试，更改完成后运行 `bun run check`，它必须无错误通过。
5. 在该更改影响到的每个宿主 CLI 中验证相应行为。
6. 除非受支持的 CLI、主要功能或 Quick start 命令发生变化，否则不要改动 `README.md`（见 `AGENTS.md`）；也不要更改 `package.json` 中的版本。
7. 使用 conventional commit 格式的提交信息。
8. 提交拉取请求并关联该 issue，说明问题、改动内容以及你如何验证。

只有维护者处理版本升级和发布。绝不要直接修改 `package.json` 或 `plugin.json` 中的版本。

## 获取开发帮助

- `bunx cc-safety-net doctor` 验证你的环境配置。
- `bunx cc-safety-net explain "<command>"` 逐步显示命令的分析过程。
- 查看源代码仓库中的 `CLAUDE.md` 或 `AGENTS.md`，了解架构和约定；在审查代码前阅读 `REVIEW.md`。
- 查看 `src/gate/analyzer/` 中的现有实现，了解代码写法；查看 `tests/helpers.ts`，了解测试工具。
- 遇到 bug 或有功能需求时，请按上述规则提交 [GitHub issue](https://github.com/kenryu42/cc-safety-net/issues)。
