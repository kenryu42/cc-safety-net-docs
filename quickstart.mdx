This guide gets CC Safety Net installed, verified, and producing a real blocked command in minutes. The steps below are agent-neutral — they are the same whichever of the ten supported agents you use.

<Steps>
  <Step title="Install CC Safety Net for your agent">
    Every integration installs with `cc-safety-net install`, but each agent has its own underlying mechanism (plugin marketplace, extension, config write, or package install). Follow the section for your agent on the **[Installation](/installation)** page, then come back here.

    That page is the single source of truth for install and uninstall commands — this guide avoids duplicating them so the instructions can't drift out of sync.
  </Step>
  <Step title="Check the status">
    Get a one-screen summary of what is currently enforcing:

    ```bash
    npx cc-safety-net status
    ```

    The verdict line reads `ready` when the policy loaded cleanly, or `degraded` when something in your configuration could not be applied. Below it you get the protections that are on, your effective level, how many custom rules are active, and the policy file path. `status` is purely informational and always exits `0`.

    If you use Claude Code, the verdict reads `not enforcing` whenever the `cc-safety-net@cc-marketplace` plugin is not enabled in `~/.claude/settings.json`.
  </Step>
  <Step title="Run doctor">
    Where `status` summarizes your policy, `doctor` verifies the wiring end to end:

    ```bash
    npx cc-safety-net doctor
    ```

    It checks every supported agent at once, so you don't need to tell it which one you use. A clean run prints a green checkmark next to each item — hook integration, a self-test that confirms blocking works (`git reset --hard` and `rm -rf /` blocked; `rm -rf ./node_modules` allowed), custom-rule validation, and more. See the [doctor command reference](/reference/cli-commands#doctor) for the full list of checks.

    If anything fails, the output explains what went wrong and how to fix it.
  </Step>
  <Step title="See a real block">
    With CC Safety Net active, ask your agent to run these two commands and observe the difference:

    ```bash
    # Should be BLOCKED — discards uncommitted changes permanently
    git checkout -- README.md

    # Should be ALLOWED — creates a new branch, no data loss
    git checkout -b test-branch
    ```

    When CC Safety Net blocks the first command, your agent receives a structured block message (see below) and is instructed to ask you for explicit permission before trying anything similar again. The second command runs normally.
  </Step>
  <Step title="Ask why, without running anything">
    If a decision surprises you, `explain` evaluates a command string through the same engine without executing it:

    ```bash
    npx cc-safety-net explain "git checkout -- README.md"
    ```

    It prints the verdict, the rule that matched, and the effective configuration behind it. Use a placeholder command like the one above while you are exploring.

    <Warning>
      An explain trace echoes the command you passed, its parsed tokens, and absolute paths including your home directory. Credential-shaped values are redacted, but paths, hostnames, and project names are not — review the output before pasting it into an issue or a chat.
    </Warning>
  </Step>
</Steps>

## What a block looks like

When CC Safety Net intercepts a destructive command, it returns a message like this to your agent:

<pre className="cc-block-message-output"><code>{`BLOCKED by CC Safety Net

Reason: git checkout -- discards uncommitted changes permanently. Use 'git stash' first.

Command: git checkout -- src/main.py

If this operation is truly needed, ask the user for explicit permission and have them run the command manually.`}</code></pre>

Your agent sees this message instead of executing the command. It will typically explain what happened, suggest a safer alternative, and ask you whether you want to proceed manually.
