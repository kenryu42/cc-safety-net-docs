`explain --json` は、コマンドに対する判定と、解析の各段階を記録したトレースを、1 つの JSON オブジェクトとして返します。スクリプトでは最上位のフィールドから判定を読み取り、詳細が必要なときにトレースをたどります。フラグと終了コードについては [`explain`](/ja/reference/cli/explain) を参照してください。

```bash
npx cc-safety-net explain --json "git checkout -- file.txt"
```

<Warning>
  トレースは、そのまま安全に共有できるとは限りません。先に[トレースを共有する前に](#before-you-share-a-trace)を読んでください。
</Warning>

## ExplainResult

`explain --json` が返す最上位のオブジェクトです。

| フィールド | 型 | 有無 | 説明 |
| --- | --- | --- | --- |
| `result` | `"blocked" \| "allowed"` | 常にある | コマンドの最終結果 |
| `reason` | `string` | ブロック時のみ | ブロックの理由 |
| `segment` | `string` | ブロック時のみ | 判定のきっかけになったセグメント |
| `ruleId` | `string` | ブロック時のみ | ブロックしたルールまたは[固定の拒否](/ja/reference/blocked-commands#fixed-denial-ids)の ID |
| `trace` | `ExplainTrace` | 常にある | 最上位とセグメントごとのステップを持つトレースのコンテナー |
| `customRule` | `object` | カスタムルールまたはルールブックのルールが一致した場合 | `id` と、省略可能な `rulebook`（`name`、`version`）、`source`、`override`（`{ type: "reason", reason }`） |
| `configSource` | `string \| null` | 常にある | 有効な設定の読み込み元になった設定ファイル |
| `configValid` | `boolean` | 常にある | 読み込んだ設定が問題なく検証されたか |
| `effectiveLevel` | `"standard" \| "strict" \| "paranoid" \| "custom"` | 常にある | 環境変数のフラグとオーバーライドを反映した、実際に有効なレベル |
| `selectedPreset` | `"standard" \| "strict" \| "paranoid"` | 常にある | ポリシーで指定したプリセット。既定値は `standard` |
| `safetyPresetScope` | `"user" \| "project" \| "default"` | プロジェクトのポリシーファイルを読み込んだ場合のみ | `selectedPreset` の指定元のスコープ |
| `effectiveCapabilities` | `object` | 常にある | 機能ごとの状態。下記を参照 |
| `destructiveCommandRuleOverrides` | `Record<string, "on" \| "off">` | 常にある。`{}` の場合もある | ポリシーに保存されたルールごとのオーバーライド |
| `ruleActivation` | `object` | 条件付き。下記を参照 | 関連するルールが有効または無効になった経緯 |

`effectiveLevel`、`selectedPreset`、`effectiveCapabilities`、`destructiveCommandRuleOverrides` は、空のコマンドを explain した場合にも含まれます。

### `effectiveCapabilities`

`effectiveCapabilities` は、`fail_closed`、`paranoid_rm`、`paranoid_interpreters` をキーとするレコードです。各値には次のフィールドがあります。

| フィールド | 型 | 説明 |
| --- | --- | --- |
| `enabled` | `boolean` | 機能が有効か |
| `source` | `"preset" \| "capability_override" \| "environment"` | 最終的な状態を決めたもの |
| `sources` | `array` | 状態に影響したすべての入力。優先順位の順 |

各機能で何が変わるかは[モード](/ja/configuration/modes)を参照してください。

### `ruleActivation`

`ruleActivation` は、関連するルールを機能が制御している場合にだけ含まれます。関連するルールとは、一致したルール、またはレベルや機能が有効であれば一致するはずだったルールです。

| フィールド | 型 | 説明 |
| --- | --- | --- |
| `id` | `string` | ルール ID |
| `enabled` | `boolean` | ルールが現在有効か |
| `inheritedEnabled` | `boolean` | 継承だけでルールが有効になるか |
| `changesInherited` | `boolean` | 実際の状態が継承した状態と異なるか |
| `source` | `string` | 状態を決めたもの。`catastrophic`、`master_disabled`、`rule_override`、`preset`、`capability_override`、`environment`、`built_in_default` のいずれか |
| `activationCapability` | `string` | 省略可能。ルールを制御する機能 |
| `override` | `"on" \| "off"` | 省略可能。保存されたルールごとのオーバーライド（ある場合） |

人間向けの出力では、<code>{'Rule activation: <id> \u2014 on|off via <source>'}</code> の 1 行で表示されます。

## `ExplainTrace`

| フィールド | 型 | 説明 |
| --- | --- | --- |
| `steps` | `TraceStep[]` | 最上位のステップ。ほとんどのトレースはグローバルな `parse` ステップで始まる。保護による短絡で終わったトレースには含まれない。 |
| `segments` | `object[]` | セグメントごとのエントリ。それぞれに `index` と専用の `steps` 配列がある |

トレースを記録しても判定は変わりません。非常に長いトレースには上限があり、長いテキストの値は切り詰め、上限を超えたステップは破棄します。

## `TraceStep` の種類

ほかのフィールドを読む前に、`type` で種類を判別してください。

| `type` | 主なフィールド | 出現する場合 |
| --- | --- | --- |
| `parse` | `input`, `segments` | 最初のシェル分割で、入力をトークンのセグメントに分けた |
| `env-strip` | `input`, `envVars`, `output` | セグメントの先頭から環境変数の代入を取り除いた。`envVars` には代入された名前だけが入り、値は含まない。代入のトークンは `input` に残るが、値はマスクされる |
| `leading-tokens-stripped` | `input`, `removed`, `output` | 解析の前に、`env` や `command` などの先頭のトークンを取り除いた |
| `shell-wrapper` | `wrapper`, `innerCommand` | `bash -c` などのシェルラッパーを展開した |
| `interpreter` | `interpreter`, `codeArg`, `paranoidBlocked` | インタープリターのワンライナーを検査した。`paranoidBlocked` は paranoid モードでそのまま拒否したことを示す |
| `busybox` | `subcommand` | busybox 形式のディスパッチをサブコマンドに解決した |
| `transparent-wrapper` | `wrapper`, `output` | 登録済みの透過ラッパーの中を確認した。下記を参照 |
| `recurse` | `reason`, `innerCommand`, `depth` | 再帰的な再解析を始めた |
| `script-file` | `path`, `bytes` | ディスクからシェルスクリプトを読み込んだ。下記を参照 |
| `rule-check` | `rule`, `matched`, `reason?` | 組み込みルールを評価した |
| `worktree-relaxation` | `originalReason`, `gitCwd` | 対象がリンクされたワークツリーなので、Git の破棄コマンドを緩和した |
| `temp-root-relaxation` | `originalReason`, `gitCwd` | 信頼された一時ルート配下の使い捨てリポジトリで git を実行するため、Git のルールを緩和した |
| `tmpdir-check` | `tmpdirValue`, `allowTmpdirVar` | `$TMPDIR` の解決と、その値が変更されているかの検出 |
| `fallback-scan` | `tokensScanned`, `embeddedCommandFound?` | 残りのトークンに対する、危険なテキストのフォールバックスキャン |
| `custom-rules-check` | `rulesChecked`, `matched`, `reason?` | カスタムルールを評価した |
| `cwd-change` | `segment`, `effectiveCwdNowUnknown` | 実効カレントディレクトリが不明になり、以降の分類でカレントディレクトリを基準にできなくなった。`effectiveCwdNowUnknown` は常に `true` で、追跡できた `cd` ではステップを記録しない |
| `dangerous-text` | `token`, `matched`, `reason?` | トークンを危険なテキストのパターンと照合した |
| `strict-unparseable` | `rawCommand`, `reason` | strict モードで、解析できないコマンドをフェイルクローズで拒否した |
| `segment-skipped` | `index`, `reason` | 前のセグメントでコマンドがすでにブロックされたため、セグメントをスキップした |
| `error` | `message`, `partial?` | 解析エラーを捕捉した。`partial` は出力が部分的であることを示す |

`temp-root-relaxation` が適用される条件は、[一時ルートの緩和](/ja/reference/blocked-commands#git-commands-in-a-temp-repository)を参照してください。

### `recurse` の理由

`recurse.reason` は、`shell-wrapper`、`interpreter`、`busybox`、`shell-eval`、`shell-trap`、`shell-stdin`、`shell-heredoc`、`heredoc-file` の 8 つの値のいずれかです。

`heredoc-file` は、同じコマンド内で先に heredoc が書き出したスクリプトを、コマンドが実行したことを示します。[アナライザーが見抜く書き方](/ja/guides/how-it-works#what-the-analyzer-sees-through)を参照してください。

### `script-file` ステップ

`script-file` ステップは、`sh deploy.sh` や `./deploy.sh` のように、アナライザーがディスクからシェルスクリプトを読み込んだときに現れます。`path` はコマンドに書かれたとおりのパス、`bytes` はファイルのサイズです。スクリプト内のコマンドについてはステップが追加されず、スクリプトのテキストを含むフィールドもありません。ツール呼び出しがそのテキストを渡していないためです。[ファイルから実行するスクリプト](/ja/reference/blocked-commands#scripts-run-from-a-file)を参照してください。同じコマンド内の heredoc が書き出したスクリプトの場合は、代わりに理由が `heredoc-file` の `recurse` ステップを記録し、そちらには本文も含まれます。

### `transparent-wrapper` ステップ

`transparent-wrapper` ステップは、[`rule wrapper add`](/ja/reference/cli/rule#rule-wrapper) で登録したコマンドの中を解析が確認したときに現れます。`wrapper` はラッパーの名前、`output` はラップされたコマンドのトークンのリストです。このステップは、ラップされたコマンドの解析の直前に、候補ごとに 1 つずつ記録されます。

## トレースの順序

典型的なトレースは `parse` で始まります。続いて各セグメントに `env-strip` または `leading-tokens-stripped` が現れ、次にラッパーを検出するステップ `shell-wrapper`、`interpreter`、`busybox`、`transparent-wrapper`、その後に `rule-check` または `custom-rules-check` が続きます。入れ子のコマンドは、`depth` を持つ `recurse` ステップとして現れます。判定だけが必要な場合は、トレースをたどらずに、最上位の `result`、`reason`、`segment`、`ruleId` を読んでください。

4 つの保護は、評価器より前に判定を確定させます。ポリシーファイルの保護、`policy apply` の保護、Git メタデータの保護、シークレット保護です。これらのいずれかがコマンドをブロックした場合、トレースには合成された `rule-check` ステップが 1 つだけ入り、`parse` ステップはありません。`ruleId` は `guard.policy-config`、`guard.policy-apply`、`guard.git-metadata`、または一致したシークレットルールの ID です。すべてのトレースが `parse` で始まることを前提にしたスクリプトは、この場合を処理する必要があります。

## トレースを共有する前に

<Warning>
  explain のトレースは、そのまま安全に共有できるものではありません。`parse` ステップは、生のコマンド文字列とパースしたすべてのトークンを記録します。ほかにも生のテキストを含むフィールドがあります。`fallback-scan.tokensScanned`、`dangerous-text.token`、`shell-wrapper.innerCommand`、`interpreter.codeArg`、`recurse.innerCommand`、`script-file.path`、`strict-unparseable.rawCommand`、`transparent-wrapper.output`、`worktree-relaxation.gitCwd`、`temp-root-relaxation.gitCwd`、`cwd-change.segment` です。`configSource` は絶対パスで、通常はホームディレクトリ内を指します。

  マスク処理が取り除くのは、認識できた資格情報の形式だけです。使うのは[監査ログ](/ja/reference/audit-log#secret-redaction)と同じ、範囲を限定したパターンのリストです。ファイルパス、ホスト名、IP アドレス、ユーザー名、プロジェクト名やクライアント名、認識できない形式のシークレットは対象外です。

  トレースを共有する前に、ダミーの資格情報とダミーのパスで問題を再現してください。そのうえで出力を最初から最後まで読み、公開したくないものを削除してください。
</Warning>

たとえば `--token=…` の代入を含むコマンドを explain すると、出力ではそのトークンがマスクされます。しかし、同じコマンドにある `/srv/acme-prod/customer-dump.sql` のようなパスは、コマンドテキスト中のホスト名、IP アドレス、アカウント名とともに、そのまま返されます。

脆弱性レポートに `explain` の出力を含めてかまいません。マスク処理は可能な範囲で行う対策であり、保証ではありません。自分で入力したテキストに含まれる資格情報の形式をマスク処理が見逃した場合、それは脆弱性ではなく、公開の GitHub Issue で報告する通常のバグです。貼り付ける前に、出力全体を確認してください。
