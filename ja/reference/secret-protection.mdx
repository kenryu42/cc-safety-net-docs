シークレット保護は、SSH キー、`.env` ファイル、クラウド資格情報ストア、コーディングエージェントの認証トークンなど、資格情報を含む可能性があるファイルの読み書きをブロックします。コマンド解析の前に動作し、**すべて**の安全レベルに適用されます。構造解析の上限を超える入力は拒否します。

このページでは、すべての組み込みルール ID、一致する対象、既定の状態を示します。パスが保護対象か、どのルール ID が制御するかを確認できます。`secret_protection` スキーマについては、[ポリシー](/ja/configuration/policy#secret-protection)を参照してください。ガードフローについては、[アーキテクチャ](/ja/guides/architecture#the-ordered-guard-stages)を参照してください。コマンド例については、[ブロックされるコマンド](/ja/reference/blocked-commands#sensitive-paths)を参照してください。

登録済みルールは **138 個**あります。大部分は同じ ID パターンを共有する生成ファミリーに属します。そのため、次の表では、すべての ID ではなく ID 形式を使ってファミリーを示します。13 ルールの[コーディング CLI 設定階層](#coding-cli-config-tier-off-by-default)を除くすべてのルールが、既定で on です。

## 動作する場所

機密パスの保護は、コマンド解析の**前**に動作するガードステージです。対応する **コマンド**、**パス**、**検索**（grep／glob）、**patch** の各形式に適用されます。CC Safety Net が認識しないツールについては、コマンドらしき部分の抽出結果と、パスらしき値の両方を検査します。そのツールの任意のテキストをシェルコマンドとして扱うことはありません。

| 形式 | 検査するもの |
| --- | --- |
| `command` | 解析済みコマンドから抽出されたパスの対象。セグメント、パイプ、リダイレクト先、コマンド置換、`VAR=value` 代入値、代入を伴う展開（`${VAR:=path}`、`${VAR=path}`）のフォールバックテキスト、`curl` のアップロードフラグが指すファイル、インタープリターが実行するインラインコードを含む |
| `path` | ツール入力から抽出した、パスらしき値（読み取り・書き込み・編集系ツールの入力） |
| `search`（`grep`、`glob`） | パターンを指定するフラグと区別されたファイルオペランド |
| `patch` | 抽出されたパスに見えるツール値 |
| 不明なツール | コマンド候補の抽出結果**と**パス値の両方 |

CC Safety Net は、パスらしきキーの値をパスとして読み取ります。そのキーの下にある配列に入った文字列も同様です。ダウンロード先を指すキーもパスらしきキーとして扱うため、ツールが書き込むファイルも、読み取るファイルと同じように検査します。`command` 以外のすべての経路では、オブジェクトではなく文字列のまま届いたツール入力を patch のテキストとして扱います。そのため、その patch が対象とするファイルもルールの検査対象になります。

一致した場合は intent `hard_stop` で拒否され、一致したルールの ID が付きます。そのため、[ブロックメッセージ](/ja/guides/how-it-works#what-a-block-looks-like)と[監査ログ](/ja/reference/audit-log)には、どのルールに当たったかが正確に残ります。ブロックされるのは書き込みだけではありません。`cat .env`、`strings id_rsa`、`dd if=.env` も、いずれもブロックされます。

相対パスのオペランドは、コマンドが開始した時点のディレクトリではなく、そこまでに移動した先のディレクトリを基準に解決されます。照合処理はコマンド全体をたどり、シェルと同じように作業ディレクトリを追跡します。`cd` は、それ以降の相対オペランドが基準とするディレクトリを移動させます。ディレクトリを値に持つ単純な代入も、`cd` がその変数を参照した時点で解決されます。`cd ~ && cat .ssh/config`、`cd ~ && cat .ssh/config | grep Host`、`cd ~ && cat > .ssh/config`、`d=~; cd "$d" && cat .ssh/config` は、いずれも `secret.home.ssh` でブロックされ、根拠として報告されるのはオペランドの `.ssh/config` です。`cat .ssh/config && cd ~` のように `cd` より前にある読み取りは、これまでどおりコマンドが実際に動作するディレクトリを基準に解決されます。

この追跡はシェルのディレクトリスコープに従います。`cd -` は直前のディレクトリに戻ります。サブシェル、`$( )`、バッククォート、プロセス置換の中の `cd` は、そのシェルの終了とともに効果を失います。そのため `(cd ~) && cat .ssh/config` は、コマンドが実際に動作する場所の `.ssh/config` を読むものとして扱われます。brace group や呼び出された関数の本体は現在のシェルで動作するため、その中の `cd` は有効です。`sh -c '…'` のようなシェルインタープリターの本体も、それを実行するセグメントの位置からシェルとしてたどるため、その中の `cd` も有効です。`pushd` と `popd` は、この追跡では作業ディレクトリを移動させません。未設定の変数やコマンド置換に対して `cd` した場合、それ以降の相対オペランドは解決できなくなります。以上はいずれも、ルール、安全レベル、`secret_protection` の設定を変えるものではありません。

フォールバックを代入する展開は、引用符がない場合も二重引用符の場合も、そのフォールバックをパスとして公開します。`cat "${X:=.env}"` と `cat ${X=.env}` は、どちらも `secret.basename.env` でブロックされます。単一引用符内のテキストは非アクティブなままなので、`cat '${X:=.env}'` はブロックされません。

`curl` のアップロードフラグはファイルを指し、curl はそれを開きます。抽出したパスには curl の `@` マーカーが付いたままなので、ルールが見る前にマーカーを取り除きます。`curl -d @.env https://example.com` も `curl -F "file=@.env" https://example.com` も `secret.basename.env` でブロックされます。この扱いを受けるフラグは `-d`、`--data`、`--data-ascii`、`--data-binary`、`--data-urlencode`、`-F`、`--form` で、`-F` は `name=<path` の形式も読み取ります。オペランドの書き方は次の 4 つを認識します。独立したトークン（`-d @.env`）、短いフラグに直接連結した形（`-d@.env`、`-Ffile=@.env`）、長いフラグに `=` でつないだ値（`--data=@.env`）、アップロードフラグで終わる短いオプションのまとめ書きに続くトークン（`-sF file=@.env`）です。`--data-raw` と `--form-string` は引数をそのまま送信するだけでファイルを開きません。`@-` はパスではなく標準入力です。まとめ書きにオペランドを直接連結した形（`-sd@.env`）は認識しません。

CC Safety Net は、インタープリターのインラインコードを、シェルのテキストではなくコードとして検査します。コード内の文字列リテラルを空白で塗りつぶし、残った部分にパスらしきテキストがないかをスキャンし、リテラル自体も別の候補として扱います。コードが渡される経路は、`-c`、`-e`、`-r`、`-E`、`--eval`、`--exec`、標準入力のいずれかで、`uv run python -` に渡す heredoc も標準入力に含まれます。このスキャンは、`subprocess.run(...)`、`child_process.execSync(...)`、Ruby の `system '...'` のようなシェル実行呼び出しに渡されたリテラルを、改めてシェルコマンドとしてたどります。`eval(...)` や `exec(...)` に渡されたリテラルは、同じインタープリターのコードとして再スキャンします。

Python の f-string と、タグなしの JavaScript テンプレートは、全体を 1 つのリテラルとして扱います。中の `{…}` や `${…}` のプレースホルダーはコードとしてスキャンするため、`print(f"{open('.env').read()}")` のようにプレースホルダーの中で読み取っていれば、引き続きブロックされます。リテラル自体のテキストでは、各プレースホルダーは空の `{}` または `${}` として残ります。

リテラルの区切りを判別できないコードでは、代わりに引用符で囲まれたトークンとパスらしきトークンがすべて候補として残ります。これはどのモードでも同じです。該当するのは、`osascript`、JavaScript のタグ付きテンプレート、閉じられていない f-string やテンプレートのプレースホルダー、文字列の外に `#`（Python）または `/`（JavaScript）を含むプレースホルダー、補間を含む Ruby、Perl、PHP の二重引用符文字列、そして 1 行内で閉じられていないリテラルです。

どのリテラルがパスの候補になるかはモードによって変わります。[strict モード](/ja/configuration/modes#strict-mode)はすべてのリテラルを候補として残し、リテラルの外のコードもスキャンし、さらにリテラルの中身にもパスらしき語がないかを調べます。standard モードはこの 3 つをいずれも絞り込みます。詳しくは [standard モードでのインタープリターのリテラル](#interpreter-literals-in-standard-mode)を参照してください。設定した deny path は、standard モードのどの絞り込みの対象にもなりません。deny path に一致するリテラルは、どちらのモードでも `secret.deny-path` でブロックされます。

組み込みの照合では、リモートの URL、検索用の正規表現、機密そうな文字列で始まるだけの文章を、ローカルのパスとは見なしません。`file:` の URL はローカルとして扱われ、引き続き保護対象です。空白を含むファイル名も、そのパスがディスク上に存在すれば保護対象になります。また、CC Safety Net の `explain` の呼び出しだと認識できた場合、その説明対象のコマンドはデータとして扱われ、ファイルのオペランドとは見なされません。

### gh と git のテキストフラグ

`gh` と `git` の一部のフラグは、検索テキスト、タイトル、メッセージ、フィルターを受け取るもので、ファイル名を受け取りません。これらの値はパス候補から外れます。同じ行のそれ以外のオペランドは、引き続きパスとして検査されます。

`gh` のテキストフラグは `--search`、`-S`、`--title`、`-t`、`--body`、`-b`、`--jq`、`-q` です。値は独立したトークンでも `=` でつないだ形でもよく、`gh issue list --search credentials` も `gh issue list --search=credentials` も実行できます。それ以外のオペランドは候補のままなので、`gh gist create credentials`、`gh pr create --body-file credentials`、`gh api --input credentials` は引き続きブロックされます。

`git` で `-m` と `--message` がテキストとして扱われるのは、`-m` がメッセージを取るサブコマンド、つまり `commit`、`merge`、`notes`、`stash`、`tag` の場合だけです。`git commit -m credentials` は実行できます。`git checkout -m credentials` と `git log -m credentials` は `-m` の意味が異なるため、引き続きブロックされます。`--grep` はどのサブコマンドでもテキストとして扱われます。末尾が `m` で、その前の文字がいずれも値を取らない短いフラグのまとめ書きは `-m` として読み取るため、`git commit -am credentials` と `git commit -nm credentials` も実行できます。`m` の前に置ける文字は `a`、`e`、`i`、`n`、`o`、`p`、`q`、`s`、`v` です。`-F` はこれに含まれません。`git commit -F` はファイルからメッセージを読むため、`git commit -Fm credentials` は引き続きブロックされます。

`--` より後のトークンはすべて再びオペランドとして扱われ、パスとして検査されます。

<span id="what-standard-mode-does-not-count-as-a-read"></span>

### standard モードが読み取りと見なさないもの

入力がコマンドの場合、[standard モード](/ja/configuration/modes)は組み込みの機密パスについて、名前が出てくるだけのものではなく実際の読み取りを検出します。次に挙げる形は読み取りとは見なされません。ただし、設定済みの deny path はどの形でも緩和されません。

**作成・書き込みの対象や、言及にすぎないファイル名。** 次の形で緩和されるのは組み込みのファイル名ルールだけです。[ホームディレクトリルール](#home-directory-rules)と[コーディング CLI ルール](#coding-cli-credential-tier-on-by-default)は緩和されません。

- ディスク上に**ディレクトリ**として存在するシークレットのファイル名。
- 空白を含む語のうち、パスらしい文字（`~`、`.`、`/`、ドライブレター）で始まらず、ディスク上にも存在しないもの。diff のヘッダーや、ファイル名に触れただけの文章などです。`$` の展開を含む語は引き続き検査されます。
- シークレットと同じ名前のファイルが存在しない場所に、そのファイルを**新規作成**する出力リダイレクト。`.env` がないディレクトリでの `printf token > .env` などです。`$` を含む対象は引き続き検査されます。
- `mkdir` または `touch` のオペランド。`$` の展開を含むものも対象なので、`mkdir -p fx/credentials && touch fx/.env` は実行できます。`-r` または `--reference` を指定した `touch` では、すべてのオペランドが引き続き検査されます。同じコマンドにあるリダイレクトは、あくまでリダイレクトとして判定されます。
- `tailscale cert` の `--cert-file` または `--key-file` の値。このコマンドが書き込むファイルを指す値です。`sudo` や `env` の後ろにある場合や、`timeout <n> tailscale cert` の形でも対象になります。
- `openssl x509 -in` の入力ファイル。`x509` は、ファイルの中身にかかわらず証明書のデータしか出力しないためです。`rsa`、`pkey`、`pkcs12` など、ほかの `openssl` サブコマンドの入力は引き続き検査されます。`-signkey` など、`x509` のほかのファイルオプションも同様です。

`tailscale cert` は書き込んだファイル名を出力し、`openssl x509` は入力の読み込みに失敗するとそのファイル名を表示します。そのため、どちらかの出力がパイプ、コプロセス、出力のキャプチャーに届きうる場合は、そのファイルも検査の対象に戻ります。例外は、行内のコマンドがすべて `cd`、`grep`、`head`、`tail`、`openssl`、`tailscale` のいずれかで（前に `timeout <n>` があってもかまいません）、コマンド置換もプロセス置換も含まない場合です。そのため `timeout 60 tailscale cert --cert-file crt.pem --key-file key.pem host 2>&1 | grep -v Warning | tail -5` は実行でき、`tailscale cert --key-file key.pem host | xargs cat` はブロックされます。出力をパイプに渡す `mkdir` や `touch`、またはプロセス置換を含むコマンド内の `mkdir` や `touch` は緩和されません。

**ループのリストにある語。** standard モードでは、`for` のリストにある語は、ループ変数がほかの検査対象の語に届かなければ、どの組み込みルールでも検査しません。`for t in .env.local; do grep -c -- "$t" notes.md; done` は、`$t` が `grep` のパターンとして使われるだけなので実行できます。次のいずれかに当てはまる場合、リストの語は引き続き検査されます。

- 変数そのもの、`${!` による間接参照、または変数名と同じ語（nameref）が、ほかの検査対象の語に現れる。読み取りコマンドのオペランド、リダイレクト先、代入値、インタープリターのインラインコード、入れ子になったループのリストなどです。
- ループ自体、または変数を参照するセグメントがパイプより前にある。
- コマンドにプロセス置換またはコプロセスが含まれる。

そのため `for f in .env; do cat "$f"; done` も `for f in .env; do echo $f; done | xargs cat` もブロックされます。ループがファイルに書き出した名前を後のコマンドが読み戻す場合や、`printf -v` で名前を別の変数にコピーする場合は追跡しません。この扱いは、ループを使わない同じコマンドと同じです。

`do`、`then`、`elif`、`else`、`if`、`while`、`until`、`!` の後ろにあるコマンドは、コマンドの先頭にある場合と同じように判定します。そのため `if true; then echo .env; fi` は実行できます。

**メタデータのみの参照。** standard モードは、保護対象パスに対するメタデータのみの参照も、すべての組み込みルールについて許可します。この許可は、単独のコマンドだけでなく、複合コマンドの 1 つのセグメントにも適用されます。許可される形は次のとおりです。

- `ls` と `stat`
- `test -e FILE`、`test -f FILE`、`[ -e FILE ]`、`[ -f FILE ]`
- `git check-ignore`
- `-delete`、`-files0-from`、`-exec`、`-execdir`、`-fls`、`-fprint`、`-fprint0`、`-fprintf`、`-ok`、`-okdir` のいずれも伴わない `find`
- オプションが `-l`、`-w`、`-c`、`-m`、`--lines`、`--words`、`--bytes`、`--chars` だけの `wc`（`wc -l .env` など）
- `-l`、`-c`、`-q`、`--files-with-matches`、`--files-without-match`、`--count`、`--quiet`、または `grep` に限り `-L` によって、出力をファイル名、件数、終了ステータスだけに絞った `grep` または `rg`（`grep -l KEY .env` など）

`find -files0-from FILE` は FILE を読むため、FILE はどのモードでもパス候補になり、メタデータのみの参照として扱われることはありません。

`-f` や `--file` のパターンファイル、`rg --pre` のプリプロセッサー、`--json` や `--format` のオプションを伴う `grep` と `rg` は、この形にあたりません。ほかのオプションの値として消費される `-l`、`-L`、`-c`、`-q` は数えないため、`grep -e -l .env` はブロックされます。`grep` では、このフラグを最初のオペランドより前に置いた場合だけ数えます。引数を並べ替えない `grep` は、後ろにある `-l` をファイル名として読むためです。したがって `grep KEY -l .env` はブロックされます。`rg -L` はシンボリックリンクをたどって一致した行を出力するため、これも対象外です。

`wc`、`grep`、`rg` による参照でも、出力が次のいずれかを通じて読み取るコマンドに届きうる場合は検査されます。

- コマンド内の後ろにあるパイプ。外側のサブシェル、brace group、条件分岐、ループ、呼び出された関数の後ろにあるパイプも含みます
- シェルとして読まれる heredoc を含むコマンド内のパイプ（位置を問いません）
- コマンド置換、プロセス置換、インタープリターの実行呼び出し
- コプロセス（`coproc` または `|&`）

出力は右へ流れるだけなので、前にあるパイプは関係ありません。`cat a | head -60; wc -l .env` は実行でき、`wc -l .env; cat a | head` と `grep -l KEY .env | xargs cat` はブロックされます。

[strict モード](/ja/configuration/modes#strict-mode)では、以上のいずれも適用されません。上記の形はすべて読み取りのままで、メタデータのみの探索もブロックされます。

<span id="interpreter-literals-in-standard-mode"></span>

### standard モードでのインタープリターのリテラル

standard モードでインタープリターのコード内の文字列リテラルをどう扱うかは、まず、ファイルシステム操作、コマンド実行、eval の痕跡（`fs`、`subprocess`、`open` の呼び出し、`readFile` のような識別子）がコードにあるかどうかで決まります。

- コードのどこにも痕跡がなければ、リテラルはすべてデータです。`python -c "x = '.env'"` は許可されます。
- Python または JavaScript のコード（`python` と `python3` などのバージョン付きの名前、`node`、`bun`、`deno`）に痕跡があれば、各リテラルを位置によって判定します。判定方法は以下のとおりです。
- それ以外のインタープリターのコードに痕跡があれば、リテラルはすべて候補として残ります。

Python と JavaScript では、次の位置にあるリテラルはデータとして扱います。

- リスト、セット、タプルの要素
- 辞書のキーや値、オブジェクトのプロパティ値
- `d['.env']` のような添字のキー
- `in`、`not in`、`==`、`!=` のオペランド（JavaScript の `===` と `!==` も含む）

それ以外の位置、たとえば関数呼び出しの引数、代入される値、戻り値にあるリテラルは候補として残ります。`python3 -c "import json; print(json.load(open('map.json'))['.env'])"` は、`'.env'` が添字のキーなので実行できます。`python -c "open('.env')"` は、`'.env'` が呼び出しの引数なので `secret.basename.env` でブロックされます。カンマを含まない括弧はタプルではなくグループ化にすぎないため、`p = ('.env')` のリテラルは候補として残ります。

コマンド実行の関数やモジュールの名前がコードに出てくる場合は、角括弧や丸括弧の中のリテラルは候補として残ります。argv を組み立てている可能性があるためです。リストやタプルの要素、添字のキーがこれにあたり、セットの要素、辞書の項目、比較のオペランドはデータのままです。コマンド実行の名前と見なすのは、識別子またはその camelCase や snake_case の一部が `exec` か `spawn` で始まる場合と、`popen`、`system`、`subprocess` のいずれかである場合です（`execFileSync`、`posix_spawnp` など）。

コードに次のいずれかが含まれる場合は位置を判定せず、リテラルはすべて候補として残ります。

- `/*` のコメント、または括弧を含む行コメント（Python は `#`、JavaScript は `//`）
- 開き括弧の前にある `*` や `...`。アンパックやスプレッド（`*(`、`*[`、`...[`）などです
- `.of(` や `.if(` のように、キーワードと同じ名前のメソッド呼び出し

書き込みで新しく作るファイルの名前を指すだけのリテラルは、出力リダイレクトと同じように扱います。つまり、その名前のファイルが存在しない場合にだけ緩和されます。対象となる書き込みは次のとおりです。

- `Path(...)` または `pathlib.Path(...)` の引数で、呼び出し内でそれより前に文字列リテラルがなく、呼び出しの直後に `.write_text(` または `.write_bytes(` が続くもの
- 修飾なしの `open(` の第 1 引数で、モードが `w`、`x`、`a` のいずれかを含み、`r` も `+` も含まないリテラルであるもの
- `writeFile`、`writeFileSync`、`appendFile`、`appendFileSync`、`Bun.write` の第 1 引数

`python3 -c "open('.env.local', 'w').write('A=1')"` は、`.env.local` が存在しない場所では実行できます。既定の読み取りモード、`r+`、`a+` で開く `open`、モードを名前で渡す `open` は引き続きブロックされます。`Path('fixtures', '.env.test')` のようにリテラルのディレクトリの下に連結したパスも同様です。同じ名前をコード内のほかの場所で、データの位置以外に使っていれば候補として残るため、書き込んだファイルを読み戻すコードもブロックされます。

データの位置と書き込みの位置で緩和されるのは、`.env`、`*.pem`、`credentials` といった組み込みのファイル名ルールだけです。[ホームディレクトリ](#home-directory-rules)や[コーディング CLI](#coding-cli-credential-tier-on-by-default) のパスは、どの位置にあっても候補として残ります。実行呼び出しが受け取るリテラルも同様です。standard モードは、データのリテラルを後の読み取りまで追跡しません。そのため `python3 -c "for f in {'.env'}: print(open(f).read())"` は、`'.env'` がセットの要素なので許可されます。

Python と JavaScript のコードでは、standard モードは文字列リテラルの外にある語もスキャンしません。そのため、JavaScript のプロパティアクセス `x.key` や、`.env` に触れた Python のコメントはパスと見なされません。ほかのインタープリターのコードは、リテラルの外も引き続きスキャンします。

standard モードがリテラルをシェルのテキストとしてたどるのは、実行呼び出しがそのリテラルを受け取れる場合だけです。つまり、リテラルがその呼び出しの括弧の中にあるか、括弧のない `system`、`exec`、`spawn`、`popen` の直後にある必要があります。呼び出しの第 1 引数が名前であるか名前を含む場合は、コードが何を渡すか分からないため、コード内のすべてのリテラルをたどります。ドットの前後や括弧の前に空白があっても呼び出しとして認識するため、`child_process . execSync ('cat .env')` も対象です。

ただし、第 1 引数がリストまたはタプルの場合は例外です。次の条件をすべて満たせば、たどるのは呼び出し内のリテラルだけです。単純なリテラルと名前だけからなり、それ単独で引数になっていて、先頭の要素がプログラム名のリテラルであり、シェルやインタープリターの名前（`cmd`、`powershell`、`pwsh` を含む）や `-c`、`-e`、`-r`、`-E`、`--eval`、`--exec` のフラグを要素に含まないことです。`subprocess.run(['ffprobe', '-v', 'error', f])` がたどるのは呼び出し内のリテラルだけですが、`subprocess.run(['sh', '-c', cmd])` と `subprocess.run(['nice', cmd] + extra)` はコード内のすべてのリテラルをたどります。`['watch', cmd]` や `['ssh', host, cmd]` のように、別の引数をコマンドラインとして実行するプログラムについては、`cmd` の中身まで追跡しません。シェルコマンドの `watch` や `ssh` と同じ扱いです。

[strict モード](/ja/configuration/modes#strict-mode)では、以上のいずれも適用されません。リテラルは位置にかかわらずすべて候補として残り、どのインタープリターでもリテラルの外のコードをスキャンします。コードに実行呼び出しがあればすべてのリテラルをシェルのテキストとしてたどり、リテラルの中身にもパスらしき語がないかを調べます。

## 一致順序

各候補パスには、次の検査が順に適用されます。最初の確定した結果が優先されます。除外は、それより後にあるルールにのみ適用されます。

1. **設定済みの [deny path](/ja/configuration/policy#deny-paths)**：すべての組み込みルールおよびすべての除外より前に検査します。一致すると `secret.deny-path` に帰属します。
2. **[ホームディレクトリルール](#home-directory-rules)**：`~/.ssh` など、保護対象のディレクトリ全体。env テンプレートと公開鍵の除外より優先されるため、secret allow path の対象でない `~/.ssh/.env.example` と `~/.ssh/id_rsa.pub` はブロックされます。
3. **env テンプレートの除外**：テンプレートのベース名は読み取り可能なままです。[除外](#exemptions)を参照してください。
4. **[コーディング CLI ルール](#coding-cli-credential-tier-on-by-default)**：エージェントごとの資格情報パスと設定パス。
5. **公開鍵の除外**：`id_rsa.pub`、`id_ed25519.pub`、`id_ecdsa.pub` は、保護対象ディレクトリの外ではシークレットではありません。
6. **[ベース名ルール](#basename-rules)**、次に **`.env.*` パターン**、次に **[キーバリエーションルール](#key-variant-rules)**。
7. **ベンダー管理ディレクトリの除外**：残り 2 つのファミリーだけを抑制します。[除外](#exemptions)を参照してください。
8. **広範な SSH ベース名パターン**、次に **[URL のクエリ文字列](#url-query-text)**のスキップ、次に **[拡張子ルール](#extension-rules)**。

組み込みルールに一致した場合でも、設定済みの [secret allow path](/ja/configuration/policy#secret-allow-paths) があれば、その一致は抑制されます。ただし、ルール ID が `secret.cli.` で始まるものは対象外です。deny path はステップ 1 の時点ですでに優先されており、Coding CLI のルールが緩和されることはありません。

<span id="basename-rules"></span>

## ベース名ルール

9 個のルールが、すべてのディレクトリで指定したベース名と完全に一致するファイルをブロックします。

| ルール ID | ベース名 |
| --- | --- |
| `secret.basename.env` | `.env` |
| `secret.basename.npmrc` | `.npmrc` |
| `secret.basename.pypirc` | `.pypirc` |
| `secret.basename.netrc` | `.netrc` |
| `secret.basename.git-credentials` | `.git-credentials` |
| `secret.basename.id-rsa` | `id_rsa` |
| `secret.basename.id-ed25519` | `id_ed25519` |
| `secret.basename.id-ecdsa` | `id_ecdsa` |
| `secret.basename.credentials` | `credentials` |

知っておく必要がある境界が 2 つあります。

- `secret.basename.credentials` は `credentials` という名前だけに一致します。`credentials.json` は、このルールにもほかの組み込みルールにも一致しません。
- `id_dsa` のベース名ルールはありません。正確な `id_dsa` は、後述する広範なパターン `secret.pattern.ssh-key-basename` によって引き続きブロックされます。

1 つのパターンルールが `.env` ファミリーを拡張します。`secret.pattern.env-variant` は、[除外テンプレート](#exemptions)を除き、`.env.local`、`.env.production`、`.env.template.local` など、`.env.` で始まるすべてのベース名をブロックします。

<span id="home-directory-rules"></span>

## ホームディレクトリルール

これらのルールは、ホームディレクトリの下にある場所を保護します。ディレクトリ自体と、その内部すべてが対象です。

比較の対象は、ホームディレクトリからの相対パスの表記そのものと、ファイルシステム上で解決したパスの両方です。`~/.ssh` や `~/.aws` のような資格情報のディレクトリは、シンボリックリンクであっても保護され、表記の比較を行う前に `..` の部分を解決します。

| ルール ID | 保護するもの |
| --- | --- |
| `secret.home.ssh` | `~/.ssh` |
| `secret.home.aws` | `~/.aws` |
| `secret.home.gcp` | `~/.gcp` |
| `secret.home.gcloud-config` | `~/.config/gcloud` |
| `secret.home.kube-config` | `~/.kube/config` |
| `secret.home.docker-config` | `~/.docker/config.json` |
| `secret.home.gh-hosts` | `~/.config/gh/hosts.yml` |

単一ファイルを対象とする 2 つのルール（`kube-config`、`docker-config`）には、それぞれ名前を変えたバックアップを対象とする関連ルールが 8 個ずつあります。ID の形式は `secret.home.<slug>.<suffix>` で、末尾は `bak`、`backup`、`copy`、`disabled`、`old`、`orig`、`save`、`tmp` のいずれかです。そのため、`~/.kube/config.bak` は `secret.home.kube-config.bak` で、`~/.docker/config.json.old` は `secret.home.docker-config.old` でブロックされます。生成されるルールは 16 個で、この分類全体では 23 個になります。

<span id="key-variant-rules"></span>

## キーバリエーションルール

名前を変更して保護を回避しようとするキーおよび資格情報ファイルのコピーには、独自のファミリーがあります。`id_rsa`、`id_dsa`、`id_ed25519`、`id_ecdsa`、`credentials` の 5 つの保護接頭辞から作られます。各 ID の slug は、接頭辞のアンダースコアをダッシュにしたものです（`id-rsa`、`credentials` など）。

- **区切り文字のバリエーション**：`secret.variant.<slug>.separator`（5 ルール）。接頭辞の後に `-` または `_` と任意の文字が続くものをブロックします。例は `id_rsa-old`、`id_rsa_backup`、`credentials_prod` です。
- **ドット付きの拡張子の派生形**：`secret.variant.<slug>.<suffix>`（50 ルール）。接頭辞の後ろに `.bak`、`.backup`、`.copy`、`.disabled`、`.key`、`.old`、`.orig`、`.pem`、`.save`、`.tmp` のちょうど 10 種類のいずれかが続くものをブロックします。そのため、`id_rsa.bak` は `secret.variant.id-rsa.bak` で、`credentials.pem` は `secret.variant.credentials.pem` でブロックされます。

この分類は意図的に厳密に定義してあるため、似た名前は許可されます。`id_rsafoo` は区切り文字が一致せず、`credentials.json` は一覧にない拡張子だからです。

1 つの広範なパターンがファミリーを完成させます。`secret.pattern.ssh-key-basename` は、`_rsa`、`_dsa`、`_ed25519`、`_ecdsa` で終わる、**拡張子がない**すべてのベース名をブロックします。例は `deploy_key_rsa` と `github_ed25519` です。ドットを含む名前は一致しません。

<span id="extension-rules"></span>

## 拡張子ルール

ID 形式 `secret.ext.<extension>` を持つ 21 個のルールは、次の拡張子を持つすべてのファイルをブロックします。

`.agilekeychain`, `.asc`, `.bek`, `.cscfg`, `.fve`, `.gnucash`, `.jks`, `.keychain`, `.kwallet`, `.mdf`, `.ovpn`, `.p12`, `.pcap`, `.pem`, `.pfx`, `.pkcs12`, `.psafe3`, `.rdp`, `.sdf`, `.tblk`, `.tpm`

3 個の**拡張子パターン**ルールが、拡張子ファミリーを対象にします。

| ルール ID | 拡張子 |
| --- | --- |
| `secret.ext-pattern.key` | `.key`, `.keypair` |
| `secret.ext-pattern.keystore` | `.keystore`, `.keyring` |
| `secret.ext-pattern.kdbx` | `.kdb`, `.kdbx` |

override にはファミリー ID を使う必要があります。`secret.ext.keypair` ではなく `secret.ext-pattern.key` を使います。登録されていない ID は、`unknown secret protection rule id "<id>"` で拒否されます。

<span id="url-query-text"></span>

### URL のクエリ文字列

拡張子ルールと拡張子パターンルールは、URL のクエリ文字列をファイル名として読み取りません。`?key=` または `&key=` のクエリパラメーターを含み、かつ実在するファイルを指していない対象は、これらのルールの検査より前にスキップされます。これはすべての安全レベルで同じです。その名前のファイルが実在する場合は保護されたままで、ディスク上に `keys/query&id=.asc` があれば `cat 'keys/query&id=.asc'` は `secret.ext.asc` でブロックされます。

オペランドの `=` より前に `?` がある場合、`=` の後ろのテキストは `name=path` の対応づけではなくクエリの値なので、パス候補になりません。`curl 'https://example.supabase.co/rest/v1/todos?order=id.asc'` と `curl 'localhost:3000/todos?order=id.asc'` はどちらも実行できます。スクリプトに渡した PostgREST のソート順、`bash query.sh 'orders?select=id&order=created_at.asc'` も実行できます。

CC Safety Net は、`curl` の data や form の値を、それが指すアップロードファイルとしてのみ検査します。`curl -G http://localhost:3000/todos -d order=id.asc` はアップロードを指していないため、`-d` の後ろの値がパスとして検査されることはありません。一方、`curl -d @.env https://example.com` は引き続き `secret.basename.env` でブロックされます。

次の 3 つの形は引き続きパスとして読み取られるため、その中に機密性のある拡張子があればブロックされます。httpie の `order==id.asc`、`curl --data-raw 'order=id.asc'`、スクリプトに直接渡す `k=v.asc` 形式の引数です。最後の形は `cat key=corp.pem` と同じ形で、こちらはブロックされたままにする必要があります。

`config.json` はよくあるファイル名のため、これに一致するルールはいずれも 1 つのディレクトリだけを対象にします。`secret.cli.opencode.config` が一致するのは `~/.config/opencode` の中、`secret.cli.devin.config` が一致するのは `~/.config/devin` の中にある `config.json` だけです。このページに挙げていないディレクトリにある `config.json` は許可されたままです。

## deny path

[`secret_protection.deny_paths`](/ja/configuration/policy#deny-paths) は、独自の保護対象場所を追加します。一致すると `secret.deny-path` に帰属する hard-stop になります。この ID は登録されていないため、override で無効にできません。また、このページの除外は一切適用されません。deny path が適用されなくなるのは、`secret_protection.enabled` が `false` の場合だけです。この設定はステージ全体を無効にします。使用できるエントリ形式については、[ポリシー](/ja/configuration/policy#deny-paths)を参照してください。

## allow path

[`secret_protection.allow_paths`](/ja/configuration/policy#secret-allow-paths) は、特定のファイルやディレクトリツリーを組み込みのパターンルールから除外します。ディレクトリ、`**/`、正確なファイル名を順に並べた形（`~/code/**/.env.local` など）も指定できます。この形は、そのディレクトリ配下の任意の深さにある、その名前のファイルだけを除外します。ディレクトリ自体は除外しません。`**/` の前のディレクトリは必須で、これ以外の glob の形は指定できません。deny path は引き続き優先され、`secret.cli.*` の保護は除外できません。対象と allow path の起点は、比較の前に既存のシンボリックリンクを解決します。一方、実際にホームディレクトリを含むことになる起点は拒否され、実効的な CC Safety Net の設定ルート配下の対象は保護されたままです。検証ルールの一覧は[ポリシー](/ja/configuration/policy#secret-allow-paths)を参照してください。

<span id="exemptions"></span>

## 除外

3 つの除外が、上記ルールの境界を定めます。設定済みの deny path を緩和するものはありません。

- **env テンプレート。** 正確なベース名 `.env.example`、`.env.sample`、`.env.template`、`.env.tpl`、`.env.defaults` と、`.env.example.` または `.env.sample.` で始まるすべての名前は、組み込みルールのうち、先に検査されるホームディレクトリルール以外のすべてから除外されます。`cat .env.tpl` は許可され、`cat ~/.ssh/.env.tpl` は `secret.home.ssh` でブロックされます。接頭辞形式はそれ以上拡張されません。`.env.template.local` は、ほかの `.env.*` 名と同様に `secret.pattern.env-variant` でブロックされます。
- **公開鍵。** `id_rsa.pub`、`id_ed25519.pub`、`id_ecdsa.pub` はシークレットではないため除外されます。ただし、先に検査される保護対象ホームディレクトリの外にある場合だけです。`./id_rsa.pub` は許可されます。`~/.ssh/id_rsa.pub` は `secret.home.ssh` でブロックされます。
- **ベンダー管理ディレクトリ。** パスセグメントが `node_modules` または `__pycache__` の場合、または隣接する組み合わせ `vendor/bundle` または `vendor/cache` がある場合、正確に 2 つのファミリーが抑制されます。拡張子ルール（単純形式とパターン形式）と、広範な `secret.pattern.ssh-key-basename` ルールです。それ以外のルールはすべて引き続き適用されます。`node_modules/x/.env` と `node_modules/x/id_rsa` は通常どおりブロックされます。`.git` は除外セットに含まれません。

## 設定

すべての設定は [`policy.json`](/ja/configuration/policy#secret-protection) にあります。

- `secret_protection.enabled: false` は、組み込みルールと deny path を含むステージ全体を無効にします。
- `secret_protection.overrides` は、登録済み ID ごとにルールの状態を設定します。`"off"` は既定で on のルールを無効にし、`"on"` は設定階層のルールを有効にします。
- `secret_protection.deny_paths` は、独自の保護対象場所を追加します。
- `secret_protection.allow_paths` は、deny path の確認後に、特定のファイル、ディレクトリツリー、またはディレクトリ配下の 1 つのファイル名を、CLI 以外の組み込みルールから除外します。

破壊的コマンド側の [allow path](/ja/guides/analysis-engine#recursive-delete-target-classification)によってシークレット保護が緩められることはありません。standard モードのどの緩和も、設定済みの deny path を緩めることはありません。上記の限定された効果を持つのは `secret_protection.allow_paths` だけです。standard モードが読み取りと見なさない形は、[上記の一覧](#what-standard-mode-does-not-count-as-a-read)を参照してください。[strict モード](/ja/configuration/modes#strict-mode)では、保護対象パスに対するメタデータのみの探索（`test -f ~/.ssh/id_rsa`、`find ~/.ssh -type f`、`ls -la ~/.ssh`、`stat .env`）もブロックされます。同じ設定は[ダッシュボード](/ja/guides/dashboard#secret-protection)の UI からも編集できます。

<Note>
  シークレット保護は範囲が限定されたパターンセットであり、一般的な読み取り境界ではありません。どのルールも認識しないファイル内の資格情報は保護されません。この境界については、[CC Safety Net が対処できない範囲](/ja/guides/vs-sandboxing#where-cc-safety-net-cannot-help)を参照してください。階層の注意点については、[既知の制限](/ja/guides/known-limitations)を参照してください。ログとブロックメッセージから資格情報の値を取り除くシークレットの**マスク**は別の仕組みです。[監査ログリファレンス](/ja/reference/audit-log#secret-redaction)と[セキュリティモデル](/ja/guides/security-model#secret-redaction)に説明があります。
</Note>
