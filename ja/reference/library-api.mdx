エージェント、タスクランナー、CI のハーネス、シェルツールを持つプラグインホストなど、自分でコマンドを実行する Node.js のホストは、エージェント連携をインストールする代わりに `checkCommand` を呼び出せます。この関数は、シェルコマンド 1 つを現在のポリシーに照らして検査し、許可か拒否かを返します。コマンドを実行することはありません。

## ライブラリ API とインストール済みの連携の使い分け

どちらも同じ解析エンジンを使います。違うのは、呼び出しを誰が担うかです。

| | インストール済みの連携 | プロセス内の `checkCommand` |
| --- | --- | --- |
| 組み込む人 | `cc-safety-net install <target>` をマシンごとに 1 回実行 | 自分のコードが、コマンドを実行するすべての箇所で呼ぶ |
| 判定が行われる場所 | フックのサブプロセス、またはエージェントが読み込むプラグイン | 自分のプロセス内で同期的に |
| 監査記録 | すべての判定が記録され、`logs` とダッシュボードで読める | なし。必要なものはホストが記録する |
| 対象 | 対応している 16 のエージェント | 任意の Node.js のホスト |

ユーザーが対応エージェントのいずれかを使っているなら、インストールコマンドを案内してください。[連携方式](/ja/guides/how-it-works#integration-models)を参照してください。自分のプログラムがコマンドを実行するなら、この関数を呼び出します。

## インストールとインポート

```bash
npm install cc-safety-net
```

```ts
import { checkCommand } from 'cc-safety-net/api';
```

Node.js 22 以降と ESM が必要です。CommonJS のビルドはないため、`require()` では読み込めません。パッケージのルートのエクスポートは `checkCommand` ではなく OpenCode のプラグインなので、`cc-safety-net/api` からインポートしてください。

## `checkCommand`

```ts
function checkCommand(input: CheckCommandInput): CheckCommandResult;
```

呼び出しは同期的です。ローカルのポリシーファイル、ファイルシステムの状態、`CC_SAFETY_NET_*` の環境設定を読み取り、許可または拒否を返します。

### 入力

```ts
type CheckCommandInput = Readonly<{
  command: string;
  cwd: string;
}>;
```

| フィールド | 型 | 説明 |
| --- | --- | --- |
| `command` | `string` | 検査するシェルコマンドのテキスト。空にはできない |
| `cwd` | `string` | 絶対パスのディレクトリ。コマンド内の相対パスの対象はこれを基準に解決され、プロジェクトのルール設定もこれで選ばれる |

`cwd` は必須で、既定値はありません。API が `process.cwd()` にフォールバックすることはないため、コマンドがどのプロジェクトに属するかはホストが決めます。

### 結果

```ts
type CheckCommandResult =
  | Readonly<{ kind: 'allow' }>
  | Readonly<{ kind: 'deny'; reason: string; ruleId: string }>;
```

| フィールド | 有無 | 説明 |
| --- | --- | --- |
| `kind` | 常にある | `'allow'` または `'deny'` |
| `reason` | 拒否時のみ | ユーザーに表示するブロックメッセージ |
| `ruleId` | 拒否時のみ | ブロックしたルールまたは固定の拒否の ID |

判定は `kind` で読み取ります。`deny` は、ホストがそのコマンドを実行してはならないことを意味します。`reason` は表示用のテキストなので、解析や比較には使わないでください。

すべての拒否に `ruleId` が付きます。値は、`git.reset-hard` のような組み込みルールの ID、シークレットルールの ID、`custom.` で始まるルールの ID、または `cwd.requested-unusable` のような[固定の拒否 ID](/ja/reference/blocked-commands#fixed-denial-ids) のいずれかです。この値で分岐すれば、特定の種類の拒否だけ扱いを変えられます。たとえば、作業ディレクトリを直すようユーザーに伝える場合です。ただし、ID が何であれ、拒否されたコマンドはブロックされます。今後のバージョンで ID が増える可能性があるため、知らない ID は通常の拒否として扱ってください。拒否の種類については[ブロックされるコマンド](/ja/reference/blocked-commands)を参照してください。

### エラー

`checkCommand` は実行時に入力を検証し、次のいずれかのメッセージを持つ `TypeError` を投げます。

| メッセージ | 条件 |
| --- | --- |
| `checkCommand requires an input object with command and cwd` | `input` が null 以外のオブジェクトではない |
| `command must be a non-empty string` | `command` が文字列でない、または空白のみ |
| `cwd must be an absolute directory path` | `cwd` が文字列でない、空白のみ、または絶対パスでない |

既知のガードの失敗は、例外を投げずにフェイルクローズの拒否として返します。それ以外のエラーは、そのまま呼び出し元に投げます。

<Warning>
  `checkCommand` が例外を投げた場合は、そのコマンドを実行しないでください。例外は許可ではありません。
</Warning>

### 使用できない作業ディレクトリ

`cwd` は、読み取りと検索ができる既存のディレクトリでなければなりません。そうでない場合、呼び出しは誤ったプロジェクトを解析する代わりに、`ruleId` が `cwd.requested-unusable` の拒否を返します。理由は次のとおりです。

```
CC Safety Net could not use the requested working directory because it does not exist, is inaccessible, is not a directory, or uses an unsupported path form. Use an existing accessible working directory. If the requested directory is missing, create it from an accessible location before retrying the command.
```

## 呼び出しが読むポリシー

呼び出しは、フックと同じユーザーファイルとプロジェクトファイルを読みます。プロジェクトファイルは、ちょうど `<cwd>/.cc-safety-net/` から読み込みます。親ディレクトリはさかのぼらないため、`cwd` にはリポジトリのルートを渡してください。そうしないと、コミットされたプロジェクトポリシーが読み込まれません。2 つのスコープのマージ方法は[ポリシー](/ja/configuration/policy#project-policy)を参照してください。

プロジェクトは `cwd` で選ばれるため、複数のチェックアウトを扱うホストも、それぞれのディレクトリを渡すだけで正しいポリシーを得られます。ホストがどう判定するかを確認するには、`cwd` として渡すディレクトリで `status`、`doctor`、`explain` を実行します。

## バージョン間の互換性

次の点はマイナーバージョンをまたいで変わりません。

- 入力の形 `{ command, cwd }` と、2 種類の結果。`allow` と、`reason` と `ruleId` を持つ `deny` です。
- `deny` と例外は、どちらもコマンドを実行してはならないことを意味します。
- コマンド内の相対パスの対象とプロジェクトの設定は、渡した `cwd` を基準に解決され、`process.cwd()` は使われません。
- 呼び出しは監査レコードを書き込まず、ネットワークリクエストも行いません。[1 回の呼び出しが検査するもの](#what-one-call-checks)を参照してください。

ルールカタログは、どのマイナーバージョンでも変わる可能性があります。新しいリリースで、以前は許可されていたコマンドが拒否されることもあり、`reason` の文言も変わります。分岐は `kind` で行い、`reason` は人とログのために残し、バージョンはロックファイルで固定してください。

## 実装例：プラグインホスト

プラグイン機構を持つホストには、たいていツール呼び出しを拒否できる実行前のフックがあります。プラグインはホストのイベントを `{ command, cwd }` に対応付けて `checkCommand` を呼び出し、拒否をホスト側の拒否に変換します。

```ts
import { checkCommand } from 'cc-safety-net/api';

export function registerSafetyNet(host: PluginHost) {
  host.beforeToolCall((call, ctx) => {
    if (call.toolName !== 'shell') return undefined;

    if (typeof call.input.command !== 'string' || call.input.command.trim() === '') {
      return { block: true, reason: 'Malformed shell tool call.' };
    }

    try {
      const result = checkCommand({ command: call.input.command, cwd: ctx.projectRoot });
      if (result.kind === 'deny') return { block: true, reason: result.reason };
      return undefined;
    } catch (error) {
      console.error('CC Safety Net could not check the command', error);
      return { block: true, reason: 'Command check failed. The command was not executed.' };
    }
  });
}
```

- プラグインが `checkCommand` に渡すのはシェルツールの呼び出しだけです。検査するのはシェルコマンドのテキストであり、ホストの読み取り、書き込み、検索のツールは対象外です。
- `cwd` はプロジェクトルートの絶対パスです。これでプロジェクトポリシーが選ばれ、`checkCommand` はコマンド内の `.env` のような相対パスをこれを基準に解決します。
- 例外が発生したら呼び出しをブロックします。ハンドラーがエラーを無視して実行に進むと、壊れた検査が許可に変わってしまいます。
- 解析する対象がないため、不正なイベントもブロックします。

ホストが例外で拒否を表す場合は、拒否メッセージを返す代わりに投げてください。

## 1 回の呼び出しが検査するもの

呼び出しはシェルの方言を自動で判別し、`cwd` をプロジェクトのディレクトリとしても実行ディレクトリとしても使います。コマンド全体を検査し、コマンドによるシークレットファイルへのアクセスも対象に含みます。読み取り、書き込み、編集、検索など、ホスト自身が持つシェル以外のファイル操作ツールは検査しません。

呼び出しがコマンドを実行したり、設定を変更したり、ネットワークリクエストを行ったりすることはありません。監査レコードも書き込まないため、`logs` コマンドやダッシュボードには表示されません。ホストが拒否を記録しなければ、どこにも残りません。

## 環境設定

呼び出しのたびにプロセスの環境から `CC_SAFETY_NET_*` の設定を読み取るため、これらを変更すると以降の判定も変わります。無効な `CC_SAFETY_NET_LEVEL` は無視し、標準エラー出力に報告します。

```
CC Safety Net: ignored invalid CC_SAFETY_NET_LEVEL="<value>". Use standard, strict, paranoid.
```

メッセージ内の値は JSON 形式で引用され、先頭の 40 文字に切り詰められます。すべての変数については[環境変数](/ja/configuration/environment)を参照してください。
