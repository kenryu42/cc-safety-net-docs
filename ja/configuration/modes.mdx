## どの安全レベルを使えばよいですか？

コマンドの出どころによって決まります。人が見ているセッションでは、既定の `standard` レベルを使います。認識できる破壊的なコマンドとシークレットへのアクセスをブロックしますが、敵対的な入力や動的な入力を確実に防げるわけではありません。プロンプトインジェクションなど信頼できない文脈からコマンドが来る可能性があるなら、`strict` を使います。解析も検証もできないコマンドまでブロックするためです。プロジェクト内の `rm -rf` と、すべての `python -c` や `node -e` のワンライナーも止めたいなら `paranoid` を選びます。Git のリンクされたワークツリーでは、ワークツリーモードを有効にすると `git reset --hard` などのローカル破棄を許可できます。信頼できないコードの実行やネットワークの制御には、サンドボックスを併用してください。

各レベルは、3 つの機能の組み合わせを表すプリセットです。

| レベル | `fail_closed` | `paranoid_rm` | `paranoid_interpreters` | 追加される内容 |
| --- | --- | --- | --- | --- |
| `standard`（既定） | off | off | off | 認識できる破壊的なコマンドとシークレットへのアクセスをブロック |
| `strict` | **on** | off | off | 解析できないコマンド、未対応の heredoc、検証できない削除対象、シークレットファイルのメタデータの確認もブロック |
| `paranoid` | **on** | **on** | **on** | 作業ディレクトリ内での一時パス以外への `rm -r` と、すべてのインタープリターのワンライナーもブロック |

レベルは、`policy.json` の `safety.level` または環境変数 `CC_SAFETY_NET_LEVEL` で設定します。2 つのうち高い方が適用されます。このページで紹介する各トグルは、そのレベルの上に機能を 1 つずつ追加します。どのプリセットにも一致しない組み合わせは、有効なレベルが `custom` として報告されます。ワークツリーモードはレベルとは独立しています。

変数の一覧とポリシー・環境変数の優先順位は[環境変数](/ja/configuration/environment)を、`safety.overrides` は[ポリシー](/ja/configuration/policy#safety-level-and-capability-overrides)を参照してください。影響を受けるコマンドは[各安全レベルで追加されるブロック](/ja/reference/blocked-commands#what-each-safety-level-adds)に一覧があります。

<span id="default-mode"></span>

## 既定モード

既定モードは `standard` 安全レベルです。環境変数を設定しなくても、組み込みの破壊的な Git 操作とファイルシステム操作、およびシークレットファイルへのアクセスをブロックします。以下の厳しいチェックが必要でなければ、まずはこのレベルを使ってください。

standard を含むどのレベルでも、不正なフック入力、アナライザーのエラー、解析できないほど大きいコマンドや入れ子が深すぎるコマンドはブロックします。[フェイルクローズによる強制](/ja/guides/security-model#what-happens-when-analysis-fails)を参照してください。

standard と strict の違いは、解析や検証ができない入力の扱いです。

- 引用符が閉じていないなどの理由でコマンドをトークンに分割できない場合、CC Safety Net はテキストをスキャンして既知の危険なパターンを探します。`echo 'unterminated` は実行されます。`git reset --hard 'unterminated` は standard でブロックされ、Claude Code ではブロックの代わりに承認を求めます。[standard がコマンドを検証できない場合](#when-standard-cannot-verify-a-command)を参照してください。
- `rm -rf "$target"` のように削除対象が動的な再帰削除は許可されます。strict ではブロックされます。

standard はこのほか、動的な実行ファイル、コマンド置換で組み立てたコマンド、`eval "$(ssh-agent -s)"` のようにリテラルなローカルの生成コマンド 1 つに対する `eval` や `source` も許可します。standard は、敵対的な入力や動的な入力を確実に防げるわけではありません。プロンプトインジェクションからコマンドが来る可能性があるなら、strict か paranoid を使ってください。

standard は、`test -f .env` や `ls ~/.ssh` のように、中身を読まずにシークレットファイルの存在を確かめる操作を許可します。strict と paranoid はこれをブロックします。該当する形はすべて[standard モードが読み取りと見なさないもの](/ja/reference/secret-protection#what-standard-mode-does-not-count-as-a-read)に一覧があります。シークレットファイルの内容の読み取り、設定した拒否パス、[致命的なルール](/ja/reference/blocked-commands#catastrophic-rules)は、どのレベルでも緩和されません。

<span id="when-standard-cannot-verify-a-command"></span>

### standard がコマンドを検証できない場合

standard レベルの拒否のうち 2 つは、「危険」ではなく「検証できなかった」ことを意味します。1 つはパースできないテキストが破壊的なパターンに一致した場合、もう 1 つは `bash -c "$CMD"` のように、CC Safety Net がシェルコマンドの実行元を解決できない場合です。Claude Code では、ほとんどの権限モードで、この 2 つはブロックせずに承認を求めます。他のホスト、および strict と paranoid では拒否のままです。[Claude Code がブロックせずに確認を求める場合](/ja/installation/claude-code#when-claude-code-asks-you-instead-of-blocking)を参照してください。

<span id="strict-mode-cc_safety_net_strict=1"></span>

## Strict モード（`CC_SAFETY_NET_STRICT=1`）

strict は `fail_closed` 機能を有効にします。敵対的な文脈や信頼できない文脈からコマンドが来る可能性がある場合や、珍しい構文でときどき誤検知が出ても構わない場合に使います。次のものをブロックします。

- **解析できないコマンド。** テキストスキャンで危険なものが見つからなくてもブロックします。理由は「Command could not be safely analyzed (strict mode)」です。`echo 'unterminated` は standard では許可され、strict ではブロックされます。
- **一部の対応形式を除く heredoc。** `git commit -F - <<'EOF'` と単純な `cat <<'EOF'` は通りますが、`python3 - <<'PY'` は拒否します。[heredoc](/ja/reference/blocked-commands#heredocs) を参照してください。
- **検証できない破壊的な対象。** 下の 5 つのルールでブロックします。
- **シークレットファイルの存在確認。** `test -f ~/.ssh/id_rsa` や `find ~/.ssh -type f` などです。
- **インタープリターのコード内にあるシークレットのパス。** `python -c "x = '.env'"` のように、standard ではデータとして扱うものです。

次の 5 つのルールは、`fail_closed` が有効なときにだけ動作します。

| ルール ID | standard で許可され、strict でブロックされる例 |
| --- | --- |
| `rm.recursive-force-dynamic-target` | `rm -rf "$target"` |
| `powershell.remove-item-recursive-force-dynamic-target` | `Remove-Item $target -Recurse -Force` |
| `powershell.remove-item-pipeline-dynamic-target` | `Get-ChildItem . -Recurse \| Remove-Item -Force` |
| `shell.dynamic-executable` | `$(printf r)m -rf /` |
| `shell.dynamic-structure` | `git reset $(printf --hard)` |

strict は、レベルで有効にするか、同じ機能を有効にする以前からのトグルで有効にします。

```bash
export CC_SAFETY_NET_LEVEL=strict
# or
export CC_SAFETY_NET_STRICT=1
```

<Note>
  上の 5 つのルールは、[policy.json](/ja/configuration/policy#destructive-command-protection) の `destructive_command_protection.overrides` で個別に無効にできます。`"on"` を指定すれば、standard でも個別に有効にできます。解析できないコマンド、未対応の heredoc、シークレットファイルの確認には無効にできるルールがないため、strict が有効なあいだはブロックされたままです。
</Note>

<span id="paranoid-mode-cc_safety_net_paranoid=1"></span>

## Paranoid モード（`CC_SAFETY_NET_PARANOID=1`）

`paranoid` レベルは、strict に `paranoid_rm` と `paranoid_interpreters` の 2 つの機能を加えたものです。通常のワークフローを妨げることがあるため、明示的に有効にしたときだけ動作します。レベル全体を選ぶことも、機能を 1 つだけ有効にすることもできます。片方だけを有効にした場合、レベルは `custom` と報告されます。

<span id="rm-check-cc_safety_net_paranoid_rm=1"></span>

### rm チェック（`CC_SAFETY_NET_PARANOID_RM=1`）

既定では、カレントディレクトリ配下の `rm -rf` と `find -delete` は許可されます。プロジェクトルート内での削除は意図的な操作だと見なすためです。paranoid の rm チェックを有効にすると、カレントディレクトリ配下であっても、一時パス以外への再帰削除をブロックします。`rm -rf ./cache` と `rm -r ./cache` は `rm.recursive-force-paranoid` に、`find ./cache -delete` は `find.delete` に一致します。PowerShell の `Remove-Item ./cache -Recurse -Force` は `powershell.remove-item-recursive-force-paranoid` に一致します。

このチェックを有効にしても、一時パスと `destructive_command_protection.allow_paths` に指定したディレクトリは許可されたままです。

<span id="paranoid-interpreters"></span>

<span id="interpreter-one-liners-cc_safety_net_paranoid_interpreters=1"></span>

### インタープリターのワンライナー（`CC_SAFETY_NET_PARANOID_INTERPRETERS=1`）

インタープリターのワンライナーは、静的には検査しにくい文字列の中に破壊的なコマンドを隠せます。paranoid 未満のレベルでは、本体に危険なコマンドを含むワンライナーだけをルール `interpreter.dangerous-command` でブロックします。このチェックを有効にすると、内容にかかわらずすべてのワンライナーを `interpreter.one-liner-paranoid` でブロックします。

- `python -c '...'`（`python3` と `python2` も含む）
- `node -e '...'`
- `ruby -e '...'`
- `perl -e '...'`

つまり `python -c "print(1)"` は、standard と strict では許可され、このチェックではブロックされます。

### paranoid チェックを有効にする

```bash
# The full paranoid level, including strict
export CC_SAFETY_NET_LEVEL=paranoid

# Both paranoid checks without strict (effective level: custom)
export CC_SAFETY_NET_PARANOID=1

# One check at a time
export CC_SAFETY_NET_PARANOID_RM=1
export CC_SAFETY_NET_PARANOID_INTERPRETERS=1
```

`CC_SAFETY_NET_PARANOID=1` では `fail_closed` は有効になりません。プリセット全体を適用するには、`CC_SAFETY_NET_LEVEL=paranoid` か `safety.level: "paranoid"` を使ってください。

## ワークツリーモード（`CC_SAFETY_NET_WORKTREE=1`）

Git のリンクされたワークツリーは独立した作業環境なので、ワークツリーモードではそこでの一部のローカル破棄ルールを緩和します。適用されるのは、カレントディレクトリがリンクされたワークツリーの中にあると CC Safety Net が確認できた場合だけです。

### ワークツリーモードを有効にする

```bash
export CC_SAFETY_NET_WORKTREE=1
```

[policy.json](/ja/configuration/policy) で `workflow.worktree_mode: true` を設定することもできます。どちらか一方を設定すればワークツリーモードが有効になります。

### リンクされたワークツリーで許可されるコマンド

ワークツリーモードが有効で、作業ディレクトリがリンクされたワークツリーだと確認できた場合、次のコマンドを許可します。

- `git restore <file>` と `git restore --worktree <file>`
- `git checkout -- <file>`、`git checkout <path>`、`git checkout <ref> -- <file>`、`git checkout --force`、および位置引数が複数あって判別できない `git checkout` の形式
- `git reset --hard` と `git reset --merge`
- `git clean -f`（`-fd` のように組み合わせた短いフラグも含む）
- `git switch --discard-changes` と `git switch -f / --force`

### リンクされたワークツリーでもブロックされるコマンド

次のコマンドは共有された ref や他のワークツリーに影響するため、ワークツリーモードでも緩和されません。

- `git push --force`：リモートに影響する
- `git branch -D`：ワークツリー間で共有されるブランチを強制削除する
- `git stash drop` / `git stash clear`：ワークツリー間で共有されるスタッシュを変更する
- `git worktree remove --force`：別のワークツリーを削除しかねない

これとは別の[一時ルートの緩和](/ja/reference/blocked-commands#git-commands-in-a-temp-repository)により、信頼された一時ルート配下にある使い捨てのワークツリーディレクトリを対象とする `git worktree remove --force` が許可されることがあります。この緩和はワークツリーモードの一部ではなく、`CC_SAFETY_NET_WORKTREE=1` も必要ありません。

### ワークツリーモードが適用されない場合

作業ディレクトリがリンクされたワークツリーだと確認できない場合は、既定のルールがそのまま適用されます。メインワークツリーとサブモジュールは、ワークツリーモードでも緩和されません。次の場合も無効になります。

- コマンドに `--git-dir` または `--work-tree` が渡されている場合や、環境変数に `GIT_DIR`、`GIT_WORK_TREE`、`GIT_COMMON_DIR`、`GIT_INDEX_FILE` のいずれかが設定されている場合
- コマンドが `git -c` または `GIT_CONFIG_*` で `core.worktree` を設定している場合や、ワークツリーの `config.worktree` または共有のリポジトリ設定に `worktree` キーがある場合
- ワークツリーの Git ディレクトリにシンボリックリンクまたは FIFO がある場合
- `git -C <path>` の対象を解決できない場合
- 引数に `$`、`*`、`?`、`[` を含む動的な値がある場合
- コマンドが `--recurse-submodules` またはサブモジュールを再帰的に扱う設定を使う場合
- ブランチを強制リセットするコマンド（`-f` または `--discard-changes` を伴う `git checkout -B` や `git switch -C`）の場合や、`-f` を複数指定した `git clean` の場合

<Tip>
  現在有効なレベルは、`npx cc-safety-net status` を実行するか、Claude Code の[ステータスライン](/ja/reference/cli/statusline)で確認できます。
</Tip>
