**degraded** は、JSON にエラーがあるルールブックや、`policy.json` の値が誤ったフィールドなど、設定の一部を CC Safety Net が拒否した状態です。CC Safety Net は読み込めた設定で動作を続けます。この縮小された設定が**フォールバック設定**です。ファイル内の有効な部分すべて、拒否された `policy.json` のフィールドに代わる組み込みの既定値、そしてすべての組み込み保護で構成されます。

`doctor` はこの状態を「Runtime is enforcing a fallback configuration」と報告し、ダッシュボードのバナーには「A fallback configuration is being enforced」と表示されます。`doctor` の検出結果には、拒否されたファイルとフィールドがそれぞれ示されます。[後述の手順](#recover-configuration)で修正してください。

拒否されたルールブックは、修正するまでブロックしなくなります。拒否された `policy.json` のフィールドは既定値に戻り、たいていは設定したときよりも多くの操作をブロックします。

<span id="configuration-states"></span>

## 設定の状態

| 状態 | 発生条件 | 意味 |
| --- | --- | --- |
| `ready` | 有効な設定元をすべて読み込み、検証にも成功した | 記述したとおりの設定で通常どおり評価する |
| `degraded` | ルールのエラー、ルールの警告、いずれかのスコープの `policy.json` のエラーのいずれかがある | フォールバックで通常どおり評価を続け、すべての表示箇所に、拒否された設定元を示す警告を出す |

警告が 1 つでもあれば、ランタイムは `degraded` になります。

- **エラー**は、CC Safety Net が破棄した設定元を示します。その設定元のルールは一切使われません。
- **警告**は、有効なままの設定元を示します。無視されるのは、拒否された部分だけです。

## 無効な設定の扱い

設定が無効だというだけで、通常の作業がブロックされることはありません。また、拒否された部分が強制されることもありません。

- 検証できないルールの設定元は破棄され、そのルールは適用されなくなります。
- 検証に成功したほかのスコープは、引き続きルールを強制します。
- 組み込みの保護はすべて適用され続けます。破壊的コマンドのルール、シークレット保護、`policy.json` の保護、Git メタデータの保護は、ルールの設定を読み取らないためです。
- 無効な `policy.json` は、有効なフィールドをそのまま使い、残りには組み込みの既定値を使います。[`policy.json`：救済するか、安全側の既定値に置き換える](#policy-json-salvaged-or-replaced-with-protective-defaults)を参照してください。

degraded 状態で追加で許可されるものはなく、復旧モードもありません。`rule.json` の読み取りや編集、`cc-safety-net rule update` の実行は通常のツール呼び出しなので、エージェント自身がルールの設定を修復できます。

<Warning>
  設定元の破棄は、安全性に影響しないわけではありません。その設定元による拒否がなくなるため、破棄されたルールブックで意図的にブロックしていたコマンドは、修復するまで再び実行できるようになります。エラーに名前が出たルールブックが、まだ保護を続けているとは考えないでください。
</Warning>

ブロックの理由が「failed closed」の場合は、これとは別のケースです。CC Safety Net がそのコマンド 1 つの解析を完了できなかったことを意味します。[フェイルクローズによる強制](/ja/guides/security-model#what-happens-when-analysis-fails)を参照してください。

## 設定のフォールバック一覧

<span id="errors-the-source-is-dropped"></span>

### エラー：設定元が破棄される

| 失敗の内容 | 強制されなくなるもの | 引き続き適用されるもの |
| --- | --- | --- |
| リモートの設定元がまだ取り込まれておらず、`rules/<name>/rulebook.json` がない | そのルールブック 1 つ | ほかのすべてのルールブックと組み込み保護 |
| ローカルの設定元の `rules/<name>/rulebook.json` がない、または削除された | そのルールブック 1 つ | ほかのすべてのルールブックと組み込み保護 |
| ルールブックのファイルが有効な JSON でない、またはルールブックのスキーマに適合しない | そのルールブック 1 つ | ほかのすべてのルールブックと組み込み保護 |
| ルールブックの `name` が、それを指定している設定元と一致しない | そのルールブック 1 つ | ほかのすべてのルールブックと組み込み保護 |
| `rule.json` が不正、空、または未対応の `version` | `transparent_wrappers` と `command_tools` を含む、そのスコープ全体 | もう一方のスコープの検証済みルールと、すべての組み込み保護 |
| ポリシー用のファイルシステムを安全に読み取れない | そのスコープ | もう一方のスコープの検証済みルールと、すべての組み込み保護 |

いずれのメッセージも、拒否したファイルまたは設定元と、それに応じた修復方法を示します。リモートの設定元のルールブックがない場合は ``run `cc-safety-net rule update` to vendor <source>`` で、ローカルの設定元のルールブックがない場合は `create that file or remove that source from the rules config` で終わります。ルールブックが無効な場合と名前が一致しない場合は、どちらも `fix that file` で終わります。

<span id="warnings-the-source-stays-active"></span>

### 警告：設定元は有効なまま

| 失敗の内容 | 無視されるもの | 強制され続けるもの |
| --- | --- | --- |
| 有効なルールブック 2 つが同じ名前を使っている | 後から読み込まれたルールブック。そのルールは有効にならない | 先に名前を確保した側。ユーザースコープを先に解決する |
| `rule.json` に未知のオーバーライドのキーがある | そのオーバーライド 1 つだけ | ほかのオーバーライドとすべてのルールは設定どおりの状態を保つ |
| プロジェクトのオーバーライドがユーザースコープのルールを対象にしている | そのオーバーライド 1 つだけ | 対象のルールはユーザー設定の状態を保つ |

名前が重複した場合の解決方法は[スコープのマージ](/ja/configuration/custom-rules#scope-merge-behavior)を参照してください。

<span id="policy-json-salvaged-or-replaced-with-protective-defaults"></span>

### `policy.json`：救済するか、安全側の既定値に置き換える

JSON オブジェクトとしてパースできるファイルは救済されます。有効なフィールドはそのまま残り、無効なフィールドは 2 つ目の表のとおりフォールバックします。それ以外の壊れたユーザーファイルは、安全側の既定値に置き換えられます。安全側の既定値とは、両方の保護が有効で、オーバーライドも許可パスも拒否パスもない組み込みの既定値です。

| 状況 | 結果 | 状態 |
| --- | --- | --- |
| ユーザーファイルがない | 組み込みの既定値 | `ready`。診断なし |
| ユーザーファイルが空、空白のみ、有効な JSON でない、または JSON オブジェクトでない | 安全側の既定値 | `degraded` |
| ユーザーファイルはオブジェクトだが、一部のフィールドが検証に失敗 | 救済 | `degraded` |
| プロジェクトファイルがない | ユーザーポリシーのみ | `ready`。診断なし |
| プロジェクトファイルが空、有効な JSON でない、または JSON オブジェクトでない | ユーザーポリシーのみ | `degraded` |
| プロジェクトファイルはオブジェクトだが、一部のフィールドが検証に失敗 | 有効なフィールドがユーザーポリシーの上に重なる | `degraded` |
| プロジェクトファイルに `audit` セクションがある | ユーザーポリシーの監査設定。プロジェクトのほかのフィールドはすべて重なる | `degraded` |
| ユーザーファイルが壊れていて、プロジェクトファイルが有効なフィールドを設定している | 安全側の既定値の上にプロジェクトのフィールドが重なる | `degraded` |

| フィールド | 無効な場合 |
| --- | --- |
| `version` | `1` として扱う |
| `safety.level` | `standard` に戻る |
| `safety.overrides.*` | 無効なキーを破棄し、その機能はプリセットから継承 |
| `workflow.worktree_mode` | `false` に戻る |
| `destructive_command_protection.enabled`、`secret_protection.enabled` | `true` に戻り、保護は有効 |
| `destructive_command_protection.overrides`、`secret_protection.overrides` | 無効な項目を破棄し、有効な `"on"` と `"off"` の項目は残す。オブジェクトでない場合は `{}` |
| `destructive_command_protection.allow_paths`、`secret_protection.allow_paths` | 無効な項目を破棄し、有効な項目は残す。配列でない場合は `[]` |
| `secret_protection.deny_paths` | 無効な項目を破棄。配列でない場合は `[]` |
| `audit.retention_days` | `1` と `365` のうち近い方。整数でない場合は `30` |

ランタイムが `policy.json` を書き換えることはありません。手作業で修正するか、[ダッシュボード](/ja/guides/dashboard)の修復機能を使ってください。

<span id="coverage-declared-in-rule-json"></span>

## `rule.json` で宣言する対象範囲

`transparent_wrappers` と `command_tools` は、組み込みの解析が届く範囲を広げます。どちらもルールブックではなく `rule.json` に書きます。

- ルールブックが破棄されても、どちらのフィールドも残ります。`rule.json` 自体は読み取れるためです。
- `rule.json` を読み取れない場合は、そのスコープで両方とも失われます。そのスコープのラッパーを透過した解析は行われなくなり、そのスコープで宣言した[コミュニティ製のシェルツール](/ja/configuration/custom-rules#community-shell-tools)も解析されなくなります。組み込みの 8 つのラッパー（`caffeinate`、`exec`、`nice`、`nohup`、`setsid`、`stdbuf`、`time`、`timeout`）はファイルを必要としないため引き続き適用され、もう一方のスコープの宣言も同様です。

拒否された設定が、独自のルールを失わせるだけでなく組み込みの対象範囲まで狭めるのは、このケースだけです。`rule.json` を読み取れずにスコープが破棄された場合は、まずそのファイルを修復してください。

## degraded 状態の報告

| 表示箇所 | 表示内容 |
| --- | --- |
| 次にユーザーの目に触れる拒否 | ブロックメッセージの末尾に、理由の全文を含む `Config warning:` の行 |
| 監査レコード | 許可・拒否どちらの判定にも付く `configFallback` フラグ |
| `cc-safety-net status` | `ready` または `degraded` の判定と、`Not active` の下に診断 1 件につき 1 行 |
| `cc-safety-net doctor` | タイトルが「Runtime is enforcing a fallback configuration」の警告 `config.runtime-degraded`。詳細欄に理由の全文 |
| `cc-safety-net rule list` | `Issues` と `Warnings` のセクション。ルールの設定のみが対象 |
| ステータスライン | スナップショットが degraded の間に表示される `⚠️` |
| ダッシュボード | 保護状況のバナーに表示される状態 |

ルールの設定と `policy.json` の両方を報告するのは `doctor` だけです。診断は拒否したファイルと問題を示しますが、ファイルの中身は写さないため、壊れたファイル内のシークレットが表示されることはありません。

## 気づきやすい失敗と気づきにくい失敗

- **設定元の破棄は気づきにくい。** 拒否が減るため、セッション中に何かがブロックされたり警告が出たりすることはありません。ルールの設定を変更したあとと、アップグレードのたびに `cc-safety-net status` を実行してください。
- **未移行の旧形式のルールファイルは、さらに気づきにくい。** CC Safety Net はそのファイルを読み込まず、状態は `ready` のままですが、そのルールは何も保護していません。`doctor` は `config.legacy-ignored` として報告します。[旧形式の設定を移行する](/ja/configuration/custom-rules#migrate-legacy-configuration)を参照してください。
- **無効な `policy.json` のフィールドは、たいてい気づける。** 保護が有効の状態に戻るため、設定したよりも多くの拒否が発生します。
- **`policy.json` の 2 種類の誤りは、気づかないうちに保護を下げる。** 無効な `safety.level` は `standard` に戻るため、`paranoid` の綴りを間違えるとプリセットが下がります。無効な `deny_paths` の項目は破棄されるため、その場所は保護されなくなります。
- 何もしなくても表示されるのは、ステータスラインの表示だけです。`Config warning:` の行は無関係な拒否が起きたときにしか現れず、ほかの表示箇所は、コマンドを実行するかダッシュボードを開くまで何も知らせません。

<span id="recover-configuration"></span>

## 設定を復旧する

以下のコマンドは、ランタイムが degraded の間でもエージェントが実行できます。オプションと終了コードは [CLI リファレンス](/ja/reference/cli/overview)にあります。

<Steps>
  <Step title="判定を確認する">
    ```bash
    npx cc-safety-net status
    ```

    `ready` または `degraded` と、`Not active` の下に診断を 1 件ずつ表示します。[`status`](/ja/reference/cli/status) を参照してください。
  </Step>
  <Step title="詳細なレポートを取得する">
    ```bash
    npx cc-safety-net doctor
    ```

    ルールの設定と `policy.json` の両方を対象にします。`config.runtime-degraded` の検出結果に、拒否されたすべての設定元が示されます。[`doctor`](/ja/reference/cli/doctor) を参照してください。
  </Step>
  <Step title="ルールの設定を確認する">
    ```bash
    npx cc-safety-net rule list
    npx cc-safety-net rule verify
    ```

    `rule list` は有効なルールを表示するため、破棄された設定元とともに何が失われたかが分かります。`rule verify` は、両方の `rule.json` をランタイムと同じ方法で読み込んで確認し、問題があれば `Config validation failed.` で終わります。[`rule verify`](/ja/reference/cli/rule#rule-verify) を参照してください。
  </Step>
  <Step title="設定元を修復する">
    ローカルのルールブックは、診断が示すファイルを編集します。ランタイムは次のツール呼び出しでそれを読み込みます。

    リモートの設定元がない、または古い場合は、取り込み直します。

    ```bash
    npx cc-safety-net rule update
    ```

    設定元の名前を指定すればそれだけを更新でき、ユーザースコープには `--global` を付けます。診断が残っている場合は、成功と報告せずにその診断を出力します。[`rule update`](/ja/reference/cli/rule#rule-update) を参照してください。
  </Step>
  <Step title="policy.json を自分で直す">
    エージェントは `policy.json` を編集できません。診断に挙がったフィールドを自分で修正するか、ダッシュボードの修復機能を使ってください。[ポリシーファイルを編集する](/ja/configuration/policy#edit-the-policy-file)を参照してください。
  </Step>
</Steps>

修復のたびに `status` を実行し直してください。ランタイムは次のツール呼び出しで再読み込みするため、再起動は必要ありません。
