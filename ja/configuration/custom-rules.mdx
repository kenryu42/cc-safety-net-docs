カスタムルールは、`git push` や `npm install -g` のように組み込みルールでは許可されるコマンドを、自分で書いた理由を添えてブロックします。ルールはルールブックのファイルに書き、各スコープの `rule.json` で読み込むルールブックを指定します。カスタムルールはブロックを追加するだけで、組み込みルールを緩和することはありません。

<Warning>
  旧形式のインライン設定ファイル（`.safety-net.json` と `~/.cc-safety-net/config.json`）は読み込まれなくなりました。[移行する](#migrate-legacy-configuration)まで、それらのルールは何もしません。
</Warning>

<Tip>
  [`/cc-safety-net` スキル](/ja/guides/skill)にルールを書かせることもできます。`/cc-safety-net block terraform destroy in this project` のように、やりたいことを説明してください。
</Tip>

## ルール設定ファイルの場所

CC Safety Net は 2 つのスコープからルールブックを読み込み、マージします。

1. **ユーザースコープ。** `~/.cc-safety-net/rules/rule.json`（`rule init --global` で作成）。すべてのプロジェクトに適用する個人の既定設定に使います。
2. **プロジェクトスコープ。** プロジェクトルートにある `.cc-safety-net/rules/rule.json`。ソース管理にコミットできる、チームやプロジェクト固有のルールに使います。

どちらのファイルもなければ、組み込みルールだけが適用されます。ユーザーの `.cc-safety-net/` があるディレクトリ（通常はホームディレクトリ）では、プロジェクトのパスがユーザー設定そのものになります。そのため、プロジェクトスコープに書き込む `rule` のサブコマンドは、そこでは実行を拒否します。[ユーザー設定ディレクトリでの rule](/ja/reference/cli/rule#rule-in-the-user-config-directory) を参照してください。

<span id="scope-merge-behavior"></span>

### スコープのマージ

- CC Safety Net はユーザースコープを先に読み込み、両スコープのルールブックを合わせて使います。
- 同じ名前のルールブックが両方のスコープにある場合は、ユーザー側が優先され、プロジェクト側のルールは使われません。警告が報告され、ランタイムは `degraded` になります。どちらかの名前を変えれば解消します。
- 各スコープの `overrides` は、そのスコープのルールにだけ適用されるため、プロジェクトの設定でユーザーのルールを無効にしたり書き換えたりすることはできません。ユーザーのルールを指定したプロジェクトのオーバーライドや、どのルールにも一致しないオーバーライドのキーは、警告付きで無視されます。
- `transparent_wrappers` と `command_tools` は、両スコープの内容を合わせて使います。

## ルールブックの設定元を管理する

`rule.json` の `rules` 配列の各項目は、ルールブックの設定元です。

| 設定元 | 例 | ルールブックのファイル |
| --- | --- | --- |
| ローカル | `project-rules` | プロジェクトでは `.cc-safety-net/rules/project-rules/rulebook.json`。ユーザースコープでは `~/.cc-safety-net/rules/` の下 |
| GitHub | `owner/repo#ref/<rulebook-name>` | そのリポジトリの `.cc-safety-net/rules/<rulebook-name>/rulebook.json`。`rule add` と `rule update` が自分のスコープの同じパスにコピーします |

`rule.json` を手で編集する代わりに、`rule` コマンドを使ってください。

```bash
# Add a local rulebook source
npx -y cc-safety-net rule add project-rules

# Add one rulebook from a GitHub repository and ref
npx -y cc-safety-net rule add kenryu42/cc-safety-net#main/example-rules

# Add every rulebook a repository publishes, from its default branch
npx -y cc-safety-net rule add acme/safety-rules

# Add selected rulebooks from a branch, tag, or commit
npx -y cc-safety-net rule add acme/safety-rules --ref v2 --only aws gcloud

# Re-fetch a single source, or every source when no source is given
npx -y cc-safety-net rule update example-rules

# List active rulebooks, rules, overrides, and wrappers
npx -y cc-safety-net rule list

# Remove a source (--delete-source also deletes a local source directory)
npx -y cc-safety-net rule remove example-rules --delete-source
```

プロジェクトスコープではなくユーザースコープを変更するには、`--global`（`-g`）を付けます。`--only` と `--ref` は[公式ルールブック](/ja/configuration/rulebooks#install)で、各サブコマンドとその出力やエラーは [`rule`](/ja/reference/cli/rule) で説明しています。

<span id="rulebooks-are-live-files"></span>

### ルールブックはライブファイル

ランタイムはツール呼び出しのたびに各 `rulebook.json` をディスクから読み取るため、保存した編集は次のコマンドから反映されます。存在しない、読み取れない、または無効なルールブックのルールは使われず、ランタイムは `degraded` を報告します。一度も取得していない GitHub の設定元がある場合は、`npx -y cc-safety-net rule update` を実行してください。[設定の復旧](/ja/configuration/recovery)を参照してください。

<span id="transparent-wrappers"></span>

## 透過ラッパー

透過ラッパーは、`timeout 5 git push` のように別のコマンドを実行するコマンドです。CC Safety Net は透過ラッパーを素通りして、その先で実行されるコマンドを検査します。そのため、組み込みルールもカスタムルールも、`timeout 5 docker system prune` には `docker system prune` と同じように適用されます。

次の 8 つのラッパーは組み込みで、設定は不要です：`caffeinate`、`exec`、`nice`、`nohup`、`setsid`、`stdbuf`、`time`、`timeout`。

チームが `rtk` のような別のラッパー経由でコマンドを実行しているなら、それを追加します。

```bash
# List configured wrappers for the project scope
npx -y cc-safety-net rule wrapper list

# Trust a wrapper, or stop trusting it
npx -y cc-safety-net rule wrapper add rtk
npx -y cc-safety-net rule wrapper remove rtk

# Operate on the user scope instead
npx -y cc-safety-net rule wrapper add rtk --global
```

- ラッパー名は `^[a-zA-Z][a-zA-Z0-9_-]*$` に一致し、ファイル内で一意でなければなりません。
- 予約されたコマンドはラッパーにできません。`git`、`busybox`、`rm`、`find`、`xargs`、`parallel`、すべてのシェルラッパー、すべてのインタープリター、awk のインタープリターが該当します。
- 追加するのは、子コマンドを書かれたとおりに実行するラッパーだけにしてください。

追加したラッパーは `rule.json` に保存されるため、`rule.json` を読み取れないと失われます。[`rule.json` で宣言する対象範囲](/ja/configuration/recovery#coverage-declared-in-rule-json)を参照してください。

<span id="community-shell-tools"></span>

## コミュニティ製のシェルツール

プラグインは、エージェントに独自のシェルツールを追加できます。たとえば `dsh-ops` プラグインは `ops_bash` と `ops_run_background` を追加します。CC Safety Net はこれらの名前を知らないため、パスの引数は検査しますが、`command` をシェルコマンドとしては読みません。宣言するまでは、`ops_bash` で `git reset --hard` を実行してもブロックされません。

ツールを宣言すると、CC Safety Net はそのコマンドを解析します。

```bash
# Declare one or more tools in the user config
npx -y cc-safety-net rule tool add ops_bash ops_run_background

# Name the argument that carries the working directory
npx -y cc-safety-net rule tool add ops_run_background --cwd-arg dir

# Write the project config instead
npx -y cc-safety-net rule tool add team_shell --project

# List every declared tool in both scopes, or stop analyzing one
npx -y cc-safety-net rule tool list
npx -y cc-safety-net rule tool remove ops_bash
```

これで `command_tools` 配列が書き込まれます。

```json
{
  "version": 1,
  "rules": [],
  "overrides": {},
  "transparent_wrappers": [],
  "command_tools": ["ops_bash", { "name": "ops_run_background", "cwd": "dir" }]
}
```

次のツール呼び出しから、宣言したツールの呼び出しには、組み込みのシェルツールと同じ組み込みルール、カスタムルール、安全レベルが適用されます。`ops_bash` で `git reset --hard` を実行すると、`git.reset-hard` でブロックされるようになります。

- 名前は、エージェントが送るツール名と大文字・小文字まで完全に一致させます。`rule tool add` は組み込みのツール名を拒否します。[`rule tool add` の名前のエラー](/ja/reference/cli/rule#rule-tool-add-name-errors)を参照してください。
- `cwd` には、作業ディレクトリを渡す引数の名前を指定します。指定しない場合は `workdir`、`cwd`、`working_directory` を読み、どれもなければセッションのワークスペースを使います。
- 作業ディレクトリが空白の場合は `tool-call.malformed`、存在しないディレクトリの場合は `cwd.requested-unusable` として呼び出しを拒否します。

宣言は `rule.json` に保存されるため、`rule.json` を読み取れないと、そのスコープのツールは失われます。ファイルを手で編集したら `npx -y cc-safety-net rule verify` を実行してください。

## 最初のカスタムルールを作る

<Steps>
  <Step title="rule.json を作成する">
    ```bash
    npx -y cc-safety-net rule init
    ```

    ルールブックの設定元が空の `.cc-safety-net/rules/rule.json` が作成されます。

    ```json
    {
      "version": 1,
      "rules": [],
      "overrides": {},
      "transparent_wrappers": []
    }
    ```

    `rule init --example` を使うと、`.cc-safety-net/rules/example-rules/rulebook.json` に例のルールブックも書き込みます。`npx -y cc-safety-net rule add example-rules` を実行するまでは有効になりません。
  </Step>
  <Step title="ルールブックを書く">
    `.cc-safety-net/rules/project-rules/rulebook.json` を作成します。

    ```json
    {
      "rulebook_version": 1,
      "name": "project-rules",
      "version": "1.0.0",
      "description": "Project-specific CC Safety Net rules.",
      "author": "project",
      "allowed_commands": ["git"],
      "rules": [
        {
          "name": "block-git-add-all",
          "command": "git",
          "subcommand": "add",
          "block_args": ["-A", "--all", "."],
          "reason": "Use 'git add <specific-files>' instead of blanket add."
        }
      ],
      "tests": [
        {
          "command": "git add -A",
          "expect": "blocked",
          "rule": "block-git-add-all"
        },
        {
          "command": "git add README.md",
          "expect": "allowed"
        }
      ]
    }
    ```
  </Step>
  <Step title="登録する">
    ```bash
    npx -y cc-safety-net rule add project-rules
    ```

    `rule.json` に `"rules": ["project-rules"]` が追加されます。次のコマンドから、`git add -A`、`git add --all`、`git add .` が、指定した理由とともにブロックされます。
  </Step>
  <Step title="検証する">
    ```bash
    npx -y cc-safety-net rule verify
    ```

    `rule verify` は両スコープの `rule.json` を確認し、各設定元をランタイムと同じ方法で読み込んで、バージョン 2 のフィクスチャを実行します。リモートのコンテンツを取得することはありません。
  </Step>
</Steps>

## `rule.json` のスキーマ

`rule.json` は、有効にするルールブックを選び、オーバーライドを適用し、透過ラッパーとコミュニティ製のシェルツールを宣言します。安全レベル、組み込みの保護、パスの許可と拒否、監査ログの保持期間は別のファイルで設定します。[ポリシー](/ja/configuration/policy)を参照してください。

<ParamField body="version" type="integer" required>
  スキーマのバージョンで、`1` でなければなりません。
</ParamField>

<ParamField body="rules" type="array">
  ルールブックの設定元を表す文字列のリストです。既定値は空の配列です。設定元の名前はファイル内で一意でなければならず、指定できる設定元は最大 64 個です。
</ParamField>

<ParamField body="overrides" type="object">
  `<rulebook-name>/<rule-name>` をキーとするルールのオーバーライドです。値は、ルールを無効にする `"off"` か、ルールのブロックメッセージを置き換えるオブジェクトです。オブジェクトでは `reason` が必須で、`intent` は任意です。`intent` を省略すると、ルール自身の `intent` がそのまま使われます。
</ParamField>

<ParamField body="transparent_wrappers" type="array">
  8 つの組み込みラッパーに加えて透過するコマンドです。既定値は空の配列です。項目は一意でなければならず、予約されたコマンドは指定できません。[透過ラッパー](#transparent-wrappers)を参照してください。
</ParamField>

<ParamField body="command_tools" type="array">
  プラグインのシェルツールです。CC Safety Net はその `command` を組み込みのシェルツールと同じように解析します。各項目は、ツール名か `{ "name": "ops_bash", "cwd": "dir" }` のようなオブジェクトです。既定値は空の配列です。名前は一意でなければならず、組み込みのツール名は指定できません。[コミュニティ製のシェルツール](#community-shell-tools)を参照してください。
</ParamField>

メッセージとエージェント向けの意図（`intent`）の両方を変えるオーバーライドは、次のようになります。

```json
{
  "version": 1,
  "rules": ["project-rules", "owner/repo#main/team-rules"],
  "overrides": {
    "project-rules/block-docker-system-prune": {
      "reason": "Use targeted Docker cleanup commands.",
      "intent": "use_alternative"
    },
    "team-rules/block-npm-global": "off"
  },
  "transparent_wrappers": ["rtk"]
}
```

### エディターでの `rule.json` 補完

CC Safety Net は `rule.json` の JSON Schema を公開しています。エディターにこのスキーマを指定すると、補完と検証が使えます。

```json
{
  "$schema": "https://raw.githubusercontent.com/kenryu42/cc-safety-net/main/assets/cc-safety-net.schema.json",
  "version": 1,
  "rules": [],
  "overrides": {},
  "transparent_wrappers": []
}
```

`rule verify` は、有効な `rule.json` にこの `$schema` 行がなければ追加します。`policy.json` のスキーマは公開されていません。

## ルールブックのスキーマ

各ルールブックは、それぞれ専用の `rulebook.json` ファイルに書きます。

<ParamField body="rulebook_version" type="integer" required>
  ルールブックのスキーマのバージョンで、`1` か `2` でなければなりません。それ以外の値は `rulebook_version must be 1 or 2` で検証に失敗します。[バージョン 2 のルール](#version-2-rules)を参照してください。
</ParamField>

<ParamField body="name" type="string" required>
  ルールブックの名前です。ローカルのディレクトリ名、または GitHub の設定元の名前と一致しなければなりません。
</ParamField>

<ParamField body="version" type="string" required>
  ルールブックのバージョン文字列です。
</ParamField>

<ParamField body="description" type="string">
  ルールブックの説明です。
</ParamField>

<ParamField body="author" type="string">
  ルールブックの作成者です。
</ParamField>

<ParamField body="allowed_commands" type="array" required>
  このルールブックでルールを定義できるコマンドです。
</ParamField>

<ParamField body="rules" type="array" required>
  カスタムのブロックルールです。[ルールのスキーマ](#rule-schema)を参照してください。
</ParamField>

<ParamField body="tests" type="array">
  任意のフィクスチャです。[フィクスチャのスキーマ](#fixture-schema)を参照してください。
</ParamField>

<span id="rule-schema"></span>

## ルールのスキーマ

以下のフィールドは、`rulebook_version` 1 のルールを定義します。バージョン 2 では、`subcommand` と `block_args` の代わりに `match` オブジェクトを使います。[バージョン 2 のルール](#version-2-rules)を参照してください。

<ParamField body="name" type="string" required>
  ルールブック内で一意な名前で、最大 64 文字です。先頭は英字で、そのあとに英字、数字、ハイフン、アンダースコアを続けます。
</ParamField>

<ParamField body="command" type="string" required>
  照合するベースコマンドです。`allowed_commands` に含まれていなければなりません。
</ParamField>

<ParamField body="subcommand" type="string">
  照合するサブコマンドです（`add` や `install` など）。省略すると、どのサブコマンドにも一致します。
</ParamField>

<ParamField body="block_args" type="array" required>
  ブロックのきっかけになる引数です。1 つ以上必要なため、バージョン 1 のルールではサブコマンドのすべての使い方をブロックすることはできません。その場合は[バージョン 2 のルール](#block-every-git-push)を使います。
</ParamField>

<ParamField body="reason" type="string" required>
  ルールがコマンドをブロックしたときに表示するメッセージで、最大 256 文字です。
</ParamField>

<ParamField body="intent" type="string">
  エージェントに伝える意図で、ブロックメッセージのフッターに追加されます。`hard_stop`、`use_alternative`、`scope_down`、`manual_only`、`stop_and_explain` のいずれかです。既定値は `manual_only` です。
</ParamField>

<span id="version-2-rules"></span>

## バージョン 2 のルール

`"rulebook_version": 2` を設定すると、サブコマンドと引数の組み合わせではなく、厳密なコマンドパスで照合します。`gcloud compute` の下の `delete` をブロックするバージョン 1 のルールは、コマンド中のどこかにそのトークンがあれば一致するため、`gcloud compute instances create delete` もブロックします。コマンドパスが `["compute", "instances", "delete"]` のバージョン 2 のルールは、これをブロックしません。

バージョン 2 のルールは、`name`、`command`、`reason`、`intent` をバージョン 1 から引き継ぎ、`subcommand` と `block_args` を `match` オブジェクトに置き換えます。

<ParamField body="match.command_path" type="array" required>
  コマンドの後ろに、この順で続かなければならないコマンドの語です。空でない文字列からなる空でない配列で指定します。パスは空にできないため、`aws` のすべての呼び出しのように、コマンドのあらゆる呼び出しに一致するルールは作れません。
</ParamField>

<ParamField body="match.any_args" type="array">
  これらのトークンのうち少なくとも 1 つが、引数の中にそのままの形で現れる必要があります。空でない一意な文字列からなる空でない配列です。省略すると、引数にかかわらずコマンドパスだけで照合します。
</ParamField>

<ParamField body="match.exclude_args" type="array">
  これらのトークンのいずれかが引数の中にそのままの形で現れると、ルールは一致しません。空でない一意な文字列からなる空でない配列です。
</ParamField>

バージョン 2 では、バージョン 1 のフィールドは無視されずにエラーになります。`subcommand` や `block_args` が残っているルールは、`rules[0].subcommand: not supported in rulebook_version 2` と `rules[0].block_args: not supported in rulebook_version 2` で検証に失敗します。

```json
{
  "rulebook_version": 2,
  "name": "terraform-rules",
  "version": "1.0.0",
  "allowed_commands": ["terraform"],
  "rules": [
    {
      "name": "block-terraform-apply-destroy",
      "command": "terraform",
      "match": {
        "command_path": ["apply"],
        "any_args": ["-destroy", "--destroy"]
      },
      "reason": "Review a destroy plan first with 'terraform plan -destroy'.",
      "intent": "use_alternative"
    }
  ],
  "tests": [
    {
      "command": "terraform apply -destroy",
      "expect": "blocked",
      "rule": "block-terraform-apply-destroy"
    },
    {
      "command": "terraform -chdir=infra apply",
      "expect": "allowed"
    }
  ]
}
```

<span id="fixture-schema"></span>

## フィクスチャのスキーマ

フィクスチャは、意図した動作を記録するものです。CC Safety Net はフィクスチャのコマンドをパースしてルールブックのルールで評価しますが、実行はしません。

<ParamField body="command" type="string" required>
  フィクスチャのシェルコマンドです。
</ParamField>

<ParamField body="expect" type="string" required>
  `blocked` か `allowed` のどちらかです。
</ParamField>

<ParamField body="rule" type="string">
  コマンドをブロックするはずのルールです。`blocked` のフィクスチャでは必須です。
</ParamField>

バージョン 1 のフィクスチャは形式だけを確認します。バージョン 2 のフィクスチャは、`rule add`、`rule update`、`rule verify` が評価します。`blocked` のフィクスチャは指定したルールが最初に一致すれば合格し、`allowed` のフィクスチャはどのルールにも一致しなければ合格します。

`rule add` と `rule update` は、フィクスチャが失敗した設定元を書き込む前に拒否します。失敗したフィクスチャは、`tests` 内のインデックスで示されます。

```text
tests[<index>]: expected "<rule>" to block "<command>" but no rule matched
tests[<index>]: expected "<rule>" to block "<command>" but "<other-rule>" matched first
tests[<index>]: expected "<command>" to be allowed but "<rule>" matched
tests[<index>]: could not parse fixture command: <command>
```

`rule verify` では、`example-rules/rulebook.json: tests[0]: ...` のように、各行の先頭にルールブックのファイルが付きます。

## 照合の挙動

| | バージョン 1 | バージョン 2 |
| --- | --- | --- |
| コマンド | 小文字の basename で照合します。`/usr/local/bin/npm` は `"command": "npm"` に一致します | バージョン 1 と同じです |
| 位置 | `subcommand` は、コマンドの後に続く最初のオプションでない引数です。`git --no-pager add -A` では `add` です。`block_args` のトークンはどこにあってもかまいません | 認識できるグローバルオプションを読み飛ばした後、コマンドの語が `command_path` と順序どおり一致する必要があります。パスより後ろの引数は影響しません |
| 引数 | `block_args` のトークンが 1 つでもあればブロックします | `any_args` のトークンが 1 つ以上必要で、`exclude_args` のトークンが 1 つでもあれば一致しません |
| 短いオプション | 分解します。`-Ap` は `-A` と `-p` として扱います | 展開しません。`-Ap` は `-Ap` のままなので、`"-destroy"` と `"--destroy"` のように書き方をすべて列挙してください |

どちらのバージョンも、トークンをそのままの形で、大文字と小文字を区別して照合します。正規表現、glob、部分一致はありません。`--all-files` は `--all` に一致しません。ルールは順番に評価され、最初に一致したルールがブロックします。

ルールは入れ子のコマンドにも適用されます。`rm` のルールがあれば、`bash -c 'rm -r ./tmpdir'`、`eval 'rm -r ./tmpdir'`、呼び出された関数の本体のいずれもブロックされます。組み込みのアナライザーが扱うコマンドも対象です。

<span id="version-2-global-options"></span>

### バージョン 2 のグローバルオプション

値を取るグローバルオプションを認識できるのは、`aws`、`gcloud`、`az` だけです。それ以外のコマンドでは、`git -C repo push` のように値を別の語として書いたオプションがあると、ルールは一致しません。Terraform の `-chdir=DIR` は 1 つのトークンなので読み飛ばされます。

リリースチャネルには別のルールが必要です。`gcloud beta compute instances delete` は `["compute", "instances", "delete"]` に一致しません。`["beta", "compute", "instances", "delete"]` で 2 つ目のルールを書いてください。

<Accordion title="バージョン 1 はオプションに続けて書いた値を誤読する">
  CC Safety Net は `-Cfoo` を `-C foo` ではなく `-C -f -o -o` として扱います。そのため、`-f` をブロックするルールが、オプションに続けて書かれた値に誤って一致することがあります。
</Accordion>

### ルールが照合するのはコマンドで、ファイルパスではない

カスタムルールが照合するのは、シェルコマンドとその引数です。エージェントが独自の読み取りツールや編集ツールで開くファイルは見えないため、`~/.zshrc` のようなファイルをルールで保護することはできません。ファイルやフォルダーへのアクセスをすべてブロックするには、`policy.json` の [`secret_protection.deny_paths`](/ja/configuration/policy#deny-paths) に追加してください。拒否パスは読み取りもブロックします。

## 例

<span id="block-every-git-push"></span>

### すべての git push をブロックする

`command_path: ["push"]` で `any_args` を指定しないバージョン 2 のルールは、引数にかかわらず `git push` をブロックします。バージョン 1 のルールでは、`block_args` に 1 つ以上の引数が必要なため、これはできません。

```json
{
  "rulebook_version": 2,
  "name": "project-rules",
  "version": "1.0.0",
  "allowed_commands": ["git"],
  "rules": [
    {
      "name": "block-git-push",
      "command": "git",
      "match": {
        "command_path": ["push"]
      },
      "reason": "A person pushes this repository. Commit locally and stop."
    }
  ],
  "tests": [
    {
      "command": "git push",
      "expect": "blocked",
      "rule": "block-git-push"
    },
    {
      "command": "git push --force origin main",
      "expect": "blocked",
      "rule": "block-git-push"
    },
    {
      "command": "git status",
      "expect": "allowed"
    }
  ]
}
```

`timeout` は[透過ラッパー](#transparent-wrappers)なので、このルールは `timeout 5 git push` もブロックします。一方、`git -C repo push` には一致しません。[バージョン 2 のグローバルオプション](#version-2-global-options)を参照してください。

<span id="turn-off-one-rule"></span>

### ルールを 1 つ無効にする

カスタムルールを無効にするには、そのルールブックを指定しているスコープの `rule.json` で、`overrides` に `<rulebook-name>/<rule-name>` のキーを値 `"off"` で追加します。このキーはブロックメッセージに表示されます。

```json
{
  "version": 1,
  "rules": ["project-rules"],
  "overrides": {
    "project-rules/block-git-push": "off"
  },
  "transparent_wrappers": []
}
```

ルールブックのファイル自体は変わらないため、`rule update` でオーバーライドが元に戻ることはありません。`git.push-force` のような組み込みルールを無効にするには、`policy.json` を使います。[ブロックされたコマンドを許可する](/ja/reference/blocked-commands#allow-a-blocked-command)を参照してください。

### npm のグローバルインストールをブロックする

```json
{
  "rulebook_version": 1,
  "name": "project-rules",
  "version": "1.0.0",
  "allowed_commands": ["npm"],
  "rules": [
    {
      "name": "block-npm-global",
      "command": "npm",
      "subcommand": "install",
      "block_args": ["-g", "--global"],
      "reason": "Global npm installs can cause version conflicts. Use npx or local install."
    }
  ],
  "tests": [
    {
      "command": "npm install -g typescript",
      "expect": "blocked",
      "rule": "block-npm-global"
    },
    {
      "command": "npm install typescript",
      "expect": "allowed"
    }
  ]
}
```

## ブロックメッセージの形式

ブロックメッセージ全体のレイアウトは[ブロック時の表示](/ja/guides/how-it-works#what-a-block-looks-like)で説明しています。カスタムルールでは、どのルールブックがブロックしたかが分かるように、ルールブック名とルール名が先頭に付きます。

```text
BLOCKED by CC Safety Net

Reason: [project-rules/block-git-add-all] Use 'git add <specific-files>' instead of blanket add.

Command: git add -A
```

先頭の `<rulebook-name>/<rule-name>` は、`rule.json` の `overrides` で[ルールを無効にする](#turn-off-one-rule)ときや、理由を置き換えるときに使うキーでもあります。

<span id="migrate-legacy-configuration"></span>

## 旧形式の設定を移行する

CC Safety Net は、旧形式のインライン設定ファイル（`.safety-net.json` と `~/.cc-safety-net/config.json`）を読み込まなくなりました。それらのルールは何もせず、ランタイムも警告を出しません。残っているファイルは、`npx -y cc-safety-net doctor` と `rule verify` が `Legacy inline rule configs are ignored` として報告します。

```bash
# Convert legacy inline rules into the rulebook layout
npx -y cc-safety-net rule migrate

# Optionally delete verified legacy files after migration
npx -y cc-safety-net rule migrate --cleanup

# Validate the migrated rules
npx -y cc-safety-net rule verify
```

`rule migrate` には `--global` がなく、両方のスコープを移行します。ホームディレクトリで実行すると、プロジェクト側の移行は省略されます。[ユーザー設定ディレクトリでの `rule migrate`](/ja/reference/cli/rule#rule-migrate-in-the-user-config-directory) を参照してください。

インラインのファイルは、次の構成に変換されます。

```text
.cc-safety-net/rules/rule.json                    # project rulebook sources + overrides
.cc-safety-net/rules/project-rules/rulebook.json  # migrated project rules
~/.cc-safety-net/rules/rule.json                  # user rulebook sources + overrides
~/.cc-safety-net/rules/user-rules/rulebook.json   # migrated user rules
```

## カスタムルールの設定が無効な場合

読み込みに失敗したカスタムルールの設定は、コマンドを拒否するのではなく破棄されます。ほかの設定元と組み込みルールは適用され続け、ランタイムは `degraded` を報告します。ブロックが減っても通知されないため、ルールを編集したときやアップグレードしたときは `npx -y cc-safety-net status` を実行してください。[設定の復旧](/ja/configuration/recovery)を参照してください。

<Warning>
  カスタムルールの設定は改ざんへの耐性がありません。`rule.json` とルールブックのファイルはエージェントが編集できます。保護されているパスは `policy.json` だけです。カスタムルールを手で追加・変更したら、`npx -y cc-safety-net rule verify` で検証してください。
</Warning>
