カスタムのブロックルールを使うと、チームの規約やプロジェクト固有の安全ポリシーを強制できます。ルールは **rulebook ベースの構成**を採用し、ユーザースコープとプロジェクトスコープの内容をマージします。これにより、個人の既定値を保ちつつ、プロジェクト側で上書きできます。

<Warning>
**破壊的変更** — 旧形式のインライン設定ファイル（`.safety-net.json` と `~/.cc-safety-net/config.json`）は、実行時に読み込まれなくなりました。これらにルールが含まれている場合、**移行するまでそのルールは何も保護しません**。ランタイムは旧形式のファイルを黙って無視し、`rule verify` だけが警告を表示します。通常のコマンドはこれまでどおり動作します。`npx -y cc-safety-net rule migrate` を実行して、旧形式のルールを rulebook 構成に変換してください。[旧形式の設定を移行する](#migrate-legacy-configuration)を参照してください。
</Warning>

<Tip>
カスタムルールを作る最も手軽な方法は、エージェント内で **`/cc-safety-net` スキル**を使い、自然言語で対話的にルールを作成することです。例：

  ```text
  /cc-safety-net read my package.json and suggest blocking rules
  /cc-safety-net set up rules to block all terraform destroy commands
  /cc-safety-net verify my rules and fix any errors
  ```

エージェントがスキルに対応していない場合は、次のように指示してください。

  ```text
  run npx -y cc-safety-net rule doc and help me set up custom rules
  ```
</Tip>

## ルール設定ファイルの場所

CC Safety Net は、2 つのスコープから rulebook を読み込んでマージします。

1. **ユーザースコープ** — `~/.cc-safety-net/rules/rule.json`（`rule init --global` で作成）。すべてのプロジェクトに適用したい個人の既定値に使います。
2. **プロジェクトスコープ** — プロジェクトルートの `.cc-safety-net/rules/rule.json`。バージョン管理にコミットできる、チームやプロジェクト固有のルールに使います。

ローカルの rulebook は、`project-rules` のような単純な名前で参照します。GitHub 上の rulebook は `owner/repo#ref/<rulebook-name>` の形式で参照し、そのリポジトリ内の `.cc-safety-net/rules/<rulebook-name>/rulebook.json` を指します。

### スコープをマージするときの挙動

- 両スコープの rulebook を、ユーザースコープを先にして結合します。
- **有効な rulebook の名前が重複した場合は、先に名前を確保した側が優先されます。** ユーザースコープを先に読み込むため、そこで確保された名前は同名のプロジェクト rulebook を覆い隠します。後から読み込まれた rulebook は、一部のルールだけが隠れるのではなく、まったく読み込まれません。この衝突は警告として報告され、ランタイムは `degraded` 状態になります。どちらかの名前を変更して `rule sync` を実行してください。衝突は致命的な問題ではなく解決済みとして扱われるため、もう一方のスコープがすでに使っている名前でも、片方のスコープの `rule sync` は成功します。
- **各スコープの `overrides` は、そのスコープ自身のルールにのみ適用されます。** ユーザースコープのルールを指定したプロジェクト側の override は警告とともに無視され、そのルールはユーザー設定の状態を保ちます。プロジェクトの設定から、ユーザーのルールを無効にしたり書き換えたりすることはできません。
- どの既知のルールにも一致しない override のキーは、警告とともに無視されます。他の override とルールは設定どおりのまま有効です。
- `transparent_wrappers` は、両スコープの内容を統合します。

どちらの場所にも設定が見つからない場合は、組み込みのルールだけが適用されます。

## rulebook の参照先を管理する

rulebook の参照先は、`rule.json` の `rules` 配列のエントリで指定します。指定できるのは次の 2 種類です。

- **ローカル** — `project-rules` のような単純な名前です。rulebook は `.cc-safety-net/rules/project-rules/rulebook.json`（プロジェクト）または `~/.cc-safety-net/rules/project-rules/rulebook.json`（ユーザー）に置きます。ローカルの参照先は、設定ディレクトリの外に出てはいけません。
- **GitHub** — `owner/repo#ref/<rulebook-name>` の形式で、そのリポジトリと ref にある `.cc-safety-net/rules/<rulebook-name>/rulebook.json` を指します。

参照先の追加・更新・削除には、`rule.json` やロックファイルを直接編集するのではなく `rule` コマンドを使ってください。

```bash
# Add a local rulebook source and sync
npx -y cc-safety-net rule add project-rules

# Add a GitHub rulebook source (creates a lock entry pinned by SHA-256 digest)
npx -y cc-safety-net rule add kenryu42/cc-safety-net#main/example-rules

# Refresh the lock and cache after editing sources
npx -y cc-safety-net rule sync

# Update a single source, or all sources when no source is given
npx -y cc-safety-net rule update example-rules

# List active rulebooks and their resolved sources
npx -y cc-safety-net rule list

# Remove a source (--delete-source also deletes a local source directory)
npx -y cc-safety-net rule remove example-rules --delete-source
```

`--global`（`-g`）を付けると、プロジェクトスコープではなくユーザースコープを対象に実行します。`rule` の各サブコマンドとそのオプション、終了時の挙動は、[CLI コマンド](/ja/reference/cli-commands)を参照してください。

<span id="resource-limits"></span>

### リソース制限

`rules` 配列に指定できる参照先は、スコープごとに最大 **64** 件です。これを超えるエントリを持つ `rule.json` は、`Rule config exceeds CC Safety Net's safe source limit.` という 1 件のエラーで検証に失敗します。件数超過の配列はエントリごとに個別報告されず、他の無効な `rule.json` と同じように、そのスコープの設定全体が実行中のスナップショットから破棄されます。

`rule sync` は決められた上限の中で動作します。同時に処理する参照先は最大 **4** 件、1 回の実行で発行する GitHub リクエストは最大 **131** 件、すべての参照先を合わせて読み取るレスポンスは最大 **64 MiB** です。いずれかの上限を超えると、`Rule synchronization exceeds CC Safety Net's safe resource limits.` を表示して処理を中止します。

### ロックとキャッシュ

設定されたすべての参照先は SHA-256 のダイジェストで `rule.lock` ファイルに固定され、その rulebook は `.cc-safety-net/cache/rulebooks/` 配下にキャッシュされます。実行時、CC Safety Net はキャッシュ済みの rulebook をダイジェストと照合して検証します。この検証中に、書き込み・取得・キャッシュのいずれも行いません。

検証に失敗したときの挙動は、どちら側が壊れているかによって異なります。

- **ロックファイルがない、ロックのエントリがない、キャッシュのエントリがない、ダイジェストが一致しない、キャッシュ済み rulebook をパースできない**場合、その参照先は実行中のスナップショットから破棄されます。`rule sync` を実行するまで、そこからルールは読み込まれません。検証に成功した他の参照先とすべての組み込み保護は適用され続け、通常のコマンドも動き続けます。破棄された参照先は、作業をブロックするのではなく、ランタイムを `degraded` にします。
- 一方、ローカルの参照先が固定済みのダイジェストと**食い違っている**場合（ディスク上で見つからない、パースできない、スキーマに適合しない場合を含む）は、障害とは扱われません。ランタイムはダイジェスト検証済みの**キャッシュ**しか読まず、ローカルのファイルを読み直すことはないためです。ローカルでの編集は、`rule sync` を実行するまで反映されません。なお、`rule sync` と `rule verify` は、無効なローカル参照先やシンボリックリンクになっている参照先を拒否します。

状態遷移の全体像、診断メッセージの正確な文言、修復手順については、[設定の復旧](/ja/configuration/recovery)を参照してください。

## transparent wrapper

チームが `rtk` のようなラッパー経由でコマンドを実行している場合、解析は既定ではラッパーだけを見て、その下で実際に動くコマンドまでは見ません。`transparent_wrappers` にラッパーを登録すると、CC Safety Net はラッパーを透過して、その先にある保護対象の子コマンドを解析できるようになります。その結果、`rtk git reset --hard` や `rtk docker system prune` に対しても、ラッパーなしのコマンドとまったく同じように、組み込みの解析とカスタムルールの両方が適用されます。

ラッパーの設定には、`rule.json` を直接編集するのではなく `rule wrapper` サブコマンドを使ってください。

```bash
# List configured wrappers for the project scope
npx -y cc-safety-net rule wrapper list

# Trust a wrapper, or stop trusting it
npx -y cc-safety-net rule wrapper add rtk
npx -y cc-safety-net rule wrapper remove rtk

# Operate on the user scope instead
npx -y cc-safety-net rule wrapper add rtk --global
```

このフィールドのルールは次のとおりです。

- **組み込みの既定値はありません。** 意図的に信頼するラッパーだけを設定してください。
- ラッパー名は `^[a-zA-Z][a-zA-Z0-9_-]*$` に一致し、ファイル内で一意である必要があります。
- **予約済みのコマンドはラッパーにできません。** 対象は `git`、`busybox`、解析対象の組み込みコマンドである `rm`、`find`、`xargs`、`parallel`、すべてのシェルラッパー、すべてのインタープリター、および awk 系のインタープリターです。
- 透過処理では、ラッパーのフラグと `VAR=value` 形式の代入を読み飛ばした後の最初の*保護対象になりうる*子コマンド、または明示的な `--` の直後のトークンを探します。子コマンド自体が保護対象になりえない場合、透過処理は行いません。
- ここに登録されて**いない**ラッパーや、子コマンドをそのまま exec せずに書き換えたり隠したりするラッパーは、透過処理の対象になりません。そうしたコマンドを拾える可能性があるのは、トップレベルの危険な文字列に対するフォールバックスキャンだけです。

<Warning>
`transparent_wrappers` は、ロックもダイジェストも持たない `rule.json` の中にあります。あるスコープの `rule.json` が読み取れなくなると、そのスコープのラッパー設定は適用されなくなります。設定が実行中のスナップショットから破棄されたときに、組み込みの保護範囲まで狭まるのはここだけです。**rulebook** の側が破棄された場合（キャッシュのエントリがない、ロックのエントリがない、ダイジェストの不一致）でも、`rule.json` 自体は読み取れるためラッパー設定は維持されます。
</Warning>

## 最初のカスタムルールを作る

まず、プロジェクト用のルール設定のひな形を作成します。

```bash
npx -y cc-safety-net rule init
```

これで、まだ何も有効になっていない `.cc-safety-net/rules/rule.json` が作成されます。rulebook の参照先はまだ設定されていない状態です。

```json
{
  "version": 1,
  "rules": [],
  "overrides": {},
  "transparent_wrappers": []
}
```

`--example` を付けると、サンプルの rulebook も `.cc-safety-net/rules/example-rules/rulebook.json` に書き出されます（この時点ではまだ有効になりません）。書き出されるのはそのファイルがまだ存在しない場合だけで、`rule init` はそれを参照先として登録しないため、有効にするには自分で参照先として追加する必要があります。

```bash
npx -y cc-safety-net rule init --example
npx -y cc-safety-net rule add example-rules
```

独自の rulebook を作る場合は、`.cc-safety-net/rules/project-rules/rulebook.json` を作成し、`npx -y cc-safety-net rule add project-rules` で登録します。すると `rule.json` は次のようになります。

```json
{
  "version": 1,
  "rules": ["project-rules"],
  "overrides": {},
  "transparent_wrappers": []
}
```

ルールの定義は、この rulebook ファイルの中に書きます。

```json
{
  "rulebook_version": 1,
  "name": "project-rules",
  "version": "1.0.0",
  "description": "Project-specific CC Safety Net rules.",
  "author": "project",
  "allowed_commands": ["git"],
  "rules": [
    {
      "name": "block-git-add-all",
      "command": "git",
      "subcommand": "add",
      "block_args": ["-A", "--all", "."],
      "reason": "Use 'git add <specific-files>' instead of blanket add."
    }
  ],
  "tests": [
    {
      "command": "git add -A",
      "expect": "blocked",
      "rule": "block-git-add-all"
    },
    {
      "command": "git add README.md",
      "expect": "allowed"
    }
  ]
}
```

rulebook を編集したら、次を実行します。

```bash
npx -y cc-safety-net rule sync
npx -y cc-safety-net rule verify
```

`rule sync` で編集した rulebook が有効になり、続く `rule verify` で有効な設定を検証します。

これで、`git add -A`、`git add --all`、`git add .` が、指定したメッセージとともにブロックされます。

## `rule.json` のスキーマ

最上位の `rule.json` は、どの rulebook を有効にするかを選び、override を適用し、transparent wrapper を宣言します。安全レベル、組み込み保護、パスの許可と拒否、監査ログの保持期間を設定する `policy.json` とは別のファイルです。`policy.json` については[ポリシー](/ja/configuration/policy)を参照してください。

<ParamField body="version" type="integer" required>
スキーマのバージョン。`1` である必要があります。
</ParamField>

<ParamField body="rules" type="array">
rulebook の参照先を表す文字列のリストです。既定値は空の配列です。参照先の名前はファイル内で一意である必要があり、指定できるのは最大 64 件です。[リソース制限](#resource-limits)を参照してください。
</ParamField>

<ParamField body="overrides" type="object">
`<rulebook-name>/<rule-name>` をキーとするルールの上書き設定です。値には、ルールを無効にする `"off"` か、ルールのブロックメッセージを差し替えるオブジェクトを指定します。オブジェクト形式では `reason` が必須で、`intent` は任意です。`intent` を省略した場合、ルール本来の intent は変わりません。
</ParamField>

<ParamField body="transparent_wrappers" type="array">
保護対象の子コマンドをそのまま実行するコマンド名です。解析はこれらを透過して子コマンドを見ます。既定値は空の配列です。各項目は一意で、予約済みコマンドであってはいけません。[transparent wrapper](#transparent-wrappers)を参照してください。
</ParamField>

メッセージとエージェント向けの intent の両方を変更する override は、次のようになります。

```json
{
  "version": 1,
  "rules": ["project-rules", "owner/repo#main/team-rules"],
  "overrides": {
    "project-rules/block-docker-system-prune": {
      "reason": "Use targeted Docker cleanup commands.",
      "intent": "use_alternative"
    },
    "team-rules/block-npm-global": "off"
  },
  "transparent_wrappers": ["rtk"]
}
```

### エディターでの `rule.json` 補完

CC Safety Net は、ランタイムが検証に使うのと同じ定義から生成した `rule.json` の JSON Schema を公開しています。エディターにこのスキーマを指定すると、補完と検証が効くようになります。

```json
{
  "$schema": "https://raw.githubusercontent.com/kenryu42/cc-safety-net/main/assets/cc-safety-net.schema.json",
  "version": 1,
  "rules": [],
  "overrides": {},
  "transparent_wrappers": []
}
```

このスキーマがカバーするのは、上で説明した `rule.json` のフィールド（`version`、`rules`、`overrides`、`transparent_wrappers`）だけです。`rule verify` を実行すると、この `$schema` の指定がない有効なルール設定に対して、指定が自動的に追加されます。`policy.json` に対応する公開スキーマはありません。

## rulebook のスキーマ

各 rulebook は、それぞれ独自の `rulebook.json` ファイルとして存在します。

<ParamField body="rulebook_version" type="integer" required>
rulebook のスキーマバージョン。`1` である必要があります。
</ParamField>

<ParamField body="name" type="string" required>
rulebook の名前。ローカルのディレクトリ名、または GitHub 参照先の名前と一致している必要があります。
</ParamField>

<ParamField body="version" type="string" required>
rulebook のバージョン文字列。
</ParamField>

<ParamField body="description" type="string">
rulebook の説明文。
</ParamField>

<ParamField body="author" type="string">
rulebook の作成者。
</ParamField>

<ParamField body="allowed_commands" type="array" required>
この rulebook でルールを定義できるコマンド。
</ParamField>

<ParamField body="rules" type="array" required>
カスタムのブロックルールです。[ルールのスキーマ](#rule-schema)を参照してください。
</ParamField>

<ParamField body="tests" type="array">
rulebook のフィクスチャ（任意）です。[フィクスチャのスキーマ](#fixture-schema)を参照してください。フィクスチャは意図した動作を記録するためのもので、CC Safety Net は形式だけを検証し、実行はしません。
</ParamField>

<span id="rule-schema"></span>

## ルールのスキーマ

<ParamField body="name" type="string" required>
rulebook 内で一意である必要があります。先頭は英字で、以降は英数字、ハイフン、アンダースコアが使えます。最大 64 文字です。
</ParamField>

<ParamField body="command" type="string" required>
照合するベースコマンド。`allowed_commands` に記載されている必要があります。
</ParamField>

<ParamField body="subcommand" type="string">
照合するサブコマンド（`add`、`install` など）。省略した場合は、すべてのサブコマンドに一致します。
</ParamField>

<ParamField body="block_args" type="array" required>
ブロックのきっかけとなる引数です。1 つ以上必要です。
</ParamField>

<ParamField body="reason" type="string" required>
ブロック時に表示するメッセージ。最大 256 文字です。
</ParamField>

<ParamField body="intent" type="string">
ブロックメッセージの末尾に付与される、エージェントの次の行動の指針です。`hard_stop`、`use_alternative`、`scope_down`、`manual_only`、`stop_and_explain` のいずれかを指定します。既定値は `manual_only` です。
</ParamField>

<span id="fixture-schema"></span>

## フィクスチャのスキーマ

フィクスチャは、意図した動作を記録するための任意の項目です。形式のみが検証され、CC Safety Net が実行することはありません。

<ParamField body="command" type="string" required>
フィクスチャとなるシェルコマンド。
</ParamField>

<ParamField body="expect" type="string" required>
`blocked` または `allowed` のいずれか。
</ParamField>

<ParamField body="rule" type="string">
そのコマンドをブロックすると想定されるルール。`blocked` のフィクスチャでは必須です。
</ParamField>

## 照合の挙動

CC Safety Net は、次のルールで照合します。

- **コマンドの正規化**：コマンドは照合前にベース名へ変換されます。`/usr/local/bin/npm` は `"command": "npm"` のルールに一致します。
- **サブコマンドの判定**：サブコマンドは、コマンドの後にある最初のオプションでない引数です。`git --no-pager add -A` のサブコマンドは `add` です。
- **引数の照合**：`block_args` の引数はリテラルとして照合されます。正規表現や glob には対応していません。
- **短いオプションの展開**：`-Ap` のようにまとめて書かれた短いフラグは、照合前に分解されます。`-Ap` は `-A` と `-p` として扱われます。
- **長いオプションの照合**：長いオプションは文字列の完全一致で照合します。`--all-files` は `--all` に一致**しません**。
- **いずれか 1 つでも一致すればブロック**：`block_args` のうち 1 つでもコマンドに含まれていれば、そのコマンドはブロックされます。
- **追加のみ可能**：カスタムルールで追加できるのは新しい制限だけです。組み込みの保護を迂回することはできません。

<Note>
**既知の制限**：`-Cfoo` は `-C foo` ではなく `-C -f -o -o` として扱われます。そのため `-f` をブロックしていると、オプションに続けて書かれた値によって誤検知が起きることがあります。
</Note>

## 例

<AccordionGroup>

## ブロックメッセージの形式

ブロックメッセージ全体の構成は、[ブロック結果の形式](/ja/guides/how-it-works#ブロック結果の形式)で説明しています。カスタムルールの場合は rulebook 名とルール名がプレフィックスとして付くため、どの rulebook によるブロックかがわかります。

```text
BLOCKED by CC Safety Net

Reason: [project-rules/block-git-add-all] Use 'git add <specific-files>' instead of blanket add.

Command: git add -A
```

プレフィックスの形式は `<rulebook-name>/<rule-name>` です。これは、`rule.json` の `overrides` でルールを無効化（`"off"`）したり理由を差し替えたりするときに使うキーでもあります。

## rulebook を検証する

rulebook を作成または編集したら、次のコマンドで検証します。

```bash
npx -y cc-safety-net rule sync
npx -y cc-safety-net rule verify
```

- `rule sync` は、設定された rulebook の参照先についてロックとキャッシュを再構築します。
- `rule verify` は、設定内容、ロックとキャッシュの状態、ローカルの rulebook、および共有可能な GitHub 参照先用の rulebook ディレクトリを検査します。リモートのコンテンツは取得しません。

## 旧形式の設定を移行する

旧形式のインライン設定ファイル（`.safety-net.json` と `~/.cc-safety-net/config.json`）は、**実行時に読み込まれなくなりました**。

| 旧形式ファイルの状態 | 新しい動作 |
| --- | --- |
| 空の旧形式ファイル | 黙って無視される。組み込みルールのみが適用される |
| ルールを含む旧形式ファイル | `rule migrate` で移行するまで、そのルールは**何も保護しない**。ランタイムはファイルを黙って無視する |
| 無効な旧形式ファイル | 同上。修正して移行するか削除するまで、何も保護しない |

旧形式のルールが元の場所から強制されることはなく、逆に作業をブロックすることもありません。ランタイムは旧形式のファイルをまったく参照しないため、ガードの実行時には何も現れません。残っている旧形式ファイルについて警告するのは `npx -y cc-safety-net rule verify` です。アップグレード後に実行してください。

```bash
# Convert legacy inline rules into the rulebook layout
npx -y cc-safety-net rule migrate

# Optionally delete verified legacy files after migration
npx -y cc-safety-net rule migrate --cleanup

# Validate the migrated rules
npx -y cc-safety-net rule verify
```

**移行前** — ルールを直接埋め込んだ 1 つの設定ファイル：

```text
.safety-net.json                # project rules (inline)
~/.cc-safety-net/config.json    # user rules (inline)
```

**移行後** — `rule migrate` が rulebook ベースの構成を自動的に作成します：

```text
.cc-safety-net/rules/rule.json                    # project rulebook sources + overrides
.cc-safety-net/rules/project-rules/rulebook.json  # migrated project rules
~/.cc-safety-net/rules/rule.json                  # user rulebook sources + overrides
~/.cc-safety-net/rules/user-rules/rulebook.json   # migrated user rules
```

## カスタムルールの設定が無効な場合

検証できないカスタムルールの設定は、**破棄され、強制されず、それ自体が拒否に変わることもありません**。通常のコマンドは動き続け、検証に成功した他の参照先は強制を続け、組み込みの保護もすべて適用されたままです。状況が分かるように、ランタイムは自身を `degraded` として報告します。

破棄された参照先は拒否を増やすのではなく、それまで提供していた拒否を**取り除く**方向に働くため、この種の失敗が単独で作業の引っかかりになることはありません。`npx cc-safety-net status` は、負荷の軽い日常的な確認手段です。失敗とフォールバックの対応表、診断メッセージ、表示箇所、修復手順については、[設定の復旧](/ja/configuration/recovery)を参照してください。

<Warning>
カスタムルールの設定に**改ざん耐性はありません**。`rule.json`、rulebook、ロックファイル、キャッシュはいずれもベストエフォートで、保護対象パスとして扱われるのは正規のユーザー `policy.json` だけです。カスタムルールを手作業で追加・変更した場合は、必ず `npx -y cc-safety-net rule verify` で検証してください。
</Warning>
