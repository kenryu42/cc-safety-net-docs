バグ報告、機能要望、技術的な分析は [GitHub Issues](https://github.com/kenryu42/cc-safety-net/issues) で受け付けています。プルリクエストの作成は、招待されたコラボレーターに限定されています。このページでは、貢献の方針、Issue 報告のルール、開発環境のセットアップ、プロジェクトの規約を説明します。詳細なガイドは、ソースリポジトリの [CONTRIBUTING.md](https://github.com/kenryu42/cc-safety-net/blob/main/CONTRIBUTING.md) を参照してください。

## プルリクエストではなく Issue を作成する

プルリクエストを作成できるのは、招待されたコラボレーターだけです。修正や改善を希望する場合は、実装に時間をかける前に、問題の内容を Issue に書いてください。検出ルール、設定の変更、ドキュメントの訂正、小さなバグ修正も、すべて Issue から始めます。提案が受け入れられても、それだけでプルリクエストが認められるわけではありません。

AI が生成した投稿により、外部からの貢献をレビューする手間が増えています。もっともらしいパッチであっても、問題の確認、変更内容の把握、プロジェクト全体への影響の確認、修正のやり取りは、誰かが行わなければなりません。メンテナー自身もコーディングエージェントを使って修正を実装しているため、依頼のないプルリクエストをレビューして作り直すより、詳細な Issue 報告のほうが早く問題を解決できることも多くあります。特に役立つのは、再現手順と技術的な分析です。

CC Safety Net のスコープは明確です。コーディングエージェントによる、`rm -rf ~/` や `git reset --hard` のようなデータ損失につながる意図しない誤操作を防ぐことに絞っています。汎用のセキュリティ強化ツールや攻撃防止ツールではありません。

## バグを報告する

Issue のほとんどはコーディングエージェントが書いています。ソースリポジトリの `AGENTS.md` では、Issue を作成する前に `CONTRIBUTING.md` を読むようエージェントに指示しています。エージェントでも人でも、次のルールに従ってください。

- まず既存の Issue を検索してください（`gh issue list --search "<keywords>" --state all`）。すでに報告されている問題であれば、新しい Issue を立てずに、その Issue へ新たな根拠を追加してください。
- 1 つの Issue で扱う問題は 1 件だけにしてください。
- 問題は最新リリースで再現してください。実際に自分で実行した再現手順だけを書き、実行できなかった場合はそう明記してください。
- 冒頭に問題と根拠を書いてください。何をして、何を期待し、何が起きたかです。報告は簡潔にまとめてください。
- CC Safety Net のバージョン、OS、コーディングエージェントまたは CLI とそのバージョン、CC Safety Net のインストール方法を記載してください。`npx cc-safety-net doctor --json` でほとんどが揃い、カスタムルールが関係しているかどうかも分かります。
- 原因の分析は歓迎します。根拠の後ろに置き、テストやトレースで確認できていない場合は仮説として明記してください。
- パッチや diff は添付しないでください。提案する修正内容は文章で説明してください。
- 提出する前に、作業を依頼した相手に Issue の内容を確認してもらってください。

コマンドの判定が誤っている場合、つまり破壊的なコマンドが許可された場合や、安全なコマンドがブロックされた場合は、次の情報も記載してください。

- コマンド全体。マッチしたセグメントだけでなく、チェーン全体を記載してください。
- 作業ディレクトリと安全レベル。
- `npx cc-safety-net explain --cwd <dir> "<command>"` の出力。
- すでに発生したブロックについては、`npx cc-safety-net logs` のエントリ（`npx cc-safety-net logs --id <id> --json`）。
- 判定がどうあるべきだったか、その理由。

破壊的コマンドの見落としは、脆弱性ではなく公開のバグとして扱います。非公開で報告すべき少数の問題は、[セキュリティポリシー](/ja/security)に記載しています。

提出する前に、資格情報とトークンを削除してください。ログはシークレットをマスクしますが、ファイルパスはマスクしません。プライベートなディレクトリ名は `<project>` と `~` に置き換え、コマンドがそのまま再現できるようにパスの構造は残してください。

## 機能を要望する

解決したい問題、望む挙動、それが役立つ具体的な場面を説明してください。上記のルールはそのまま適用されます。まず検索すること、1 つの Issue で扱う要望は 1 件だけにすること、パッチを添付しないことです。

## 開発環境をセットアップする

ここから先は、招待されたコラボレーターと、ローカルでビルドする人に向けた内容です。

- **Bun 1.4.2**：ビルドとテストに必須のランタイムで、サポートされる唯一のパッケージマネージャーです（[インストールガイド](https://bun.sh/docs/installation)）。`package.json` の `packageManager` で固定しています。
- **Node.js 18 以降**：ビルド成果物を実行するためのランタイムです。公開されている CLI やプラグインの実行に Bun は不要です。
- **Claude Code** または **OpenCode**：プラグインをローカルで読み込んで動作を確認する場合にのみ必要です。プロジェクトのビルドやテストスイートの実行には不要です。

```bash
git clone https://github.com/kenryu42/cc-safety-net.git
cd cc-safety-net
bun install
bun run build
bun run check
```

`bun run check` が唯一のゲートです。Oxlint、コードコメントのチェック、Oxfmt によるフォーマットチェック、TypeScript の型チェック、`knip` によるデッドコード検出、`jscpd` による重複検出、カバレッジ付きのテストスイート、カバレッジしきい値チェックを、この順に実行します。変更が一段落したら、このコマンドを 1 回実行してください。`AGENTS.md` では、これが必須の最終チェックであり、個々のコマンドを追加の最終チェックとして別に実行しないよう定めています。

作業中は、個別のコマンドも使えます。

```bash
bun run lint          # Lint (Oxlint, type-aware)
bun run lint:comments # Code-comment check
bun run format        # Format (Oxfmt)
bun run typecheck     # TypeScript
bun run knip          # Dead-code detection
bun test              # Full test suite
bun test tests/gate                          # One directory or file
bun test --test-name-pattern "checkout"      # Tests matching a pattern
bun run build         # Build for distribution
bun run gui:dev       # Dashboard that rebuilds the page on every load
```

## ローカルプラグインをテストする

ビルドしてからローカルのプラグインを読み込むと、実際のブロックを試せます。

- **Claude Code**：インストール済みの safety-net プラグインを無効にして Claude Code を終了し、リポジトリのルートで `claude --plugin-dir .` を実行します。
- **OpenCode**：`~/.config/opencode/opencode.json` の `plugin[]` 配列を、ビルド済みの `file://.../cc-safety-net/dist/index.js` に向けます。競合を避けるため npm の `cc-safety-net` の項目を削除し、OpenCode を再起動します。`/status` を実行し、プラグイン名が `dist` と表示されることを確認します。

安全な除外専用 pathspec を使って、既知のブロックが働くことを確認します。`git checkout -- ':(exclude,top)**'` はブロックされなければなりません。保護が有効になっていない場合も、この pathspec はファイルを 1 つも選択しません。

## コード規約に従う

| 規約 | ルール |
| --- | --- |
| ビルド／テストのランタイム | Bun 1.4.2 |
| 公開時のランタイム | Node.js 18+ |
| パッケージマネージャー | bun のみ（`bun install`、`bun run`） |
| フォーマッター／リンター | Oxfmt と、type-aware モードの Oxlint |
| 型 | 基本は型推論に任せ、export や可読性のために必要な場合だけ明示的に型注釈を付けます。`type \| undefined` より `type \| null` を推奨します |
| ファイル名 | `kebab-case`。`docs/` 内のファイルも小文字の kebab-case にします |
| 関数／型の命名 | 関数は `camelCase`、型は `PascalCase` |
| 定数 | `SCREAMING_SNAKE_CASE`（reason 定数など） |
| import | パッケージ内では相対 import |
| テスト | `src/` と同じ構成で `tests/` に配置し、`src/` 内には置きません |
| ビルド出力 | `dist/` は変更対象外です。lefthook の pre-commit hook が再ビルドします |

### スタイルガイド

- 本当に組み合わせや再利用が必要な場合を除き、コードは 1 つの関数にまとめます。
- `try`／`catch`、`any` 型、`else` 節は避け、早期 return を使います。
- `for` ループより配列メソッド（`flatMap`、`filter`、`map`）を優先します。`filter` には型ガードを使い、後続処理でも型推論が効くようにします。
- `let` より `const` を優先し、再代入ではなく三項演算子か早期 return を使います。
- 1 回しか使わない値は名前を付けずにインライン化し、不要な分割代入は避けます。

### スコープを厳守する

このプロジェクトでは、過剰設計を避けてください。要求を満たす最小の変更を実装します。それ以上を追加する場合は、その追加で防げる具体的な失敗を示してください。チェックには、実際に反証できる条件が必要です。実データがない段階で、スキーマ、バリデーター、レジストリ、ハーネスを作らないでください。プロセスは、コードで強制する前に文書化してください。

### Knip

`knip.ts` の `ignoreIssues` に項目を追加してはいけません。knip が未使用の export を報告した場合は、根本原因を修正します。本当に不要なコードは削除するか export を外し、テスト専用の export には `/** @internal */` の JSDoc コメントを付けます（knip は `--production` モードで動作するため、テストファイルは対象外です）。barrel ファイルからは未使用の名前を削除します。

## 招待されたコラボレーターがプルリクエストを作成する

変更を実装する前に、関連する Issue でメンテナーとスコープを合意してください。

1. `main` からブランチを作成します。
2. `AGENTS.md` と上記の規約に従います。
3. 挙動を変える場合は、まず意味のあるテストを書いて失敗させ、修正によってそのテストが通ることを確認します。新しいルールにはテストが必要で、カバレッジは 90% 以上にします。
4. 開発中は対象を絞ったテストを実行し、変更が完了したら `bun run check` を実行します。エラーなく完了する必要があります。
5. その変更が影響するホスト CLI のそれぞれで、該当する挙動を確認します。
6. サポート対象の CLI、主要な機能、Quick start のコマンドが変わらないかぎり、`README.md` は変更しません（`AGENTS.md` を参照）。`package.json` のバージョンも変更しません。
7. コミットメッセージは conventional commit 形式にします。
8. Issue にリンクしたプルリクエストを作成します。問題、変更内容、検証方法を説明してください。

バージョンの更新とリリースはメンテナーのみが行います。`package.json` や `plugin.json` のバージョンを直接変更しないでください。

## 開発の支援を得る

- `bunx cc-safety-net doctor` でセットアップを確認できます。
- `bunx cc-safety-net explain "<command>"` を使うと、コマンドがどう解析されるかを段階ごとに確認できます。
- アーキテクチャと規約はソースリポジトリの `CLAUDE.md` または `AGENTS.md` を参照し、コードをレビューする前に `REVIEW.md` を読んでください。
- 実装パターンは `src/gate/analyzer/` の既存コードを、テスト用ユーティリティは `tests/helpers.ts` を参照してください。
- バグの報告や機能の要望は、上記のルールに従って [GitHub Issue](https://github.com/kenryu42/cc-safety-net/issues) を作成してください。
