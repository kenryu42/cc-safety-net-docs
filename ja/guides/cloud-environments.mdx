クラウドセッションは誰もサインインしないマシンの上で動き、タスクが終わればマシンは回収されます。CC Safety Net をそこへ届ける経路は、リポジトリ、環境のセットアップスクリプト、コンテナイメージの 3 つです。どれも通常のパッケージで動作します。

## クラウド VM で変わること

VM は使い捨てでも、クラウドセッションは実在のリモートにプッシュします。`git push --force` はチームメイトがプルするブランチを書き換え、`git reset --hard` はセッションの未コミットの作業を失わせます。インフラ作業向けに用意された環境では、有効なクラウドの資格情報を使って `terraform destroy` や `aws s3 rm` も実行できます。これらは[公式ルールブック](/ja/configuration/rulebooks)がブロックするコマンドです。リポジトリにコミットした拒否のレイヤーは、そのリポジトリをクローンするすべてのセッションに適用されます。

## Claude Code のクラウドセッションとセルフホスト環境

[Claude Code on the web](https://code.claude.com/docs/en/claude-code-on-the-web) は、フックを含む設定をリポジトリにコミットされたファイルから読みます。次の 2 つをそろえると、クラウドセッションがポリシーを適用します。

<Steps>
  <Step title="プロジェクトポリシーをコミットする">
    `.cc-safety-net/policy.json` と、`.cc-safety-net/rules/` 配下のプロジェクトルールブックをコミットします。セッションはリポジトリと一緒にそれらをクローンします。[チームセットアップ](/ja/guides/team-setup)で開発者のマシン向けにコミットするのと同じ設定です。

    クラウドセッションには自前のユーザーポリシーファイルがないため、プロジェクトファイルが指定していない箇所には組み込みの既定値が適用されます。メンバーがローカルで使っているプリセットを当てにせず、セッションのプリセットはプロジェクトファイルで設定してください。
  </Step>
  <Step title="フックをセッションに入れる">
    環境にセットアップスクリプトがあるかどうかで、方法は 2 つに分かれます。

    環境の[セットアップスクリプト](https://code.claude.com/docs/en/cloud-environments)、またはセルフホスト環境の元になるイメージでは、通常のインストールを実行します。

    ```bash
    npx -y cc-safety-net@latest install --claude-code
    ```

    ターゲットフラグを付けるとインストールは非対話になります。確認用のターミナルが要らないため、ヘッドレスで実行できます。

    セットアップスクリプトがない場合は、フックのエントリ自体を `.claude/settings.json` としてコミットします。

    ```json
    {
      "hooks": {
        "PreToolUse": [
          {
            "matcher": "*",
            "hooks": [
              { "type": "command", "command": "npx -y cc-safety-net@latest hook --coding-cli" }
            ]
          }
        ]
      }
    }
    ```

    `hook --coding-cli` は正規のフックエントリポイントで、インストール済みのプラグインが呼び出すものと同じです。ツール呼び出しのたびに `npx` の起動コストがかかるため、セットアップスクリプトがある環境ではそちらを選んでください。
  </Step>
</Steps>

どちらの形式も、インストール時または呼び出し時にネットワークからパッケージを取得します。ネットワークにアクセスできない環境では、代わりにパッケージをイメージに含めておく必要があります。

CC Safety Net は[監査ログ](/ja/reference/audit-log)をセッションのホームディレクトリに書き込むため、ログは VM と一緒に消えます。また、フックが入っていなくてもセッションは何も知らせません。環境ごとに一度、ポリシーが拒否するコマンドをセッションに実行させ、ブロックされることを確認してください。`npx -y cc-safety-net@latest explain "git reset --hard"` を使えば、コマンドを実行せずに、現在の設定が下す判定を確認できます。

## Amp の Orb スレッド

Amp にはコンテナごとの手順が要りません。`npx -y cc-safety-net@latest install --amp` はプラグインを Amp アカウントに公開するため、Orb を含むリモート実行のスレッドもカバーされます。プラグインにはユーザーポリシーのスナップショットが含まれ、ポリシーファイルのないマシンではそれが適用されます。ユーザーポリシーを編集したら、インストールを再実行してください。[Amp Code のポリシースナップショット](/ja/installation/amp-code#amp-code-policy-snapshot)を参照してください。

## devcontainer とコンテナイメージ

自分でビルドするコンテナでは、ビルド時にインストールを実行します。次の Dockerfile で動作します。

```dockerfile
FROM node:22-slim
RUN apt-get update && apt-get install -y --no-install-recommends git ca-certificates \
    && rm -rf /var/lib/apt/lists/*
RUN npm install -g @anthropic-ai/claude-code
RUN npx -y cc-safety-net install --claude-code
```

この順序から、ビルド時の要件が 2 つ出てきます。

- **`git` と `ca-certificates` が必要です。** Claude Code のインストールはプラグインのマーケットプレイスを追加し、その際に HTTPS でクローンします。slim 系のベースイメージにはどちらも入っていません。
- **エージェント CLI を先にインストールします。** インストーラーはエージェント自身のプラグインコマンドを呼び出すため、エージェントより先に CC Safety Net をインストールするビルドは失敗します。

devcontainer では、同じコマンドを `postCreateCommand` に書きます。

```json
{
  "postCreateCommand": "npx -y cc-safety-net@latest install --claude-code"
}
```

[チームセットアップ](/ja/guides/team-setup)の `process.env.CI` ガードは付けないでください。ここではエージェントがコンテナ内で動くため、インストールが必要です。

## 人の承認が必要なまま残るもの

保護のインストールは自動化できますが、保護を緩めることは自動化できません。クラウド VM でもノート PC でも同じです。エージェントはポリシーの提案を起草できても、`policy apply` は実行できません。[エージェントは policy apply を実行できない](/ja/reference/cli/policy#agents-cannot-run-policy-apply)を参照してください。
