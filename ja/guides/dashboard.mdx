`cc-safety-net gui` を実行すると、ローカルのダッシュボードが開きます。このマシン上での判定を確認し、JSON を手で編集せずにポリシーを変更できます。何がブロックされたのか、その理由は何か、どの設定を変更できるのかを一望できます。

このページでは、ダッシュボードの機能と、元に戻せない操作を説明します。`policy.json` のスキーマは[ポリシー](/ja/configuration/policy)、rulebook の作り方は[カスタムルール](/ja/configuration/custom-rules)、監査レコードのスキーマは[監査ログ](/ja/reference/audit-log)を参照してください。

## ダッシュボードを起動する

```bash
cc-safety-net gui
```

このコマンドはダッシュボードの URL を出力し、既定のブラウザーで開きます。

```text
CC Safety Net policy GUI: http://127.0.0.1:52341/?token=...
```

ブラウザーを起動せずに URL だけを取得したい場合は、`--no-open` を指定します。SSH 経由での利用、コンテナ内での実行、特定のブラウザープロファイルに URL を貼り付けたい場合に便利です。

```bash
cc-safety-net gui --no-open
```

`--no-open` は、`-h, --help` を除けば唯一指定できるフラグです。それ以外の引数を渡すと、`Usage: cc-safety-net gui [--no-open]` を表示して 0 以外の終了コードで終了します。

ブラウザーを起動できなかった場合でも、処理自体は失敗しません。原因となったエラーに続けて `Open this URL manually: <url>` を出力し、サーバーはそのまま動き続けます。サーバーは `Ctrl-C` で停止するまでフォアグラウンドで動作します。

<span id="local-loopback-scope"></span>

### ローカルループバックに限定されている

このダッシュボードはホスティングされたサービスではありません。サーバーはローカルのループバックインターフェースだけで待ち受けます。

- サーバーは、**`127.0.0.1` の一時ポートにのみ**バインドします。LAN 上の他のマシンからは接続できません。
- 起動のたびに新しいランダムなトークンを生成し、URL に埋め込みます。すべてのリクエストにこのトークンが必要で、状態を変更するリクエストではリクエストヘッダーにもトークンが必要です。トークンのないリクエストは `403` で拒否します。
- JSON のリクエストボディが 1 MiB を超える場合は、パースする前に `413` とエラー `Request body is too large` を返して拒否します。そうしなければ、ボディ全体がメモリ上に載ってしまうためです。
- レスポンスには `cache-control: no-store` を設定します。

トークンは stdout に出力されるため、このコマンドを起動した人はトークンを読み取れます。ブラウザーのページが動作するのはそのためですが、同時に、`cc-safety-net gui` を自分で実行したエージェントも、同じトークンで保護されたエンドポイントに到達できます。後述のプロジェクトポリシーの適用も含まれます。トークンが締め出せるのは、別のページと、この 1 行を見ていないプロセスです。起動した本人は締め出せません。ただし直接の経路は塞がれたままです。エージェントがコマンドで `policy.json` を編集する操作や、`cc-safety-net policy apply` を実行する操作は、引き続き拒否されます。

ページがデータ取得のために外部へ通信することはありません。表示する内容はすべて、ローカルのポリシーファイルと監査ログから取得します。例外は、任意で有効にする更新チェックと、概要画面に表示される GitHub のスターボタンだけです。

<Note>
トークンは起動のたびに変わるため、前回のセッションで保存した URL は使えません。`cc-safety-net gui` を実行し直して、新しい URL を取得してください。
</Note>

## 6 つの画面

サイドバーには 6 つの画面があります。画面ごとに URL のハッシュが決まっているため、同じセッション内であればリンクやブックマークを作成できます。

| 画面 | ハッシュ | 確認できること |
| --- | --- | --- |
| **概要**（Overview） | `#overview` | 最近、このマシンで CC Safety Net がどのように動作したか |
| **アクティビティ**（Activity） | `#activity` | エージェントが実行した各コマンドと、その判定結果 |
| **保護**（Protections） | `#policy` | CC Safety Net がブロックする操作 |
| **カスタムルール**（Custom rules） | `#rules` | 現在実際に適用しているカスタム rulebook のルール |
| **エージェント**（Agents） | `#integrations` | このマシンで hook をインストール済みのコーディングエージェント |
| **設定**（Settings） | `#settings` | ログの保持期間、ファイルの場所、リセットの方法 |

認識できないハッシュを指定した場合は、概要画面にフォールバックします。カスタムルール画面は、最初に開いたときに rulebook を読み込みます。エージェントは起動時に検出します。概要画面に hook の状態を表示するためです。

保護が無効になっている場合や、設定のエラーによってランタイムがフォールバックの設定を適用している場合は、すべての画面の上部にバナーが表示されます。状態ごとに 1 行ずつ、次の文言が並びます。

- `Command protection is off: built-in destructive command rules are not enforced. Catastrophic and custom rules still apply.`
- `Secret protection is off: sensitive files and deny paths are not blocked.`
- `A fallback configuration is being enforced: <reason>`

保護画面以外では、バナーの末尾に `Open Protections` のリンクが付きます。バナーが反映するのは保存済みのポリシーで、未保存の編集内容は反映されません。

### URL に保持される絞り込み

アクティビティ、保護、カスタムルールの各画面は、`#activity?decision=error` のようにハッシュに付けたパラメーターを読み取ります。アクティビティ画面と保護画面では、絞り込みを変えるたびに URL がその場で書き換わります。既定値のままの絞り込みは URL に含まれません。そのため、再読み込みしてもブラウザーの「戻る」で戻っても絞り込んだ状態が復元され、サイドバーのリンクからは常に既定の絞り込みで画面が開きます。

| 画面 | パラメーター | 値 |
| --- | --- | --- |
| アクティビティ | `days` | 表示期間の日数。既定は `7` で、保持期間を超える値は保持期間に切り詰められます |
| アクティビティ | `decision` | `deny`（画面上の `Blocked`。既定）、`allow`、`error`、`suspect`、`all` のいずれか |
| アクティビティ | `agent` | 監査ログに記録されたエージェント名。既定は `all` |
| アクティビティ | `q` | 検索文字列 |
| アクティビティ | `command` | コマンドの形式。この形式に完全一致するエントリだけを表示します |
| 保護 | `q` | 検索文字列。ルール ID と一致する場合は、そのルールの位置までスクロールします |
| 保護 | `show` | `changed` を指定すると、既定から変更した保護だけを表示します。既定は `all` |
| カスタムルール | `focus` | カスタムルールの ID。`custom.` の接頭辞はあってもなくてもかまいません。そのルールを強調表示し、その位置までスクロールします |
| カスタムルール | `compose` | `What should be blocked?` の欄にあらかじめ入力する文字列 |

## 概要

概要画面には、累計ではなく**保持されている期間**の集計が表示されます。対象は直近 7 日間です。保持期間が 7 日未満の場合は、その全期間を集計します。タイルと Most-triggered rules の見出しには、集計期間が `last N days` の形で表示されます。

**状態カード。** 画面上部のカードには、次のいずれかの見出しが表示されます。

| 見出し | 表示される条件 |
| --- | --- |
| `Your policy file needs repair` | 保存済みのポリシーファイルにエラーがある |
| `Checking your agents…` | エージェントの検出が終わっていない |
| `Not checking any agent yet` | 検出したエージェントのどれにも、有効な hook がない |
| `Partly protected` | コマンド保護かシークレット保護が無効になっている |
| `Protected` | 上記のいずれにも当てはまらない |

見出しの下には、まず preset が表示されます。override によって preset と異なる状態になっている場合は `, customized` が付きます。続いて、有効なコマンドルールの数とシークレット保護が有効かどうか、または無効になっている保護が表示されます。最後に、hook が有効なエージェントの名前が並びます。hook が有効なエージェントが 1 つもない場合、カードのリンクはエージェント画面（`Install a hook`）を指します。それ以外の場合は保護画面（`Configure`、ファイルにエラーがあるときは `Repair`）を指します。このカードが反映するのは**保存済み**のポリシーだけです。保護画面で編集した未保存の内容は、保存するまで反映されません。

**Needs attention。** 対応が必要な項目があるときだけ表示される一覧です。各項目は、対応する場所へのリンクになっています。

- `<Agent> is detected but its hook is disabled.`：エージェント画面を開きます。
- `N blocks in the last N days look like a false positive.`：誤検知の候補に絞ったアクティビティ画面を開きます。
- `N guard errors in the last N days: commands blocked because evaluation failed, not by policy.`：エラーに絞ったアクティビティ画面を開きます。これは fail closed による拒否で、CC Safety Net が解析を完了できなかったためにコマンドを拒否したものです。繰り返し発生する場合は、[トラブルシューティング](/ja/guides/troubleshooting)を参照してください。
- `Version <version> is available.`：GitHub のリリースノートを開きます。

**タイル。** `Blocked` と `Commands checked` の 2 つのタイルに、件数と、古い日から新しい日の順に並ぶ日別のスパークラインが表示されます。スパークラインはそれぞれ独自の最大値を基準にするため、2 つのタイルは棒の高さで比べられません。数値のほうを見てください。

**Recent blocks。** 直近にブロックされたコマンド 8 件を、時刻、エージェント、コマンド、ルール ID とともに表示します。評価の失敗による拒否には、ルール ID の代わりに `guard error` と表示されます。`custom.*` のルール ID を持つ行を選ぶと、カスタムルール画面でそのルールが開きます。組み込みのルール ID を持つ行はその ID を検索欄に入れた状態のアクティビティ画面へ、ルール ID のない行はアクティビティ画面へ移動します。`All activity` もアクティビティ画面を開きます。

**Most-triggered rules。** 対象期間にブロックの多かったルール ID の上位 5 件を、`N blocks` の形の件数とともに表示します。選んだときの遷移先は Recent blocks と同じです。

## アクティビティ

アクティビティ画面には、エージェントが実行したコマンドが新しい順に表示されます。日ごとの見出しは `Today`、`Yesterday`、それ以前は日付です。コマンドは、ログに書き込まれる前にシークレットのマスク処理を受けます。マスクの対象は認識済みの資格情報の形式だけなので、エントリにはパス、ホスト名、各種の名前が残ることがあります。この画面の内容を共有する前に、レコードのスキーマとマスクの対象範囲を[監査ログ](/ja/reference/audit-log#secret-redaction)で確認してください。

<span id="windows-are-derived-from-retention"></span>

### 表示期間は保持期間から決まる

表示期間の選択肢は**固定ではありません**。設定した監査ログの保持期間から算出されます。候補となる 7、30、90、180、365 日のうち保持期間より短いものだけを表示し、保持期間そのものを最も広い選択肢として必ず加えます。そのため、すでに削除済みの履歴を表示できるかのように見せる選択肢は現れず、保持されているログには常に全期間アクセスできます。

| 保持期間 | 表示する期間 |
| --- | --- |
| 5 日 | 5 |
| 14 日 | 7、14 |
| 30 日（既定） | 7、30 |
| 90 日 | 7、30、90 |
| 365 日 | 7、30、90、180、365 |

アクティビティ画面は、直近 7 日間を表示した状態で開きます。URL で保持期間内の別の期間を指定した場合（保持期間 30 日で `days=14` など）は、その期間も選択肢に加わります。

どの期間も、今日を含めたローカルの暦日単位で区切られます。そのため、概要画面の日別スパークラインの合計は、表示された総数と正確に一致します。保持期間より広い期間を要求した場合は拒否されます。保持期間を短くすると、現在選択中の期間も新しい範囲内に収まるよう調整されます。保持期間の設定方法と適用のされ方は、[監査ログ](/ja/reference/audit-log#retention)を参照してください。

### 絞り込み

- **判定**：`Blocked`、`Allowed`、`All` は常に件数付きで表示されます。既定は `Blocked` で、ガードのエラーもここに含まれます。`Errors` は対象期間にガードのエラーがある場合、`Likely false positive` はヒューリスティックが候補を見つけた場合だけ表示されます。このヒューリスティックは、失敗ステージが記録された拒否か、同じセッション内で 2 回以上拒否されたコマンドの形式を候補にします。
- **検索**：`Search commands or rule IDs` の欄は、ルール ID とコマンド文字列に対して照合します。大文字・小文字の違いと前後の空白は無視します。
- **エージェント**：`All agents` と、エージェントごとの選択肢を件数付きで並べたセレクターです。対象期間に 2 種類以上の既知のエージェントがある場合だけ表示されます。
- **期間**：前述のとおり、保持期間から決まる選択肢です。
- **コマンドの形式**：URL の `command` パラメーターで、1 つのコマンドの形式に完全一致するエントリだけに絞り込めます。`Showing blocks of <command>` の行にその形式が表示され、`Show all blocks` で解除できます。判定を選び直したり検索欄に入力したりしても解除されます。

一覧を読み込み直したときに意味をなさなくなった絞り込みは、自動的にリセットされます。選択中のエージェントがいなくなった場合は `All agents` に、対象期間にエラーや誤検知の候補がなくなった場合は `Blocked` に戻ります。既定の絞り込みで何もブロックされていない場合は、`Nothing was blocked in the last N days.` と表示され、`Show all activity` のボタンが付きます。

### 再読み込み

ページ見出しの横にある再読み込みのアイコン（`Refresh activity`）は、概要とアクティビティの**両方**を読み込み直します。そのため、タイルと一覧の内容が食い違うことはありません。読み込みが終わるまで、ボタンは操作できません。

### 表示されるエントリと件数

一覧に表示されるのは最大 **500 件**です。この上限は判定の種類ごとに分け合い、各種類には上限の半分が確保されたうえで、使われなかった分を他の種類に融通します。そのため、拒否が大量にあっても、許可されたエントリが完全に押し出されることはありません。

一方、件数の集計にはこの 500 件の上限は適用されません。判定とエージェントの件数、タイル、Most-triggered rules の数値は、一覧に表示されるエントリとは別に、サーバー側で対象期間全体を集計した結果です。例外は `Likely false positive` の件数で、これはページが読み込んだエントリから算出します。

フッターには `Showing X of Y entries from the last N days.` と表示されます。X は現在の絞り込みで表示しているエントリの数、Y は対象期間のエントリの総数です。上限によって一覧が切り詰められた場合は、`Only the newest 500 entries of each decision are loaded; narrow the time window to see older ones.` が加わります。

件数そのものが不足するケースが 1 つあります。監査ログの一部を読み取れなかった場合、フッターに `N log files could not be read, so this list is incomplete.` が加わります。この場合は集計からもそれらのエントリが抜け落ちるため、読み取れるようになるまで、一覧も件数も総数ではなく下限として扱ってください。

<Note>
一覧を見て結論を出す前に、フッターを読んでください。`Showing 500 of 4,120 entries` は、一覧が直近の一部にすぎない一方で、判定ごとの件数は 4,120 件すべてを反映していることを意味します。
</Note>

### エントリごとの操作

各行には、時刻、判定のバッジ（`Blocked`、`Allowed`、`Error`）、エージェント、コマンド、ルール ID が表示されます。行を選ぶと展開されます。展開した行には、行内で途切れていた場合はコマンド全体が表示され、その下に操作ボタン、さらに該当する詳細項目として `Full command`（照合したセグメントがコマンド全体と異なる場合）、`Reason`、`Rule`、`Folder`、`Time` が並びます。組み込みのルール ID は保護画面の該当ルールへ、`custom.*` のルール ID はカスタムルール画面の該当ルールへのリンクになっています。

- ブロックされたエントリ（エラーを含む）には **Report false positive** があります。次の節を参照してください。
- 許可されたエントリには **Block this in future** があります。選ぶと、`What should be blocked?` の欄にそのコマンドが入力された状態でカスタムルール画面が開きます。ルールが自動的に作られるわけではありません。下記の[カスタムルール](#custom-rules)を参照してください。
- すべてのエントリに **Copy log entry** があり、監査レコードそのものを JSON としてコピーします。各フィールドの意味は[監査ログ](/ja/reference/audit-log#record-schema)を参照してください。

### 誤検知を報告する

**Report false positive** を選ぶと、`Report a false positive` のダイアログが開きます。このダイアログは、プロジェクトの誤検知報告フォームを使って**公開**の GitHub Issue を用意します。どの項目も編集できます。

- `Why should it have been allowed? (optional)`：空欄のままなら送信されません。
- `Title`：<code>{'[False Positive]: <rule-id> blocked \u0060<command>\u0060'}</code> の形で入力済みです。コマンドの部分は、ブロックされたセグメントの 1 行目を最大 80 文字に切り詰めたものです。
- `Blocked command`：コマンド全体です。
- `Audit log entry`：JSON 形式のエントリです。

ダイアログは項目を埋める前に、プロジェクトのパスを `<project>` に、ホームディレクトリを `~` に置き換えます。それ以外のパスや名前は残るため、公開したくない内容は編集してください。`Open GitHub form` を選ぶと、これらの項目を入力した状態の Issue フォームが新しいタブで開きます。GitHub 上で自分が送信するまで、何も送信されません。

入力済みの URL が 8,000 文字を超える場合は、収まるまで最も長い項目から省き、省いた項目をクリップボードにコピーします。`Report too long to prefill` のメッセージに、フォームに貼り付けるべき項目が示されます。クリップボードを使えない場合は、どの項目が省かれたかが示されます。

## 保護

保護画面では、CC Safety Net が何をブロックするかを設定します。URL のハッシュは `#policy` です。この画面にあるのはすべて**組み込み**の保護です。安全 preset、破壊的コマンドのルール、CC Safety Net に同梱されるシークレット保護のパターンが含まれます。自作の rulebook はこれとは別の仕組みで、ここでは編集しません。

画面上部には、編集するポリシーを切り替える `My policy` と `Project policy` のボタンと、`Test a command` のボタンがあります。この画面が書き込むファイルのフィールドごとの仕様は、[ポリシー](/ja/configuration/policy)にまとめてあります。

### 保存済みと未保存

編集内容はいったん下書きとして溜まり、保存したときにだけ適用されます。

- 下書きがディスク上の内容と異なる場合は、保存バーが表示されます。保存バーには `N unsaved changes` の形で変更の数と、最大 3 件の変更内容が表示され、**Discard** と **Save** のボタンが付きます。
- どの画面にいても、サイドバーの保護画面のリンクに `Unsaved` と表示されます。
- 下書きは、同じブラウザーセッション内であれば再読み込みしても残り、`Restored your unsaved changes` と表示されます。保存、破棄、修復、リセットのいずれかを行うと消えます。
- 未保存の変更がある状態でページを離れようとすると、確認を求められます。

保存するとポリシーファイルを書き込み、そのパスを表示します。ディスク上のポリシーにエラーがある間は、ダッシュボードが保護画面に切り替わります。このとき、フォームの各項目には、ランタイムがディスクから救済した値ではなく組み込みの既定値が表示されます。ファイルの内容を表示するのは Policy JSON のカードだけです。この状態では **Save** が無効になるため、画面上の既定値でファイルを上書きしてしまうことはありません。先にポリシーを修復してください。修復後は、残せた設定を使ってフォームを読み込み直します。

<span id="draft-a-project-policy"></span>

### プロジェクトポリシーを下書きする

画面上部の `Project policy` を押すと、保護画面全体がプロジェクトファイルの下書きに切り替わります。プロジェクトの下書きは保存済みのポリシーから始まるため、未保存の変更がある場合は、先にそれを破棄するかどうかを確認されます（`Discard unsaved changes?`）。下書きバーには `Editing the project policy` と書き込み先のパスが表示され、そのファイルが従う原則が示されます。`Only settings tagged Project are written. Everything else keeps following each person's own policy. Click a Project tag to stop setting that field.`

`My policy` を押すと、自分のポリシーの編集に戻ります。下書きに変更がある場合は、戻る前に確認を求められます。`Change folder…` は、OS 標準のディレクトリ選択が使える場合に、下書きの対象を別のディレクトリに切り替えます。確認に同意すると、現在の下書きは破棄されます。変更しないかぎり、対象はダッシュボードを起動したディレクトリです。

**マークと継承。** 各コントロールには、表示している値の出どころを示すタグが付きます。`Inherited` は、そのフィールドをプロジェクトファイルに書かず、各メンバーが自分の値を使い続けるという意味です。`Project` は下書きがそのフィールドを書き込むという意味で、タグをクリックすると継承に戻ります。コントロールを編集すると、そのフィールドがマークされます。下書き中にルールの `Reset` を押した場合も、そのルールは継承に戻ります。マークされたパスのリストにはプロジェクト自身の項目だけが表示されるため、マークした直後は空の状態から始まります。自分の個人的なパスがリポジトリに公開されることはありません。

**確認して適用する。** **Save** は **Review and apply** に変わります。押すとサーバーに差分を要求し、`Apply this project policy?` のダイアログを開きます。ダイアログには `Everyone who works in this project gets these settings on top of their own policy.` という説明、書き込み先のパス、実効ポリシーの変更前後を並べた `Setting` / `Now` / `After` の表が表示されます。片側にフィールドがない場合は `(unset)` になります。差分がなければ、表の代わりに `No change to the effective policy.` と表示されます。表の下には、下書きがユーザーポリシーに対して緩和するフィールドごとに 1 行ずつ警告が並びます。文言は[ポリシー](/ja/configuration/policy#reported-weakenings)に記載のものと同じです。ディスク上の既存ファイルが読み取れない場合は、`The existing project policy file is invalid and will be replaced.` も加わります。表と警告は `CC_SAFETY_NET_PROJECT_TIGHTEN_ONLY` を考慮しないため、このスイッチを設定していないメンバーに適用される内容を示します。`Apply project policy` を押すとファイルが書き込まれます。既定でフォーカスされるのは Cancel です。

下書き中に **Discard** を押すと、確認のうえで、下書きをプロジェクトファイルにすでにある設定に戻します。

差分の読み込み中にフォームを編集すると、確認をやり直すことになります。このとき `Review again` と `The draft changed while the review was loading.` が表示されます。別のタブがプロジェクトのディレクトリを変更した場合は、新しい対象で下書きを読み込み直して `The project folder changed` と表示し、適用前にもう一度確認するよう求めます。

**下書きを開始できない場合。** ユーザーポリシーにエラーがあると、ランタイムはそれを保護的な既定値に切り替えます。その値をもとに下書きを作ると、既定値がチームの継承元であるかのように見えてしまいます。そのためダッシュボードは `Repair your policy first` と表示して、下書きの開始を拒否します。サーバー側でエラーが見つかった場合は、`Your own policy file must be repaired before you can edit a project policy.` と診断メッセージも表示されます。プロジェクトファイルが存在するのに読み取れない場合は扱いが異なります。下書きは空の状態で始まり、そのファイルの診断メッセージをフォームの上に表示します。

**対象がユーザー設定ディレクトリの場合。** ユーザーの `.cc-safety-net/` があるディレクトリで起動すると、下書きの書き込み先はユーザーポリシーになってしまいます。それでも下書き自体は開くため、`Change folder…` は使えます。ただし下書きバーの下に診断メッセージが 1 行表示され、すべてのコントロールは `Inherited` のままで、確認と適用はどちらも同じ内容で失敗します。

```text
<dir>/.cc-safety-net/policy.json is the user policy, not a project policy; choose a project directory, or run the GUI from one
```

`Review and apply` では `Review failed` と表示されます。`Change folder…` でプロジェクトのディレクトリを選べば、下書きは通常どおり読み込まれます。別のタブがプロジェクトのディレクトリを変更していた場合は、上記の下書きの読み込み直しが先に起こります。どのディレクトリが対象になるか、`CC_SAFETY_NET_HOME` やシンボリックリンク経由のホームディレクトリをどう解決するかは、[ポリシー](/ja/configuration/policy#the-user-config-directory-is-not-a-project)を参照してください。

**CLI と同じ保証。** この下書きは、`cc-safety-net policy check` と `cc-safety-net policy apply` をフォームにしたものです。書き込むのは、設定したフィールドだけを持つ同じファイルです。差分もランタイムの同じユーザーベースラインに対して取り、確認するまで何も書き込みません。ファイルの仕様と 2 つのスコープのマージ規則は、[ポリシー](/ja/configuration/policy#project-policy)を参照してください。

違いは 1 つだけあります。エージェントが実行した `cc-safety-net policy apply` は、ガードが intent `hard_stop` で拒否します。CC Safety Net が強制する設定の書き換えは、ユーザー本人が行う必要があるからです。ダッシュボードの適用も同じく人間の操作で、セッショントークンを持つ人だけが開けるページで自分でクリックします。ただし[ローカルループバックに限定されている](#local-loopback-scope)で述べたとおり、ダッシュボードを起動したエージェントもそのトークンを持っています。

### コマンドを試す

`Test a command` を押すとダイアログが開きます。シェルコマンドを入力して `Test` を押すと、ブロックされるかどうかを確認できます。コマンドは実行されません。判定は**現在の未保存の編集内容**に対して行われるため、保存する前に変更の効果を確かめられます。

ブロックされる場合は、`Blocked` とルール ID、理由が表示されます。複合コマンドでは、ブロックされた部分も示されます。ブロックされない場合は `Allowed. No rule blocks this command.` と表示され、`Create a rule to block it` のリンクから、そのコマンドを入力した状態でカスタムルール画面を開けます。結果に表示されるルール ID は、保護画面またはカスタムルール画面の該当ルールへのリンクです。

プロジェクトの下書き中は、ランタイムが実際に読み込む内容、つまり継承元のベースラインに下書きがマークしたフィールドを重ねたものを評価します。パスのリストは、自分の項目と下書きの項目を合わせた和集合として扱います。ローダーも同じように和集合を取るためです。この画面の保護状況の概要とルールごとの注記も同じ評価結果を使うため、マークしたパスのリストが画面上で空に見えても、自分のパスが保護されていないかのように表示されることはありません。

ダッシュボードから rulebook は編集できませんが、このテストではディスクから読み込んだカスタム rulebook のルールも適用されます。組み込みの層だけでなく、実際の判定結果のプレビューとして使えます。ターミナルで同じ解析を行う方法は、[`explain`](/ja/reference/cli-commands#explain)を参照してください。

### 安全 preset

この画面では、**Standard**、**Strict**、**Paranoid** の 3 つの安全 preset をカードから選べます。後の preset は前の preset の内容をすべて含みます。これらを継承元の既定値として、個別に調整できます。override によって preset と異なる状態になっている場合は、見出しの横に `<Preset>, customized` と表示されます。各 preset と機能の正確な動作は、[モード](/ja/configuration/modes)を参照してください。

保護を強める環境変数が設定されている場合は、`An environment variable raises protection beyond these settings:` に続けて変数名が表示されます。この通知は、表示中の preset より実際の動作が厳しくなりうる理由を示します。

既定で折りたたまれている **Advanced settings** のカードには、機能ごとのセレクターがあります。対象は `Fail closed`、`Paranoid rm -rf checks`、`Paranoid interpreters` です。各セレクターでは `From preset (on)` または `From preset (off)`、`Always on`、`Always off` を選べるため、preset を変えずに 1 つの機能だけを変更できます。同じカードには、ワークフローのスイッチ `Allow discarding local changes in linked git worktrees` もあります。緩和されるのは、linked worktree 内での変更の破棄に関するチェックだけです。

### 保護を検索する

保護のパネルの上にある検索欄には `Type / to search by name, path or rule ID` と表示されています。ルール名、ルール ID、説明、カテゴリ、シークレットのルールが保護するパスに対して照合します。保護画面のどこにいても `/` を押すと、この欄にフォーカスが移ります。ただし、入力欄に入力している間やダイアログが開いている間は除きます。

`All` と `Changed from default` で、表示するルールを切り替えます。`Changed from default` には件数が表示されます。対象は、自分の override が設定されたルールと、Advanced settings や環境変数によって値が決まっているコマンドルールです。

ルールのグループは、最初は折りたたまれた状態です。検索するか `Changed from default` を選ぶと、一致するルールを含むグループがすべて開きます。

### コマンド保護

**Command protection** のパネルには、組み込みの破壊的コマンドのルールがまとめられています。ヘッダーには、マスタースイッチ、`Reset all` のボタン、`N on · N off · N always on` という概要があります。

ルールはグループに分かれています。最初の `Always on` には致命的な操作に対するルールが並び、件数は `N rules · can't be turned off` と表示されます。これらのルールには、スイッチの代わりに錠前のアイコンが付きます。その後に、`Git` や `Filesystem` など、ルールのカテゴリごとのグループが続きます。各グループのヘッダーにはルール数が表示され、オフのルールがある場合は `N off` が加わります。

各ルールの行には、スイッチ、ルール名、ルール ID、説明が表示されます。その preset の機能が必要なルールには、`Strict` または `Paranoid` のバッジが付きます。情報ボタンを押すと、そのルールがブロックするコマンドの例が表示されます。値が preset からそのまま決まっていない場合は、注記でその理由が示されます。

| 注記 | 意味 |
| --- | --- |
| `Changed by you` | 自分の override がこのルールを設定している。横の `Reset` で override を削除できる |
| `<Capability> forced on in Advanced` または `<Capability> forced off in Advanced` | Advanced settings の設定でルールの値が決まっている |
| `Set by environment: <variable>` | 環境変数がルールを有効にしている |
| `Needs the Strict preset` または `Needs the Paranoid preset` | 現在の preset にそのルールの機能が含まれないため、オフになっている |

ルールを切り替えると、明示的な `on` または `off` の override が保存されます。継承値に戻すと、冗長な override を保存するのではなく、override 自体が**削除**されます。ルールの `Reset` でも同じことができます。`Reset all` を使うと、確認のうえでパネル内のすべての override を削除します。override が 1 つもない場合は `Nothing to reset: every rule already uses its default` と表示されます。

マスタースイッチをオフにすると、概要が `Off. Built-in rules are not enforced; catastrophic and custom rules still apply. Your rule settings are kept.` に置き換わります。その状態でも、`Always on` のグループはブロックを続けます。

<span id="secret-protection"></span>

### シークレット保護

**Secret protection** のパネルには、マスタースイッチ、`Reset all` のボタン、`N on · N off` という概要があります。ルールはカテゴリ別に、`Sensitive file names`、`Sensitive file name patterns`、`Sensitive home folders`、`Key file name variants`、`Sensitive file extensions`、`Sensitive extension patterns`、`Coding agent credentials`、`Coding agent settings` のグループに分かれています。各グループのヘッダーにはルール数が表示され、グループの一部だけがオフの場合は `N off` が加わります。ヘッダーには、グループ全体を切り替えるスイッチもあります。このスイッチは、グループ内のルールが 1 つでもオンならオンの状態になり、マスタースイッチがオフの間は操作できません。切り替えると、ルール単位の override をまとめて書き込みます。

リテラルのファイルパスを保護するルールには、情報ボタンが付いています。押すと `Protected paths` のポップオーバーが開き、そのルールが対象とするパスが正確に列挙されます。

すべてのルールが既定でオンになっているわけではありません。`Coding agent settings` のルール（Coding CLI config のルール）は既定で**オフ**で、`Off by default` と表示されます。設定ファイルや MCP 設定ファイルには資格情報が書かれることがある一方、エージェントが通常の作業で編集するファイルでもあるためです。これらのルールは個別に有効にする必要があります。スイッチは、ルールの既定値から外れたときにだけ override を保存します。既定がオフのルールをオンにすると `on` の override が書き込まれ、オフに戻すと override が削除されます。逆に既定がオンのルールは、オフにすると `off` が書き込まれ、オンに戻すと override が削除されます。override のあるルールには、`Changed by you` と `Reset` のボタンが表示されます。

マスタースイッチをオフにすると、概要が `Off. Sensitive files and deny paths are not blocked. Your rule settings and paths are kept.` に置き換わります。

### 例外と追加のパス

**Exceptions and extra paths** のパネルには、3 つのパスのリストがあります。各項目は絶対パスか `~/` で始まるパスで指定し、ホームディレクトリそのものや、その上位のフォルダーを指す項目は拒否されます。複数行を貼り付けると、まとめて追加できます。

| リスト | ポリシーのフィールド | 効果 |
| --- | --- | --- |
| `Allow recursive deletes in` | `destructive_command_protection.allow_paths` | このパスの中での再帰削除はブロックされません。`/tmp` 配下の作業用フォルダーなどを使えるようにする設定です。コマンド保護が無効の間は操作できません |
| `Always block access to` | `secret_protection.deny_paths` | シークレット保護が有効な間、このパスとその配下をすべてブロックします |
| `Exempt from secret patterns` | `secret_protection.allow_paths` | ファイル、フォルダー、または `~/code/**/.env.local` のようにフォルダー配下の 1 つのファイル名を、組み込みのパターンルールから除外します。deny path とコーディングエージェントの資格情報の保護は引き続き適用されます |

deny path と除外のリストは、シークレット保護が無効の間は操作できません。ダッシュボードは、各項目を下書きに追加する前に検証します。拒否された項目には `Not added: <paths>. <reason>`、すでにリストにある項目には `Already listed: <paths>` と表示されます。

allow path が緩和する範囲と緩和しない範囲は [Allow path](/ja/configuration/policy#allow-paths) と[許可されるコマンド](/ja/reference/allowed-commands#configured-allow-paths)、指定できる形式は [deny path](/ja/configuration/policy#deny-paths)、優先順位と検証ルールは [Secret allow path](/ja/configuration/policy#secret-allow-paths) を参照してください。

### ポリシー JSON

**Policy JSON** のカードは、この画面のいちばん下にあり、既定では折りたたまれています。`Copy` ボタン付きの読み取り専用のミラーで、2 つ目のエディターではありません。何を表示しているかは、カードの説明文でわかります。

| 説明文 | 表示される内容 |
| --- | --- |
| `Read-only. Mirrors the settings above.` | フォームが保存するユーザーポリシー |
| `The file as it is on disk.` | エラーがある間の、ポリシーファイルの内容そのもの |
| `Only the fields set by this project. Written to <path>.` | プロジェクトの適用が書き込む、設定したフィールドだけのファイルそのもの |

### 確認が求められる操作

ルールの切り替え、preset の変更、パスの追加・削除は下書きに保存され、**Save** でまとめて適用されます。個別の確認はありません。確認ダイアログが出るのは、保護を弱める操作か、設定を破棄する操作だけです。

| 操作 | ダイアログのタイトル | 確認で示される内容 |
| --- | --- | --- |
| コマンド保護をオフにする | `Turn off command protection?` | 組み込みの破壊的な git・ファイルシステム・実行系のルールは、再びオンにするまでコマンドをブロックしなくなります。致命的な操作に対するルールとカスタムルールは引き続き適用されます。 |
| シークレット保護をオフにする | `Turn off secret protection?` | 機密ファイル、コーディングエージェントの資格情報、deny path は、再びオンにするまでブロックされなくなります。 |
| 保護のパネルで `Reset all` を押す | `Reset every rule to its default?` | すべてのコマンドルール、またはすべてのシークレットのルールが、preset が与える設定に戻ります。保存する前なら破棄できます。 |
| 未保存の変更を破棄する | `Discard unsaved changes?` | 最後に保存してからの変更がすべて取り消されます。 |
| 修復する | `Repair your policy file?` | 有効な設定は残し、無効な設定は破棄します。JSON をまったく読み取れない場合は、既定値に戻します。 |
| ポリシーをリセットする（設定画面） | `Reset your policy?` | ポリシーファイルが既定値に置き換わり、カスタマイズはすべて失われます。 |
| 保持期間を短縮する（設定画面） | `Keep logs for only N days?` | N 日より古いログのエントリは次回のクリーンアップで削除され、復元できません。 |

これらのダイアログでは、既定でキャンセル側にフォーカスが当たります。

<Warning>
コマンド保護やシークレット保護をオフにすると、再びオンにするまで、その層の設定可能なルールが一度にすべて無効になります。ブロックを続けるのは、`Always on` のコマンドルールだけです。マスタースイッチを切るより、個々のルールの override や、より低い preset の選択を優先してください。
</Warning>

### 修復

ディスク上のポリシーファイルにエラーがあると、保護画面に `Your policy file needs repair` とエラーの内容、`Repair` ボタンが表示されます。修復すると正規の JSON が書き込まれます。有効な設定は保持し、無効なフィールドは破棄します。JSON をパースできない場合は、既定値を書き戻します。

<Warning>
修復すると無効なフィールドは破棄され、ファイルをパースできない場合は既定値に戻ります。手書きで書いた重要な設定がファイルに含まれている場合は、修復する前に安全な場所へコピーしておいてください。
</Warning>

### リセット

リセットは、意図的にこの画面には置いていません。設定画面の Danger zone にあります。

<span id="custom-rules"></span>

## カスタムルール

カスタムルール画面では、ユーザーが作成したカスタム rulebook を扱います。URL のハッシュは `#rules` です。これらのルールは、保護画面の組み込みの保護とは別のものです。rulebook の形式、スコープ、override、検証は[カスタムルール](/ja/configuration/custom-rules)を参照してください。

<Warning>
カスタムルール画面は **rulebook のエディターではありません**。CC Safety Net がダッシュボードから rulebook を書き込むことはありません。この画面の役割は、実際に適用されているルールを読み取り専用で表示することと、rulebook を作成させるためにコーディングエージェントへ渡すプロンプト文を生成することです。
</Warning>

### rulebook の一覧（読み取り専用）

各 rulebook には、名前、`v<version>` のバッジ、スコープ（`All projects` または `This project`）、ルール数が表示され、名前と異なる場合は設定元の指定も表示されます。各ルールには、照合するコマンドとサブコマンド、`custom.<name>` の ID、理由、そして `Blocks when any of these arguments is present:` に続けて、ブロックの条件となる引数が表示されます。

ルールは、**override 適用後の状態**で一覧表示されます。override で無効になったルールは rulebook に残りますが、ルール一覧には表示されません。この画面が示すのは、ファイルの内容そのものではなく、実際に有効な rulebook です。再読み込みのアイコン（`Refresh custom rules`）を押すと、ファイルを読み込み直します。

rulebook を 1 つも設定していない場合は `No custom rules yet.` と表示され、`Create a rule` か `npx -y cc-safety-net rule init` が案内されます。rulebook はあるもののすべて破棄されている場合は、`Every rulebook was skipped because of errors, so no custom rule is enforced. See Problems above.` と表示されます。

`#rules?focus=custom.<name>` へのリンク（概要画面やアクティビティ画面のカスタムルール ID など）を開くと、そのルールが強調表示され、その位置までスクロールします。どの rulebook にもそのルールがない場合は、`custom.<name> is not in any rulebook` と表示されます。

### Problems

報告すべき内容がない場合、**Problems** の欄は表示されません。この欄にエラーがある場合は、rulebook が**スキップ**され、そのルールが 1 つも適用されていないことを示します。作ったルールが効かないときは、まずここを確認してください。

### Create a rule（コピーのみ）

**Create a rule** の欄は、コーディングエージェントに渡すプロンプトを生成します。実行できる操作は **Copy prompt** だけです。画面には作成・保存・書き込みの操作はなく、rulebook を書き込むためのサーバー側の処理も存在しません。

次の項目を入力します。

- **Applies to**：`This project` または `All projects`。
- **Project folder**：`This project` のときだけ表示され、ダッシュボードを起動したディレクトリがあらかじめ入力されます。長いパスは末尾が見えるように表示され、マウスを重ねるとパス全体が表示されます。OS 標準のディレクトリ選択が使える場合、この欄は読み取り専用になり `Choose…` ボタンが表示されます。選択画面が使えない場合は、代わりに欄が編集可能になります。
- **What should be blocked?**：どんなルールが欲しいかを記述します。ルールが照合するのは、ファイルパスやパターンではなく、コマンド、そのサブコマンド、正確な引数です。
- **Try**：1 クリックで入力できるサンプルで、`Suggest rules`、`Block a command`、`Verify rules` があります。

生成されるプロンプトは、`cc-safety-net` の skill を使うようエージェントに指示します。その skill が使えない場合は、先に `npx -y cc-safety-net rule doc` を実行し、その出力をスキーマ・パス・検証の正として扱うよう指示します。スコープ、プロジェクトのパス、既存の rulebook の名前を含むため、エージェントはまだ使われていない名前を選べます。プロンプトに含めるのは、rulebook の**名前だけ**です。ルール名、ブロック対象の引数、理由、バージョンは含まれません。

ルールがまだ読み込まれていない場合（`Rules have not loaded yet`）、要望が空の場合（`Describe what should be blocked first`）、`This project` を選んでいるのにプロジェクトのフォルダーが未指定の場合（`Enter the project folder the rule belongs to`）は、コピーが拒否されます。コピーに成功すると要望の欄が空になり、`Prompt copied` と表示されます。

## エージェント

エージェント画面では、このマシン上の各コーディングエージェントについて、CC Safety Net の hook をインストールまたは削除します。URL のハッシュは `#integrations` です。各エージェントの接続方式は[連携アーキテクチャ](/ja/guides/integration-architecture)、GUI を使わない場合の手順は[インストール](/ja/installation)を参照してください。

エージェントは 3 つのリストに分かれて表示されます。

- **Installed**：hook が有効なエージェント。
- **Detected on this machine**：このマシンで見つかったものの、hook が有効になっていないエージェント。hook を持つエージェントが 1 つもない場合は、`No agent has the hook yet. Install it for each agent you use; until then its commands are not checked.` という説明が付きます。
- **Not detected on this machine**：見つからなかったエージェントのリストで、折りたたまれています。

各行には、エージェント名、バージョン（見つからない場合は `Not detected`）、状態、操作のボタンが表示されます。

| 状態 | 意味 | 表示される操作 |
| --- | --- | --- |
| `Hook installed` | hook が設定され、有効になっている | `Uninstall` |
| `Hook disabled` | エージェントはこのマシンにあるが、hook が無効になっている | `Enable` |
| `Status unknown: its settings file could not be read` | エージェントは見つかったが、その状態ファイルを読み取れない。インストールの操作は引き続き表示される | `Install` |
| 表示なし | エージェントはこのマシンにあるが、hook がない | `Install` |
| バージョンの欄に `Not detected` | このマシンでエージェントが見つからない | なし |

表示される操作は検出結果によって変わります。エージェントが見つからない場合は、hook を入れる対象がないためボタンを表示しません。インストールとアンインストールは順番に実行し、同時には処理しません。処理中のボタンは `Installing…` または `Uninstalling…` と表示され、操作できなくなります。処理が終わると、コマンドの出力が行の下に表示されます。失敗した場合は、黙って元の状態に戻すのではなく、`Install failed` または `Uninstall failed` と表示されます。

再読み込みのアイコン（`Refresh agents`）を押すと、すべてのエージェントを検出し直します。CLI をインストールした後や、エージェントの設定を手作業で編集した後に必要な操作です。

## 設定

設定画面には、外観、監査ログ、ファイルの場所、バージョン情報、リセットの項目があります。

**外観。** `Theme` で `Auto`、`Light`、`Dark` を選べます。この設定はポリシーではなく、このブラウザーに保存されます。

**監査ログ。** `Keep logs for` で、監査レコードを保持する日数を設定します。指定範囲、記録内容、スイープの挙動は[監査ログ](/ja/reference/audit-log#retention)を参照してください。`Log folder` の行には監査ログのディレクトリが表示され、`Copy` ボタンが付きます。

保護画面と異なり、保持期間は**変更した時点で保存**されます。保存バーは表示されません。次の場合は変更が拒否され、`Retention unchanged` と表示されます。

- ポリシーファイルの修復が必要な場合：`Repair your policy file in Protections first.`
- プロジェクトポリシーの下書き中の場合（保持期間はユーザースコープ専用の設定のため）：`Apply or leave your project policy draft first.`
- 保護画面に未保存の変更がある場合：`Save or discard your unsaved Protections changes first.`

ほかのポリシーの書き込みを処理している間も、この欄は操作できません。範囲外の値を入力すると、`Enter a whole number of days from 1 to 365.` と表示されます。

<Warning>
保持期間の短縮は元に戻せません。新しい期間より古い監査エントリは次回のスイープで削除され、復元できません。アクティビティ画面で確認できる範囲も、新しい期間までになります。ダッシュボードは短縮前に確認を求め、削除対象のログディレクトリを表示します。必要なエントリは先に保存してください。各エントリは、アクティビティ画面の `Copy log entry` で JSON としてコピーできます。
</Warning>

**ファイル。** CC Safety Net がこのマシン上で読み書きする場所を、読み取り専用の行で表示します。`Policy file` の行にはユーザーポリシーのパスが表示され、ファイルがまだない場合は `(not created yet)` が付きます。プロジェクトポリシーが効いている場合は、`Project policy` の行も現れます。各行の `Copy` ボタンは、パスだけをコピーします。プロジェクトポリシーが設定を緩めている場合は、行の下に `The project policy changes these settings:` という通知が表示され、緩和の内容が 1 つずつ並びます。`CC_SAFETY_NET_PROJECT_TIGHTEN_ONLY` が設定されている場合は緩和がマージされないため、この通知は表示されません。

**About。** CC Safety Net のバージョン、Node.js のバージョン、検出されたプラットフォームを、読み取り専用の行で表示します。

**Danger zone。** 操作は 1 つだけで、**Reset policy** です。設定されたパスに既定のポリシー JSON を書き戻します。プロジェクトポリシーの下書き中は使えず（`Reset unavailable`）、ほかのポリシーの書き込みを処理している間も操作できません。

<Warning>
リセットすると、保存済みの設定は破棄されます。preset の選択、ルールの override、allow path、deny path はすべて既定に戻り、元には戻せません。影響を受けるのはポリシーファイルだけで、カスタム rulebook は別のファイルなので影響を受けません。
</Warning>

<Note>
ポリシーファイルのスキーマは[ポリシー](/ja/configuration/policy)、rulebook の作り方は[カスタムルール](/ja/configuration/custom-rules)、監査ログの形式と保持の挙動は[監査ログ](/ja/reference/audit-log)、`gui` を含むすべてのコマンドは [CLI コマンド](/ja/reference/cli-commands)を参照してください。
</Note>
