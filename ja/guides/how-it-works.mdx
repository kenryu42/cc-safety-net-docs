CC Safety Net は実行前フックです。コーディングエージェントが実行しようとするシェルコマンドとファイル操作を 1 つずつ受け取り、手元のマシンで検査して、操作が OS に届く前に許可かブロックを返します。ブロックされた呼び出しは実行されず、エージェントには理由と代わりに取るべき行動を伝えるメッセージが返ります。

<span id="does-cc-safety-net-use-an-llm"></span>

## CC Safety Net は LLM を使いますか？

使いません。判定はすべて、ローカルのルールベースのパーサーが行います。コマンドを実行ファイル、サブコマンド、フラグ、引数に分解し、その構造に固定のルールを適用します。コマンド、作業ディレクトリ、設定が同じなら、判定は常に同じです。モデルにもネットワークにも何も送らないため、プロンプトの書き方でブロックを許可に変えることはできません。

## 1 つのツール呼び出しのライフサイクル

<Steps>
  <Step title="エージェントがツール呼び出しを準備する">
    エージェントが `git reset --hard` のようなシェルコマンドや、ファイルの書き込み・編集・検索・パッチを用意し、自身のツール層に渡します。
  </Step>
  <Step title="連携が呼び出しをインターセプトする">
    そのエージェント用の CC Safety Net の連携が、ツールの実行前に呼び出しを受け取ります。受け取り方はエージェントによって異なります。[連携方式](#integration-models)を参照してください。
  </Step>
  <Step title="CC Safety Net が操作を検査する">
    CC Safety Net は入力を 1 回だけ解析し、[検査の順序](#what-gets-checked-in-order)に示す検査を実行します。この順序はどのエージェントでも同じです。
  </Step>
  <Step title="許可またはブロックが返る">
    許可された呼び出しは通常どおり実行されます。ブロックされた呼び出しは実行されず、エージェントはツールの結果として[ブロックメッセージ](#what-a-block-looks-like)を受け取ります。
  </Step>
  <Step title="判定が記録される">
    判定はローカルの[監査ログ](#the-audit-record)に記録されます。
  </Step>
</Steps>

<span id="integration-models"></span>

## 連携方式

CC Safety Net は 4 つの連携方式で 16 のエージェントに対応しています。どの方式でも検査の内容は同じで、同じ呼び出しには同じ判定が出ます。

| 方式 | エージェント | エージェントが CC Safety Net を呼び出す方法 |
| --- | --- | --- |
| 標準入力のフックサブプロセス | [Antigravity CLI](/ja/installation/antigravity-cli)、[Claude Code](/ja/installation/claude-code)、[Codex](/ja/installation/codex)、[Cursor](/ja/installation/cursor)、[Devin CLI](/ja/installation/devin-cli)、[Factory Droid](/ja/installation/factory-droid)、[Gemini CLI](/ja/installation/gemini-cli)、[GitHub Copilot CLI](/ja/installation/github-copilot-cli)、[Grok Build](/ja/installation/grok-build)、[Hermes Agent](/ja/installation/hermes-agent)、[Kimi Code](/ja/installation/kimi-code) | エージェントはツール呼び出しのたびに [`cc-safety-net hook`](/ja/reference/cli/hook) を短命のプロセスとして実行し、呼び出し内容を JSON で標準入力に渡します。 |
| エージェントが読み込むプラグイン | [DeepSeek Harness](/ja/installation/deepseek-harness)、[OpenClaw](/ja/installation/openclaw)、[OpenCode](/ja/installation/opencode) | エージェントが、自身のパッケージ形式のプラグインとして CC Safety Net を読み込みます。これらのエージェントに `hook` フラグはありません。 |
| プロセス内の拡張機能 | [Pi](/ja/installation/pi) | Pi は CC Safety Net の拡張機能を自身のプロセスに読み込み、メモリ内で呼び出します。 |
| イベントプラグイン | [Amp Code](/ja/installation/amp-code) | Amp は、アカウントの Personal Plugins リポジトリからプラグインを読み込み、`tool.call` イベントを 1 つずつ渡します。 |

保護されるツールと設定の場所は、「インストール」にある各エージェントのページに載っています。同じ検査を自分の Node.js プログラムから呼び出す方法は、[ライブラリ API](/ja/reference/library-api) を参照してください。

<span id="what-gets-checked-in-order"></span>

## 検査の順序

どのツール呼び出しも、同じ段階を次の順に通ります。

1. **上限付きの入力抽出。** 深さ、フィールド数、サイズに上限を設けたうえで、ツール入力からコマンドを読み取ります。上限を超えた入力はブロックします。
2. **1 回だけの解析。** コマンドを 1 回だけ解析し、後続のすべての段階がその結果を使い回します。パーサーの処理上限を使い切った入力は、どの安全レベルでもブロックします。
3. **ポリシーファイルの保護。** CC Safety Net 自身の `policy.json`、そのディレクトリ、上位ディレクトリを変更・削除しようとする操作をブロックします。
4. **Git メタデータの保護。** リポジトリの `.git` メタデータやフックディレクトリを削除・移動・上書き・パッチしようとする操作をブロックします。作業ディレクトリの中から行う操作も対象です。
5. **設定の読み込み。** ポリシー、ルールブック、安全レベルを解決します。
6. **機密パスの保護。** コマンド、パス、検索、パッチを、組み込みの機密の場所（`.env`、`~/.ssh`、クラウドやコーディング CLI の資格情報ファイル）と、設定した拒否パスに照らして検査します。
7. **破壊的コマンドの解析。** コマンドをセグメントに分割し、ラッパーとインタープリターを展開します。そのうえで、該当するアナライザーが各セグメントを分類します。アナライザーの対象は `git`、`rm`、`Remove-Item`、`find`、`xargs`、`parallel`、デバイス系コマンド、カスタムルールです。

手順 3 と 4 は手順 5 より前に実行するため、どんな設定でも弱められません。手順 6 はポリシーに従うため、無効にすることも、独自の拒否パスで広げることもできます。

<span id="what-the-analyzer-sees-through"></span>

## アナライザーが見抜く書き方

コマンドを別のコマンドの中に隠しても、手順 7 はすり抜けられません。

- **ラッパーとインタープリター。** `sh -c`、`bash -c`、`sudo`、`env`、`python -c` や `node -e` のワンライナーを展開し、中のコマンドを最大 10 階層まで解析します。それより深いネストはブロックします。[シェルラッパーとインタープリターのワンライナー](/ja/reference/blocked-commands#shell-wrappers-and-interpreter-one-liners)を参照してください。
- **1 つのコマンド内の `cd`。** `cd dir && rm -rf x` は `dir` を基準に判定します。解決できない `cd` があると、それ以降の対象は検証できなくなります。[ファイルシステムコマンド](/ja/reference/blocked-commands#filesystem-commands)を参照してください。
- **シェル関数。** 関数の本体は呼び出し位置で検査するため、`cleanup() { rm -rf ../outside; }; cleanup` はブロックされます。定義だけで呼び出さない場合は許可されます。[ファイルシステムコマンド](/ja/reference/blocked-commands#filesystem-commands)を参照してください。
- **heredoc。** `cat > note.md <<'EOF'` はデータを書き込むだけなので、本文の内容にかかわらず許可されます。`cat > x.sh <<'EOF' … EOF && bash x.sh` のように、heredoc で書いたスクリプトを同じコマンド内で実行する場合は、スクリプトとして解析します。[strict と paranoid での heredoc](/ja/reference/blocked-commands#heredocs) を参照してください。
- **複合コマンド。** `if`、`while`、`until`、`{ …; }` の本体にあるコマンドも、トップレベルのコマンドと同じように検査します。そのため `if true; then rm -rf ~; fi` はブロックされます。
- **動的な対象。** `rm -rf "$target"` のように変数や置換で組み立てた対象は、実行前に検証できません。standard では許可し、[strict](/ja/configuration/modes#strict-mode-cc_safety_net_strict=1) と paranoid ではブロックします。[ファイルシステムコマンド](/ja/reference/blocked-commands#filesystem-commands)を参照してください。

## 文字列一致ではなく意図で判定する理由

CC Safety Net は、コマンドが実際に何をするかで判定します。先頭の語が同じでも、結果が分かれることがあります。

| コマンド | 動作 | 結果 |
| --- | --- | --- |
| `git checkout -b feature` | 新しいブランチを作成する | 許可 |
| `git checkout -- file` | ファイルの未コミットの変更を破棄する | ブロック |

どちらも `git checkout` で始まるため、前方一致のルールでは、Git のオプション解釈を作り直さないかぎり区別できません。コマンドを解析すれば、フラグの順序の入れ替え（`rm -r -f /`）、シェルラッパー（`sh -c "rm -rf /"`）、インタープリターのワンライナー（`python -c 'import os; os.system("rm -rf /")'`）も検出できます。

このページではルールを一覧しません。何を止め、何を止めないかは[ブロックされるコマンドと許可されるコマンド](/ja/reference/blocked-commands)にまとめています。

<span id="what-a-block-looks-like"></span>

## ブロック時の表示

エージェントは、ツールの結果としてブロックメッセージを受け取ります。

```text
BLOCKED by CC Safety Net

Reason: git checkout -- discards uncommitted changes permanently. Use 'git stash' first.

Rule: git.checkout-double-dash

Command: git checkout -- src/main.py

Do not retry the blocked form. Continue the task using the safer alternative described above.
```

`Rule:` 行には、呼び出しをブロックしたルールまたは[固定の拒否](/ja/reference/blocked-commands#fixed-denial-ids)の ID が入ります。この行が付かないのは、フックの入力がない、または有効な JSON でない呼び出しをブロックした場合だけです。該当する場合は、ツール名を示す `Tool:`、ブロックのきっかけになった `Segment:`、フォールバック設定が有効なときの `Config warning:` も付きます。実行先のディレクトリを理由に拒否したときは、`Working directory:` 行が加わります。コマンドとセグメントのテキストは短縮され、メッセージ全体からシークレットがマスクされます。

ブロックによってエージェントのセッションが終わることはありません。最後の指示はルールの意図（`intent`）によって決まり、別の書き方を試すのではなく本来のタスクに戻るようエージェントを促します。

| 意図 | エージェントへの指示 |
| --- | --- |
| `hard_stop` | どんな方法でも再試行や回避をせず、ブロックを報告して残りのタスクを続ける |
| `use_alternative` | ブロックされた形式を再試行せず、理由に示された安全な代替手段で続ける |
| `scope_down` | より狭い明示的な対象で再試行し、広い操作が必要ならユーザーに確認する |
| `manual_only` | ユーザーに明示的な許可を求め、ユーザー自身に手動で実行してもらう |
| `stop_and_explain` | 別の形式を総当たりで試さず、コマンドを単純化または組み直すか、ブロックを報告する |

この指示は、エージェントが次に何をすべきかを伝えるものです。コマンドは実行されないため、ブロックそのものはエージェントが指示に従うかどうかに左右されません。

<span id="when-the-message-asks-instead-of-blocking"></span>

### ブロックせずに確認を求める場合

Claude Code では、standard モードで検証できなかったコマンドは、ブロックではなく権限確認のプロンプトとして届きます。メッセージの項目は同じで、最初と最後の行だけが変わります。

```text
CC Safety Net could not verify this command

Reason: shell execution source cannot be verified safely. Use a literal command string or ask the user to run it manually.

Command: eval "$CMD"

Segment: eval $CMD

Approve only if you expected this command.
```

最後の行は、意図に応じた指示の代わりに入ります。これを判断するのはエージェントではなくユーザーだからです。承認すればコマンドは実行され、拒否すれば実行されません。どちらの場合も、監査ログには拒否として記録されます。どの拒否が確認に変わるか、どの権限モードで変わるかは、[Claude Code がブロックせずに確認を求める場合](/ja/installation/claude-code#when-claude-code-asks-you-instead-of-blocking)を参照してください。

<span id="the-audit-record"></span>

## 監査記録

CC Safety Net は、すべての拒否と、既定では許可したコマンドの判定もローカルの監査ログに記録します。ログは `npx cc-safety-net logs` で読めます。場所、フィールド、保持期間、マスク処理は[監査ログのリファレンス](/ja/reference/audit-log)を参照してください。

## 判定が予想と異なる場合

<Steps>
  <Step title="理由を確認する">
    `npx cc-safety-net explain "<command>"` は解析を再現し、どのルールがなぜ一致したかを表示します。構造化されたトレースが必要なら `--json` を付けます。
  </Step>
  <Step title="保護が効いているか確認する">
    `npx cc-safety-net status` は `ready` または `degraded` を表示します。`degraded` は、設定元のどれかが拒否され、フォールバックが適用されている状態です。出力の見方は [`status`](/ja/reference/cli/status) を、設定元の直し方は[設定の復旧](/ja/configuration/recovery)を参照してください。
  </Step>
  <Step title="設定を調整する、または報告する">
    ブロックは正しいものの自分のワークフローには厳しすぎる場合は、[安全モード](/ja/configuration/modes)を変えるか、ルール単位のオーバーライドを追加します。安全なコマンドがブロックされた場合や、破壊的なコマンドがブロックされなかった場合の報告先は、[トラブルシューティング](/ja/guides/troubleshooting)と[セキュリティポリシー](/ja/security)を参照してください。
  </Step>
</Steps>

## CC Safety Net の対象外のもの

CC Safety Net が検査するのは、エージェントが実行しようとするツール呼び出しです。任意のバイナリが実行後に何をするか、不透明なプロキシを通して送られるコマンド、ネットワーク通信は見えません。OS のサンドボックスでも権限境界でもなく、インストール済みの連携を経由しないコマンドは保護できません。全一覧と緩和策は[既知の制限](/ja/guides/known-limitations)を参照してください。
