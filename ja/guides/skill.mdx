CC Safety Net には、コーディングエージェントに CC Safety Net を操作させるためのスキルが同梱されています。コマンドがブロックされた理由を尋ねる、ルールブックのルールを書かせる、インストール状態を確認させる、といった使い方ができます。スキルは `cc-safety-net` CLI を実行し、その出力を読んで、平易な言葉で報告します。

スキルは CC Safety Net を操作するだけで、保護そのものは担いません。保護はフックが行い、スキルを読み込んでいるかどうかに関係なく動作します。

<span id="how-you-invoke-it"></span>

## 呼び出し方

スキルは Claude Code のプラグインと Codex のプラグインに同梱されています。どちらかをインストールすれば、スキルも入ります。

| エージェント | 呼び出し方 |
| --- | --- |
| Claude Code | プラグインの名前空間の下に表示される `/cc-safety-net:cc-safety-net` |
| Codex | Codex のプラグインと一緒にインストールされます。Codex でスキルを呼び出す通常の方法で呼び出します |
| Pi と OpenCode | 各連携が組み込みコマンドとして登録する `/cc-safety-net` |
| Antigravity CLI と Kimi Code | `npx skill add kenryu42/cc-safety-net` でスキルを追加し、そのエージェントでスキルを呼び出す通常の方法で呼び出します |

呼び出しに続けて書いた内容が、そのまま依頼になります。このページの例では `/cc-safety-net` を使います。

```text
/cc-safety-net why was my last git command blocked
/cc-safety-net block terraform destroy in this project
```

スキルが動くのは、呼び出したときだけです。作業の途中でモデルが自分からスキルを読み込むことはできません。

## こんなときに使う

- `BLOCKED by CC Safety Net` でコマンドがブロックされ、その理由を順を追って知りたいとき。
- ブロックが誤りに見え、トリアージしてほしいとき。判定の再現、原因となったカスタムルールの修正、組み込みルールの誤検知の報告まで対応します。
- カスタムのブロックルールを作成、編集、移行してほしいとき。
- 安全レベルの変更、保護の切り替え、パスリストの調整をしたいとき。
- 別のエージェント CLI に CC Safety Net をインストール、更新、削除したいとき。
- 追加したルールが発火しないとき、または保護が有効かどうかを確認したいとき。
- `explain` や `rule doc` の出力だけでは分からない、アナライザーがある構文をそう扱う理由を知りたいとき。

## 各ワークフローの内容

スキルは依頼内容に応じて、7 つのワークフローのいずれかに振り分けます。

**判定を説明する。** ブロックされたコマンドを、必要なら `logs` から探し出し、`explain` を実行します。一致したルールと、その理由が示す安全な代替手段を報告します。[explain トレース](/ja/reference/explain-trace)を参照してください。

**誤検知をトリアージする。** `logs --suspect --since 7` で最近の疑わしい拒否を一覧し、`explain` で判定を再現して、発火したルールを特定します。カスタムルールなら修正するかオーバーライドで無効にし、`explain` を再実行して確認します。組み込みルールの場合は、理由に記載された回避手段を探します。たとえば信頼できるラッパーなら `rule wrapper add` です。組み込みルールを無効にしたいと依頼すると、ポリシーのオーバーライドを提案します。適用は自分で行います。

**ルールを設定する。** スコープを選び、`rule doc` の出力をもとにルールブックの JSON を書いて、`rule verify` で検証します。依頼内容を[公式ルールブック](/ja/configuration/rulebooks)がすでにカバーしている場合は、そちらを導入します。[カスタムルール](/ja/configuration/custom-rules)を参照してください。

**ポリシーを設定する。** 保護されていないパスに提案ファイルを書き、`policy check` を実行して差分を見せます。スキルが示す `policy apply` コマンドは、自分のターミナルで実行してください。[ポリシー](/ja/configuration/policy)を参照してください。

**連携を管理する。** `doctor` を実行し、`install --claude-code` のようにターゲットフラグを明示してインストールした後、もう一度 `doctor` を実行して確認します。

**診断する。** `status` と `doctor` を実行します。カスタムルールが発火しない場合は、`rule verify`、`rule list` の順に実行し、`explain` でコマンドを再テストします。[トラブルシューティング](/ja/guides/troubleshooting)を参照してください。

**ソースから答える。** CLI の出力だけでは決着しない質問には、インストール済みのバージョンのソースを読みます。`main` は読みません。回答には、どのバージョンを読んだかを明記します。

## スキルが行わないこと

- CC Safety Net の回避に手を貸すこと。ブロックされたコマンドを通すためにレベルを下げる、アンインストールする、設定を編集する、保護を弱めるポリシーを提案する、といったことはしません。その結果を自分から求め、そのブロックが何を防いでいるかを理解している場合は別です。
- どちらの `policy.json` にも書き込むこと。読み取りはできます。エージェントは `policy apply` を実行できず、スキルが別の方法でファイルを書くこともありません。
- GitHub のルールブックの設定元を追加すること。既存のルールブックを導入するよう依頼した場合は別です。
- `hook` を実行すること。これはエージェント連携のエントリポイントです。
- 明示的な依頼なしに `logs --prune-legacy` を実行すること。このコマンドはレガシーログを完全に削除するため、依頼された場合もまず `--dry-run` を実行します。
- 確認なしに `rule remove --delete-source` を実行すること。このフラグはローカルの設定元ディレクトリを削除します。

ダッシュボードを求められたときは、スキルは `gui --no-open` を実行します。セッションからブラウザーを開く代わりに、URL を渡します。
