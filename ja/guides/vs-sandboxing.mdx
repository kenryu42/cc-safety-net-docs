<span id="do-i-still-need-cc-safety-net-if-i-run-my-agent-in-a-sandbox-or-container"></span>

## エージェントをサンドボックスやコンテナで動かしていても、CC Safety Net は必要ですか？

未コミットの作業を守りたいなら、おそらく必要です。Claude Code や Codex のサンドボックスは、書き込みをプロジェクトディレクトリに限定し、ネットワークアクセスを制限します。しかし `git reset --hard` と `rm -rf .` が書き込むのはそのディレクトリの中で、`git push --force` の送り先は許可済みのリモートです。そのため、サンドボックスは 3 つとも通します。CC Safety Net はこれらをブロックしますが、プロセスの封じ込めやネットワークの制御はしません。主な懸念がプロンプトインジェクション、悪意のある依存関係、信頼できないコード、ネットワーク経由のデータ流出なら、サンドボックスのほうが適しています。両方を使ってください。

<span id="do-i-need-cc-safety-net-if-my-agent-has-permission-deny-rules"></span>

## エージェントに権限の拒否ルールがあれば、CC Safety Net は不要ですか？

場合によります。2026 年 10 月時点で、Claude Code の拒否ルールは決定的で、`bypassPermissions` モードでも適用されます。1 つの CLI でいくつかの決まったコマンドを止めるだけなら、それで足りるかもしれません。ただし拒否ルールはコマンド文字列をワイルドカードのパターンと照合するため、フラグの順序の入れ替え（`rm -r -f`）、シェルラッパー（`sh -c "..."`）、インタープリターを使うとすり抜けられます。CC Safety Net はコマンドが何をするかを解析するため、こうした変形も捕捉します。さらに、16 の CLI に 1 つのポリシーと 1 つの監査ログを適用します。両方を使う構成も多くあります。

<span id="what-each-layer-covers-and-misses"></span>

## 各レイヤーが守る範囲と守れない範囲

レイヤーごとに判断の根拠が違うため、どのレイヤーにも、ほかのレイヤーが拾う見落としがあります。

| レイヤー | 判断の方法 | 守る範囲 | 守れない範囲 |
|---|---|---|---|
| OS レベルのサンドボックス | OS がプロセスツリー全体に境界を強制する | 作業ディレクトリと一時ディレクトリの外への書き込み、ネットワークアクセス（制限または無効） | 境界の内側で起きること。`git reset --hard`、`rm -rf .`、資格情報ファイルの読み取り（読み取りは既定で広く許可されるため） |
| 権限の拒否ルール | ワイルドカードのパターンをコマンド文字列と照合する | 指定した決まったコマンド。どの権限モードでも有効 | フラグの順序を入れ替えた形、ラッパーやインタープリターを使った形、指定していないすべてのコマンド |
| 許可プロンプトと自動承認の分類器 | 実行前に、ユーザーか分類器モデルが各操作を判断する | 破壊的な git コマンドなど、審査する側が見て分かる操作 | 2026 年 10 月時点で公表されている偽陰性率 17%。そして、何も確認しないバイパスモード |
| コンテナ・VM・チェックポイント | 使い捨てのマシンでセッションを動かし、編集を巻き戻せるようにする | 自分のマシンへの被害と、各プロンプトの前に記録されたファイル編集 | マウントしたワークスペースには実際の作業があり、プッシュは実在のリモートに届き、巻き戻しは bash コマンドを対象にしない |
| CC Safety Net | 対応するツール呼び出しが何をするかを、実行前に静的解析する | 対象がどこであっても破壊的な git 操作とファイルシステム操作、Git メタデータ、認識できる資格情報ファイルの読み取り | ネットワークへの送信、認識しないファイル内の資格情報、バイナリ内部の動作、インストール済みの連携を経由しないコマンド。拒否はファイルシステムの権限強制ではない |

CC Safety Net が守れないものと、それぞれを受け持つレイヤーは、[既知の制限](/ja/guides/known-limitations#out-of-scope-protections)にまとめています。

<span id="why-a-sandbox-allows-destructive-git-commands"></span>

## サンドボックスが破壊的な git コマンドを許可する理由

サンドボックスが制限するのは、プロセスが書き込める*場所*です。その範囲の中で何をするかは制限しません。2026 年 10 月時点で、Claude Code の[サンドボックスのドキュメント](https://code.claude.com/docs/en/sandboxing)では、書き込みは既定で作業ディレクトリに限定されます。そのため、プロジェクトに対する `git reset --hard` と `rm -rf .` は許可された書き込みです。`git push --force` はリモートを書き換えるだけでローカルには何も書き込まないため、ローカルの書き込み範囲では捉えられません。サンドボックスには、Git の履歴、未コミットの変更、スタッシュの内容、どのファイルが資格情報を持つかといった概念がありません。

| コマンド | OS レベルのサンドボックス | CC Safety Net |
|---|---|---|
| `git reset --hard` | 許可（カレントディレクトリ内） | ブロック |
| `git checkout -- .` | 許可（カレントディレクトリ内） | ブロック |
| `git stash clear` | 許可（カレントディレクトリ内） | ブロック |
| `git push --force` | 許可（リモートのドメインが許可されている場合） | ブロック |
| `rm -rf .` | 許可（カレントディレクトリ内） | ブロック |
| `cat .env` | 許可（読み取りは広く許可） | ブロック |

<Note>
  これらのコマンドが自動で実行されるか確認を求められるかは、エージェントのサンドボックスモードと承認ポリシーによって決まります。`git push --force` は、許可ドメインの設定にも左右されます。
</Note>

サンドボックスの読み取りは、既定で広く許可されています。2026 年 10 月時点で、Claude Code のサンドボックスのドキュメントは既定の読み取り動作について「There is no built-in credential deny list」と述べ、今も読み取りを許可するファイルとして `~/.aws/credentials` と `~/.ssh/` を挙げています。CC Safety Net は、設定なしでこれらのパスの内容へのアクセスをブロックします。

<span id="when-sandboxing-is-the-better-choice"></span>

## サンドボックスのほうが適している場面

主な懸念が次のいずれかなら、サンドボックスを使ってください。

- **プロンプトインジェクション**：外向きの通信先ドメインを制限し、情報流出を減らす。
- **悪意のある依存関係**：信頼できないパッケージによるファイルシステムへの書き込みとネットワークアクセスを制限する。
- **信頼できないコード**：OS レベルの封じ込めは、コマンド文字列の解析より強い。
- **ネットワークの制御**：CC Safety Net にはネットワークのレイヤーがない。

<span id="permission-prompts-and-approval-classifiers"></span>

## 許可プロンプトと自動承認の分類器

このレイヤーは、操作の前にユーザーか分類器モデルに確認します。2026 年 10 月時点で、Claude Code の[権限モードのドキュメント](https://code.claude.com/docs/en/permission-modes)によれば、Manual モードではほとんどの編集とシェルコマンドの前に止まって確認を求めます。auto モードでは「a second model, the classifier, reviews actions instead of you」とされ、分類器は `git reset --hard` や `git stash clear` などの破壊的な git コマンドを既定でブロックします。

この審査は判断であり、無効にもできます。Anthropic は、[auto モード](https://www.anthropic.com/engineering/claude-code-auto-mode)の分類器について、実際の行き過ぎた操作に対する偽陰性率 17% を公表し、「not a drop-in replacement for careful human review」としています。`bypassPermissions` では、すべてが確認なしに実行されます。

CC Safety Net の拒否は、`bypassPermissions` を含むすべての権限モードで有効です。検証に使ったバージョンは [Claude Code の権限モードとバイパスモード](/ja/installation/claude-code#claude-code-permission-modes-and-bypass-mode)を参照してください。

<span id="containers-vms-and-checkpoints"></span>

## コンテナ・VM・チェックポイント

使い捨てのマシンは本物の封じ込めで、Claude Code も `bypassPermissions` を「Isolated containers and VMs only」向けとしています。ただし、マシンの中の作業は守れません。クラウドセッションはリポジトリをクローンし、コミットし、実在のリモートにプッシュします。そのため `git reset --hard` はそこでも同じように未コミットの作業を失わせ、`git push --force` はチームメイトがプルするブランチを書き換えます。作業ツリーをマウントするローカルのコンテナも同じです。マウントは書き込み可能だからです。資格情報の面は[クラウド環境](/ja/guides/cloud-environments)で扱っています。

チェックポイントは、この隙間の一部を埋めます。2026 年 10 月時点で、Claude Code の[チェックポイントのドキュメント](https://code.claude.com/docs/en/checkpointing)には「Checkpointing does not track files modified by bash commands.」とあります。破壊的な git コマンドは bash コマンドとして実行されるため、それが捨てた作業は巻き戻しでは戻りません。

<span id="use-sandboxing-with-cc-safety-net"></span>

## サンドボックスと CC Safety Net を併用する

サンドボックスは、どのコマンドが届く範囲も制限します。CC Safety Net は、その境界の内側でサンドボックスが許可してしまう破壊的なコマンドと資格情報の読み取りを止めます。分類器と、チェックポイント付きの使い捨てマシンは、残りの一部を捕捉するか元に戻します。

サンドボックスと許可リスト自体も破られることがあります。2026 年には、CVE-2026-25725 が `settings.json` を介して Claude Code の bubblewrap サンドボックスを脱出し、CVE-2026-22708 が Cursor のコマンド許可リストを回避しました。手元にあるレイヤーは、すべて動かしてください。
