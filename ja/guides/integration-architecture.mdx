このページは、連携の設定や不具合の調査に使います。各エージェントが CC Safety Net を呼び出し、判定を受け取るまでの流れを示します。ユーザー向けのライフサイクルは[仕組み](/ja/guides/how-it-works)を参照してください。

CC Safety Net は 13 のコーディングエージェントに対応し、接続方式は 4 種類あります。方式が分かれば、hook が動かない原因や設定ファイルの場所を絞り込めます。

各連携のインストール／削除コマンドは[インストール](/ja/installation)を参照してください。このページで扱うどの方式も、[アーキテクチャ](/ja/guides/architecture)で一度だけ規定した同じガードに接続します。

## エージェント別の連携方式

| 方式 | エージェント | 仕組み |
| --- | --- | --- |
| **標準入力の hook subprocess** | Antigravity CLI、Claude Code、Codex、Cursor、Gemini CLI、GitHub Copilot CLI、Grok Build、Hermes Agent、Kimi Code | エージェントはツール呼び出しのたびに `cc-safety-net hook <flag>` を短命のプロセスとして実行し、呼び出し内容を JSON で標準入力に書き込みます。CC Safety Net は解析結果として、エージェントごとの拒否オブジェクトを標準出力に返し、終了コード 0 で終了します。 |
| **エージェントが読み込むプラグイン** | OpenClaw、OpenCode | エージェントが、自身のパッケージ形式のプラグインとして CC Safety Net を読み込みます。これらのエージェントに `hook` フラグはありません。 |
| **プロセス内の拡張機能** | Pi | Pi は CC Safety Net の拡張機能を自身のプロセスに直接読み込み、メモリ内で呼び出します。subprocess も標準入出力も使いません。 |
| **イベントプラグイン** | Amp Code | Amp は、アカウントの Personal Plugins リポジトリから管理対象の personal plugin を読み込み、`tool.call` の各イベントをプロセス内で渡します。 |

## 標準入力の hook subprocess を使うエージェント

この 9 つのエージェントでは、標準入力から JSON を読み取る `hook <flag>` コマンドが保護を担います。実行前イベントの名前もコマンド用ツールの名前もエージェントごとに異なり、標準出力に求められる拒否の形式も異なります。

| エージェント | 実行時フラグ | hook イベント | コマンド用ツール | 拒否時の出力形式 |
| --- | --- | --- | --- | --- |
| Antigravity CLI | `-ac` / `--agy-cli` | `PreToolUse` | `run_command` | `{ "decision": "deny", "reason": … }` |
| Claude Code | `-cc` / `--coding-cli` | `PreToolUse` | `Bash`, `PowerShell`, `Monitor` | `hookSpecificOutput.permissionDecision: "deny"`。[standard モードで検証できなかったコマンド](#when-claude-code-asks-instead-of-denying)では `"ask"` |
| Codex | `-cx` / `--codex` | `PreToolUse` | `Bash` | `hookSpecificOutput.permissionDecision: "deny"` |
| Cursor | `-cu` / `--cursor` | `preToolUse` | `Shell` | `{ "permission": "deny", "user_message": …, "agent_message": … }` |
| Gemini CLI | `-gc` / `--gemini-cli` | `BeforeTool` | `run_shell_command` | `{ "decision": "deny", "reason": …, "systemMessage": … }` |
| GitHub Copilot CLI | `-cp` / `--copilot-cli` | `PreToolUse` | `bash`, `Bash`, `powershell`, `PowerShell` | `{ "permissionDecision": "deny", "permissionDecisionReason": … }` |
| Grok Build | `-gb` / `--grok-build` | `PreToolUse` | `run_terminal_command`, `monitor` | `{ "decision": "deny", "reason": … }` |
| Hermes Agent | `-ha` / `--hermes-agent` | `pre_tool_call` | `terminal` | `{ "action": "block", "message": … }` |
| Kimi Code | `-kc` / `--kimi-code` | `PreToolUse` | `Bash` | `hookSpecificOutput.permissionDecision: "deny"` |

Claude Code の `Monitor` と Grok Build の `monitor` もシェルコマンドを実行するため、どちらもコマンド用ツールとして扱います。`Monitor` は POSIX のアナライザーを、`monitor` は方言の自動判定を使います。ただし `command` フィールドを持たない `Monitor` の呼び出しだけは、コマンド用ツールとして扱いません。これは `ws: { url, protocols? }` を送る WebSocket 版です。コマンド用ツールとして扱うとコマンドが見つからずに fail closed となり、WebSocket の監視をすべて拒否してしまいます。

<Note>
  エージェントごとにイベント名も拒否の形式も異なるため、CC Safety Net はそれぞれに合った形式で出力します。たとえば Gemini CLI は、Claude Code の `hookSpecificOutput` ではなく、終了コード 0 と `decision`／`systemMessage` を持つオブジェクトを求めます。出力形式を自分で設定する必要はありません。指定したフラグによって自動的に決まります。
</Note>

<span id="when-claude-code-asks-instead-of-denying"></span>

### Claude Code が拒否ではなく確認を求める場合

`ask` を返せるのは Claude Code の hook だけです。`permissionDecision: "deny"` の代わりに `permissionDecision: "ask"` を出力し、Claude Code はその呼び出しを権限確認のプロンプトとして表示します。

`ask` になる拒否は次の 2 つだけで、しかも fail closed の機能が無効な場合、つまり standard レベルに限られます。

- ルール `raw-text.dangerous-command`。CC Safety Net がパースできなかったコマンドのテキストが、それでも破壊的に読み取れる場合に発火します。
- 理由 `shell execution source cannot be verified safely. Use a literal command string or ask the user to run it manually.`。ただし 2 つの場合は拒否のままです。1 つはコマンドの生テキスト自体にも破壊的なパターンが含まれる場合、もう 1 つは検証できないソースを `sh -` のような標準入力を読むだけのシェルに渡す場合です。

これ以外の拒否はすべて拒否のままです。[strict と paranoid](/ja/configuration/modes#strict-mode) はどちらも fail closed を有効にするため、これらのレベルでは確認に変わることがありません。

`ask` は人が見て初めて意味を持つため、hook が出力するのは `default`、`acceptEdits`、`plan` の 3 つの permission mode の場合だけです。それ以外の値の場合や、値がない場合は拒否になります。残りのモードでは Claude Code が誰も見ないままプロンプトを処理できてしまい、`ask` が黙って許可されるのと変わらなくなるためです。

`ask` を出力するホストは他にありません。Codex と Kimi Code は同じ `PreToolUse` のアダプターを使いますが、`ask` の出力を有効にしていません。Cursor の hook 形式には `allow` と `deny` しかありません。`ask` でプロンプトを出さないホストでは、コマンドが止まらずに実行されてしまいます。Codex はこの値を受け付けず、ツールを実行します。

プロンプトの文面はブロックメッセージとは異なります。監査ログには、引き続き拒否として記録されます。どちらのメッセージも[ブロック結果の形式](/ja/guides/how-it-works#what-a-block-looks-like)で確認できます。同じ 2 つの拒否をポリシーの側から見た説明は、[standard がコマンドを検証できない場合](/ja/configuration/modes#when-standard-cannot-verify-a-command)にあります。

### 共通の Coding CLI hook を使う

`hook --coding-cli`（短いフラグは `-cc`）が、Claude 形式の hook の正式な名前です。このエントリーポイントは、その形式のペイロードを送ってくるエージェントであればどれでも受け付けます。そのため「Claude Code」ではなく「Coding CLI」という名前にしています。

`hook --claude-code` は以前からのエイリアスとして受け付けますが、`hook --help` には表示されません。新しい設定では使わないでください。

これとは別に、3 つのエージェントについては `hook` を省略する以前の**トップレベル**の書き方も残っています。`cc-safety-net -cc` / `--claude-code`、`-gc` / `--gemini-cli`、`-cp` / `--copilot-cli` です。正式な `--coding-cli` は、意図的にトップレベルのフラグにしていません。`cc-safety-net --coding-cli` だけを実行すると、`Unknown option: --coding-cli` というエラーになります。

<Note>
  `statusline` コマンドは hook とは無関係で、引き続き `--claude-code` または `-cc` を指定する必要があります。[ステータスライン](/ja/configuration/status-line)を参照してください。
</Note>

### hook 設定の場所

9 つのうち 5 つは、CC Safety Net がファイルを直接書き込みます。4 つは hook の設定エントリとして、Hermes Agent は管理対象プラグインとして書き込みます。残りの 4 つは、それぞれのプラグインや拡張機能の配布経路を通して接続し、そのうえで標準入力の hook を呼び出します。

| エージェント | 設定の場所と読み込まれ方 |
| --- | --- |
| Antigravity CLI | 直接書き込み。`npx -y cc-safety-net hook --agy-cli` を実行する管理対象の `PreToolUse` エントリを `~/.gemini/config/hooks.json` に追加する |
| Claude Code | プラグイン `cc-safety-net@cc-marketplace`。有効・無効の状態は `~/.claude/settings.json` の `enabledPlugins` に保存される |
| Codex | プラグイン `cc-safety-net@cc-marketplace`。プラグイン自身の `hooks/codex.json` が、`node "${PLUGIN_ROOT}/dist/bin/cc-safety-net.js" hook --codex` を実行する `PreToolUse` エントリを登録する |
| Cursor | 直接書き込み。`npx -y cc-safety-net hook --cursor` を実行する管理対象の `preToolUse` エントリを、`timeout: 30` と `failClosed: true` を付けて `~/.cursor/hooks.json` に追加する。この設定はグローバルで、すべてのプロジェクトの Cursor IDE と Cursor CLI が対象になる |
| Gemini CLI | `gemini-safety-net` リポジトリから読み込む拡張機能 `gemini-safety-net`。`cc-marketplace` のプラグインではない |
| GitHub Copilot CLI | プラグイン `cc-safety-net@cc-marketplace`、または `~/.copilot/hooks` 配下の hook ファイルや Copilot の設定内のインライン hook。hook 対応にはバージョン条件があるため、使える取得元は Copilot CLI のバージョンによって異なる（[インストール](/ja/installation#github-copilot-cli-installation)を参照）。`disableAllHooks: true` はすべての hook を無効にする |
| Grok Build | 直接書き込み。`npx -y cc-safety-net hook --grok-build` を実行する管理対象の `PreToolUse` エントリを、`timeout: 30` を付けて `~/.grok/hooks/cc-safety-net.json`（または `$GROK_HOME/hooks/cc-safety-net.json`）に追加する。このエントリにマッチャーはないため、`run_terminal_command` だけでなくファイル系ツールやパッチ系ツールも hook に届く。インストールもアンインストールも管理対象のハンドラーだけを操作するため、同じファイル内の管理対象外のエントリや、同じエントリ内の管理対象外のハンドラーはそのまま残る |
| Hermes Agent | 直接書き込み。`<Hermes home>/plugins/cc-safety-net/` に管理対象の Python プラグイン（`__init__.py` と `plugin.yaml`）を追加し、`hermes plugins enable cc-safety-net --no-allow-tool-override` で有効化する。有効化の状態は Hermes 自身の `config.yaml` の `plugins.enabled` に記録される |
| Kimi Code | 直接書き込み。`npx -y cc-safety-net hook --kimi-code` を実行する `[[hooks]]` ブロックを `~/.kimi-code/config.toml`（または `$KIMI_CODE_HOME/config.toml`）に追加する。もう 1 つの方法として、Kimi Code 内で `/plugins install https://github.com/kenryu42/cc-safety-net` を実行し、ネイティブのプラグインをインストールすることもできる。そのマニフェストは同じ hook エントリ（`node ./dist/bin/cc-safety-net.js hook --kimi-code`、`PreToolUse` イベント、タイムアウト 30 秒）をマッチャーなしで実行するため、ファイル系ツールも hook に届く |

Kimi Code の `Bash` 呼び出しでは、`tool_input.cwd` があればその値を実行ディレクトリとして使います。値は空でない文字列で、セッションの `cwd` の内側に解決できる必要があります。無効な値や外側を指す値は fail closed になります。

Gemini CLI の `run_shell_command` 呼び出しでは、文字列の `dir_path` が実行ディレクトリになります。Gemini 自身がコマンドを `path.resolve(targetDir, dir_path)` で実行するためです。CC Safety Net はこの値をペイロードの `cwd` を基準に解決し、絶対パスはそのまま使います。設定ディレクトリはセッションのカレントディレクトリのままなので、プロジェクト自身のルール設定が引き続き適用されます。

解決先は実在するディレクトリである必要があります。存在しない場合は拒否し、要求された作業ディレクトリが原因であることを示します。空白だけの値や文字列以外の値は fail closed になります。`""` は `dir_path` の指定がないことを意味し、これは Gemini 自身の判定と同じです。この場合はセッションのカレントディレクトリで解析します。

Kimi Code の `cwd` とは異なり、解決後のディレクトリがセッションのカレントディレクトリの内側に収まっている必要はありません。`BeforeTool` の hook が発火する前に、Gemini 側がワークスペース、`--include-directories` のルート、プロジェクトの一時ディレクトリと照らして `dir_path` を検証済みだからです。Amp の `dir` も同じように解決します。

GitHub Copilot CLI の呼び出しでは、`toolArgs` はオブジェクトか文字列で届きます。オブジェクトはそのまま使います。文字列は JSON としてパースし、JSON でない文字列は `Failed to parse toolArgs JSON.` という理由で拒否します。例外は 1 つだけです。patch の経路では、先頭の空白を除いて `*** Begin Patch` で始まる文字列を、パッチのテキストとしてそのまま渡します。`powershell` と `PowerShell` の呼び出しは PowerShell のアナライザーに、`bash` と `Bash` の呼び出しは方言の自動判定に振り分けます。

プラグイン経由の場合、Copilot は Windows の `powershell` ツールを `Bash` という名前で送ります。そのままでは Claude 形式のアダプターが POSIX のコマンドとして扱ってしまいます。そこでアダプターは環境変数 `COPILOT_CLI` を読み、値が `1` であれば `Bash` を `auto` の方言に振り分けます。これにより PowerShell の削除ルールが引き続き適用されます。[PowerShell `Remove-Item`](/ja/guides/analysis-engine#powershell-remove-item) を参照してください。

Grok Build の呼び出しでは、信頼するルートは `workspaceRoot` で、`workspaceRoot` がない場合は `cwd` をルートとします。`cwd` はそのルートの内側のディレクトリとして正規化できる必要があり、`cwd` がないか空の場合は `.` として扱います。ルートを正規化できない場合や、`cwd` がルートの外を指す場合は fail closed になります。`toolInputTruncated: true` も fail closed になります。Grok Build はツール入力を 128 KB で切り詰めるため、途中で切れたコマンドは解析できません。

### Codex が hook に到達する仕組み

Codex は、`cc-marketplace` マーケットプレイスのプラグイン `cc-safety-net@cc-marketplace` として CC Safety Net を読み込みます。このプラグインは Codex 独自の形式でパッケージ化されており、マニフェストが指す `hooks/codex.json` が `PreToolUse` hook を登録します。`cc-safety-net` スキルも同じプラグインに同梱されています。

Codex は信頼されていない hook を実行しないため、Codex 内で信頼済みにするまで hook は動作しません。手順は[インストール](/ja/installation#codex-installation)を参照してください。

### Hermes Agent が hook に到達する仕組み

Hermes は、hook の設定ファイルから hook コマンドを実行するわけではありません。CC Safety Net は、Hermes がプロセス内で読み込む管理対象の Python プラグインをインストールし、そのプラグインが `pre_tool_call` のハンドラーを登録します。対象のツール呼び出しのたびに、ハンドラーは `npx -y cc-safety-net hook --hermes-agent` を実行し、呼び出し内容を JSON で標準入力に書き込みます。標準出力が空であれば許可を意味します。`{ "action": "block", "message": … }` が返ればブロックで、Hermes はそのメッセージをツール結果としてモデルに提示します。

プラグインが渡すツールは 4 つです。コマンド解析用の `terminal`、書き込み保護用の `write_file` と `patch`、読み取り保護用の `read_file` です。それ以外の Hermes のツール呼び出しは渡されず、判定も行われません。

プラグインは、すべての失敗を原因を明示したブロックに変換します。対象は、PATH に `npx` がない、プロセスの起動に失敗する、タイムアウトする（30 秒でアナライザーのプロセスグループ全体を kill）、終了コードが 0 以外になる、出力が読み取れないか想定外である、といった場合です。Hermes 側のディレクトリ解決の仕組みを読み込めない場合もブロックします。誤ったディレクトリを基準に解析すると、パスに基づく保護がすべて失われてしまうためです。

プラグインは、Hermes 自身が使うディレクトリを基準に各ツールを解析します。`terminal` の呼び出しでは、プラグインはまず Hermes がセッションごとに保持する作業ディレクトリの記録を読み取ります。この記録には、そのセッションでの `cd` の状態が反映されています。最初のコマンドでまだ記録がない場合は、`TERMINAL_CWD`、次に Hermes のプロセスのディレクトリを使います。使用できない `workdir` を持つ `terminal` の呼び出しは fail closed になります。

`read_file`、`write_file`、`patch` の呼び出しでは、プラグインは `_resolve_base_dir(task_id or "default")` を呼び出します。Hermes もこれらのツールの相対パスを同じ仕組みで解決します。この解決は、セッションの作業ディレクトリの記録、タスクごとの作業ディレクトリの上書き、`TERMINAL_CWD`、最後に Hermes のプロセスのディレクトリの順にたどります。import 元は `tools.file_tools` です。Hermes v2026.8.31 までは `tools.file_tools` が `_resolve_base_dir` を定義し、v2026.9.7 以降は `tools.file_tools_paths` から再エクスポートしています。import に失敗した場合、プラグインは呼び出しをブロックし、どの解決に失敗したかを示します。

```text
CC Safety Net failed closed: the Hermes file tool directory could not be read (<error>). Update cc-safety-net and reinstall the plugin with: npx -y cc-safety-net install --hermes-agent.
```

`terminal` の解決に失敗した場合も同じメッセージで、`file tool` の部分が `session` になります。

アナライザーの subprocess は Hermes の作業ディレクトリではなくホームディレクトリから起動します。これにより、`npx` が正規のパッケージの代わりにリポジトリ内の `cc-safety-net` を解決してしまうのを防ぎます。

管理対象プラグインの配置先は Hermes のホームで決まります。Hermes の CLI は、プロファイルのディレクトリをホームとして使います。親ディレクトリ名が `profiles` である `HERMES_HOME` はすでにプロファイルのディレクトリなので、CC Safety Net はその値をそのまま使います。そうでない場合、ルートは `HERMES_HOME`、未設定なら `~/.hermes` です。CC Safety Net はそのルートにある `active_profile` ファイルを読み取り、前後の空白を除いて小文字に変換します。得られた名前で `<root>/profiles/<name>` を選びます。名前が空の場合、名前が `default` の場合、ファイルが存在しないか読み取れない場合は、いずれもルートのままです。Hermes のプロファイル ID のパターンに合わない名前の場合は、次のエラーで処理を中止します。

```text
Invalid Hermes profile name "<profile>" in <root>/active_profile; run `hermes profile use <name>` with a valid profile.
```

管理対象のファイルはいずれも、CC Safety Net のファイルであることを示すヘッダー行で始まります。インストーラーは、このヘッダーがないファイルを上書きしません。Hermes はディスク上に存在しないプラグインを解決しないため、アンインストールではファイルを削除する前に `hermes plugins disable cc-safety-net` を実行します。インストール・アンインストールのいずれの場合も、Hermes を再起動するまでプラグインの変更は反映されません。設定と削除のコマンドは[インストール](/ja/installation#hermes-agent-installation)を参照してください。

Pi の場合と違い、`doctor` は管理対象プラグインのディレクトリと Hermes の `config.yaml` の `plugins.enabled` の一覧だけを見て、ディスク上から Hermes Agent を検出します。実行時のプローブは使いません。

## エージェントが読み込むプラグイン

### OpenClaw

OpenClaw は、ネイティブの OpenClaw プラグインとして CC Safety Net を**プロセス内**に読み込みます。プラグインは 3 つのファイルからなるパッケージ済みディレクトリとして提供されます。実行エントリの `index.js` は、ローカルディレクトリからのインストールでは `node_modules` が存在しないため、依存関係をすべてインライン展開した自己完結型のバンドルになっています。`openclaw.plugin.json` のマニフェストは、コードを読み込む前に OpenClaw が検証します。`package.json` の `openclaw.extensions` がエントリを指しています。`hook` フラグも、標準入出力を経由する JSON のやり取りもありません。

プラグインは、`exec` ツールに一致する `before_tool_call` のハンドラーを登録します。解析するのは、タグの付いていないシェルの `exec` だけです。Code Mode の JavaScript `exec` のように `toolKind` の識別子が付いた `exec` イベントには判定を返しません。それらの `command` フィールドがシェルコマンドを表す保証がないためです。それ以外の OpenClaw のツールはガードに渡しません。ハンドラーは、判定なし（許可）か `{ block: true, blockReason }` のいずれかを返すだけで、ツールのパラメーターを書き換えることはありません。

エージェントのワークスペースディレクトリは OpenClaw の実行時 API で解決し、ポリシー用と実行用の両方のディレクトリとして使います。呼び出しに含まれる `workdir` は、ワークスペースの内側に収まるように解決します。CC Safety Net が fail closed になるのは、次の場合です。

- イベントが不正
- コマンドが欠けているか空
- ワークスペースを解決できない
- `workdir` がワークスペースの外を指す
- すでにキャンセル済みの呼び出し

`host` が `auto` と `gateway` 以外の `exec` 呼び出しもブロックします。`gateway` はローカルであることが確認できているためです。`host: "auto"`（または `host` の指定なし）の呼び出しは、ローカル Gateway の前提で解析しますが、OpenClaw が実際にどこへ振り分けるかまではプラグインからは確認できません。サンドボックスの場合については、[既知の制限](/ja/guides/known-limitations)を参照してください。

プラグインの状態は OpenClaw が管理しているため、インストールには OpenClaw 自身の CLI を使います。実行するコマンドは `openclaw plugins install <packaged dir> --force --accept-capabilities` の 1 つだけです。OpenClaw 2026.8.1 以降では、`--no-enable` を指定しないかぎり install がプラグインの有効化まで行うため、`openclaw plugins enable` を別に実行する必要はありません。`openclaw.json` で手動で無効にしている場合は無効のままで、下記のランタイム確認が読み込まれていない状態をそのまま報告します。CC Safety Net が黙って有効に戻すことはありません。`--accept-capabilities` は 2026.8.1 より前には存在しないため、それ以前の OpenClaw では unknown-option エラーでインストールが失敗します。バージョンの判定もフォールバックもありません。

`openclaw plugins uninstall` は `enabled: false` のマーカーを残し、`plugins install` は明示的に無効化されたエントリを有効化しません。そのため、インストール、アンインストール、インストールの順に実行すると、以前は状態が `disabled` のままになっていました。CC Safety Net はこの 1 ケースだけを補います。インストール前に管理対象プラグインのエントリファイルが存在せず、かつランタイム確認の結果が `disabled` の場合にかぎり、`openclaw plugins enable cc-safety-net` を 1 回だけ実行し、もう一度確認します。すでにインストール済みでユーザーが無効にしたプラグインは、インストールでもアップデートでも無効のままです。つまり通常のインストールやアップデートで enable を実行することはありません。

Gateway が動作している場合、この enable は `config reload superseded by a newer runtime config source` で失敗することがあります。OpenClaw は、上書きされることになるランタイムへの反映より先に `plugins.entries.cc-safety-net.enabled=true` を保存し、その書き込みを巻き戻すことはありません。そのため CC Safety Net は enable を再試行せず、これを理由にインストールを失敗させることもありません。結果を決めるのは 2 回目のランタイム確認です。それ以外の理由で enable が失敗した場合は、これまでどおりインストールが失敗します。保存された設定は、Gateway 自身の後続の reload か、次回の起動時に反映されます。

`--force` を使うコマンドの前に、CC Safety Net は対象の拡張機能ディレクトリが自身の管理対象ファイルだけを含むことを確認します。これにより、自分のものだと確認できないプラグインを上書きしたり削除したりすることはありません。インストール後には `openclaw plugins inspect cc-safety-net --runtime --json` を実行し、状態が `loaded` の場合だけ成功とみなします。バンドルが壊れたまま有効になっているプラグインは、インストール自体は問題なく完了しても、何も保護しないまま終わってしまうためです。状態が `disabled` の場合は、実行すべきコマンドをメッセージに含めます。

```text
OpenClaw reports the cc-safety-net plugin with status "disabled"; run `openclaw plugins enable cc-safety-net`. Run `openclaw plugins inspect cc-safety-net --runtime` for details.
```

インストールされたファイルは `<state dir>/extensions/cc-safety-net/` にあります。実効ホームは、`OPENCLAW_HOME` が空でない値に設定されていればその値、設定されていなければ OS のホームディレクトリです。`OPENCLAW_HOME` の先頭の `~` は OS のホームディレクトリを基準に展開します。状態ディレクトリは `OPENCLAW_STATE_DIR`、なければ `OPENCLAW_CONFIG_PATH` があるディレクトリ、いずれもなければ `<effective home>/.openclaw` です。この 2 つの環境変数の先頭の `~` は、実効ホームを基準に展開します。有効・無効の状態は OpenClaw 自身の設定（状態ディレクトリの `openclaw.json`、または `OPENCLAW_CONFIG_PATH`）にあります。全体の `plugins.enabled` スイッチ、`plugins.allow` / `plugins.deny` の一覧、プラグインごとの `plugins.entries.cc-safety-net.enabled` の項目が、いずれも影響します。`plugins.allow` を設定している場合は、そこに `cc-safety-net` も記載する必要があります。

インストールまたはアンインストールの後は、OpenClaw Gateway を再起動してください。マニフェストは起動時にプラグインを有効化する設定（`activation: { onStartup: true }`）になっているため、実行中の Gateway には変更が反映されません。設定と削除のコマンドは[インストール](/ja/installation#openclaw-installation)を参照してください。

### OpenCode

OpenCode は CC Safety Net を**プロセス内**にプラグインオブジェクトとして読み込みます。宣言先は、OpenCode の設定ディレクトリにある `opencode.json`（または `.jsonc`）の `plugin` 配列または `plugins` 配列です。1 つの npm パッケージが OpenCode 1.18.29 以降と 2.0.6 以降の両方に対応しており、2 つの世代はそれぞれ別のプラグイン仕様を実装しています。v1 の `bash` ツールと v2 の `shell` ツールは、同じポリシー、アナライザー、監査ログのコードを通ります。

OpenCode 1.x では、プラグインは `@opencode-ai/plugin` の仕様を実装し、次の 2 つを行います。

1. `tool.execute.before` を実装します。OpenCode は各ツールの実行前にこれを呼び出します。CC Safety Net は呼び出しを解析し、コマンドが破壊的であれば拒否を例外として投げます。標準入出力経由の JSON のやり取りはありません。
2. `config` の hook を実装し、CC Safety Net の組み込みコマンドを OpenCode のコマンド一覧に追加します。ユーザーがすでに定義しているコマンドを上書きすることはありません。

`bash` ツールでは、プラグインは OpenCode の `shell` の設定からアナライザーの方言を選びます。この設定が文字列でない場合、Windows では PowerShell を既定とし、それ以外では `SHELL` を参照します。認識できる `powershell` と `pwsh` の実行ファイルなら PowerShell を、認識できる POSIX シェルなら POSIX を選びます。それ以外の値の場合は自動判定に任せます。指定された `workdir` は、読み取りと検索ができるディレクトリとして解決できた場合にかぎり、実行ディレクトリになります。Windows では、`/C:`、`/C`、`/cygdrive/C`、`/mnt/C` という文書化された形式を正規化し、それ以外のスラッシュ始まりのパスは OpenCode 側で解決できるようそのまま渡します。

OpenCode 2.x では、プラグインは `cc-safety-net` という ID で登録され、`tool.execute.before` を hook して、型付きの `Tool.Error` で拒否を返します。`shell` ツールはコマンドとして検査し、read、edit、write、patch、grep、glob と未知のツールは v1 と同じ入力経路で検査します。Code Mode から呼ばれる子ツールもこの hook を通りますが、CC Safety Net は外側の Code Mode の JavaScript 自体は解釈しません。プラグインはさらに command API 経由で `/cc-safety-net` を登録し、同名のコマンドがすでにある場合はそれをそのまま残します。

v2 の `shell` ツールは、ホストの `FileAccess.resolvePath` で `workdir` を解決します。これは `~` をホームディレクトリに、`~/x` を `<home>/x` に対応付けます。v2 のプラグインも、上記の Windows のドライブ正規化の後に同じ解決を行います。`~` だけならホームディレクトリ、`~/` で始まればその下に結合し、win32 では `~\` も同様に扱います。`~other` や `~x` のようなそれ以外の形式は、プロジェクトからの相対パスのままです。v1 はチルダを展開しません。OpenCode v1 が `path.resolve` で `workdir` を解決するためです。

#### v2 のシェル方言

v2 のツールイベントはシェルの実行ファイル名を伝えないため、アナライザーの方言は OpenCode の `shell` 設定ではなく、プラグインの `shell` オプションで決まります。既定値は Windows では `powershell`、それ以外では `posix` です。Unix で PowerShell を使う場合や、Windows で Git Bash を使う場合は、設定のエントリで指定してください。

```json
{
  "plugins": [
    {
      "package": "cc-safety-net@latest",
      "options": { "shell": "powershell" }
    }
  ]
}
```

bash、dash、ksh、sh、zsh には `"posix"` を、powershell と pwsh には `"powershell"` を指定します。このオプションは OpenCode が使う実行ファイルを選ぶものではありません。OpenCode が実際に使う実行ファイルと一致させる必要があります。それ以外の値を指定すると、プラグインは `CC Safety Net: plugin option shell must be posix or powershell.` で失敗します。

`shell.create.before` の hook が、シェルの起動前に実際の実行ファイルと設定された方言を突き合わせ、食い違っていれば次のメッセージで停止します。

```text
CC Safety Net: actual shell "<actual>" does not match plugin option shell "<configured>". Configure the plugin's shell option to match OpenCode; supported dialects are posix and powershell.
```

cmd.exe、fish、nushell を含む未対応のシェルは、誤った parser で解析せずに拒否します。この停止は通常のツール拒否とは異なります。OpenCode のシェル hook には型付きの拒否の経路もセッション ID もないため、実行中の操作そのものが失敗することがあり、セッションに紐づく監査エントリも残りません。この検査は、プラグインの `location`、つまりプラグインが読み込まれた OpenCode のディレクトリコンテキストで作成されるすべてのシェルが対象で、エージェントのツール呼び出し以外のシェル操作も含みます。OS レベルのサンドボックスではありません。

OpenCode 1.x は古いキャッシュのプラグインを使い続けることがあるため、キャッシュを消去するまで設定変更が反映されない場合があります。[インストール](/ja/installation#opencode-installation)を参照してください。

## Pi の拡張機能

Pi は、パッケージの `pi.extensions` フィールドで宣言され、Pi のエージェントディレクトリにある `settings.json` にパッケージの取得元 `npm:cc-safety-net` として記録された、プロセス内の拡張機能として CC Safety Net を読み込みます。このディレクトリは、`PI_CODING_AGENT_DIR` が設定されていればその値（先頭の `~` は展開されます）、設定されていなければ `~/.pi/agent` です。拡張機能が行うことは 2 つです。

1. **`tool_call` イベントのハンドラーを登録します**（`pi.on('tool_call')`）。ハンドラーは Pi のツール呼び出しを実行前に検査し、コマンドやパスがポリシーに違反していればブロックの結果を返します。プロセスの境界を越えるやり取りは一切ありません。
2. Pi 内から rulebook を対話的に管理するための、**組み込みコマンド `/cc-safety-net` を登録します**。

### Pi で保護されるツール

Pi でコマンド用ツールとして扱うのは、組み込みの `bash` と `powershell` の 2 つです。どちらも `command` フィールドを読み取り、そのコマンドはセッションのカレントディレクトリを基準に実行されます。`bash` は POSIX のアナライザー、`powershell` は PowerShell のアナライザーに振り分けます。以前のカスタム `Shell` ツールには対応していません。Pi のコマンド以外のツールも、引き続きパスの保護とシークレット保護の対象になります。特に `find` は読み取り専用の glob ツールとして分類されるため、検索自体を書き込みとして扱うことなく、`pattern` とパスの値を検査します。コマンドの呼び出し内容やセッションのカレントディレクトリが不正な場合、CC Safety Net は fail closed になります。

| ツール | コマンドのフィールド | 作業ディレクトリ |
| --- | --- | --- |
| `bash` | `command` | セッションのカレントディレクトリ |
| `powershell` | `command` | セッションのカレントディレクトリ |

### Pi の検出

検査すべき hook の設定ファイルがないため、`doctor` コマンドは実行時のプローブで Pi を検出します（`pi` を起動し、拡張機能が読み込まれて有効になっているかを確認します）。そのため、Pi がインストール済みでもプローブを実行できない場合、`doctor` の Pi の状態が `n/a` になることがあります。

## Amp Code のイベントプラグイン

Amp Code は CC Safety Net を **personal plugin** として読み込みます。実体は、Amp アカウントがホストする Personal Plugins リポジトリ内の `cc-safety-net` ディレクトリで、自己完結したエントリファイル `index.ts` を収めています。このプラグインは `@ampcode/plugin` の API を使って Amp の `tool.call` イベントを購読し、`allow` か、メッセージを添えた `reject-and-continue` を返します。Pi、OpenClaw、OpenCode と同様、プロセス内で動作します。personal plugin は 1 台のマシンではなくアカウントに紐づくため、Amp Orb のようなリモート環境で実行されるスレッドも保護できます。

Amp のワークスペースルート（`amp.system.workspaceRoot`）が設定ディレクトリになります。シェルのツール呼び出しに文字列の `dir` が含まれる場合は、その値が実行ディレクトリになります。相対パスはワークスペースルートを基準に解決し、その結果を `realpath` で正規化します。実在するディレクトリであることも必要です。Windows の名前空間パスは拒否します。解決できない `dir` は fail closed になり、このときコマンドが破壊的かどうかは解析しません。この拒否は、アナライザーの想定外の失敗としては報告しなくなりました。作業ディレクトリが原因であることを示し、すでに存在してアクセスできるディレクトリを使うか、存在しないディレクトリであれば先に作成するよう、エージェントに伝えます。OpenClaw の `workdir` とは異なり、解決後のディレクトリがワークスペースの内側に収まっている必要はありません。Amp は自身のスキルのキャッシュや隣接するリポジトリを指定することがあり、これは正当な使い方です。同じ作業を `cd <dir> && …` と書いた場合も、もともとそこで実行されます。設定ディレクトリはワークスペースルートのままなので、プロジェクト自身のルール設定は引き続き適用されます。さらに、Git メタデータのガードは実行ディレクトリと設定ディレクトリの両方を起点とするため、コマンドを別の場所で実行しても、ワークスペース自身の `.git` は保護されたままです。[Git メタデータ](/ja/reference/blocked-commands#git-metadata)を参照してください。

`install --amp` は、このプラグインをリポジトリに公開します。まずアカウントに書き込み可能な Personal Plugins リポジトリがあることを確認し（`amp plugins repositories --json`）、使い捨てのディレクトリにクローンして（`amp clone user-plugins`）、`cc-safety-net/index.ts` を書き込み、コミットしてプッシュします。ステージングでは、ディレクトリを渡さず明示的なパス（`git add -- cc-safety-net/index.ts`）を指定します。そのため、プラグインのパスが gitignore されている場合は、何もステージしないまま進むことはなく、インストールが止まります。インストールもアンインストールも、書き込みや `git rm` の対象はこのエントリ 1 つだけなので、同じディレクトリに置いた他のファイルに触れることはありません。

エントリには、CC Safety Net の管理対象であり安全に置き換えてよいことを示す管理用ヘッダーが付きます。インストールもアンインストールも、`cc-safety-net` がシンボリックリンクである場合やディレクトリでない場合、また `index.ts` がシンボリックリンク、通常ファイル以外、管理対象外のいずれかである場合は、そのプラグインを拒否します。ディレクトリ構成になる前のリリースは、リポジトリのルートに `cc-safety-net.ts` を公開していました。これが管理対象であれば同じコミットで削除し、管理対象外であればインストールは失敗します。

ローカルのプラグインは personal plugin を覆い隠すため、インストールは `~/.config/amp/plugins/` 以下も片付けます。削除するのは、管理対象の旧ファイル `cc-safety-net.ts` と、管理対象の `index.ts` だけを含む手作業でコピーされた `cc-safety-net/` ディレクトリです。この 2 つのパスにそれ以外のローカルエントリがある場合、インストールは失敗します。設定と削除のコマンドは[インストール](/ja/installation#amp-code-installation)を参照してください。

### 埋め込まれるポリシーのスナップショット

公開されるファイルには、ユーザーのポリシーのスナップショットが含まれます。ファイル末尾に追加される `globalThis.__CC_SAFETY_NET_EMBEDDED_POLICY__ = …` という 1 つの代入で、ポリシーは書き込み前に正規化されます。実行時にこのスナップショットが適用されるのは、自前のポリシーファイルを持たないマシン、つまりホームディレクトリが空の Orb のような環境だけです。ポリシーファイルがあるマシンでは、たとえその内容が不正でも、そのマシン自身の設定が優先されます。監査ログの保持期間、ユーザー rulebook、プロジェクトスコープのポリシーは埋め込まれず、ポリシーの変更は次回の `install` または `update` で反映されます。

Amp は起動時にプラグインを読み込むため、新しく公開したプラグインや削除したプラグインは、Amp を再読み込みするまで実行中のセッションに影響しません。

### Amp Code の検出

`doctor` は `amp plugins list` の出力を解析してプラグインを検出します。personal スコープのプラグインは `✓ cc-safety-net (User Plugins) <status>` と表示されます。この出力にはバージョンが含まれないため、`doctor` は Amp 側のバージョンのずれを報告しません。`cc-safety-net update` は常に、現在のファイルを公開し直します。

### Amp Code の対象範囲の制限

- Amp は、同じ `tool.call` イベントを購読する複数のプラグインの実行順序を定めていません。CC Safety Net は受け取った入力をその時点で評価するだけで、許可を返した後に別のプラグインが入力を書き換えた場合、それを評価し直すことはできません。

## 連携を検証する

`npx cc-safety-net doctor` は、エージェントごとに検出した連携方式と設定ファイルのパスを報告し、保護が有効な場合はセルフテストも実行します。オプションと終了時の挙動は [CLI コマンド](/ja/reference/cli-commands)を参照してください。

特定のエージェントで hook が動作しない場合は、[トラブルシューティング](/ja/guides/troubleshooting)のエージェント別の手順を参照してください。

- 戻る：[仕組み](/ja/guides/how-it-works)では、同じインターセプトを 1 回のツール呼び出しとして最初から最後まで説明しています。
- 次へ：[アーキテクチャ](/ja/guides/architecture)では、このページのすべての連携が接続するガードと、順序付きステージの一覧を説明します。
- その次：[解析エンジン](/ja/guides/analysis-engine)では、分類処理に届いたコマンドをどう分類するかを説明します。
- 最後：[設計原則](/ja/guides/design-principles)では、これらの連携方式とガードの順序を採用した理由を説明します。

関連ページ：設定と削除のコマンドは[インストール](/ja/installation)、エージェント別の診断は[トラブルシューティング](/ja/guides/troubleshooting)にあります。
