A custom rule blocks a command that the built-in rules allow, such as `git push` or `npm install -g`, with a reason you write. Rules live in rulebook files, and a `rule.json` in each scope lists the rulebooks to load. Custom rules only add blocks. They never relax a built-in rule.

<Warning>
  Legacy inline configuration files (`.safety-net.json` and `~/.cc-safety-net/config.json`) no longer load. Their rules do nothing until you [migrate them](#migrate-legacy-configuration).
</Warning>

<Tip>
  The [`/cc-safety-net` skill](/guides/skill) can write rules for you. Describe what you want, for example `/cc-safety-net block terraform destroy in this project`.
</Tip>

## Rule configuration file locations

CC Safety Net loads rulebooks from two scopes and merges them:

1. **User scope.** `~/.cc-safety-net/rules/rule.json` (created with `rule init --global`). Use this for personal defaults that apply to every project.
2. **Project scope.** `.cc-safety-net/rules/rule.json` in the project root. Use this for team or project-specific rules you can commit to source control.

If neither file exists, only built-in rules apply. In the directory that holds your user `.cc-safety-net/` (your home directory by default), the project path is the user config, so `rule` subcommands that write the project scope refuse to run there. See [rule in the user config directory](/reference/cli/rule#rule-in-the-user-config-directory).

### Scope merge behavior

- CC Safety Net loads the user scope first and combines both scopes' rulebooks.
- When both scopes list a rulebook with the same name, the user rulebook wins and the project one contributes no rules. CC Safety Net reports a warning and the runtime shows `degraded`. Rename one of them to fix it.
- Each scope's `overrides` apply only to its own rules. CC Safety Net ignores a project override that names a user rule and reports a warning, so project config cannot disable or rewrite a user rule.
- CC Safety Net also ignores, with a warning, an override key that matches no rule.
- CC Safety Net combines `transparent_wrappers` and `command_tools` from both scopes.

## Managing rulebook sources

Each entry in `rule.json`'s `rules` array is a rulebook source:

- **Local source.** A bare name such as `project-rules`. The rulebook lives at `.cc-safety-net/rules/project-rules/rulebook.json` (project) or `~/.cc-safety-net/rules/project-rules/rulebook.json` (user).
- **GitHub source.** `owner/repo#ref/<rulebook-name>` names `.cc-safety-net/rules/<rulebook-name>/rulebook.json` in that repository. `rule add` and `rule update` copy that file into your own scope at the same path, so it loads like a local rulebook.

Use the `rule` command instead of editing `rule.json` by hand:

```bash
# Add a local rulebook source
npx -y cc-safety-net rule add project-rules

# Add one rulebook from a GitHub repository and ref
npx -y cc-safety-net rule add kenryu42/cc-safety-net#main/example-rules

# Add every rulebook a repository publishes, from its default branch
npx -y cc-safety-net rule add acme/safety-rules

# Add selected rulebooks from a branch, tag, or commit
npx -y cc-safety-net rule add acme/safety-rules --ref v2 --only aws gcloud

# Re-fetch a single source, or every source when no source is given
npx -y cc-safety-net rule update example-rules

# List active rulebooks, rules, overrides, and wrappers
npx -y cc-safety-net rule list

# Remove a source (--delete-source also deletes a local source directory)
npx -y cc-safety-net rule remove example-rules --delete-source
```

Add `--global` (`-g`) to change the user scope instead of the project scope. [Official rulebooks](/configuration/rulebooks#install) explains `--only` and `--ref`, and [`rule`](/reference/cli/rule) covers every subcommand, its output, and its errors.

### Rulebooks are live files

The runtime reads each `rulebook.json` from disk on every tool call. A saved edit applies to the next command, with nothing to publish or rebuild. A rulebook that is missing, unreadable, or invalid contributes no rules. Every other rulebook and every built-in rule keeps applying, and the runtime reports `degraded`. For a GitHub source you have never fetched, run `npx -y cc-safety-net rule update`. See [Configuration recovery](/configuration/recovery) for the repair steps.

## Transparent wrappers

A transparent wrapper is a command that runs another command, such as `timeout 5 git push`. CC Safety Net looks through a transparent wrapper to the command it runs, so built-in rules and your custom rules apply to `timeout 5 docker system prune` as they do to `docker system prune`.

Eight wrappers are built in and need no configuration: `caffeinate`, `exec`, `nice`, `nohup`, `setsid`, `stdbuf`, `time`, and `timeout`.

If your team runs commands through another wrapper, such as `rtk`, add it:

```bash
# List configured wrappers for the project scope
npx -y cc-safety-net rule wrapper list

# Trust a wrapper, or stop trusting it
npx -y cc-safety-net rule wrapper add rtk
npx -y cc-safety-net rule wrapper remove rtk

# Operate on the user scope instead
npx -y cc-safety-net rule wrapper add rtk --global
```

- A wrapper name must match `^[a-zA-Z][a-zA-Z0-9_-]*$` and must be unique within the file.
- Reserved commands cannot be wrappers: `git`, `busybox`, the built-in analyzed commands `rm`, `find`, `xargs`, and `parallel`, every shell wrapper, every interpreter, and the awk interpreters.
- Add only a wrapper that runs its child command as written. CC Safety Net does not look through a wrapper that rewrites or hides its child, even when you list it.

The wrappers you add live in `rule.json`, so an unreadable `rule.json` drops them. See [Coverage declared in `rule.json`](/configuration/recovery#coverage-declared-in-rule-json).

## Community shell tools

A plugin can give an agent its own shell tool. The `dsh-ops` plugin, for example, adds `ops_bash` and `ops_run_background`. CC Safety Net does not know those names, so it checks their path arguments but never reads their `command` as a shell command. Until you declare them, `ops_bash` can run `git reset --hard` unblocked.

Declare the tool and CC Safety Net analyzes its commands:

```bash
# Declare one or more tools in the user config
npx -y cc-safety-net rule tool add ops_bash ops_run_background

# Name the argument that carries the working directory
npx -y cc-safety-net rule tool add ops_run_background --cwd-arg dir

# Write the project config instead
npx -y cc-safety-net rule tool add team_shell --project

# List every declared tool in both scopes, or stop analyzing one
npx -y cc-safety-net rule tool list
npx -y cc-safety-net rule tool remove ops_bash
```

That writes the `command_tools` array:

```json
{
  "version": 1,
  "rules": [],
  "overrides": {},
  "transparent_wrappers": [],
  "command_tools": ["ops_bash", { "name": "ops_run_background", "cwd": "dir" }]
}
```

From the next tool call, a declared call gets the same built-in rules, custom rules, and safety level as a built-in shell tool. `git.reset-hard` then blocks `ops_bash` running `git reset --hard`.

- `rule tool` writes the user config by default. Pass `--project` for the project config.
- The name must match the tool name the agent sends exactly, including case.
- A declaration cannot change how CC Safety Net handles a built-in tool, and `rule tool add` refuses built-in tool names. [`rule tool add` name errors](/reference/cli/rule#rule-tool-add-name-errors) lists the other naming rules.
- CC Safety Net analyzes only a call with a non-empty string `command`.
- `cwd` names the argument that holds the working directory. Without it, CC Safety Net reads `workdir`, `cwd`, or `working_directory`. A call with no working directory runs in the session workspace. A blank value or a directory that does not exist makes the call fail closed.

Declarations live in `rule.json`, so an unreadable `rule.json` drops that scope's tools. Run `npx -y cc-safety-net rule verify` after editing the file by hand.

## Create your first custom rule

<Steps>
  <Step title="Create rule.json">
    ```bash
    npx -y cc-safety-net rule init
    ```

    This creates an empty `.cc-safety-net/rules/rule.json` with no rulebook sources:

    ```json
    {
      "version": 1,
      "rules": [],
      "overrides": {},
      "transparent_wrappers": []
    }
    ```

    `rule init --example` also writes an example rulebook at `.cc-safety-net/rules/example-rules/rulebook.json`. It stays inactive until you run `npx -y cc-safety-net rule add example-rules`.
  </Step>
  <Step title="Write a rulebook">
    Create `.cc-safety-net/rules/project-rules/rulebook.json`:

    ```json
    {
      "rulebook_version": 1,
      "name": "project-rules",
      "version": "1.0.0",
      "description": "Project-specific CC Safety Net rules.",
      "author": "project",
      "allowed_commands": ["git"],
      "rules": [
        {
          "name": "block-git-add-all",
          "command": "git",
          "subcommand": "add",
          "block_args": ["-A", "--all", "."],
          "reason": "Use 'git add <specific-files>' instead of blanket add."
        }
      ],
      "tests": [
        {
          "command": "git add -A",
          "expect": "blocked",
          "rule": "block-git-add-all"
        },
        {
          "command": "git add README.md",
          "expect": "allowed"
        }
      ]
    }
    ```
  </Step>
  <Step title="Register it">
    ```bash
    npx -y cc-safety-net rule add project-rules
    ```

    `rule.json` now lists `"rules": ["project-rules"]`. From the next command, CC Safety Net blocks `git add -A`, `git add --all`, and `git add .` with your reason.
  </Step>
  <Step title="Validate it">
    ```bash
    npx -y cc-safety-net rule verify
    ```

    `rule verify` checks both scopes' `rule.json`, loads each source the way the runtime does, and runs the version 2 fixtures. It never fetches remote content.
  </Step>
</Steps>

## `rule.json` schema

`rule.json` selects active rulebooks, applies overrides, and declares transparent wrappers and community shell tools. Safety levels, built-in protections, allow and deny paths, and audit retention live in a separate file. See [Policy](/configuration/policy).

<ParamField body="version" type="integer" required>
  The schema version, which must be `1`.
</ParamField>

<ParamField body="rules" type="array">
  List of rulebook source strings. Defaults to an empty array. Source names must be unique within the file, and the file can list at most 64 sources.
</ParamField>

<ParamField body="overrides" type="object">
  Rule overrides keyed by `<rulebook-name>/<rule-name>`. Values are either `"off"` to disable a rule, or an object to replace the rule's block message. The object form requires `reason` and accepts an optional `intent`. An omitted `intent` leaves the rule's own intent unchanged.
</ParamField>

<ParamField body="transparent_wrappers" type="array">
  Extra commands to look through, on top of the eight built-in wrappers. Defaults to an empty array. Entries must be unique and must not be reserved commands. See [Transparent wrappers](#transparent-wrappers).
</ParamField>

<ParamField body="command_tools" type="array">
  Shell tools a plugin added to your agent that CC Safety Net does not know. Declaring one here makes CC Safety Net analyze its `command` like a built-in shell tool's. Each entry is a tool name, or an object like `{ "name": "ops_bash", "cwd": "dir" }` naming the argument that carries the working directory. Defaults to an empty array. Names must be unique within the file and must not be built-in tool names. See [Community shell tools](#community-shell-tools).
</ParamField>

An override that changes both the message and the agent-facing intent looks like this:

```json
{
  "version": 1,
  "rules": ["project-rules", "owner/repo#main/team-rules"],
  "overrides": {
    "project-rules/block-docker-system-prune": {
      "reason": "Use targeted Docker cleanup commands.",
      "intent": "use_alternative"
    },
    "team-rules/block-npm-global": "off"
  },
  "transparent_wrappers": ["rtk"]
}
```

### `rule.json` editor support

CC Safety Net publishes a JSON Schema for `rule.json`. Point your editor at it for completion and validation:

```json
{
  "$schema": "https://raw.githubusercontent.com/kenryu42/cc-safety-net/main/assets/cc-safety-net.schema.json",
  "version": 1,
  "rules": [],
  "overrides": {},
  "transparent_wrappers": []
}
```

`rule verify` adds this `$schema` line to a valid `rule.json` that lacks one. There is no published schema for `policy.json`.

## Rulebook schema

Each rulebook lives in its own `rulebook.json` file.

<ParamField body="rulebook_version" type="integer" required>
  The rulebook schema version, which must be `1` or `2`. Any other value fails validation with `rulebook_version must be 1 or 2`. See [Version 2 rules](#version-2-rules).
</ParamField>

<ParamField body="name" type="string" required>
  The rulebook name, which must match the local directory name or GitHub source name.
</ParamField>

<ParamField body="version" type="string" required>
  Rulebook version string.
</ParamField>

<ParamField body="description" type="string">
  Human-readable description of the rulebook.
</ParamField>

<ParamField body="author" type="string">
  Rulebook author.
</ParamField>

<ParamField body="allowed_commands" type="array" required>
  The commands this rulebook can define rules for.
</ParamField>

<ParamField body="rules" type="array" required>
  Custom blocking rules. See [Rule schema](#rule-schema).
</ParamField>

<ParamField body="tests" type="array">
  Optional rulebook fixtures. See [Fixture schema](#fixture-schema). CC Safety Net checks only the shape of version 1 fixtures. It also evaluates version 2 fixtures against the rulebook's own rules.
</ParamField>

## Rule schema

The fields below define a `rulebook_version` 1 rule. Version 2 replaces `subcommand` and `block_args` with a `match` object. See [Version 2 rules](#version-2-rules).

<ParamField body="name" type="string" required>
  A name unique within the rulebook, at most 64 characters long. It must start with a letter, followed by letters, numbers, hyphens, or underscores.
</ParamField>

<ParamField body="command" type="string" required>
  The base command to match. `allowed_commands` must list it.
</ParamField>

<ParamField body="subcommand" type="string">
  The subcommand to match, for example `add` or `install`. Without it, the rule matches any subcommand.
</ParamField>

<ParamField body="block_args" type="array" required>
  Arguments that trigger the block. At least one is required, so a version 1 rule cannot block every use of a subcommand. Use a [version 2 rule](#block-every-git-push) for that.
</ParamField>

<ParamField body="reason" type="string" required>
  The message CC Safety Net shows when the rule blocks a command, at most 256 characters long.
</ParamField>

<ParamField body="intent" type="string">
  The intent for the agent, appended to the block message footer. One of `hard_stop`, `use_alternative`, `scope_down`, `manual_only`, or `stop_and_explain`. Defaults to `manual_only`.
</ParamField>

## Version 2 rules

Set `"rulebook_version": 2` to match on an exact command path instead of a subcommand plus a set of arguments. A version 1 rule that blocks `delete` under `gcloud compute` also blocks `gcloud compute instances create delete`, because it looks for the token anywhere in the command. A version 2 rule with the command path `["compute", "instances", "delete"]` does not.

Version 1 rulebooks keep their fields, their matching, and their shape-only fixtures. CC Safety Net validates each rulebook against the version it declares.

A version 2 rule keeps `name`, `command`, `reason`, and `intent` from version 1 and replaces `subcommand` and `block_args` with a `match` object.

<ParamField body="match.command_path" type="array" required>
  Command words that must follow the command, in order, as a non-empty array of non-empty strings. Because the path cannot be empty, no rule matches every call of a command, such as every `aws` invocation.
</ParamField>

<ParamField body="match.any_args" type="array">
  At least one of these tokens must appear literally among the arguments. It is a non-empty array of unique non-empty strings. Leave it out to match the command path with any arguments.
</ParamField>

<ParamField body="match.exclude_args" type="array">
  If any of these tokens appears literally among the arguments, the rule does not match. It is a non-empty array of unique non-empty strings.
</ParamField>

Version 2 rejects the version 1 fields instead of ignoring them. A rule that still carries `subcommand` or `block_args` fails validation with `rules[0].subcommand: not supported in rulebook_version 2` and `rules[0].block_args: not supported in rulebook_version 2`.

```json
{
  "rulebook_version": 2,
  "name": "terraform-rules",
  "version": "1.0.0",
  "allowed_commands": ["terraform"],
  "rules": [
    {
      "name": "block-terraform-apply-destroy",
      "command": "terraform",
      "match": {
        "command_path": ["apply"],
        "any_args": ["-destroy", "--destroy"]
      },
      "reason": "Review a destroy plan first with 'terraform plan -destroy'.",
      "intent": "use_alternative"
    }
  ],
  "tests": [
    {
      "command": "terraform apply -destroy",
      "expect": "blocked",
      "rule": "block-terraform-apply-destroy"
    },
    {
      "command": "terraform -chdir=infra apply",
      "expect": "allowed"
    }
  ]
}
```

### Version 2 matching

- **Command.** CC Safety Net reduces the command to its lowercase basename, as in version 1.
- **Command path.** CC Safety Net skips recognized global options and their values. The command words that follow must equal `command_path` exactly, in order. Arguments after the path do not affect the path match.
- **Global options.** CC Safety Net knows the value-taking global options of `aws`, `gcloud`, and `az` only. For any other command, an option written with a separate value, such as `git -C repo push`, makes the rule miss. Terraform's `-chdir=DIR` is one token, so CC Safety Net skips it.
- **No short-option expansion.** `-Ap` stays `-Ap`. List every spelling you want to catch, such as `"-destroy"` and `"--destroy"`.
- **Literal and case-sensitive.** There is no regex, glob, or substring matching.
- **First match wins.** CC Safety Net evaluates rules in order, and the first rule that matches produces the block.
- **Release channels need their own rule.** `gcloud beta compute instances delete` does not match a `command_path` of `["compute", "instances", "delete"]`. Write a second rule with `["beta", "compute", "instances", "delete"]`.

## Fixture schema

Fixtures document intended behavior. CC Safety Net parses their commands and runs them through the rulebook's rules. It never executes them.

<ParamField body="command" type="string" required>
  Shell command fixture.
</ParamField>

<ParamField body="expect" type="string" required>
  Either `blocked` or `allowed`.
</ParamField>

<ParamField body="rule" type="string">
  Rule expected to block the command. Required for blocked fixtures.
</ParamField>

CC Safety Net checks only the shape of version 1 fixtures. `rule add`, `rule update`, and `rule verify` evaluate version 2 fixtures. A `blocked` fixture passes only when its named rule is the first match, and an `allowed` fixture passes only when no rule matches. `rule add` and `rule update` reject a source whose fixtures fail, before writing it. Each failure names the fixture by its index in `tests`:

```text
tests[<index>]: expected "<rule>" to block "<command>" but no rule matched
tests[<index>]: expected "<rule>" to block "<command>" but "<other-rule>" matched first
tests[<index>]: expected "<command>" to be allowed but "<rule>" matched
tests[<index>]: could not parse fixture command: <command>
```

`rule verify` prefixes each one with the rulebook file, as `example-rules/rulebook.json: tests[0]: ...`.

## Matching behavior

The subcommand, argument, and option rules below describe `rulebook_version` 1 rules. Version 2 rules match as described in [Version 2 matching](#version-2-matching). Command normalization, transparent wrappers, and nesting apply to both.

- **Command normalization.** CC Safety Net reduces a command to its basename before matching. `/usr/local/bin/npm` matches a rule with `"command": "npm"`.
- **Subcommand detection.** The subcommand is the first non-option argument following the command. In `git --no-pager add -A`, the subcommand is `add`.
- **Argument matching.** Arguments in `block_args` match literally. There is no regex or glob support.
- **Short option expansion.** CC Safety Net unbundles short flags before matching. `-Ap` counts as `-A` and `-p`.
- **Long option matching.** Long options use exact string matching. `--all-files` does not match `--all`.
- **Any-argument matching.** The rule blocks a command if any single argument in `block_args` is present.
- **Additive only.** Custom rules can only add new restrictions. They cannot bypass built-in protections.
- **Every depth.** A rule applies to a nested command the same way it applies to a top-level one. Under a rule for `rm`, both `bash -c 'rm -r ./tmpdir'` and `eval 'rm -r ./tmpdir'` block, and the same goes for `sh -c` and a called function body. This includes the commands a built-in analyzer also covers: `rm`, `rmdir`, `git`, `find`, `xargs`, and `parallel`.

<Note>
  **Known limitation.** CC Safety Net treats `-Cfoo` as `-C -f -o -o`, not `-C foo`. A rule that blocks `-f` can therefore match an attached option value by mistake.
</Note>

### Rules match commands, not file paths

A custom rule matches a shell command and its arguments. It does not see the files an agent opens with its own read and edit tools, so a rule cannot protect a file such as `~/.zshrc`. To block every access to a file or folder, add it to [`secret_protection.deny_paths`](/configuration/policy#deny-paths) in `policy.json`. A deny path also blocks reads.

## Examples

### Block every git push

A version 2 rule with `command_path: ["push"]` and no `any_args` blocks `git push` with any arguments. A version 1 rule cannot do this, because `block_args` needs at least one argument.

```json
{
  "rulebook_version": 2,
  "name": "project-rules",
  "version": "1.0.0",
  "allowed_commands": ["git"],
  "rules": [
    {
      "name": "block-git-push",
      "command": "git",
      "match": {
        "command_path": ["push"]
      },
      "reason": "A person pushes this repository. Commit locally and stop."
    }
  ],
  "tests": [
    {
      "command": "git push",
      "expect": "blocked",
      "rule": "block-git-push"
    },
    {
      "command": "git push --force origin main",
      "expect": "blocked",
      "rule": "block-git-push"
    },
    {
      "command": "git status",
      "expect": "allowed"
    }
  ]
}
```

The rule also blocks `timeout 5 git push`, because `timeout` is a [transparent wrapper](#transparent-wrappers). It misses `git -C repo push`, because a git global option with a separate value comes before `push`. See [Version 2 matching](#version-2-matching).

### Turn off one rule

To turn off a custom rule, add its `<rulebook-name>/<rule-name>` key to `overrides` in the `rule.json` of the scope that lists the rulebook, with the value `"off"`. The block message prints this key.

```json
{
  "version": 1,
  "rules": ["project-rules"],
  "overrides": {
    "project-rules/block-git-push": "off"
  },
  "transparent_wrappers": []
}
```

The rulebook file stays unchanged, so `rule update` never undoes the override. To turn off a built-in rule such as `git.push-force`, use `policy.json` instead. See [Allow a blocked command](/reference/blocked-commands#allow-a-blocked-command).

## Block message format

[What a block looks like](/guides/how-it-works#what-a-block-looks-like) describes the full block message layout. A custom rule adds the rulebook name and the rule name as a prefix, so you can tell which rulebook produced the block:

```text
BLOCKED by CC Safety Net

Reason: [project-rules/block-git-add-all] Use 'git add <specific-files>' instead of blanket add.

Command: git add -A
```

The prefix `<rulebook-name>/<rule-name>` is also the key you use in `rule.json` `overrides` to [turn the rule off](#turn-off-one-rule) or replace its reason.

## Migrate legacy configuration

CC Safety Net no longer loads legacy inline config files (`.safety-net.json` and `~/.cc-safety-net/config.json`). Their rules do nothing, and the runtime gives no warning. `npx -y cc-safety-net doctor` and `rule verify` report a leftover file as `Legacy inline rule configs are ignored`.

```bash
# Convert legacy inline rules into the rulebook layout
npx -y cc-safety-net rule migrate

# Optionally delete verified legacy files after migration
npx -y cc-safety-net rule migrate --cleanup

# Validate the migrated rules
npx -y cc-safety-net rule verify
```

`rule migrate` has no `--global` and migrates both scopes. From your home directory it skips the project half. See [`rule migrate` in the user config directory](/reference/cli/rule#rule-migrate-in-the-user-config-directory).

It turns the inline files into this layout:

```text
.cc-safety-net/rules/rule.json                    # project rulebook sources + overrides
.cc-safety-net/rules/project-rules/rulebook.json  # migrated project rules
~/.cc-safety-net/rules/rule.json                  # user rulebook sources + overrides
~/.cc-safety-net/rules/user-rules/rulebook.json   # migrated user rules
```

## Invalid custom-rule configuration

CC Safety Net drops custom-rule configuration that fails to load. It never turns the failure into a denial. Every other valid source and every built-in rule keeps applying, and the runtime reports `degraded`. A dropped source removes blocks, and no denial alerts you to it. Run `npx -y cc-safety-net status` after editing rules or upgrading. See [Configuration recovery](/configuration/recovery).

<Warning>
  Custom rule configuration is not tamper-resistant. An agent can edit `rule.json` and the rulebook files. Only `policy.json` is a protected path. If you add or change custom rules by hand, validate them with `npx -y cc-safety-net rule verify`.
</Warning>
