**Degraded** means CC Safety Net rejected part of your configuration, such as a rulebook with a JSON error or a `policy.json` field with a wrong value. It keeps working with what it could load. That reduced set is the **fallback configuration**: every valid part of your files, built-in defaults in place of rejected `policy.json` fields, and every built-in protection.

`doctor` reports this state as "Runtime is enforcing a fallback configuration", and the dashboard banner says "A fallback configuration is being enforced". The `doctor` finding names each rejected file and field. Fix them with the [steps below](#recover-configuration).

A rejected rulebook stops blocking until you fix it. A rejected `policy.json` field falls back to a default that usually blocks more than you configured.

## Configuration states

| State | When it happens | What it means |
| --- | --- | --- |
| `ready` | Every active source loaded and validated cleanly | Ordinary evaluation against exactly the configuration you wrote |
| `degraded` | Any rule error, any rule warning, or any error from either scope's `policy.json` | Ordinary evaluation continues against a fallback, and every reporting surface carries a warning naming the rejected source |

A single warning is enough to move the runtime to `degraded`:

- An **error** names a source that CC Safety Net dropped. That source contributes no rules at all.
- A **warning** names a source that stays active. CC Safety Net ignores only the rejected part.

## Invalid configuration behavior

An invalid configuration never blocks ordinary work on its own, and CC Safety Net never enforces the rejected part.

- CC Safety Net drops a rule source it cannot verify, and that source's rules stop applying.
- Every other verified scope keeps enforcing its rules.
- Every built-in protection keeps applying. Destructive-command rules, secret protection, `policy.json` protection, and Git metadata protection do not read rule configuration.
- An invalid `policy.json` keeps its valid fields and uses built-in defaults for the rest. See [Salvaged `policy.json` or protective defaults](#policy-json-salvaged-or-replaced-with-protective-defaults).

The degraded state allows nothing extra, and there is no recovery mode. Reading or editing `rule.json` and running `cc-safety-net rule update` are ordinary tool calls, so your agent can repair rule configuration itself.

<Warning>
  Dropping a source is not security-neutral. It removes the denials that source contributed, so a command you deliberately blocked in a dropped rulebook can run again until you repair it. Never assume a rulebook named in an error is still protecting you.
</Warning>

A blocked command with a "failed closed" reason is a different case. It means CC Safety Net could not finish analyzing that one command. See [Fail-closed enforcement](/guides/security-model#what-happens-when-analysis-fails).

## Configuration fallback matrix

<span id="errors-the-source-is-dropped"></span>

### Errors that drop the source

| Failure | What stops being enforced | What still applies |
| --- | --- | --- |
| A remote source has nothing vendored yet, so `rules/<name>/rulebook.json` is missing | That one rulebook | Every other rulebook and all built-ins |
| A local source's `rules/<name>/rulebook.json` is missing or was deleted | That one rulebook | Every other rulebook and all built-ins |
| A rulebook file is not valid JSON or fails the rulebook schema | That one rulebook | Every other rulebook and all built-ins |
| A rulebook's `name` does not match the source that lists it | That one rulebook | Every other rulebook and all built-ins |
| `rule.json` is malformed, empty, or has an unsupported `version` | That whole scope, including its `transparent_wrappers` and `command_tools` | The other scope's verified rules and all built-ins |
| The policy filesystem cannot be read safely | That scope | The other scope's verified rules and all built-ins |

Every one of these messages names the file or source it rejected and the repair that fits it. A missing rulebook for a remote source ends with ``run `cc-safety-net rule update` to vendor <source>``. A missing rulebook for a local source ends with `create that file or remove that source from the rules config`. An invalid rulebook and a name mismatch both end with `fix that file`.

<span id="warnings-the-source-stays-active"></span>

### Warnings that keep the source active

| Failure | What is ignored | What stays enforced |
| --- | --- | --- |
| Two active rulebooks claim the same name | The later rulebook, whose rules are not active | The first claim, resolved user scope first |
| Unknown override key in `rule.json` | Only that one override | Every other override and every rule keeps its configured state |
| A project override targets a user-scoped rule | Only that one override | The rule keeps its user-configured state |

See [Scope merge behavior](/configuration/custom-rules#scope-merge-behavior) for how duplicate names resolve.

<span id="policy-json-salvaged-or-replaced-with-protective-defaults"></span>

### Salvaged `policy.json` or protective defaults

CC Safety Net salvages a file it can parse as a JSON object. Each valid field stays, and each invalid field falls back as the second table shows. CC Safety Net replaces any other broken user file with protective defaults, which are the built-in defaults with both protections on, no overrides, and no allow or deny paths.

| Situation | Result | State |
| --- | --- | --- |
| The user file does not exist | Built-in defaults | `ready`. No diagnostic |
| The user file is empty, whitespace only, not valid JSON, or not a JSON object | Protective defaults | `degraded` |
| The user file is an object but some fields fail validation | Salvage | `degraded` |
| The project file does not exist | The user policy alone | `ready`. No diagnostic |
| The project file is empty, not valid JSON, or not a JSON object | The user policy alone | `degraded` |
| The project file is an object but some fields fail validation | Its valid fields layer over the user policy | `degraded` |
| The project file has an `audit` section | The user policy's audit settings, with every other project field layered on | `degraded` |
| The user file is broken while the project file sets valid fields | Protective defaults with the project fields layered on top | `degraded` |

| Field | When invalid |
| --- | --- |
| `version` | Treated as `1` |
| `safety.level` | Falls back to `standard` |
| `safety.overrides.*` | The invalid key is dropped, so the capability inherits from the preset |
| `workflow.worktree_mode` | Falls back to `false` |
| `destructive_command_protection.enabled`, `secret_protection.enabled` | Falls back to `true`, so protection is on |
| `destructive_command_protection.overrides`, `secret_protection.overrides` | Invalid entries are dropped and valid `"on"` and `"off"` entries stay. A non-object becomes `{}` |
| `destructive_command_protection.allow_paths`, `secret_protection.allow_paths` | Invalid entries are dropped and valid ones stay. A non-array becomes `[]` |
| `secret_protection.deny_paths` | Invalid entries are dropped. A non-array becomes `[]` |
| `audit.retention_days` | The nearest of `1` or `365`, or `30` when not a whole number |

The runtime never rewrites `policy.json`. Fix it by hand, or use the repair action in the [dashboard](/guides/dashboard).

## Coverage declared in `rule.json`

`transparent_wrappers` and `command_tools` widen what built-in analysis reaches, and both live in `rule.json`, not in a rulebook.

- A dropped rulebook keeps both fields, because `rule.json` itself is still readable.
- An unreadable `rule.json` loses both for that scope. Analysis stops looking through that scope's wrapper commands, and CC Safety Net no longer analyzes the [community shell tools](/configuration/custom-rules#community-shell-tools) it declared. The eight built-in wrappers (`caffeinate`, `exec`, `nice`, `nohup`, `setsid`, `stdbuf`, `time`, `timeout`) need no file and still apply, and so do the other scope's declarations.

This is the one case where rejected configuration reduces built-in coverage rather than only removing your own rules. When an unreadable `rule.json` drops a scope, repair that file first.

## Degraded-state reporting

| Surface | What you see |
| --- | --- |
| The next user-visible denial | A `Config warning:` line carrying the full reason, appended to the block message |
| Audit records | A `configFallback` flag, set on allowed and denied decisions alike |
| `cc-safety-net status` | The verdict `ready` or `degraded`, and one line per diagnostic under `Not active` |
| `cc-safety-net doctor` | A `config.runtime-degraded` warning finding titled "Runtime is enforcing a fallback configuration", with the full reason as detail |
| `cc-safety-net rule list` | An `Issues` and a `Warnings` section. Rule configuration only |
| Status line | A `⚠️` marker while the snapshot is degraded |
| Dashboard | The state in the protection banner |

`doctor` is the only command that reports both rule configuration and `policy.json`. Diagnostics name the rejected file and the problem but never copy its contents, so they never repeat a secret inside a broken file.

## Visible and silent failures

- **A dropped rule source is quiet.** It removes denials, so nothing in the session blocks or warns you. Run `cc-safety-net status` after any change to rule configuration and after every upgrade.
- **An unmigrated legacy rule file is quieter.** CC Safety Net does not load it and the state stays `ready`, while those rules protect nothing. `doctor` reports `config.legacy-ignored`. See [Migrate legacy configuration](/configuration/custom-rules#migrate-legacy-configuration).
- **An invalid `policy.json` field is usually visible.** Protections fall back to on, so you see more denials than you configured.
- **Two `policy.json` mistakes lower protection silently.** An invalid `safety.level` falls back to `standard`, so a typo in `paranoid` lowers your preset. CC Safety Net drops an invalid `deny_paths` entry, so it stops protecting that location.
- Only the status line marker appears without you doing anything. The `Config warning:` line needs an unrelated denial to appear on, and every other surface waits for you to run a command or open the dashboard.

## Recover configuration

Your agent can run each command below, even while the runtime is degraded. The [CLI reference](/reference/cli/overview) has the options and exit codes.

<Steps>
  <Step title="Check the verdict">
    ```bash
    npx cc-safety-net status
    ```

    It prints `ready` or `degraded`, plus one line per diagnostic under `Not active`. See [`status`](/reference/cli/status).
  </Step>
  <Step title="Get the full report">
    ```bash
    npx cc-safety-net doctor
    ```

    It covers both rule configuration and `policy.json`. The `config.runtime-degraded` finding names every rejected source. See [`doctor`](/reference/cli/doctor).
  </Step>
  <Step title="Check rule configuration">
    ```bash
    npx cc-safety-net rule list
    npx cc-safety-net rule verify
    ```

    `rule list` shows which rules are active, so you can see what a dropped source took with it. `rule verify` checks both `rule.json` files the way the runtime loads them and ends with `Config validation failed.` when something is broken. See [`rule verify`](/reference/cli/rule#rule-verify).
  </Step>
  <Step title="Repair the source">
    For a local rulebook, edit the file the diagnostic names. The runtime reads it on the next tool call.

    For a remote source that is missing or stale, vendor it again:

    ```bash
    npx cc-safety-net rule update
    ```

    Add a source name to update only that one, and `--global` for the user scope. It reports any diagnostic that remains instead of claiming success. See [`rule update`](/reference/cli/rule#rule-update).
  </Step>
  <Step title="Fix policy.json yourself">
    Your agent cannot edit `policy.json`. Correct the fields named in the diagnostic, or use the repair action in the dashboard. See [Edit the policy file](/configuration/policy#edit-the-policy-file).
  </Step>
</Steps>

Run `status` again after each repair. The runtime reloads on the next tool call, so there is nothing to restart.
