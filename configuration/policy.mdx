`policy.json` is CC Safety Net's settings file. It selects your safety preset, turns built-in rules on or off, allows or blocks specific paths, and sets how long audit records are kept. Your user file applies everywhere, and an optional project file committed to a repository layers on top of it.

Your own blocking rules live in `rule.json` and rulebooks instead. See [Custom rules](/configuration/custom-rules).

## Policy file location

| Scope | Path |
| --- | --- |
| User | `~/.cc-safety-net/policy.json`, or `$CC_SAFETY_NET_HOME/policy.json` |
| Project | `.cc-safety-net/policy.json` in the config working directory |

The runtime reads both files on every tool call, so an edit applies to the next command. [Where configuration lives](/configuration/environment#where-configuration-lives) lists every file CC Safety Net reads and what `CC_SAFETY_NET_HOME` moves.

## What the config working directory is

The config working directory is the directory your agent session runs in, which the agent reports with each tool call. CC Safety Net reads the project `.cc-safety-net/` folder from there, and resolves relative `deny_paths` and `allow_paths` entries against it. A `cd` inside a command, or a tool call that names its own working directory, changes where that command's targets resolve. It does not change the config working directory.

## Project policy

A team ships a safety policy through the repository by committing `.cc-safety-net/policy.json`. Members run nothing. The runtime reads the file on the next tool call, in every checkout.

The project file is sparse. It holds only the fields it sets, and an absent field keeps inheriting from the user policy. A project file that sets one rule override changes that one rule and nothing else.

The effective policy is the user policy with the project policy layered on top:

| Field | How the scopes combine |
| --- | --- |
| `safety.level`, `workflow.worktree_mode`, and each `enabled` flag | The project value wins wherever the project sets one |
| `safety.overrides` | Merged by capability key, and the project entry wins |
| `destructive_command_protection.overrides`, `secret_protection.overrides` | Merged by rule id, and the project entry wins |
| `destructive_command_protection.allow_paths`, `secret_protection.deny_paths`, `secret_protection.allow_paths` | The union of both scopes, so neither scope erases the other's entries |
| `audit` | User scope only |

CC Safety Net ignores an `audit` section in a project file and reports `project policy audit settings are ignored; audit is user scope only`.

### The user config directory is not a project

The directory that holds your user `.cc-safety-net/`, your home directory by default, is never also a project. Run from there and `.cc-safety-net/policy.json` is your user file, so no project file layers on top. Commands that write the project file refuse to run there. See [Which file policy writes](/reference/cli/policy#which-file-policy-writes).

### Reported weakenings

By default, CC Safety Net applies a project policy as written and does not raise it back to the user baseline. Instead, it reports each field the project relaxes relative to the user policy on its own line:

- `project policy lowers level: <user> -> <project>`
- `project policy disables fail_closed`, `project policy disables paranoid_rm`, `project policy disables paranoid_interpreters`
- `project policy enables worktree mode relaxations`
- `project policy disables destructive command protection`
- `project policy disables secret protection`
- `project policy disables rule <id>`
- `project policy adds destructive allow path: <path>`
- `project policy adds secret allow path: <path>`

CC Safety Net measures a lowered level against `safety.level` in the user policy. It measures a disabled capability against the user policy with its level raised by `CC_SAFETY_NET_LEVEL`. So under `CC_SAFETY_NET_LEVEL=paranoid`, a project `safety.overrides.paranoid_rm: false` turns `paranoid_rm` off and appears as a weakening. [The switch below](#ignore-project-weakenings) keeps `paranoid_rm` on.

`status` lists these lines under `Project policy`, `doctor` prints them under `Project policy deltas:`, and the [status line](/reference/cli/statusline) shows `🔻` while any weakening is in force.

### Ignore project weakenings

Set `CC_SAFETY_NET_PROJECT_TIGHTEN_ONLY=1` to refuse every weakening a project policy makes. The merge drops each field listed above, and the project file's tightenings still apply. See [Environment](/configuration/environment#project-policy-weakenings).

`status` still reports the dropped fields under `Project policy (ignored)`, and `doctor` under `Project policy deltas (ignored):`. The status line shows no `🔻`. `policy check`, `policy apply`, and the dashboard's project draft preview the merge without the switch, so they show what a member without it gets.

## Edit the policy file

Your agent cannot change `policy.json` in either scope. [Protected policy.json files](/reference/blocked-commands#protected-policy-json-files) describes the block. Make the change yourself in one of these ways:

- **Use the dashboard.** Run `cc-safety-net gui`. It can also repair a file that does not validate. See [Dashboard](/guides/dashboard).
- **Edit the JSON directly.** The runtime reads the change on the next tool call. You do not need to restart anything.
- **Apply an agent's proposal.** The agent writes a proposal file and runs `cc-safety-net policy check <file>` to show you the diff. You run `cc-safety-net policy apply <file>` in a terminal and confirm. See [`policy`](/reference/cli/policy).

After a hand edit, confirm the result:

```bash
npx cc-safety-net status
```

A `degraded` verdict means CC Safety Net rejected part of your file, and `npx cc-safety-net doctor` names the fields. The runtime never rewrites `policy.json`, so an invalid file stays as you left it until you fix it. See [Invalid policy behavior](#invalid-policy-behavior).

## Complete policy example

Every field, with its default value:

```json
{
  "version": 1,
  "safety": {
    "level": "standard",
    "overrides": {}
  },
  "workflow": {
    "worktree_mode": false
  },
  "destructive_command_protection": {
    "enabled": true,
    "overrides": {},
    "allow_paths": []
  },
  "secret_protection": {
    "enabled": true,
    "overrides": {},
    "deny_paths": [],
    "allow_paths": []
  },
  "audit": {
    "retention_days": 30
  }
}
```

Only `version` is required. You can omit every other field, and an omitted field takes the default shown above. If the file does not exist at all, CC Safety Net runs on these defaults and stays `ready`.

The root object is strict. An unrecognized top-level key is an error, and so is an unrecognized key inside `safety`, `workflow`, `destructive_command_protection`, `secret_protection`, or `audit`.

## Schema reference

<ParamField body="version" type="integer" required>
  The schema version, which must be `1`. It is the only required field. A missing or wrong value reports `version must be 1`.
</ParamField>

<ParamField body="safety.level" type="string" default="standard">
  The safety preset, one of `"standard"`, `"strict"`, or `"paranoid"`. Each preset supplies the capability defaults you inherit. `strict` enables `fail_closed`, and `paranoid` enables `fail_closed`, `paranoid_rm`, and `paranoid_interpreters`. See [Modes](/configuration/modes) for what each capability changes.
</ParamField>

<ParamField body="safety.overrides.fail_closed" type="boolean">
  Set the fail-closed capability explicitly, up or down, regardless of the preset. Omit the key to inherit from the preset.
</ParamField>

<ParamField body="safety.overrides.paranoid_rm" type="boolean">
  Set the paranoid `rm` capability explicitly, up or down. Omit the key to inherit from the preset.
</ParamField>

<ParamField body="safety.overrides.paranoid_interpreters" type="boolean">
  Set the paranoid interpreter capability explicitly, up or down. Omit the key to inherit from the preset.
</ParamField>

<ParamField body="workflow.worktree_mode" type="boolean" default="false">
  Relax local-discard git rules inside a confirmed linked worktree. Detection is fail-closed. If CC Safety Net cannot confirm that the working directory is a linked worktree, the stricter default rules stay in effect. See [Modes](/configuration/modes) for the exact list of what worktree mode relaxes and what it never relaxes.
</ParamField>

<ParamField body="destructive_command_protection.enabled" type="boolean" default="true">
  Master switch for the registered destructive-command rules. Setting it to `false` skips every registered rule except the catastrophic rules, which always apply.
</ParamField>

<ParamField body="destructive_command_protection.overrides" type="object" default="{}">
  Per-rule state, keyed by registered destructive-command rule id, with the value `"on"` or `"off"`. The override applies on top of the state your capabilities set, so `"on"` can enable a rule your preset leaves off and `"off"` can disable one it turns on.
</ParamField>

<ParamField body="destructive_command_protection.allow_paths" type="string[]" default="[]">
  Paths exempted from destructive-command rules. Entries must be absolute or start with `~/`.
</ParamField>

<ParamField body="secret_protection.enabled" type="boolean" default="true">
  Master switch for secret protection. Setting it to `false` skips the entire secret stage, including your `deny_paths`.
</ParamField>

<ParamField body="secret_protection.overrides" type="object" default="{}">
  Per-rule state, keyed by registered secret-protection rule id, with the value `"on"` or `"off"`. Most secret rules are on whenever secret protection is enabled, so `"off"` is the usual direction. The [Coding CLI config tier](#rules-that-are-off-by-default) is off by default, and an explicit `"on"` is how you opt into one of those rules.
</ParamField>

<ParamField body="secret_protection.deny_paths" type="string[]" default="[]">
  Extra paths to protect as secrets, in addition to the built-in sensitive paths. See [Deny paths](#deny-paths) for the validation rules.
</ParamField>

<ParamField body="secret_protection.allow_paths" type="string[]" default="[]">
  Exact files or directory trees exempted from built-in secret-pattern rules. An entry can instead be a folder, then `**/`, then an exact file name, such as `~/code/**/.env.local`. Configured deny paths and Coding CLI protections still apply. See [Secret allow paths](#secret-allow-paths) for the validation rules and precedence.
</ParamField>

<ParamField body="audit.retention_days" type="integer" default="30">
  Days of audit history to keep before the sweep deletes it. Must be an integer between `1` and `365`.
</ParamField>

## Safety level and capability overrides

`safety.level` picks a preset. `safety.overrides` then sets individual capabilities explicitly. This is the only place that can turn a capability down. Environment flags can only raise it.

```json
{
  "version": 1,
  "safety": {
    "level": "paranoid",
    "overrides": {
      "paranoid_interpreters": false
    }
  }
}
```

That example takes the `paranoid` preset but leaves interpreter one-liners alone. CC Safety Net reports the effective level as `custom` whenever the resulting combination of capabilities matches no preset.

<Note>
  The environment can raise your policy's level and force capabilities on, but never the reverse. See [Environment](/configuration/environment) for the full ordering between `policy.json` and the environment, including the `worktree_mode` OR and the legacy `SAFETY_NET_*` aliases.
</Note>

## Which allow list do I use

Pick the setting by what blocked the command. The block message names the rule id.

| What is blocked | Example | Use |
| --- | --- | --- |
| A recursive delete in a folder of yours | `rm -rf ~/scratch/build` blocks as `rm.recursive-force-outside-cwd` | `"~/scratch"` in [`destructive_command_protection.allow_paths`](#allow-paths) |
| Reading or editing a file with a secret-like name | `cat fixtures/.env` blocks as `secret.basename.env` | `"fixtures"` in [`secret_protection.allow_paths`](#secret-allow-paths), or [turn that rule off](/reference/secret-protection#allow-a-blocked-file) |
| A Git discard such as `git reset --hard` | `cd ~/scratch && git reset --hard` blocks as `git.reset-hard` | Nothing in a throwaway repository under a temp directory, where it is [already allowed](/reference/blocked-commands#git-commands-in-a-temp-repository). In a linked worktree, use [worktree mode](/configuration/modes#worktree-mode-cc_safety_net_worktree=1). Otherwise, turn the rule off |
| Any other command | `git push --force` blocks as `git.push-force` | [Turn the rule off](/reference/blocked-commands#allow-a-blocked-command) |

To let an agent work freely in a scratch folder, put the folder under a temp directory such as `/tmp`, where recursive deletes and Git discards already pass. CC Safety Net blocks an edit to an ordinary file only when it has a secret-like name, sits under a deny path, or is `policy.json` or Git metadata. The two `allow_paths` lists are separate, and neither relaxes the other's rules.

## Destructive-command protection

To allow a blocked command, turn off the rule that blocks it. [Allow a blocked command](/reference/blocked-commands#allow-a-blocked-command) walks through finding the rule id and testing the change.

`destructive_command_protection.overrides` addresses built-in rules by id, for example:

```json
{
  "version": 1,
  "destructive_command_protection": {
    "overrides": {
      "git.push-force": "off",
      "rm.recursive-force-paranoid": "on"
    }
  }
}
```

CC Safety Net rejects an id that is not registered with `unknown destructive command rule id "<id>"`, and any value other than `"on"` or `"off"` with `destructive_command_protection.overrides.<id> must be "on" or "off"`. The [fixed denial ids](/reference/blocked-commands#fixed-denial-ids), such as `guard.policy-config` or `analysis.dynamic-shell-source`, are not registered rules, so CC Safety Net rejects an override that names one the same way.

You cannot turn off [catastrophic rules](/reference/blocked-commands#catastrophic-rules). They ignore `enabled: false` and an `"off"` override.

### Allow paths

`destructive_command_protection.allow_paths` treats each listed directory like a temp directory for recursive deletes. See [Recursive deletes under allow_paths](/reference/blocked-commands#recursive-deletes-under-allow_paths) for what it covers. Validation is stricter than for deny paths:

| Entry | Result |
| --- | --- |
| Non-string, or a string that trims to empty | Invalid. `must be a non-empty path string` |
| Relative path | Invalid. `must be an absolute path or start with ~/` |
| Exactly the home directory | Invalid. `cannot be the home directory` |
| A path containing the home directory, such as `/` | Invalid. `cannot contain the home directory` |
| Any other absolute or `~/`-rooted path | Valid |

## Secret protection

Secret protection blocks reads and writes of files that can hold credentials. The [Secret protection reference](/reference/secret-protection) lists every built-in rule id and the paths each one protects. To allow a protected file, see [Allow a blocked file](/reference/secret-protection#allow-a-blocked-file).

`secret_protection.overrides` addresses individual built-in rules by id, with the value `"on"` or `"off"`. `"off"` disables a rule that is on by default, and `"on"` opts into a rule from the default-off tier:

```json
{
  "version": 1,
  "secret_protection": {
    "overrides": {
      "secret.ext.pcap": "off",
      "secret.cli.claude-code.config": "on"
    },
    "deny_paths": ["config/secrets", "~/work/vault"],
    "allow_paths": [".env.test", "fixtures/credentials"]
  }
}
```

CC Safety Net rejects an unregistered id with `unknown secret protection rule id "<id>"`, and any other value with `secret_protection.overrides.<id> must be "on" or "off"`.

### Rules that are off by default

The Coding CLI config rules, which cover coding agents' settings and MCP files, ship off because agents edit those files as routine work. Turn one on with an explicit `"on"` override. The [Secret protection reference](/reference/secret-protection#coding-cli-config-tier-off-by-default) lists the thirteen ids and their paths.

### Block any file or folder with deny paths

`secret_protection.deny_paths` blocks every agent access to a file or folder you name, whether or not it holds secrets. For example, to stop the agent from touching your shell profile:

```json
{
  "version": 1,
  "secret_protection": {
    "deny_paths": ["~/.zshrc"]
  }
}
```

A deny path blocks reads as well as writes, at every safety level. With the entry above, `cat ~/.zshrc`, `ls ~/.zshrc`, `echo x >> ~/.zshrc`, and `rm ~/.zshrc` all block as `secret.deny-path`. A folder entry also covers everything inside it. CC Safety Net checks deny paths before every other secret rule, and no allow path or override relaxes them.

Validation:

| Entry | Result |
| --- | --- |
| Non-string, or a string that trims to empty | Invalid. `must be a non-empty path string` |
| Relative path, such as `config/secrets` or `./secrets` | Valid. Resolved per session against the [config working directory](#what-the-config-working-directory-is) |
| `~`, `$HOME`, or `${HOME}` alone | Invalid. The home directory itself is rejected |
| `~/…`, `$HOME/…` | Valid once expanded, unless it resolves to home or above |
| A path that resolves to exactly the home directory | Invalid. `cannot be the home directory or a path above it (this would block every command the agent runs)` |
| A path that resolves to an ancestor of home, such as `/`, `/Users`, or `/home` | Invalid. Same message |
| Any other absolute path | Valid |

Deny paths belong to secret protection, so `secret_protection.enabled: false` turns them off too. `secret.deny-path` is not a registered rule id, so an override cannot disable it.

### Secret allow paths

`secret_protection.allow_paths` exempts an exact file or a directory and all its descendants from the built-in basename, home-directory, key-variant, and extension rules. Use it for files you keep on purpose, such as a repository's `.env.test`, or a fixture directory that contains non-secret credential-shaped filenames.

An entry can instead name one file name under a folder: the folder, then `**/`, then an exact file name, such as `~/code/**/.env.local`. That entry exempts every `.env.local` at any depth below `~/code`, and nothing else. The folder before `**/` is required, and it goes through the same checks a plain entry does. CC Safety Net accepts no other glob form.

The precedence is fixed:

1. A configured deny path always wins. If the same target is in both lists, the result is `secret.deny-path`.
2. Coding CLI credential and config rules (`secret.cli.*`) always win. An allow path cannot expose the agent's own credentials or configuration.
3. An allow-path match suppresses any other built-in secret rule for that target.

Validation:

| Entry | Result |
| --- | --- |
| Non-string, or a string that trims to empty | Invalid. `must be a non-empty path string` |
| Relative path, such as `.env.test` or `fixtures/credentials` | Valid. Resolved per session against the [config working directory](#what-the-config-working-directory-is) |
| A folder, then `**/`, then an exact file name, such as `~/code/**/.env.local` or `packages/**/.env.local` | Valid. Exempts that one file name at any depth below the folder |
| An entry with no folder before `**/`, such as `**/.env.local` | Invalid. `supports only a folder followed by **/ and an exact file name, such as ~/code/**/.env.local` |
| Any other use of `*` or `?`, such as `apps/*/.env`, `.env.v?`, or `~/**/.ssh/config` | Invalid. Same message |
| `~`, `$HOME`, or `${HOME}` alone, or a path above home | Invalid. `cannot cover the home directory or a path above it (this would disable secret protection everywhere)` |
| A `**/` entry whose folder is home or above, such as `~/**/config` or `/**/id_rsa` | Invalid. Same message |
| `~/.cc-safety-net` or anything below it, including `~/.cc-safety-net/**/.env.local` | Invalid. `cannot cover the guard's own configuration` |
| Any other literal absolute, `~/…`, `$HOME/…`, or `${HOME}/…` path | Valid |

The name after `**/` is one file name and cannot contain a slash, so CC Safety Net rejects `~/**/.ssh/config` as a glob. Apart from this form, entries are literal paths, not glob patterns. A `**/` entry never exempts the folder itself. An allow path also covers a target reached through a symlink.

## Audit retention

`audit.retention_days` sets how many days of audit records to keep. The default is 30, and the accepted range is 1 to 365.

```json
{
  "version": 1,
  "audit": {
    "retention_days": 90
  }
}
```

A value outside the range is an error that puts the runtime in `degraded`. Retention then uses the nearest bound, or 30 when the value is not a whole number. See [Retention](/reference/audit-log#retention) for when the sweep deletes records.

## Invalid policy behavior

An invalid `policy.json` never blocks ordinary work. CC Safety Net keeps each valid field, replaces each invalid one with a protective default, and reports the runtime as `degraded`. A missing file is not an error. CC Safety Net uses the built-in defaults, and the runtime stays `ready`.

<Warning>
  CC Safety Net discards invalid entries instead of repairing them. A mistyped deny path silently stops protecting that location, and an invalid `safety.level` silently lowers you to `standard`. These are the two quiet failure modes. Run `npx cc-safety-net status` after every hand edit.
</Warning>

[Configuration recovery](/configuration/recovery#policy-json-salvaged-or-replaced-with-protective-defaults) lists what each invalid field falls back to and how to get back to `ready`.
