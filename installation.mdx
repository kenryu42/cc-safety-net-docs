CC Safety Net installs as a plugin, extension, or hook inside your coding agent. You do not need a persistent service or daemon. Some integrations start a short-lived hook subprocess for each check.

Most integrations run on **Windows, macOS, and Linux**. They detect the host operating system for path handling and command resolution. On Windows, this includes case-insensitive paths and `cmd.exe` or PowerShell resolution through `COMSPEC` and `PATHEXT`. The install commands and the interactive picker also resolve agent CLIs that npm installs as `.cmd` shims on Windows, so commands like `install --codex` find them. CI runs the same full check on `windows-latest` that it runs on Linux and macOS: lint, type checks, and the whole test suite, with three test cases skipped on Windows. Those tests exercise the analyzer and the integration code, not each coding agent running on Windows. Amp's own manual documents macOS, Linux, and WSL rather than native Windows.

The **Hermes Agent** and **OpenClaw** integrations run only on macOS and Linux. They assume the POSIX state layout, which defaults to `~/.hermes` and `~/.openclaw`, and they do not support the Windows defaults. Both hosts can relocate that state, so see [Hermes Agent installation](#hermes-agent-installation) and [OpenClaw installation](#openclaw-installation) for the directories each one reads.

CC Safety Net supports the **DeepSeek Harness** web profile on Windows, macOS, and Linux. It looks for the Desktop app only on macOS and Windows, so a Linux install covers the web profile alone. See [DeepSeek Harness installation](#deepseek-harness-installation).

Install **Node.js 18 or later** before you start. The examples use `npx` to run CLI subcommands.

Use `cc-safety-net install <target-flag>` to install one integration and `cc-safety-net uninstall <target-flag>` to remove it. Use `cc-safety-net update` to refresh all installed integrations.

## Install interactively

Run the installer with no target flag to get an interactive multi-select over the coding CLIs detected on your machine:

```bash
npx -y cc-safety-net@latest install
```

In the selector, `Space` selects a target, `Enter` confirms, `u` switches to updating every installed integration instead, and `q` or `Esc` cancels without changing anything. The `@latest` qualifier matters: a bare `cc-safety-net` spec can re-run an older cached copy from the npx cache instead of the current release, so every install, uninstall, and update command on this page pins it.

To remove integrations the same way:

```bash
npx -y cc-safety-net@latest uninstall
```

If you use the CLI often, install it globally to get `ccsn`, a shorter alias for the same commands:

```bash
npm install -g cc-safety-net
ccsn doctor
```

The alias ships with the global install; `npx` runs use the full `cc-safety-net` name.

## Update installed integrations

To refresh every installed integration in place, run:

```bash
npx -y cc-safety-net@latest update
```

`update` detects the integrations already installed on your machine, including disabled ones. It runs each install path again in update mode. The command reports an integration as skipped when it cannot find the agent CLI. If no integrations are installed, it tells you to run `cc-safety-net install` first. Pressing `u` in the interactive installer runs the same update.

`update` is also the upgrade path between major versions. Running it on a v1 installation moves every installed integration to the current v2 release. If you defined custom rules under v1's inline configuration, complete the [legacy migration](/configuration/custom-rules#migrate-legacy-configuration). Then confirm that the runtime is `ready` with `npx cc-safety-net doctor`.

If you installed rulebooks from GitHub on 2.2 or earlier, run [`rule sync`](/reference/cli-commands#rule-sync) once per scope after upgrading, adding `--global` for user-scope sources. Rulebooks are now live vendored files instead of lock-and-cache state, and the command migrates each cached rulebook into the live path its source loads from, then removes the leftovers. Until it runs, those GitHub-sourced rules are inactive and `status` and `doctor` report the degraded sources.

## Amp Code installation

```bash
npx -y cc-safety-net@latest install --amp
```

This publishes the managed plugin artifact to your account's hosted Amp Personal Plugins repository. The artifact is a directory named `cc-safety-net` holding `index.ts`, the entry file Amp loads. A personal plugin follows your account everywhere, so it also covers threads that execute on a remote machine, such as Amp Orbs.

Install requires the `amp` CLI and a signed-in account. It first runs `amp plugins repositories --json` to find your writable Personal Plugins repository. If the CLI or login is missing, install stops and points you to `amp login`. It then clones `user-plugins` into a temporary checkout, writes `cc-safety-net/index.ts`, commits under the tool identity `cc-safety-net`, and pushes. Staging names that one file (`git add -- cc-safety-net/index.ts`) instead of the directory. If your repository gitignores that path, `git add` fails and the install stops, instead of staging nothing and reporting the plugin as already installed. Commit signing is off, so your global git config cannot stall the install. Run the command again to update the published artifact in place.

Earlier releases published a single file `cc-safety-net.ts` at the root of that repository. Install migrates away from it. A managed legacy file goes in the same commit; an unmanaged one fails the install.

Install also embeds a snapshot of your user policy file into the published artifact. At runtime, the snapshot applies only on a machine that has no policy file, such as an Orb's empty home directory. A policy file on the machine always wins, even when it is invalid. If your policy file is absent or cannot be parsed, install publishes the bare artifact without a snapshot. The snapshot does not carry audit retention, user rulebooks, or project-scope policy. A policy edit ships on the next `install --amp` or `update`.

```bash
npx -y cc-safety-net@latest uninstall --amp
```

Uninstall removes `cc-safety-net/index.ts` from the personal repository with the same commit-and-push flow, together with a managed legacy `cc-safety-net.ts` at the root. Uninstall removes only that entry file, so anything else you keep in the `cc-safety-net` directory stays. It leaves anything else at the legacy root path untouched: an unmanaged file, a symlink, or a directory. It reports the `cc-safety-net` directory as the removed path, or the legacy root file when that was all it found.

<Note>
  Restart Amp or run `plugins: reload` after installing, updating, or uninstalling so the change takes effect.
</Note>

Install and uninstall both refuse to touch a plugin in the personal repository that is not theirs to replace. They refuse a `cc-safety-net` entry that is a symlink or is not a directory. They refuse an `index.ts` inside it that is a symlink, is not a regular file, or does not carry the CC Safety Net managed header. Remove the entry there and rerun the command.

Earlier releases copied the plugin to a local file at `~/.config/amp/plugins/cc-safety-net.ts`. The plugin directory can also be copied to `~/.config/amp/plugins/cc-safety-net/` by hand. Either one masks the personal plugin, so install removes it after publishing: the legacy file when it is a managed copy, and the local directory when it holds nothing but a managed `index.ts`. Any other local entry at those two paths fails the install:

```text
Local Amp plugin <path> is not a managed copy and masks the personal plugin. Remove it and rerun install --amp.
```

Uninstall also removes managed local copies but leaves an unmanaged local entry in place.

## Antigravity CLI installation

```bash
npx -y cc-safety-net@latest install --agy-cli
```

This writes a managed `PreToolUse` entry to `~/.gemini/config/hooks.json` that runs `npx -y cc-safety-net hook --agy-cli` on each `run_command` tool call.

Because the hook runs through `npx`, install first deletes any cached `cc-safety-net` copies from the npm cache's `_npx` directory (`$npm_config_cache` if set, otherwise `~/.npm` on macOS and Linux, `%LOCALAPPDATA%\npm-cache` on Windows) so the hook resolves the current release. Uninstall does not touch the cache.

```bash
npx -y cc-safety-net@latest uninstall --agy-cli
```

Optionally install the `/cc-safety-net` skill so you can author rules interactively inside Antigravity CLI:

```bash
npx skill add kenryu42/cc-safety-net
```

## Cursor installation

```bash
npx -y cc-safety-net@latest install --cursor
```

This writes a managed `preToolUse` entry to your global Cursor hooks config, `~/.cursor/hooks.json`:

```json
{ "command": "npx -y cc-safety-net hook --cursor", "timeout": 30, "failClosed": true }
```

Because the config is global, this protects Cursor IDE and Cursor CLI sessions across all your projects. `failClosed` means Cursor denies the tool call if the hook cannot produce a decision.

Because the hook runs through `npx`, install first clears cached `cc-safety-net` copies from the npm `_npx` cache so the hook resolves the current release; uninstall does not touch the cache. The cache locations are listed in the [Antigravity CLI section](#antigravity-cli-installation).

```bash
npx -y cc-safety-net@latest uninstall --cursor
```

The Claude Code plugin also carries a Cursor plugin manifest, `.cursor-plugin/plugin.json`. Its hook config, `hooks/cursor.json`, registers a `preToolUse` hook with no matcher that runs `node "${CURSOR_PLUGIN_ROOT}/dist/bin/cc-safety-net.js" hook --cursor` with `timeout: 30` and `failClosed: true`. When Cursor imports Claude Code plugins, it runs this hook from an enabled [Claude Code plugin](#claude-code-installation). If the `install --cursor` hook is also in place, Cursor checks every tool call twice. `doctor` reports both setups. See [Cursor through the Claude Code plugin](/reference/cli-commands#cursor-through-the-claude-code-plugin).

Cursor can also install CC Safety Net as a native Cursor plugin from a personal marketplace. `install --cursor` does not offer that route. Cursor pins a marketplace plugin to the commit it was added at, so `cc-safety-net update` cannot move it to a newer release, while the `npx` hook resolves the current release on every call. If you added the plugin yourself, `doctor` finds it under `~/.cursor/plugins/cache/cc-safety-net/cc-safety-net` and warns that the hook runs the same check a second time. `uninstall --cursor` then removes the marketplace along with the hook. See [Cursor through a native Cursor plugin](/reference/cli-commands#cursor-through-a-native-cursor-plugin).

## DeepSeek Harness installation

```bash
npx -y cc-safety-net@latest install --deepseek-harness
```

DeepSeek Harness loads CC Safety Net as a profile plugin bundle rather than a hook subprocess, so there is no `hook` flag for it. One install covers every DeepSeek Harness profile on the machine: the `web` profile that `npx @deepseek-ai/dsh web` and a global install share, and the `desktop` profile the Desktop app uses.

Profiles live in `~/.dsh/profiles`, or in `$DSH_HOME/profiles` when `DSH_HOME` is set, with a leading `~` expanded against your home directory. Each profile's `package.json` records both the `cc-safety-net` dependency and the bundle list that enables it. Install, uninstall, and `doctor` all read those manifests.

Install adds `cc-safety-net` to each profile at the installer's own version. Without a version in the spec, pnpm's `minimumReleaseAge` setting installs an older release instead of the one you ran.

For the web profile, install runs DeepSeek Harness's own plugin command through `npx`:

```bash
npx -y @deepseek-ai/dsh plugin --profile web add cc-safety-net@<version>
```

This reuses the DeepSeek Harness that `npx @deepseek-ai/dsh web` or a global install runs, and DeepSeek Harness needs `pnpm` on your `PATH` to add the bundle. Install targets the web profile when Desktop is absent, when a `web` profile manifest already exists, or when `npx --offline --no-install @deepseek-ai/dsh --version` finds a cached copy. The second case covers a web profile whose npx cache you cleared, which would otherwise be skipped.

For the `desktop` profile, install runs the same command through Desktop's own bundled `dsh`. On macOS it looks for that binary under `~/Applications` and then `/Applications`, at `DeepSeek Harness.app/Contents/Resources/runtime/cli/bin/dsh`. On Windows it looks at `%LOCALAPPDATA%\Programs\DeepSeek Harness\resources\runtime\cli\bin\dsh.cmd`. It looks there only when a `desktop` profile already exists, so open Desktop once before you install.

Desktop plugins can change only while Desktop is closed, so install and uninstall both stop when it is running:

```text
Quit DeepSeek Harness Desktop, then run this command again: Desktop plugins can only change while it is closed.
```

When a `desktop` profile exists but Desktop itself is somewhere else, install covers the web profile and tells you to finish the Desktop half yourself:

```text
DeepSeek Harness Desktop is not in its default location, so add cc-safety-net from its Plugins page.
```

A bundle that DeepSeek Harness installed but did not enable protects nothing, so install reads the profile manifests afterwards and fails when the bundle is off:

```text
DeepSeek Harness installed cc-safety-net in the web profile but did not enable it. Enable it from the Plugins page.
```

A successful install reports `Added cc-safety-net to the DeepSeek Harness Desktop and web profiles.` Both that message and the enable failure above name whichever profiles they cover, so a web-only run says `the web profile` in place of `the Desktop and web profiles`.

```bash
npx -y cc-safety-net@latest uninstall --deepseek-harness
```

Uninstall removes the bundle from each profile whose manifest lists it. When neither profile carries it, uninstall runs no command and stops:

```text
cc-safety-net is not installed in the DeepSeek Harness web or Desktop profile
```

If Desktop holds the bundle but is not in its default location, uninstall removes the web copy first and then exits `1`, because a success would leave the dashboard offering `Install` while Desktop keeps the bundle active:

```text
Removed cc-safety-net from the DeepSeek Harness web profile, but DeepSeek Harness Desktop is not in its default location, so remove cc-safety-net from its Plugins page.
```

When Desktop is the only profile with the bundle, uninstall removes nothing and prints the same instruction on its own.

At runtime the bundle registers a deny-only tool guard that DeepSeek Harness runs after every `tools/pre-execute` listener, including approvals and Auto review. `bash` goes to the POSIX analyzer and `pwsh` to the PowerShell analyzer, and file and search tools reach path and secret protection. Several DeepSeek Harness tools stay outside that guard; see [DeepSeek Harness coverage boundaries](/guides/known-limitations#deepseek-harness-coverage-boundaries) and [DeepSeek Harness](/guides/integration-architecture#deepseek-harness).

## Devin CLI installation

```bash
npx -y cc-safety-net@latest install --devin
```

This writes a managed `PreToolUse` entry under `hooks` in `$XDG_CONFIG_HOME/devin/config.json`, which defaults to `~/.config/devin/config.json`. On Windows the file is `%APPDATA%\devin\config.json`:

```json
{ "hooks": [{ "type": "command", "command": "npx -y cc-safety-net hook --devin", "timeout": 30 }] }
```

The entry carries no matcher, so every tool call reaches the adapter instead of only `exec`. Devin's own keys and its other hook events stay in the file. When the file does not exist, install creates it with that one `hooks` key and nothing else. Both commands keep the file's existing permission bits when they replace it.

Devin allows comments in `config.json`, so install, uninstall, and detection strip `//` and `/* */` comments before parsing. A rewrite is plain JSON, so an install or uninstall that changes the file drops its comments.

Install stops without writing and names the file when `config.json` does not parse, when its root is not a JSON object, when `hooks` is not an object, or when `hooks.PreToolUse` is not an array.

Because the hook runs through `npx`, install first clears cached `cc-safety-net` copies from the npm `_npx` cache so the hook resolves the current release; uninstall does not touch the cache. The cache locations are listed in the [Antigravity CLI section](#antigravity-cli-installation).

```bash
npx -y cc-safety-net@latest uninstall --devin
```

Uninstall removes the managed handler and writes the file back. It never deletes `config.json`, not even when stripping the handler leaves `hooks.PreToolUse` empty. When the file holds no managed handler, uninstall writes nothing and reports the hook as not installed.

At runtime the adapter treats `exec` as a shell-command tool, and it analyzes a `write_to_process` call as a command when its `text_input` is a non-empty string. It inspects other tool inputs for protected paths. Devin's payload carries no `cwd`, so the adapter resolves the analysis against the hook process's working directory, which is the session directory. The adapter answers only with a block decision and stays silent on an allowed call, so Devin's own permission prompt still applies. See the [`hook` command](/reference/cli-commands#hook) and [Integration architecture](/guides/integration-architecture).

<Note>
  Devin CLI hooks are fail-open. Only exit code 2 or a `block` decision on stdout blocks a tool call. A timeout, a missing `npx`, or a hook process that dies before printing a decision lets the call proceed. See [Devin CLI is a fail-open host](/guides/known-limitations#devin-cli-is-a-fail-open-host).
</Note>

## Factory Droid installation

```bash
npx -y cc-safety-net@latest install --droid
```

This writes a managed `PreToolUse` entry to the top-level `PreToolUse` array in `~/.factory/hooks.json`:

```json
{ "hooks": [{ "type": "command", "command": "npx -y cc-safety-net hook --droid", "timeout": 30 }] }
```

The entry carries no matcher, so every tool call reaches the adapter instead of only `Execute`. Foreign entries and other hook events in the file stay as they are, and both commands keep the file's existing permission bits when they replace it.

Droid reads hooks from the `hooks` key of `~/.factory/settings.json` whenever `hooks.json` is absent. A `hooks.json` holding only the managed entry would therefore switch off every hook declared in `settings.json`. So when `hooks.json` does not exist, install seeds the new file with the hook events from `settings.json` and appends the managed entry to them. `settings.json` itself is never written.

Install stops without writing and names the file when `hooks.json` does not parse, when its root is not a JSON object, or when its `PreToolUse` is not an array.

Because the hook runs through `npx`, install first clears cached `cc-safety-net` copies from the npm `_npx` cache so the hook resolves the current release; uninstall does not touch the cache. The cache locations are listed in the [Antigravity CLI section](#antigravity-cli-installation).

```bash
npx -y cc-safety-net@latest uninstall --droid
```

Uninstall removes the managed handler and drops an entry once it has no handlers left. Hooks that install carried over from `settings.json` stay in `hooks.json`, so the hook set in effect after uninstall matches the one before install. Uninstall deletes `hooks.json` only when stripping the handler leaves an empty `PreToolUse` as the file's one remaining key and no `settings.json` exists. With a `settings.json` present it writes the stripped file instead, because deleting `hooks.json` would re-activate the `settings.json` fallback, including any copy of the managed handler sitting there.

At runtime the adapter treats `Execute` as a shell-command tool and inspects other tool inputs for protected paths. It resolves the analysis against the `cwd` in Droid's payload. The adapter emits nothing for an allowed call, so Droid's own permission prompt still applies. See the [`hook` command](/reference/cli-commands#hook) and [Integration architecture](/guides/integration-architecture).

<Note>
  Factory Droid hooks are fail-open. Only exit code 2 or an explicit deny decision on stdout blocks a tool call. An exit code other than 0 or 2, a crash, a timeout, or a missing `npx` lets the call proceed. An enterprise `allowManagedHooksOnly` setting ignores user and project hooks, so the hook that `install --droid` writes does not run under it. See [Factory Droid is a fail-open host](/guides/known-limitations#factory-droid-is-a-fail-open-host).
</Note>

## GitHub Copilot CLI installation

```bash
npx -y cc-safety-net@latest install --copilot-cli
```

This adds the `cc-marketplace` marketplace if it is not already registered, installs the `cc-safety-net@cc-marketplace` plugin, and flips the plugin to `true` in `enabledPlugins` in `~/.copilot/settings.json` if it was explicitly disabled.

```bash
npx -y cc-safety-net@latest uninstall --copilot-cli
```

<Note>
  Restart Copilot CLI after installing or removing the plugin for the change to take effect.
</Note>

Hook support in Copilot CLI depends on its version. Doctor checks repository hook files under `.github/hooks`; inline hook definitions in `.github/copilot/settings.local.json`, `.github/copilot/settings.json`, `.claude/settings.local.json`, `.claude/settings.json`, `~/.copilot/settings.json`, and `~/.copilot/config.json`; and user hook files under `~/.copilot/hooks`. Inline hook definitions require Copilot CLI **1.0.8** or later, and user hook files require **0.0.422** or later. The plugin handles this for you. If you configure hooks manually and find a problem, run `npx cc-safety-net doctor`. It reports the detected Copilot version and the supported hook sources.


Both commands only ever touch the managed handler. Install strips managed handlers out of the existing entries and appends the canonical entry standalone, so foreign entries, foreign handlers that shared an entry with it, and other hook events all survive. Uninstall removes the managed handler, drops an entry once it has no handlers left, and deletes the file only when nothing else remains in it. Uninstall leaves an unparsable file alone; install repairs one to the canonical entry, because Grok Build skips an unparsable hook file entirely, so such a file cannot carry working hooks anyway.

<Note>
  Grok Build hooks are fail-open and the host exposes no `failClosed` knob. Only an explicit deny blocks a tool call. A hook that crashes, times out, or emits malformed output lets the call proceed.
</Note>

## Hermes Agent installation

```bash
npx -y cc-safety-net@latest install --hermes-agent
```

This writes the managed Python plugin files `__init__.py` and `plugin.yaml` to `plugins/cc-safety-net/` inside the Hermes home directory. It then runs `hermes plugins enable cc-safety-net --no-allow-tool-override`. The files alone are inert. Hermes loads a user plugin only when its own config lists it as enabled, so install runs the enable command even when the files are already current.

The Hermes CLI re-homes itself to a profile directory, so the home directory is not always `~/.hermes`. A `HERMES_HOME` whose parent directory is named `profiles` is used as is. Otherwise the root is `HERMES_HOME`, or `~/.hermes` when that is unset, and the root's `active_profile` file selects the home directory. Its contents, trimmed and lowercased, name `<root>/profiles/<name>`. An empty value or `default` in any casing keeps the root, and so does an `active_profile` that is missing or unreadable. A profile name that does not match Hermes' own profile-id pattern, `^[a-z0-9][a-z0-9_-]{0,63}$`, stops the command and names the file:

```text
Invalid Hermes profile name "<profile>" in <root>/active_profile; run `hermes profile use <name>` with a valid profile.
```

Install, uninstall, and detection all use this one lookup.

Because the plugin shells out through `npx`, install first clears cached `cc-safety-net` copies from the npm `_npx` cache so the plugin resolves the current release; uninstall does not touch the cache. The cache locations are listed in the [Antigravity CLI section](#antigravity-cli-installation).

<Note>
  Restart Hermes after installing, updating, or uninstalling so the change takes effect.
</Note>

On each `pre_tool_call`, the plugin sends the tool call to `npx -y cc-safety-net hook --hermes-agent` (short flag `-ha`) over JSON stdin, with a 30-second timeout. It protects the `terminal`, `read_file`, `write_file`, and `patch` tools; other Hermes tools are not forwarded. The plugin fails closed: when `npx` is missing, the analysis cannot start, times out, exits non-zero, or returns unreadable output, the tool call is blocked with an explicit message instead of slipping through.

```bash
npx -y cc-safety-net@latest uninstall --hermes-agent
```

Uninstall runs `hermes plugins disable cc-safety-net` *before* it removes the plugin files. Hermes resolves only plugins that are still on disk. An enabled config entry would automatically load any future plugin with the same name. If the `hermes` CLI fails or is missing, uninstall still removes the files and warns that the Hermes config may still list `cc-safety-net`. Uninstall also removes the Python `__pycache__` bytecode directory and reclaims the plugin directory only when nothing else remains.

Install and uninstall both refuse to touch the plugin directory if it is a symlink or not a regular directory, and refuse to overwrite or remove any managed file that is a symlink, not a regular file, or does not carry the CC Safety Net managed header. Move or remove it yourself and rerun the command.

This integration is macOS and Linux only.

## Kimi Code installation

Kimi Code supports two install methods: a global hook written to your Kimi Code config, or a native Kimi Code plugin you install from inside Kimi Code. In an interactive terminal, `install --kimi-code` (or picking Kimi Code in the interactive installer) opens a single-select prompt asking which method to use: install the global hook now, or print the native-plugin steps. In a non-interactive session the flag installs the global hook directly, so scripts and CI pipelines never hang on a prompt. `update` is unchanged.

<Note>
  Kimi Code hooks are fail-open with either method: when the hook process cannot start, crashes, or times out, Kimi Code allows the tool call.
</Note>

**Global hook**

```bash
npx -y cc-safety-net@latest install --kimi-code
```

This writes a `[[hooks]]` block to `~/.kimi-code/config.toml` (or `$KIMI_CODE_HOME/config.toml`) that runs `npx -y cc-safety-net hook --kimi-code` on each `PreToolUse` call. The adapter treats `Bash` as a shell-command tool and inspects other tool inputs for protected paths.

Because the hook runs through `npx`, install first clears cached `cc-safety-net` copies from the npm `_npx` cache so the hook resolves the current release; uninstall does not touch the cache. The cache locations are listed in the [Antigravity CLI section](#antigravity-cli-installation).

```bash
npx -y cc-safety-net@latest uninstall --kimi-code
```

**Native plugin**

To use the native plugin instead, run this inside Kimi Code:

```text
/plugins install https://github.com/kenryu42/cc-safety-net/tree/plugin
```

The URL names the repository's `plugin` branch, which every release publishes. That branch carries the plugin manifests, the bundled hook, the hook configs, the `cc-safety-net` skill, the logos, and the license, and nothing else. Without the `/tree/plugin` suffix, Kimi Code installs the whole repository.

Confirm the trust prompt, which defaults to cancel. Then run `/reload` or start a new session. The plugin declares one `PreToolUse` hook with no tool matcher. It runs `node ./dist/bin/cc-safety-net.js hook --kimi-code` for every tool call with a 30-second timeout and uses the same adapter as the global hook.

When the global hook is already configured, the Kimi Code row in the interactive installer stays selectable and is labeled `(global hook installed)`, and the printed plugin steps add a caution: run `cc-safety-net uninstall --kimi-code` only *after* the plugin is active. A brief overlap where both hooks run just duplicates the denial message, while a gap with neither active leaves you unprotected.

Optionally install the `/cc-safety-net` skill so you can author rules interactively inside Kimi Code:

```bash
npx skill add kenryu42/cc-safety-net
```

## OpenClaw installation

```bash
npx -y cc-safety-net@latest install --openclaw
```

CC Safety Net requires OpenClaw 2026.8.1 or later. The installer accepts the plugin's declared capabilities for you with `--accept-capabilities`, and older OpenClaw releases do not recognize that option and reject the install with an unknown-option error. There is no runtime version check and no fallback, so upgrade OpenClaw if you see one.

This installs the plugin through OpenClaw's own CLI. It runs one command, `openclaw plugins install <packaged plugin dir> --force --accept-capabilities`, where the packaged plugin directory ships inside the npm package. Since 2026.8.1 that install also enables the plugin unless you pass `--no-enable`, so there is no separate `openclaw plugins enable` step. A plugin you disabled by hand in `openclaw.json` stays disabled, and the load check below reports that rather than re-enabling it for you; run `openclaw plugins enable cc-safety-net` yourself if that is what you want.

The install then verifies the plugin actually loaded by running `openclaw plugins inspect cc-safety-net --runtime --json`. An enabled plugin whose runtime is broken installs cleanly and then protects nothing, so any status other than `loaded` fails the install and points you at `openclaw plugins inspect cc-safety-net --runtime` for details. A `disabled` status also names the enable command:

```text
OpenClaw reports the cc-safety-net plugin with status "disabled"; run `openclaw plugins enable cc-safety-net`. Run `openclaw plugins inspect cc-safety-net --runtime` for details.
```

Install enables the plugin for you in one case. `openclaw plugins uninstall` leaves an `enabled: false` marker behind, and `plugins install` skips enabling an entry that is explicitly disabled, so running install, then uninstall, then install again used to end at status `disabled`. Now, when the managed plugin's entry file was absent before the install and the first inspect reports `disabled`, install runs `openclaw plugins enable cc-safety-net` once and inspects again. A plugin that was already installed and that you disabled by hand stays disabled, on install and on update alike.

With the Gateway running, that enable can fail with `config reload superseded by a newer runtime config source`. OpenClaw saves the enable to config before the runtime apply that gets superseded, and it never rolls that write back, so install accepts this one failure. Install does not retry the enable and does not fail on it. The second `openclaw plugins inspect cc-safety-net --runtime --json` decides the result. Any other enable failure still fails the install. The Gateway applies the saved config at its next reload or start, which is why the restart below still matters.

Because `--force` overwrites the entry with the `cc-safety-net` extension id and uninstall deletes that entry, both commands first inspect the extension directory. They continue only if the directory contains only a managed CC Safety Net plugin or is empty. Otherwise, they refuse to run. Move or remove the directory and run the command again.

```bash
npx -y cc-safety-net@latest uninstall --openclaw
```

<Note>
  Restart the OpenClaw Gateway after installing, updating, or uninstalling so the change takes effect. If `plugins.allow` is set in `openclaw.json`, it must also list `cc-safety-net`. An allowlist that omits it prevents the plugin from loading even when it is enabled.
</Note>

OpenClaw loads CC Safety Net as an in-process plugin rather than a hook subprocess, so there is no runtime hook flag. The plugin registers a `before_tool_call` handler for the untagged `exec` tool only. OpenClaw's file tools and tagged `exec` variants are not covered. Each supported `exec` call is analyzed against the agent's workspace directory, and the plugin fails closed when that workspace cannot be resolved, when `workdir` resolves outside it, or when the call names an execution host other than `auto` or `gateway` (for example `sandbox` or `node`).

`OPENCLAW_HOME` sets the home directory the other OpenClaw paths resolve against. When it is set, that value is the effective home, with a leading `~` expanded against your operating-system home directory. Otherwise the effective home is your operating-system home directory. The state directory is `OPENCLAW_STATE_DIR` when set, otherwise the directory holding `OPENCLAW_CONFIG_PATH`, otherwise `.openclaw` inside the effective home. A leading `~` in those two variables expands against the effective home, not the operating-system home. The config file is `OPENCLAW_CONFIG_PATH` when set, otherwise `openclaw.json` in the state directory. CC Safety Net trims all three variables and treats a blank value as unset. Install and doctor resolve paths the same way, so `doctor` finds a relocated OpenClaw install instead of reporting it as absent.

This integration is macOS and Linux only.

## OpenCode installation

```bash
npx -y cc-safety-net@latest install --opencode
```

CC Safety Net supports OpenCode 1.18.29+ and 2.0.6+ from the same npm package. Install runs `opencode --version` first and refuses anything else with `OpenCode 1.18.29+ or 2.0.6+ is required; found <version>.` Older v1 releases do not support the combined plugin entry, so upgrade OpenCode before you update CC Safety Net.

OpenCode's config directory is `OPENCODE_CONFIG_DIR` when that variable is set and non-empty, otherwise `$XDG_CONFIG_HOME/opencode`, otherwise `~/.config/opencode`. An empty value counts as unset on both OpenCode 1.x and 2.x. The config file is `opencode.json` or `opencode.jsonc` there.

The v2 install preflight reads only that directory. Detection and uninstall scan every directory either version loads, the override directory first and then the XDG directory, because OpenCode 1.x always loads the XDG directory whether or not `OPENCODE_CONFIG_DIR` is set. [`doctor`](/reference/cli-commands#doctor) is narrower. On a host that reports a 2.x version, detection reads only the config directory above, because that is the only directory v2 reads. When the version is unknown, because `opencode` is off your `PATH` or because install and update are detecting targets, detection scans both directories. Uninstall always scans both.

On OpenCode 1.x, install clears the cached package and runs `opencode plugin -g -f cc-safety-net@latest`. The cache directory is `$XDG_CACHE_HOME/opencode` when `XDG_CACHE_HOME` is set and non-empty, otherwise `~/.cache/opencode`, and the package cleared under it is `packages/cc-safety-net@latest`. OpenCode can keep serving a stale cached plugin version, which is why the cache goes first. Install then proves that the cached package exists, its declared `main` entry loads, and it exports a callable `CCSafetyNetPlugin`; a failed proof stops the install because OpenCode would otherwise continue without protection.

On OpenCode 2.x, install reads both config files before it changes anything. If either one lists a `cc-safety-net` entry in its `plugin` or `plugins` array whose package spec is not `cc-safety-net@latest`, it stops:

```text
Change the cc-safety-net package spec in <path> to cc-safety-net@latest, preserving its options, then retry. Adding another spec would create a duplicate plugin ID.
```

Edit that entry yourself, keep its options and comments, and run the install again.

Otherwise install runs `opencode plugin add cc-safety-net@latest`. It runs `opencode plugin update cc-safety-net@latest` only when the output of `add` contains `is already configured in`. On a first install, OpenCode's background service has not loaded the new entry yet, and an unconditional `update` fails there with `Plugin is not configured`.

Install then polls `opencode plugin list` every 250 ms, up to 60 times, until a row carries the `cc-safety-net` id or the `cc-safety-net@latest` source. That bounds the wait at about 15 seconds. The listing must hold a row whose three columns are the plugin id `cc-safety-net`, its version, and the source `cc-safety-net@latest`, as in `cc-safety-net  2.4.4  cc-safety-net@latest`. Without that row it fails:

```text
OpenCode did not load cc-safety-net from cc-safety-net@latest. Run `opencode plugin list` for details.
```

The listing proves that OpenCode found the plugin, not that the plugin activated, so install then asks the host for the activation state. It runs `opencode api integration.list` and then `opencode api plugin.list`, both with `--param location[directory]=<cwd>`. The first call waits on the host's plugin activation. The second returns the inventory right away, so on its own it can miss a failure that is still queued.

If the inventory reports a failed `cc-safety-net` row and no active copy of it, install fails with the host's first error line:

```text
OpenCode reports cc-safety-net failed: <first line of OpenCode's error>
```

If the inventory lists no active `cc-safety-net` row at all, because it is empty, unreadable, or lists only other plugins as active, install fails too:

```text
OpenCode lists no active cc-safety-net for this directory. Run `opencode api plugin.list` for details.
```

This path clears no cache. The dashboard's `Enable` button runs this same install.

```bash
npx -y cc-safety-net@latest uninstall --opencode
```

Uninstall clears the cached package, then removes managed `cc-safety-net` entries from the `plugin` and `plugins` arrays in both `opencode.json` and `opencode.jsonc`. It removes plain string entries and object entries carrying a `package` key, and it keeps JSONC comments.

On OpenCode 2.x, the plugin's `shell` option selects the analyzer dialect. See [Integration architecture](/guides/integration-architecture#opencode).

Restart OpenCode after installing or updating so the change takes effect.

## Pi installation

```bash
npx -y cc-safety-net@latest install --pi
```

This runs `pi install npm:cc-safety-net` and, if your Pi settings pin an `extensions` filter that would leave CC Safety Net disabled, clears that filter in `settings.json` under your Pi agent directory. That directory is `PI_CODING_AGENT_DIR` when it is set, with a leading `~` expanded against your home directory, and `~/.pi/agent` otherwise. Detection reads the same file.

```bash
npx -y cc-safety-net@latest uninstall --pi
```

Pi loads CC Safety Net as an in-process extension rather than a hook subprocess. The extension analyzes only Pi's built-in `bash` tool as a shell command. It also inspects other tool inputs for protected paths, but it does not support custom command tools named `Shell` (for example pi-grok-cli). It registers a `/cc-safety-net` builtin command for managing rulebooks. See [Integration architecture](/guides/integration-architecture) for details.

## Migrating from a legacy plugin identifier

The current plugin identifier is `cc-safety-net@cc-marketplace` everywhere it applies. Two identifiers from earlier releases still show up on existing machines:

| Legacy identifier | Agent | What happens |
| --- | --- | --- |
| `safety-net@cc-marketplace` | Claude Code, Codex | Detected during install and uninstalled automatically once the current plugin is in place |

## Verify your installation

After installing, run the doctor command to confirm CC Safety Net is wired up correctly and blocking commands as expected:

```bash
npx cc-safety-net doctor
```

`doctor` runs a full health check across every supported agent. It checks hook integration, runs a self-test that confirms blocking works, validates custom rules, and checks active mode flags, recent activity, system versions, and updates. See the [doctor command reference](/reference/cli-commands#doctor) for details and available flags.

If any check fails, the output includes a description of the problem and suggested fixes.
